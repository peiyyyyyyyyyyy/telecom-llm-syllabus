# 10.3.1 只給草案

所屬：[10.3 高風險操作](10-3.md)

## 內文

#### 1. 是什麼、什麼時候會用到

高風險操作是一旦執行就可能中斷服務、遺失資料或對外造成影響的動作。助理在這類操作上只提供草案：把要做的事寫成可審查的文件，由有權限的人審查、核可後，再由授權的工作流程執行。第 9 章 9.5.1 說得很清楚：「設定草案可由模型整理，但核可與設備操作仍由具備權限的工作流程處理。」維運人員最常在這些時候請助理幫忙：改小區參數、重啟設備、刪除舊資料或設定、批次調整多個站點，以及發出對外的停機公告或客戶通知。

#### 2. 怎麼做／怎麼判斷

**哪些操作屬於高風險：**

| 類型 | 例子 | 風險 |
|---|---|---|
| 改設定 | 改切換門檻、頻率、功率、排程 | 服務品質下降、干擾、掉話 |
| 重啟 | 重啟基站、控制器、核心網元件 | 服務中斷 |
| 刪資料 | 刪除設定物件、日誌、備份、用戶資料 | 無法復原、違反留存規定 |
| 批次操作 | 一次套用到多個站點 | 影響範圍擴大 |
| 對外通知 | 停機公告、客戶簡訊、對主管機關的通報 | 發出後無法收回，影響信譽與法律責任 |

判斷原則：只要動作會改變網路或資料的狀態，或會對外發出，就屬於高風險，只給草案。純讀取、計算、整理資料不在此限。

**草案要寫清楚什麼（承 9.3.2 與 9.4）：**

1. **目標物件**：完整識別（例如完整 DN），不能只寫最後一段名稱。
2. **參數**：版本適用的精確名稱。
3. **舊值**：附讀回時間與來源；未知就標待補。
4. **新值**：附單位，能追溯到原請求。
5. **理由**：可觀察的改善，不寫「配合調整」。
6. **影響範圍、衝突、退回方式、變更後驗證**（9.4.1～9.4.4）。
7. **狀態標示**：草案開頭明確寫「草案，待核可，未執行」。

**助理不做的事：**不直接執行、不替使用者產生可直接貼上執行的「一鍵指令」並暗示可以直接跑、不把草案寫成已完成的語氣（例如「已將門檻調整為……」）。

#### 3. 實際例子

```
【維運工程師訊息】2026/11/27 14:20
NB-217 掉話太多，你直接把它的切換門檻從 -2 dB 改成 -4 dB，
改完順便重啟一下讓它生效，我等等要開會。
```

```yaml
# 草案，待核可，未執行（甲電信變更草案格式，虛構）
draft_id: DR-1127-03
status: draft-pending-approval
target_dn: SubNetwork=North,ManagedElement=NB-21,GNBDUFunction=DU-1,NRCellDU=NB-217
parameter: handoverThresholdDb   # 虛構欄位名，需依設備版本參數表確認
old_value: -2      # 來源：工程師口述，待設備讀回確認
new_value: -4
unit: dB
reason: 降低 NB-217 掉話率（目前 1.9%）；根因尚未確認，見 10.1.1
impact: NB-217 與鄰區 NB-218 的切換行為；需查 NB-218 承接能力
rollback: 恢復為讀回的舊值
verification: 變更後 2 小時掉話率、往 NB-218 切換成功率
restart_required: 待查（依設備版本文件確認是否需重啟）
```

逐步判斷：

1. **屬於高風險**：改參數和重啟都會改變網路狀態。
2. **只給草案**：整理成上面的草案，標明待核可、未執行，不直接改也不重啟。
3. **補上缺的資訊**：舊值只是口述，要讀回確認；是否需要重啟要查設備版本文件，不能預設要重啟。
4. **指出風險**：10.1.1 的分析顯示根因尚未確認，草案理由中要寫明，讓審查者知道這是假設性的處理。
5. **回覆工程師**：「已整理成草案 DR-1127-03，請依異動流程送核可；舊值與是否需重啟兩項待確認。」

#### 4. 容易搞混的地方

- **草案不是執行前的形式**：草案是給人審查用的，要有足以判斷的資訊，不是貼一行指令。
- **讀取不是高風險**：查告警、讀 KPI、讀組態不需要草案，正常回答即可。
- **對外通知也是高風險**：停機公告、客戶簡訊發出就收不回，也只給草稿。
- **語氣要一致**：草案裡不能出現「已調整」「已重啟」這類已完成的說法。
- **使用者催促不改變性質**：「我等等要開會」「直接改就好」不會讓高風險操作變成低風險，仍然只給草案，並說明下一步要送誰核可。

#### 5. 和其他小節的關係

草案格式與必填欄位見第 9 章 9.3；影響、衝突、退回、驗證見 9.4。草案寫好後要等人核可（10.3.2），核可流程依 9.5.1。草案理由若依賴尚未確認的根因，要依 10.1 標明不確定。

**010.** 停用一個可疑帳號看起來是「讓系統更安全」的動作。為什麼它仍屬於只能給草案的高風險操作？

<details><summary>看答案</summary>

**答案**　因為停用帳號會改變系統狀態：如果判斷錯誤，可能中斷委外廠商正在進行的合法維運作業，造成服務或維修延誤；安全上看起來保守的動作一樣要經審查。

**詳解**　判斷依據是「會不會改變狀態」，不是「目的是不是為了安全」。封鎖、停用、刪除常被當成防禦性動作，但同樣可能誤傷正常業務。

**出處**　方法論（無外部出處）

</details>
