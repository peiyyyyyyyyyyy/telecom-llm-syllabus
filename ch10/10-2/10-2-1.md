# 10.2.1 不回答權限外的資料

所屬：[10.2 權限與資料](../10-2.md)

## 正文

In operational networks, every service—whether a remote login, file transfer, or local console—represents a *system function* that can affect the integrity, confidentiality, and availability of the carrier’s infrastructure. If a user can invoke such a function without proving their identity, the network becomes vulnerable to information disclosure, service disruption, and loss of accountability. The 3GPP specification TS 33.117 §4.2.3.4 therefore mandates that *“the usage of a system function without successful authentication on basis of the user identity and at least one authentication attribute … shall be prevented”*【TS 33.117 §4.2.3.4.1.1】. This principle underpins all secure‑by‑design deployments.

### Authentication and Authorization Requirements

A *system function* includes, but is not limited to, network services (e.g., SSH, SFTP, Web services), local access via a management console, and the use of operating‑system or application binaries【TS 33.117 §4.2.3.4.1.1】. The specification distinguishes two complementary controls:

* **Authentication** – verification that the caller possesses a valid *user identity* $U_i$ **and** at least one *authentication attribute* $A_u$ (e.g., password, certificate).  
* **Authorization** – enforcement of an *access control* mechanism $AC$ (DAC, MAC, capabilities, etc.) that maps $U_i$ to permitted functions.

Formally, access to a function $F$ is granted only if  

$$
\text{Auth}(U_i, A_u) = \text{true} \;\land\; \text{Authorise}(U_i, AC, F) = \text{true}
$$

where $\text{Auth}$ denotes successful authentication and $\text{Authorise}$ denotes a positive decision by the $AC$ engine. The test case TC\_SYS\_FUN\_USAGE explicitly requires the tester to *“verify that the access entries … require successful authentication on basis of the user name and at least one authentication attribute”* and that *“require authorization via an access control mechanism (e.g. Discretionary access control/Ownership/Capabilities or Mandatory access control)”*【TS 33.117 §4.2.3.4.1.1】.  

Public‑facing services such as an Internet web server are the sole exception; they may be offered without per‑user authentication because the information is intended for unrestricted consumption【TS 33.117 §4.2.3.4.1.1】.

### Unambiguous User Identification

Beyond merely authenticating, the product must *identify the user unambiguously*. This means each logical entity—person, application, or system—must have its own account. The specification requires support for **individual accounts** and explicitly forbids default group accounts or shared credentials *“by default”*【TS 33.117 §4.2.3.4.1.2】.  

A minimum of $N_{\min}=50$ individual accounts per user database shall be supported unless a specific SCAS states otherwise, guaranteeing scalability for large operators【TS 33.117 §4.2.3.4.1.2】. Moreover, *“the network product shall not support user access credentials unrelated to an account”*【TS 33.117 §4.2.3.4.1.2】, preventing back‑door passwords or master keys that bypass the per‑account model.

### Worked Example

Consider a telecom edge router that offers SSH (remote CLI) and a local management console. The operator configures the following:

| Account | Type   | Auth Attribute | Allowed Functions |
|---------|--------|----------------|-------------------|
| alice   | Person | password       | SSH, console      |
| svc‑bgp | Machine| X.509 cert     | BGP config API    |

The router’s AAA database contains $N=60$ accounts, satisfying the $N_{\min}=50$ requirement.  

**Step 1 – Authentication**  
When Alice initiates an SSH session, the router checks $\text{Auth}(\text{alice}, \text{password})$. If the password matches, authentication succeeds.  

**Step 2 – Authorization**  
The router then evaluates $\text{Authorise}(\text{alice}, \text{DAC}, \text{SSH})$. Because the DAC policy grants Alice SSH access, the function is allowed.  

**Step 3 – Enforcement of Unambiguous Identity**  
If the same device had a shared “admin” account used by multiple operators, the specification would deem this non‑compliant because *“the network product shall not enable the use of group accounts … by default”*【TS 33.117 §4.2.3.4.1.2】.  

If an attacker attempts to connect via SFTP using no credentials, the router denies the request, satisfying the test expectation that *“the network product does not allow access … without a successful user authentication and authorization”*【TS 33.117 §4.2.3.4.1.1】.

### Common Pitfalls and Practical Guidance

| Pitfall | Why It Violates the Spec | Remedy |
|---------|--------------------------|--------|
| Leaving default shared accounts (e.g., *guest*, *anonymous*) enabled | Such accounts *“suggest … sharing of the same account between several users”* and are assumed disabled per the test case TC\_ACCOUNT\_DEFA【TS 33.117 §4.2.3.4.1.2】 | Delete or disable all default group‑type accounts before deployment. |
| Using a “master password” to unlock privileged mode | The product *“shall not support user access credentials unrelated to an account”*【TS 33.117 §4.2.3.4.1.2】 | Map every privileged action to a specific user account with its own credentials. |
| Relying solely on IP‑based ACLs without per‑user authentication | Authentication must be based on *user name and at least one authentication attribute*; IP filters alone do not satisfy this【TS 33.117 §4.2.3.4.1.1】 | Combine network‑level filtering with strong per‑user authentication (e.g., certificate‑based SSH). |
| Assuming that a service exposed to the public does not need any access control | Only *functions for public use such as those for a Web server on the Internet* are exempt【TS 33.117 §4.2.3.4.1.1】 | Verify that the public service truly delivers only non‑sensitive information; otherwise, enforce authentication. |
| Mixing group‑based ACLs with group accounts for login | Group concepts are allowed for *access control* but *not* for authentication credentials【TS 33.117 §4.2.3.4.1.2】 | Use groups only in the authorization layer; keep login credentials strictly per‑account. |

By systematically applying the authentication, authorization, and unambiguous identification rules, network operators can assure that every invocation of a system function is traceable to a single, authenticated entity, thereby meeting both security best practice and the explicit 3GPP requirements.

## 練習題

**1.** What must be prevented before a system function can be used?

- A. Access without network connectivity
- B. Use without successful authentication based on user identity and at least one authentication attribute
- C. Execution of functions during maintenance windows
- D. Access by administrative users only

<details><summary>看答案</summary>

正解：B。The requirement states that a system function must not be usable without successful authentication that includes the user identity and an attribute such as a password or certificate.

</details>

**2.** Which type of function is explicitly exempted from the authentication and authorization requirement?

- A. Remote SSH access
- B. Local console login
- C. Public Web server functions providing information to the Internet
- D. SFTP file transfer services

<details><summary>看答案</summary>

正解：C。The specification lists public‑use functions, such as an Internet‑facing web server, as the only exception.

</details>

**3.** By default, what is the network product prohibited from enabling?

- A. Two‑factor authentication
- B. Group accounts or group credentials, or sharing of the same account between several users
- C. Role‑based access control
- D. Logging of successful logins

<details><summary>看答案</summary>

正解：B。The requirement explicitly forbids the default use of shared or group credentials.

</details>

**4.** During the documentation review test, what must the tester verify regarding group accounts?

- A. That the product requires group accounts for all privileged actions
- B. That the documentation encourages the use of shared credentials
- C. That the documentation does not encourage or require the use of group accounts, group credentials, or sharing of the same account between several users
- D. That group accounts are the only way to access the management console

<details><summary>看答案</summary>

正解：C。The test case directs the reviewer to ensure the documentation does not promote group or shared accounts.

</details>
