# 10.5.1 資安管理制度：ISO/IEC 27001 架構與控制措施

所屬：[10.5 資安規範](../10-5.md)

## 正文

In a telecommunications network, the ability to detect, investigate, and respond to security incidents hinges on reliable audit trails. Logging creates immutable records of who did what, when, and from where, enabling operators to satisfy regulatory audits, support forensic analysis, and enforce accountability. Without comprehensive logs, a breach may go unnoticed, and the root cause may be impossible to reconstruct, jeopardising service continuity and violating compliance obligations such as ISO/IEC 27001 — which mandates the implementation of appropriate security event logging controls [TS 33.117 §4.2.3.6].

### Core Logging Requirements Defined by TS 33.117
The specification enumerates a minimum set of security events that must be captured by any network product. Each log entry shall contain:  

* **Unique system reference** – e.g., host name, IP address, or MAC address.  
* **Exact timestamp** – the precise time the event occurred.  
* **Event‑specific data** – user name, performed action, result, session length, values exceeded or reached, etc.  

These elements satisfy the “Security event logging” requirement and must be documented by the vendor for verification [TS 33.117 §4.2.3.6].

### Mandatory Event Types
| Event Type | Description | Data to Log |
|------------|-------------|-------------|
| Incorrect login attempts | Records any user incorrect login attempts to the network product | Username, Source (IP address) if remote access, Timestamp |
| Administrator access | Records any access attempts to accounts that have system privileges | Username, Timestamp, Length of session, Source (IP address) if remote access |
| Account administration | Records all account administration activity (configure, delete, enable, disable) | Administrator username, Administered account, Activity performed, Timestamp |
| Resource usage | Records events triggered when system parameters exceed defined thresholds (e.g., disk space, CPU load) | Value exceeded, Value reached, Timestamp |
| Configuration change | Records changes to the configuration of the network device | Change made, Username |
| Reboot/shutdown/crash | Records any action that forces a reboot or shutdown, or a crash event | Action performed (reboot, shutdown, etc.), Username (for intentional actions), Timestamp |
| Interface status change | Records changes to the status of interfaces (e.g., shutdown, link loss) | Interface name and type, Status, Timestamp |

Each of these rows reflects a concrete logging requirement that must be implemented and, optionally, enabled by default at manufacturing time or later by the operator [TS 33.117 §4.2.3.6].

### Optional Event Types
The specification also allows optional logging of group‑membership changes, where the log shall contain the administrator username and the administered account [TS 33.117 §4.2.3.6].

### Mapping to ISO/IEC 27001 Control Objectives
ISO/IEC 27001 Annex A includes a control (A.12.4 — Logging and monitoring) that requires organizations to “record events and generate evidence of compliance”. The TS 33.117 logging matrix provides a concrete, industry‑aligned implementation for that control. While ISO/IEC 27001 does not prescribe exact event fields, the detailed list above satisfies the spirit of the standard by ensuring traceability, integrity, and availability of log data.

### Worked Example: Logging an Incorrect Login Attempt
Assume a remote user **alice** attempts to log into a base station controller from IP **192.0.2.45** at **2026‑11‑23 08:15:30 UTC** and supplies a wrong password. The product must generate a log entry containing the mandatory fields:

```
Timestamp: 2026-11-23T08:15:30Z
SystemRef: BS-CTRL-01 (host name)
EventType: Incorrect login attempt
Username: alice
SourceIP: 192.0.2.45
Result: authentication failure
```

If the vendor follows the specification, the entry will be stored in a tamper‑evident log file (e.g., syslog) and can be queried by the security information and event management (SIEM) system for correlation with other events. The presence of the exact timestamp and source IP satisfies the requirement that “Security events shall be logged together with a unique system reference … and the exact time the incident occurred” [TS 33.117 §4.2.3.6].

### Common Mistakes and Practical Notes
1. **Omitting the source address** – Remote login events must include the source IP; failure to record it defeats attribution [TS 33.117 §4.2.3.6].  
2. **Inconsistent timestamps** – Using local time without UTC offset can lead to ambiguous ordering of events across distributed nodes. Always log in a standardized format (e.g., ISO 8601).  
3. **Over‑filtering** – Disabling optional events (e.g., group‑membership changes) may be permissible, but operators should assess the risk of missing insider‑threat indicators.  
4. **Insufficient retention** – ISO/IEC 27001 expects logs to be retained for a period that supports investigations; the telecom operator must define this period in its security policy, even though the exact duration is outside the scope of the reference.  
5. **Lack of vendor documentation** – Each product must “document what security events the product logs so that it can be verified by testing” [TS 33.117 §4.2.3.6]; without this documentation, compliance audits cannot confirm that mandatory events are captured.

By aligning the logging implementation with the TS 33.117 matrix, telecom operators fulfill a critical ISO/IEC 27001 control while ensuring that security events are observable, searchable, and auditable across the network.

## 練習題

**1.** Which of the following data elements is **mandatory** for every security event log entry according to TS 33.117?

- A. The operating system version
- B. The unique system reference (e.g., host name, IP, MAC)
- C. The administrator’s contact phone number
- D. The physical location of the device
