# 4.4.1 日誌格式與層級

所屬：[4.4 日誌與錯誤訊息](../4-4.md)

## 正文

In an O‑RAN Radio Unit (O‑RU) three log families are defined: **troubleshooting logs**, **trace logs**, and **security logs**.  They are *independent* of each other, meaning that the collection or storage of one type does not affect the others.  Troubleshooting logs are used by operators to diagnose performance or configuration problems; trace logs capture a continuous, fine‑grained view of the software execution after a specific trigger; security logs record events relevant to the security posture of the unit.  Understanding the distinction is essential because each family follows its own lifecycle and retrieval procedure, and mixing them can lead to mis‑interpretation of the data or violation of security policies.  [O-RAN MP.0 §14.2]  

### File Naming, Compression, and Level Indication

When an O‑RU generates log files, the file name must contain a **compression extension** that identifies the algorithm used.  The supported extensions are  

* `.gz` – DEFLATE,  
* `.lz4` – LZ4,  
* `.xz` – LZMA2 (xz utils),  
* `.zip` – DEFLATE (zlib library).  

The extension is the *only* formal indicator of the compression level; the specification does not prescribe additional “log level” identifiers such as INFO, WARN, or ERROR.  Consequently, any level semantics must be embedded in the log content itself, which is implementation‑dependent.  The O‑RU may produce any number of files, but it is encouraged to keep the set **reasonably small** so that the complete upload can be finished within the timing limits described later.  [O-RAN MP.0 §14.2.2]  

### Triggering, Filtering, and Retrieval

The **troubleshooting log** lifecycle is controlled by NETCONF RPCs.  

* `<start-troubleshooting-logs>` – starts generation of a new batch of troubleshooting logs.  
* `<stop-troubleshooting-logs>` – cancels the generation; in this case the O‑RU does **not** send the `<troubleshooting‑log‑generated>` notification.  

When generation finishes, the O‑RU emits a `<troubleshooting‑log‑generated>` notification that contains the list of file names ready for download.  The download itself follows the generic file‑management procedures defined elsewhere in the O‑RAN spec (Clause 12).  

If the O‑RU advertises the **LOG‑FILTER** feature, the controller may include a *filter list* in the `<start-troubleshooting-logs>` RPC.  The O‑RU must then generate only those log entries that match the supplied filter criteria.  When a filter element is unsupported, the O‑RU may **ignore** it or respond with a **FAILURE** status indicating the unsupported filter.  [O-RAN MP.0 §14.2.2]  

Security logs differ fundamentally: they are **always** collected; there is no RPC to start or stop them.  An O‑RU signals support for this behavior by exposing the `SECURITY-LOGGING` feature in its YANG library.  The logs must be integrity‑protected and stored in non‑volatile memory, and the O‑RU shall provide a log‑rotation mechanism that closes the current file and opens a new one after a configured time interval.  [O-RAN MP.0 §14.2.3]  

### Worked Example: Estimating Upload Time

Assume an O‑RU generates three troubleshooting log files after a `<start-troubleshooting-logs>` request:  

| File | Uncompressed size (MiB) | Compression (chosen) | Extension | Compressed size (MiB) |
|------|------------------------|----------------------|-----------|-----------------------|
| log‑a | 120 | LZ4 | `.lz4` | 48 |
| log‑b | 80  | DEFLATE | `.gz` | 30 |
| log‑c | 50  | LZMA2 | `.xz` | 20 |

The total compressed payload is **98 MiB**.  If the back‑haul link provides a sustained throughput of **10 Mbit s⁻¹** (≈ 1.25 MiB s⁻¹), the raw transmission time is  

$$
T_{\text{tx}} = \frac{98\ \text{MiB}}{1.25\ \text{MiB/s}} \approx 78.4\ \text{s} \approx 1.3\ \text{min}.
$$

Adding protocol overhead and a modest safety margin (≈ 30 %), the expected upload duration is about **1.7 minutes**, comfortably within the **15‑minute** limit (target **3 minutes**) recommended for the whole troubleshooting data upload scenario.  [O-RAN MP.0 §14.2.2]  

### Common Mistakes and Practical Notes

1. **Confusing log families** – Using trace‑log files for troubleshooting analysis can omit pre‑trigger data that is required for root‑cause identification.  Each family must be requested with its appropriate RPC.  

2. **Omitting compression extensions** – The file name must carry the correct extension; otherwise the receiver cannot automatically select the decompression routine, leading to failed uploads.  

3. **Assuming built‑in log levels** – The spec does not define standard level tags (e.g., DEBUG/INFO).  Engineers should verify the vendor’s log format before writing parsers.  

4. **Neglecting log‑rotation** – For security logs, failing to configure rotation may cause a single file to grow beyond the storage capacity of the non‑volatile memory, risking loss of integrity‑protected data.  

5. **Improper handling of unsupported filters** – If a controller supplies an unsupported filter and the O‑RU silently ignores it, the resulting log set may be larger than expected, potentially breaching the upload time budget.  Controllers should check the RPC response status for **FAILURE** indications.  

By respecting the defined log families, file‑naming conventions, and RPC semantics, network operators can reliably collect, transport, and analyse log data without violating O‑RAN security or performance expectations.

## 練習題

**1.** Which O‑RU log family is always collected and does not require a start/stop RPC?

- A. Troubleshooting log
- B. Trace log
- C. Security log
- D. Application log

<details><summary>看答案</summary>

正解：C。Security logs are always collected; there is no defined procedure to start or stop them.

</details>

**2.** Which NETCONF RPC initiates the generation of troubleshooting log files?

- A. <stop-troubleshooting-logs>
- B. <start-trace-logs>
- C. <start-troubleshooting-logs>
- D. <generate-log-files>

<details><summary>看答案</summary>

正解：C。The specification states that this RPC triggers the O‑RU to start generating troubleshooting logs.

</details>

**3.** What is the maximum recommended duration for completing the entire troubleshooting data upload scenario?

- A. 5 minutes
- B. 10 minutes
- C. 15 minutes
- D. 30 minutes

<details><summary>看答案</summary>

正解：C。The spec recommends keeping the total upload time within 15 minutes (target 3 minutes).

</details>

**4.** If a filter type/value supplied in <start-troubleshooting-logs> is not supported, what may the O‑RU do?

- A. Reject the entire RPC with an error code 404.
- B. Ignore the unsupported filter or reply with a FAILURE status.
- C. Automatically convert it to a supported filter.
- D. Restart the O‑RU.

<details><summary>看答案</summary>

正解：B。The O‑RU can either ignore the unsupported filter or respond with a FAILURE status indicating the reason.

</details>
