# 4.3.3 結構化設定檔：YAML、JSON、XML

所屬：[4.3 維運腳本與設定檔](../4-3.md)

## 正文

In an O‑RAN deployment the *M‑Plane* (management plane) must expose a set of data that can be read, written, or subscribed to by network‑wide orchestration tools.  The industry standard way to describe that data is with **YANG modules** – a formal, machine‑readable language that defines the hierarchy, types, and constraints of configuration and operational parameters.  By using a structured description, automated tools can generate configuration files, validate user input, and translate the model into the wire‑format required by the underlying protocol (e.g., NETCONF).  The reference specification states that *“The data models representing the M‑Plane are organized as a set of reusable YANG modules.”* [O‑RAN MP.0 §5.3]

### Key definitions

| Symbol | Definition |
|--------|------------|
| **M‑Plane** | Management‑plane data model for O‑RAN elements. |
| **YANG module** | A reusable collection of node definitions, type definitions, and constraints that together describe a portion of the M‑Plane. |
| **Reusable** | A module that can be imported by many different O‑RAN components without modification. |
| **Generic YANG model** | A module that is publicly available and not tied to a single vendor or product. |

The specification explicitly encourages the use of *generic* YANG models: *“It is also the intent to reuse the publicly available and generic YANG models as much as possible instead of developing customized O‑RAN specific modules.”* [O‑RAN MP.0 §5.3]

### Worked example: measuring reuse ratio

Assume an O‑RAN node adopts **four** YANG modules to describe its configuration:

* Module A – generic “interface‑statistics” model (publicly available)  
* Module B – generic “system‑health” model (publicly available)  
* Module C – generic “radio‑resource‑management” model (publicly available)  
* Module D – a custom “vendor‑specific‑enhancement” model

The **reuse ratio** is defined as the fraction of modules that are generic:

$$
\text{Reuse ratio} = \frac{\text{Number of generic modules}}{\text{Total number of modules}} = \frac{3}{4}=0.75
$$

A reuse ratio of **0.75 (75 %)** shows that the majority of the data model is built from shared, reusable definitions, which aligns with the intent expressed in the reference.  By contrast, a lower ratio would indicate a tendency toward custom, potentially non‑interoperable modules.

### Practical notes and common pitfalls

* **Prefer import over copy** – When a generic YANG module provides the needed nodes, import it rather than copying its definitions into a new, O‑RAN‑specific module.  Copying defeats reusability and creates maintenance overhead.
* **Version alignment** – Generic YANG models evolve independently of O‑RAN releases.  Always verify that the version of the imported module is compatible with the O‑RAN node’s software version; the reference points readers to “the repository of YANG models for more details on each of these modules.”
* **Avoid over‑customisation** – The specification’s intent is to *reuse* generic models *as much as possible*.  Introducing bespoke nodes should be justified by a genuine functional gap, not by convenience.
* **Naming conventions** – YANG modules follow a namespace convention (e.g., `ietf‑interfaces`).  Using the official namespace avoids clashes when multiple modules are combined.
* **Validation tooling** – Leverage existing YANG validators (e.g., `pyang`) to ensure that a module conforms to the YANG syntax and that imported modules are reachable.  Validation catches structural errors before they propagate to runtime configuration files.

By adhering to these guidelines, engineers can keep configuration files lightweight, interoperable, and future‑proof, which is essential for large‑scale O‑RAN deployments where many vendors and software versions coexist.  The overarching principle is simple: **reuse publicly available generic YANG models whenever possible**, as mandated by the O‑RAN specification. [O‑RAN MP.0 §5.3]

## 練習題

**1.** According to the O‑RAN specification, how are M‑Plane data models organized?

- A. As a set of proprietary binary files
- B. As a collection of reusable YANG modules
- C. As free‑form text documents
- D. As a single monolithic XML schema

<details><summary>看答案</summary>

正解：B。The specification explicitly states that M‑Plane data models are organized as reusable YANG modules.

</details>

**2.** What is the intent of the O‑RAN specification regarding the use of YANG models?

- A. To develop only O‑RAN‑specific custom modules
- B. To reuse publicly available and generic YANG models whenever possible
- C. To replace YANG with proprietary formats
- D. To limit the number of modules to a maximum of three

<details><summary>看答案</summary>

正解：B。The specification encourages reuse of generic models instead of creating custom ones.

</details>

**3.** In the worked example, what reuse ratio is obtained when three out of four YANG modules are generic?

- A. 0.25
- B. 0.50
- C. 0.75
- D. 1.00

<details><summary>看答案</summary>

正解：C。The reuse ratio is calculated as generic modules divided by total modules: 3/4 = 0.75.

</details>

**4.** Which of the following actions best follows the specification’s guidance on module creation?

- A. Copying definitions from a generic module into a new custom module
- B. Importing the generic module directly into the O‑RAN node configuration
- C. Ignoring generic modules and writing all definitions from scratch
- D. Using only XML files without YANG

<details><summary>看答案</summary>

正解：B。Importing preserves reusability, aligning with the specification’s intent to reuse generic models.

</details>

**5.** Where can engineers find detailed information about each YANG module referenced in O‑RAN?

- A. In the O‑RAN hardware manual
- B. In clause D and the repository of YANG models
- C. In the source code of the network element
- D. In the user interface of the O‑RAN GUI

<details><summary>看答案</summary>

正解：B。The specification directs readers to clause D and the YANG model repository for details.

</details>
