# 4.2.7 CU／DU 分離與介面

所屬：[4.2 基地台軟體](../4-2.md)

## 正文

In 5G NR the gNB can be split into a **Central Unit (CU)** and a **Distributed Unit (DU)**.  The split is motivated by the need to place latency‑sensitive radio functions (PHY, some MAC) close to the antenna (DU) while centralising higher‑layer control and user‑plane processing (CU) in a data‑center or edge cloud.  This improves scalability, allows multi‑vendor integration, and supports network sharing and resiliency scenarios [TS 38.401 §6]​.

### Key functional blocks

* **gNB‑CU‑CP** – the control‑plane part of the CU; implements RRC, SDAP, and higher‑layer RRC‑related functions.  
* **gNB‑CU‑UP** – the user‑plane part of the CU; hosts PDCP and higher‑layer user‑plane processing.  
* **gNB‑DU** – hosts the lower MAC, PHY and the radio front‑end.  

When the CU is split, the logical interfaces are:

| Interface | Direction | Connects |
|-----------|-----------|----------|
| **F1‑C** | Control plane | gNB‑CU‑CP ↔ gNB‑DU |
| **F1‑U** | User plane | gNB‑CU‑UP ↔ gNB‑DU |
| **E1**   | Both planes (control & user) | gNB‑CU‑CP ↔ gNB‑CU‑UP |

These statements are taken directly from the specification [TS 38.401 §6]​.

### Connectivity rules

* A **gNB‑CU‑CP** may be paired with **multiple gNB‑CU‑UPs** and **multiple gNB‑DUs**.  
* Each **gNB‑DU** is connected to **exactly one gNB‑CU‑CP** (unless a resiliency implementation deliberately adds extra links).  
* Each **gNB‑CU‑UP** is connected to **exactly one gNB‑CU‑CP** (again, multiple links are optional for resiliency).  
* A **gNB‑DU** can serve **multiple gNB‑CU‑UPs** under the same CU‑CP.  
* Conversely, a **gNB‑CU‑UP** can serve **multiple DUs** under the same CU‑CP.  

These rules are verbatim from the reference [TS 38.401 §6]​.

### Procedure for establishing a bearer

When a UE requests a service, the **gNB‑CU‑CP** selects an appropriate **gNB‑CU‑UP** (or set of CU‑UPs) and instructs it to create the necessary bearer.  The actual linkage between the selected CU‑UP and the DU is performed by the CU‑CP using **Bearer Context Management** functions [TS 38.401 §6]​.

### Worked example

Assume an operator deploys a gNB consisting of:

* 1 gNB‑CU‑CP
* 2 gNB‑CU‑UPs (CU‑UP‑A, CU‑UP‑B)
* 3 gNB‑DUs (DU‑1, DU‑2, DU‑3)

According to the connectivity rules:

* Each DU must connect to the single CU‑CP via **F1‑C**.  
* CU‑UP‑A and CU‑UP‑B each connect to the CU‑CP via **E1**.  
* DU‑1 may carry user‑plane traffic for both CU‑UP‑A and CU‑UP‑B over separate **F1‑U** streams.  
* Similarly, CU‑UP‑A may serve DU‑1 and DU‑2 simultaneously.

If a UE attached to DU‑2 requests a high‑throughput service, the CU‑CP may decide to route the user‑plane through CU‑UP‑B (perhaps because CU‑UP‑B has a larger processing pool).  The CU‑CP then triggers Bearer Context Management to set up an **F1‑U** tunnel between CU‑UP‑B and DU‑2, while control messages continue on **F1‑C** between CU‑CP and DU‑2.

### Practical notes & common mistakes

| Mistake | Why it matters | Correct practice |
|---------|----------------|------------------|
| **Assuming a DU can connect to two CU‑CPs simultaneously** | The spec mandates “one gNB‑DU is connected to only one gNB‑CU‑CP” unless a special resiliency design is implemented. Ignoring this can cause routing loops or duplicated control state. | Design the topology so each DU has a single primary CU‑CP; add redundant links only as an optional resiliency feature. |
| **Confusing F1‑C with F1‑U** | F1‑C carries control signalling; F1‑U carries user data. Mixing them leads to protocol violations. | Map control messages (e.g., RRC, MAC‑C) to F1‑C and user payloads to F1‑U as defined. |
| **Skipping the E1 interface when CU‑CP and CU‑UP are co‑located** | Even if physically co‑located, the logical E1 link must exist; omitting it breaks the defined separation. | Preserve the logical E1 connection in software, even if it maps to an intra‑process call. |
| **Connecting a CU‑UP to a DU without CU‑CP involvement** | The spec states that the CU‑CP establishes the CU‑UP↔DU link using Bearer Context Management. Bypassing the CU‑CP leaves the bearer unmanaged. | Always trigger the Bearer Context Management procedure from the CU‑CP before traffic flows. |

Understanding these rules ensures that open‑source gNB projects (e.g., O-RAN, Open5GS) implement the split in a standards‑compliant way and interoperate with commercial 5GCs. [TS 38.401 §6]​.

## 練習題

**1.** Which interface carries control‑plane signalling between the gNB‑CU‑CP and the gNB‑DU?

- A. F1‑U
- B. F1‑C
- C. E1
- D. Xn

<details><summary>看答案</summary>

正解：B。The specification states that the CU‑CP is connected to the DU through the F1‑C interface, which carries control information.

</details>

**2.** How are the gNB‑CU‑CP and gNB‑CU‑UP linked?

- A. Via the F1‑U interface
- B. Via the E1 interface
- C. Directly over the NG interface
- D. They are not linked

<details><summary>看答案</summary>

正解：B。The CU‑CP and CU‑UP communicate over the logical E1 interface.

</details>

**3.** According to the specification, can a single gNB‑DU be attached to two different gNB‑CU‑CPs in a normal deployment?

- A. Yes, always
- B. No, it must be attached to only one CU‑CP
- C. Only if they share the same security domain
- D. Only when using the W1 interface

<details><summary>看答案</summary>

正解：B。The reference explicitly limits each DU to one CU‑CP, except for optional resiliency designs.

</details>

**4.** Which of the following statements is true about a gNB‑CU‑UP's ability to serve DUs?

- A. It can serve only a single DU.
- B. It can serve multiple DUs under the control of the same CU‑CP.
- C. It can serve multiple DUs only if each DU has a different CU‑CP.
- D. It cannot serve any DU; only the CU‑CP does.

<details><summary>看答案</summary>

正解：B。The spec permits a CU‑UP to be connected to several DUs as long as they share the same CU‑CP.

</details>

**5.** Who establishes the connectivity between a gNB‑CU‑UP and a gNB‑DU?

- A. The gNB‑DU itself
- B. The gNB‑CU‑CP using Bearer Context Management functions
- C. The 5GC via the NG interface
- D. The UE during registration

<details><summary>看答案</summary>

正解：B。The CU‑CP is responsible for setting up the CU‑UP↔DU link through Bearer Context Management.

</details>
