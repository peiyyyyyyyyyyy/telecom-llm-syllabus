```cpp
std::vector<CLI::ConfigItem> yaml_config_parser::from_config(std::istream& input) const
{
  YAML::Node config;
  try {
    config = YAML::Load(input);
  } catch (const YAML::ParserException& ex) {
    throw CLI::FileError(std::string("Error parsing YAML configuration file: ") + ex.what());
  }

  return from_config_impl(config);
}
```

程式以 `YAML::Load` 讀取資料流。若遇到對應的解析例外，轉成 CLI 檔案錯誤並保留訊息，成功時則將節點傳入 `from_config_impl`。縮排錯誤可能在讀取階段就被判為語法錯誤，也可能形成語法有效卻不同的階層。後者須用實際設定 schema 或欄位路徑定位，不能只看解析器是否有回傳資料。相鄰的樣板與預設值也要區分，尤其是沒有在範例列出的欄位。 [YAML 1.2.2 §6.1 與 §8.2](https://yaml.org/spec/1.2.2/)

專案的測試宣告提供另一個閱讀方向。驗證器先載入 JSON schema，再用該結構驗證 YAML 資料。JSON 的物件和陣列分別用大括號和方括號標示，schema 中的 `required` 定義存在性條件，`type` 定義預期型別，兩者要分開看。閱讀 XML 時可辨認元素、屬性與命名空間。這些格式有不同的語法及資料模型，不能把它們的設定檔視為同一種輸入來源。專案此處的 gNB 入口註冊的是 YAML 解析器。 [RFC 8259 §4–5](https://www.rfc-editor.org/rfc/rfc8259.html) · [W3C XML 1.0 §3](https://www.w3.org/TR/xml/#sec-logical-struct) · [gNB 解析器註冊](https://github.com/srsran/srsRAN_Project/blob/d2f4b70dda8e2c557d5b05a0ac5f92dbddda19bc/apps/gnb/gnb.cpp#L226-L234)

無線欄位的工程意義可查 3GPP TS 38.104 V18.5.0 §5.2–§5.4 的工作頻段、頻寬及頻率資訊。YAML 鍵名和樣板的通用性須另外由程式決定。遇到來源看似重複時，可用 4.3.4 追查命令列與檔案的優先順序，再用 4.4.3 的錯誤定位方式分辨縮排、型別和不支援的設定。 [3GPP TS 38.104 V18.5.0](https://www.etsi.org/deliver/etsi_ts/138100_138199/138104/18.05.00_60/ts_138104v180500p.pdf)
