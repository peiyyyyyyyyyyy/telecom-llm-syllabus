# 4.2.1 開源基地台專案的結構

所屬：[4.2 基地台軟體](4-2.md)

## 內文

第一次讀基地台專案時，先分辨你手上的證據屬於啟動入口、協定實作、可供其他模組使用的介面、部署範例，還是測試。這個順序能縮小搜尋範圍。要查應用程式接受哪個欄位，就從入口組態往解析與驗證走。要查某個訊息怎麼處理，先從介面宣告確認資料型別，再追到實作與測試。閱讀建置清單能把分散的原始碼、連結的程式庫與最終執行檔接起來，也能辨認名稱相似的目標是否共用同一個入口。

```text
# Default gNB target with dynamic split.
add_executable(gnb gnb.cpp)
add_backward(gnb)
target_include_directories(gnb PRIVATE ${CMAKE_SOURCE_DIR})
install(TARGETS gnb RUNTIME)
target_link_libraries(gnb PRIVATE gnb_base srsran_flexible_o_du_split_dynamic)
notify_binary_target(gnb)

# Add the targets for the rest of the splits.
set(EXTENSIONS gnb_split_6 gnb_split_7_2 gnb_split_8)
set(LIBRARIES srsran_flexible_o_du_split_6 srsran_flexible_o_du_split_7_2 srsran_flexible_o_du_split_8)

foreach (NAME LIB IN ZIP_LISTS EXTENSIONS LIBRARIES)
    add_executable(${NAME} gnb.cpp)
    add_backward(${NAME})
    target_include_directories(${NAME} PRIVATE ${CMAKE_SOURCE_DIR})
    target_link_libraries(${NAME} PRIVATE gnb_base ${LIB})
    set_target_properties(${NAME} PROPERTIES
            RUNTIME_OUTPUT_DIRECTORY "${CMAKE_CURRENT_BINARY_DIR}/../${NAME}"   # Path to the binary.
            RUNTIME_OUTPUT_NAME "gnb"                                           # Binary name.
            EXCLUDE_FROM_ALL 1)                                                 # Do not build by default.
    notify_binary_target(${NAME})
endforeach ()
```

來源 [`apps/gnb/CMakeLists.txt` 第 53–75 行](https://github.com/srsran/srsRAN_Project/blob/d2f4b70dda8e2c557d5b05a0ac5f92dbddda19bc/apps/gnb/CMakeLists.txt#L53-L75)。

第 54 行把 `gnb.cpp` 宣告為預設 gNB 目標的入口。第 56 行補上這個目標的標頭搜尋目錄，第 57 行把執行檔列入安裝。第 58 行把共用的 `gnb_base` 和支援動態分割的應用單元接到入口。回到同一個建置檔前段，可以看見組態綱要、驗證、轉換與 YAML 輸出編譯到同一個靜態程式庫。這些單元負責把輸入組成程式可使用的設定。跟讀時先在綱要定位輸入名稱，再看驗證器對可接受值的限制，最後看轉換器把它寫到哪一個子模組。組態範例可用來確定巢狀結構。當某欄位只在範例出現，還要追到解析和驗證才知道它是選填、必要或示範值。 [gNB 共用設定編譯單元](https://github.com/srsran/srsRAN_Project/blob/d2f4b70dda8e2c557d5b05a0ac5f92dbddda19bc/apps/gnb/CMakeLists.txt#L21-L44) [B200 範例](https://github.com/srsran/srsRAN_Project/blob/d2f4b70dda8e2c557d5b05a0ac5f92dbddda19bc/configs/gnb_rf_b200_tdd_n78_20mhz.yml#L6-L33)

第 62、63 行各定義一個清單，前者列目標，後者列對應程式庫。第 65 行按相同位置逐組取出名稱與程式庫，使第 66 行可以對每個變體共用 `gnb.cpp`，第 69 行則接上該組程式庫。第 71、72 行分開設定「輸出目錄」和「檔名」，所以即使多份可執行檔都叫 `gnb`，也能由路徑區分。第 73 行將這些變體排除在預設建置目標之外。當安裝後找不到某個變體時，可從這段先辨認預設安裝與變體輸出位置，再沿目標名回查建置紀錄。 [gNB 變體目標](https://github.com/srsran/srsRAN_Project/blob/d2f4b70dda8e2c557d5b05a0ac5f92dbddda19bc/apps/gnb/CMakeLists.txt#L53-L75)

3GPP TS 38.401 第 6.1.2 節描述 gNB-CU-CP、gNB-CU-UP 與 gNB-DU 的關係。閱讀這個專案時，可用架構圖辨認邏輯端點與 F1、E1 介面，再回到應用程式的建置和初始化觀察如何組裝。資料夾、CMake 目標與執行檔命名是這個版本的工程組織方式，協定邊界則要由規格和實作共同定位。 [3GPP TS 38.401 V18.5.0，第 6.1.2 節](https://www.etsi.org/deliver/etsi_ts/138400_138499/138401/18.05.00_60/ts_138401v180500p.pdf)

常見的誤判包括只用同名資料夾猜測函式所在位置，或把測試替身當成線上執行路徑。標頭主要描述型別和介面，有些短函式也直接定義在標頭。遇到不同版本或多種部署入口時，請先核對目標連結的程式庫與來源行，再比較控制流程。接下來可在 4.2.2 將協定分層對到程式庫，在 4.2.5 追蹤建置與啟動，在 4.2.7 對照 CU／DU 的角色和介面。
