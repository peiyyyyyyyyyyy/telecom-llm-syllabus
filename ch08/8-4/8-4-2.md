# 8.4.2 參數調整與流量分流

所屬：[8.4 方案與取捨](../8-4.md)

## 正文

In modern cellular systems, the distribution of user traffic across cells is not static. Operators continuously adjust handover (HO) thresholds, reselection parameters, and load‑balancing flags to prevent congestion, improve mobility robustness, and meet service‑level objectives. These adjustments are defined in the **Load Balancing Optimisation (LBO)** and **Mobility Robustness Optimisation (MRO)** functions of 3GPP TS 28.313. By exposing the relevant parameters to an authorized consumer (e.g., a network‑management system), the network can react to traffic spikes, equipment failures, or energy‑saving policies without physically adding sites. This makes parameter tuning a primary lever for traffic steering and quality‑of‑service (QoS) management. [TS 28.313 §6.1.1.5][TS 28.313 §6.1.1.2]

### Key Definitions

| Symbol | Definition | Unit / Legal Values |
|--------|------------|---------------------|
| $dlboControl$ | Boolean flag that enables (`On`) or disables (`Off`) the D‑LBO function. | Boolean (On, Off) |
| $maxDev_{Low}$ | Maximum allowed lower deviation of the HO trigger from its default point. | dB, integer steps of 0.5 dB, range $[-20,\,20]$ |
| $maxDev_{High}$ | Maximum allowed upper deviation of the HO trigger from its default point. | dB, integer steps of 0.5 dB, range $[-20,\,20]$ |
| $t_{min}$ | Minimum time interval between two consecutive HO‑trigger changes performed by MRO. | seconds, range $[0,\,604800]$ |
| $MLB_{Allowed}$ | Boolean flag that permits (TRUE) or prohibits (FALSE) mobility load balancing from a source cell to a target cell. | Boolean (TRUE, FALSE) |
| $T_{def}$ | Default handover trigger value defined by the radio specifications (e.g., TS 38.300). | dB (reference value, not specified here) |
| $\Delta$ | Deviation applied to $T_{def}$, chosen within $maxDev_{Low}$ … $maxDev_{High}$. | dB |

The effective handover trigger after a parameter update is  

$$
T_{new}=T_{def}+\Delta ,\qquad \Delta\in[\,maxDev_{Low},\,maxDev_{High}\,].
$$

The MRO function additionally allows the consumer to **set targets, HO offset ranges, and control parameters**, and to **enable or disable** the function altogether. [TS 28.313 §6.1.1.5][TS 28.313 §6.1.1.2]

### Provisioning Operations

The Management Service (MnS) component of type A supports the core CRUD‑style operations defined in TS 28.532 (e.g., `createMOI`, `modifyMOIAttributes`) and the notification primitives (`notifyMOIAttributeValueChanges`, etc.). [TS 28.313 §7.1.5.1]  

A separate MnS component type B provides streaming‑related operations such as `establishStreamingConnection`, `notifyFileReady`, and `reportStreamData`. [TS 28.313 §7.1.5.2]

### Worked Example

An operator wishes to reduce congestion on Cell A by encouraging handovers to neighboring Cell B. The following configuration is applied through the provisioning MnS:

| Parameter | Value |
|-----------|-------|
| $dlboControl$ | On |
| $maxDev_{Low}$ | –5 dB |
| $maxDev_{High}$ | +3 dB |
| $t_{min}$ | 300 s |
| $MLB_{Allowed}$ | TRUE |

Assume the default HO trigger for the down‑link is $T_{def}= –80 dB$ (a typical value defined in TS 38.300, but the exact number is outside the scope of this subsection).  

*Step 1 – Choose a deviation.*  
The operator selects a lower deviation to make handover easier: $\Delta = –5 dB$ (within the allowed $[-20,20]$ dB range).  

*Step 2 – Compute the new trigger.*  

$$
T_{new}= -80\;\text{dB} + (-5\;\text{dB}) = -85\;\text{dB}.
$$

*Step 3 – Apply timing constraint.*  
Because $t_{min}=300$ s, the MnS will reject any subsequent HO‑trigger change for Cell A that occurs within the next five minutes, ensuring algorithm stability.  

*Step 4 – Verify load‑balancing permission.*  
With $MLB_{Allowed}=TRUE$, the network is allowed to move UEs from Cell A to Cell B when the adjusted trigger is satisfied.  

All values respect the legal ranges defined in the specification, and the MnS will generate notifications (`notifyMOIChanges`) to inform the consumer that the D‑LBO action has been performed. [TS 28.313 §7.1.5.2.1][TS 28.313 §7.1.5.2.2][TS 28.313 §6.1.1.5][TS 28.313 §6.1.1.2]

### Practical Notes and Common Pitfalls

* **Range violations** – Setting a deviation outside $[-20,20]$ dB or a time interval beyond $604800$ s will be rejected by the MnS. Always validate against the tables. [TS 28.313 §7.1.5.2.2]  
* **Confusing component types** – CRUD operations belong to MnS component A, whereas streaming‑related operations belong to component B. Mixing them leads to interface errors. [TS 28.313 §7.1.5.1][TS 28.313 §7.1.5.2]  
* **Neglecting the notification path** – The specification requires the MnS to notify the consumer of any LBO action. Without handling `notifyMOIChanges`, the operator may miss critical updates. [TS 28.313 §6.1.1.5]  
* **Disabling MRO inadvertently** – The MRO function can be globally disabled via its own control flag (REQ‑MRO‑FUN‑3). Ensure the flag is set to enable when tuning HO parameters; otherwise, the changes will have no effect. [TS 28.313 §6.1.1.2]  
* **Assuming instantaneous effect** – Even after a successful parameter update, the $t_{min}$ constraint may delay the next change, and the UE measurement reporting cycle adds additional latency. Plan the optimisation cycle accordingly. [TS 28.313 §7.1.5.2.2]

These guidelines help engineers use the standard‑defined knobs responsibly, achieving a balance between load distribution and mobility robustness without violating the normative constraints.

## 練習題

**1.** Which operation is NOT part of MnS Component Type A for D‑LBO?

- A. createMOI
- B. modifyMOIAttributes
- C. establishStreamingConnection
- D. notifyMOICreation

<details><summary>看答案</summary>

正解：C。`establishStreamingConnection` belongs to Component Type B, not Type A.

</details>

**2.** According to the MRO requirements, which capability must the provisioning MnS provide?

- A. Ability to set targets and HO offset ranges
- B. Ability to collect handover performance measurements
- C. Ability to enable or disable the MRO function
- D. All of the above

<details><summary>看答案</summary>

正解：D。The four MRO functional requirements cover setting targets, collecting measurements, enabling/disabling, and updating parameters.

</details>
