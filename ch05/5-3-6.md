# 5.3.6 告警類型與可能原因

所屬：[5.3 告警](5-3.md)

## 內文

#### 是什麼、什麼時候會用到

告警類型（alarm type）說明告警「大致發生在哪個領域」，可能原因（probable cause）則進一步說明「可能是什麼原因」。在 3GPP TS 28.111 的告警紀錄裡分別是 `alarmType` 與 `probableCause` 兩個欄位，再往下還有選用的 `specificProblem` 做更細的區分。這兩個欄位和嚴重度 `perceivedSeverity`（5.3.1）是不同的欄位：類型與原因回答「是什麼問題」，嚴重度回答「有多急」。維運人員分派工單時，常依 `alarmType` 決定交給傳輸、無線、機房環境還是軟體團隊；寫事件摘要時，也要把 `probableCause` 的原文值照抄，不能自己改寫成別的名稱。

#### 怎麼讀

**一、alarmType 的五個基本類型**

ITU-T X.733 把告警分成五個基本類別（X.733 clause 8.1.1，原文稱 Event type），X.733 Table 3 對應到 X.721 的通知類型名稱。TS 28.111 沿用這五類，並以大寫列舉值表示（TS 28.111 V18.8.0 clause 6.3、7.4.1）：

| TS 28.111 列舉值 | X.721 通知類型 | 意義（依 X.733 clause 8.1.1） |
|---|---|---|
| `COMMUNICATIONS_ALARM` | communicationsAlarm | 主要和「把資訊從一點傳到另一點」所需的程序或處理有關 |
| `QUALITY_OF_SERVICE_ALARM` | qualityofServiceAlarm | 主要和服務品質劣化有關 |
| `PROCESSING_ERROR_ALARM` | processingErrorAlarm | 主要和軟體或處理錯誤有關 |
| `EQUIPMENT_ALARM` | equipmentAlarm | 主要和設備故障有關 |
| `ENVIRONMENTAL_ALARM` | environmentalAlarm | 主要和設備所在機櫃、機房等外殼環境的狀況有關 |

TS 28.111 另外列出五個安全類告警類型（`INTEGRITY_VIOLATION`、`OPERATIONAL_VIOLATION`、`PHYSICAL_VIOLATION`、`SECURITY_SERVICE_OR_MECHANISM_VIOLATION`、`TIME_DOMAIN_VIOLATION`）與 `OTHER`（clause 7.4.1）。TS 28.111 也特別說明，`QUALITY_OF_SERVICE_ALARM` 不指出問題發生的領域，常和另一種類型的告警針對同一個故障同時產生，方便只篩出和服務劣化有關的告警（clause 6.3）。

**二、probableCause 的寫法**

| 規格 | 寫法 | 條號 |
|---|---|---|
| X.733 | 定義一組標準 Probable cause（例如 loss of signal、congestion、out of memory、power problem、temperature unacceptable）；管理物件類別定義者「should」選最具體的值 | X.733 clause 8.1.2.1 |
| X.721 | 把上述值登錄為物件識別碼（例如 `lossOfSignal`、`congestion`），語法為 `ProbableCause ::= CHOICE { globalValue OBJECT IDENTIFIER, localValue INTEGER }` | X.721 clause 14.2；X.733 clause 11.2.6 |
| TS 28.111 | 型別為字串或整數；完整清單見 informative 的 Annex B，產生端「should」選最具體的值 | TS 28.111 clause 7.4.1、Annex B |

TS 28.111 Annex B 收錄四個來源的清單，每一列有字串、整數與建議的 alarmType：Table B.1 來自 ITU-T M.3100、Table B.2 來自 X.733、Table B.3 來自 ETSI TS 101 251（無線系統）、Table B.4 來自 X.736（安全告警）。原文說這些字串（或整數）「should」使用，清單裡找不到合適值時也可以用清單外的值（Annex B）。TS 28.111 附帶的 OpenAPI 定義則把 Annex B 的字串寫成大寫加底線的列舉值（例如 `LOSS_OF_SIGNAL`），同時允許任意字串或整數。

**三、類型與原因一起決定「是不是同一筆告警」**

`objectInstance`、`alarmType`、`probableCause` 與 `specificProblem`（若有）合稱告警識別屬性（alarm identifying attributes）；四者相同才算同一筆告警（TS 28.111 clause 3.1、6.4）。所以同一物件上，`probableCause` 不同就是兩筆告警。

**四、probableCause 不夠細時：specificProblem 與 additionalText**

X.733 要求引用告警的管理物件類別，為每一種告警選出最貼近實際事件的告警類型與可能原因；如果同一組類型與原因底下還有好幾種事件，可以再用 Specific problems 區分（X.733 clause 8.3）。TS 28.111 的對應欄位是 `specificProblem`，用來進一步細分 `probableCause`，型別也是字串或整數（TS 28.111 clause 6.3、7.4.1）。`additionalText` 則是自由文字（clause 7.4.1），X.733 說明理解這個欄位的語意不是解讀告警的必要條件（X.733 clause 8.1.2.13）。實務上，廠商常把板卡位置、埠號等細節放在 `specificProblem` 或 `additionalText`；判讀時先看 `alarmType` 與 `probableCause` 定大方向，再看這兩個欄位找細節。

#### 實際例子

以下是某基地台機房一個上午的 5 筆告警（欄位名稱照 TS 28.111 clause 7.3.1.2，列舉值照 TS 28.111 附帶的 OpenAPI 定義；設備名、時間與文字為虛構）：

```
alarmId  alarmRaisedTime            objectInstance                                         alarmType                 probableCause      perceivedSeverity
b-2101   2026-11-05T09:12:03+08:00  SubNetwork=South,ManagedElement=gNB-2040                ENVIRONMENTAL_ALARM       HIGH_TEMPERATURE   MINOR
b-2102   2026-11-05T09:40:17+08:00  SubNetwork=South,ManagedElement=gNB-2040                EQUIPMENT_ALARM           POWER_PROBLEM      MAJOR
b-2103   2026-11-05T09:41:55+08:00  SubNetwork=South,ManagedElement=gNB-2040,GNBDUFunction=1  PROCESSING_ERROR_ALARM    OUT_OF_MEMORY      MAJOR
b-2104   2026-11-05T10:05:30+08:00  SubNetwork=South,ManagedElement=gNB-2040,GNBDUFunction=1,NRCellDU=2  COMMUNICATIONS_ALARM  LOSS_OF_SIGNAL  CRITICAL
b-2105   2026-11-05T10:06:02+08:00  SubNetwork=South,ManagedElement=gNB-2040,GNBDUFunction=1,NRCellDU=2  QUALITY_OF_SERVICE_ALARM  CONGESTION  MINOR
```

對照 TS 28.111 Annex B：

| probableCause | Annex B 字串／整數 | 來源表 | Annex B 建議的 alarmType |
|---|---|---|---|
| HIGH_TEMPERATURE | High Temperature／123 | Table B.1（M.3100） | Environmental |
| POWER_PROBLEM | Power Problem／58 | Table B.1（M.3100） | Equipment |
| OUT_OF_MEMORY | Out of Memory／332 | Table B.2（X.733） | Processing error |
| LOSS_OF_SIGNAL | Loss Of Signal (LOS)／8 | Table B.1（M.3100） | Communications |
| CONGESTION | Congestion／308 | Table B.2（X.733） | Quality of service |

怎麼讀：
- 五筆剛好涵蓋五個基本類型，可以依 `alarmType` 分派：b-2101 給機房環境、b-2102 給設備維護、b-2103 給軟體、b-2104 給傳輸或無線，b-2105 則是服務品質的提示。
- b-2104 與 b-2105 在同一個 `NRCellDU`、相差 32 秒，符合 TS 28.111 clause 6.3 的描述：服務品質類告警常和另一類告警因同一個故障一起出現。但兩者 `alarmType`、`probableCause` 都不同，依 clause 6.4 仍是兩筆告警。
- 從 09:12 的高溫到 09:40 的電源問題，時間先後可以提出「環境導致設備問題」的假設，但告警類型本身不提供因果關係，要用 5.3.4 的方法與現場資料確認。

#### 容易搞混的地方

- **`alarmType` 與 `perceivedSeverity` 是不同欄位**：CRITICAL、MAJOR 是嚴重度，不是類型；`QUALITY_OF_SERVICE_ALARM` 也可以搭配任何嚴重度（TS 28.111 clause 6.3）。
- **同一個原因在不同文件的寫法不同**：X.733 寫 bandwidth reduced、X.721 寫 `bandwidthReduced`、TS 28.111 Annex B 寫 Bandwidth Reduction、OpenAPI 寫 `BANDWIDTH_REDUCED`。引用時要註明是哪一份規格的寫法，不可混用。
- **Annex B 的 alarmType 欄只是建議**：Annex B 是 informative；Table B.2 有幾列的建議類型和 X.733 的類別語意對不上（例如 Bandwidth Reduction 對到 Security Service or Mechanism Violation），實際值以設備的告警定義為準。
- **整數值不一定通用**：Annex B 列了整數，但 OpenAPI 定義的說明寫明整數與原因的對應由廠商決定；看到整數型的 `probableCause`，要查該廠商的對照表。

#### 和其他小節的關係

本節是 5.1.1 告警欄位的細部說明，和 5.3.1 嚴重度互補。`alarmType` 常用來做 5.3.3 的過濾條件，也是 5.3.4 判斷拓撲層次的線索（通訊類多在傳輸路徑上）。`probableCause` 是 6.1 根因的類型與 6.2 推理的起點，但只代表「可能」原因，不等於最後的根因。
