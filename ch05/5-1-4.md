# 5.1.4 信令追蹤

所屬：[5.1 資料的種類](5-1.md)

## 內文

#### 是什麼、什麼時候會用到

信令追蹤（Trace，3GPP 稱為 Subscriber and Equipment Trace）是讓網元把特定用戶、特定終端或特定小區上的信令訊息記錄下來，再送到追蹤收集實體（Trace Collection Entity，TCE）的功能。告警（5.1.1）告訴你「哪個物件出事」，績效量測（5.1.2）告訴你「整體指標變差多少」，但若要回答「這通連線到底在哪一步失敗、失敗原因碼是什麼」，就要看追蹤紀錄。維運人員常在下列情況讀到追蹤資料：客訴個案（某支手機反覆斷線）、新功能或新站開通後的驗證、某小區切換失敗率突然升高需要逐通檢查，以及 MDT（5.1.5）資料的收集，因為 MDT 本身就是沿用追蹤機制。

#### 怎麼讀

讀追蹤資料前，先弄清楚三件事：追蹤是怎麼啟動的、記錄到多細、檔案裡每個欄位代表什麼。

**1. 啟動方式。** TS 32.421 把啟動分成兩種（TS 32.421 V18.4.0 clause 3.1、4.2）：

| 啟動方式 | 原文定義重點 | 典型用途 |
|---|---|---|
| 管理面啟動（management based activation） | 由管理系統直接在各網元啟動 Trace Session | 小區追蹤（Cell Traffic Trace）：追蹤一個或多個小區裡的進行中通話 |
| 信令面啟動（signalling based activation） | 透過網元之間的信令介面，把源自管理系統的啟動往下傳遞 | 追蹤特定用戶或終端，跟著用戶跨網元記錄 |

5GS 的管理面啟動是由管理系統（Provisioning MnS consumer）把追蹤控制與組態參數設給網元，而且被設定的網元不會把這些參數再傳給其他網元（TS 32.422 V18.7.0 clause 4.1.1.1.2）。信令面啟動則是設給 UDM、AMF、SMF 這類 5GC 網元，再由它依參數往 RAN 與核心網其他網元傳遞（TS 32.422 V18.7.0 clause 4.1.2.1.2）。

**2. 兩層「期間」。** Trace Session 是從啟動到停用的整段時間，以 Trace Reference 識別；Trace Recording Session 是其中「真的有在產生紀錄」的區間，以 Trace Recording Session Reference 識別（TS 32.421 V18.4.0 clause 3.1）。Trace Reference 由 MCC＋MNC＋Trace ID 組成，Trace ID 是 3 bytes；Trace Recording Session Reference 是 2 bytes（TS 32.422 V18.7.0 clause 5.6、5.7）。

**3. 追蹤深度（Trace Depth）。** 這個參數決定網元記錄得多細，同一個 Trace Session 裡所有網元用同一個深度（TS 32.422 V18.7.0 clause 5.3）：

| 列舉值 | 記錄內容 | 格式 |
|---|---|---|
| Minimum (0) | 信令訊息中的部分 IE，加上廠商擴充 | 解碼後 |
| Medium (1) | Minimum 的 IE，再加上無線量測相關 IE，加上廠商擴充 | 解碼後 |
| Maximum (2) | 完整信令訊息，加上廠商擴充 | 編碼（原始） |
| MinimumWithoutVendorSpecificExtension (3) | 同 Minimum，但不含廠商擴充 | 解碼後 |
| MediumWithoutVendorSpecificExtension (4) | 同 Medium，但不含廠商擴充 | 解碼後 |
| MaximumWithoutVendorSpecificExtension (5) | 同 Maximum，但不含廠商擴充 | 編碼 |

各網元要記錄哪些 IE，列在 TS 32.423 clause 4 的各網元表格中。以 gNB-CU-CP 為例，原文要求至少支援 Maximum、Medium、Minimum 其中一種深度，記錄 Uu（RRC）、NG-C 等介面的訊息（TS 32.423 V18.6.0 clause 4.30）。

**4. 檔案欄位。** 檔案式回報用 XML，主要元素如下（TS 32.423 V18.6.0 Annex A.1）：

| 元素／屬性 | 意義 |
|---|---|
| `fileHeader`（`fileFormatVersion`、`vendorName`） | 檔頭：格式版本、廠商 |
| `fileSender elementDn`、`elementType` | 產生檔案的網元 DN 與類型 |
| `traceCollec beginTime` | 檔案中第一筆資料的起始時間（含 UTC 時差） |
| `traceRecSession`（`traceRecSessionRef`、`stime`） | 一個 Trace Recording Session，`stime` 是通話開始時間 |
| `msg`（`function`、`name`、`changeTime`、`vendorSpecific`） | 一則被追蹤的訊息；`changeTime` 是相對 `beginTime` 的秒數（nbsec.ms） |
| `ie`、`ieGroup` | 解碼後的 IE，只在 medium 或 minimum 深度出現 |
| `rawMsg`（`protocol`、`version`） | 十六進位編碼的整則訊息，只在 maximum 深度出現 |
| `traceSessionRef`（`MCC`、`MNC`、`TRACE_ID`） | Trace Reference |

另外，串流式回報的紀錄標頭有 `timeStamp`、`traceReference`、`traceRecordingSessionReference`、`traceRecordTypeId` 等欄位（TS 32.423 V18.6.0 clause 5.2.2），和上面的 XML 檔是不同的回報方式，不要混著讀。

#### 實際例子

下面是一段仿真的 gNB-CU-CP 小區追蹤檔（管理面啟動、Minimum 深度），元素名稱照 TS 32.423 Annex A，IE 名稱照 Table 4.30.2，網元名稱、PLMN（001/01 為測試用代碼）與時間都是虛構的：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<traceCollecFile xmlns="http://www.3gpp.org/ftp/specs/archive/32_series/32.423#traceData">
  <fileHeader fileFormatVersion="32.423 V18.6" vendorName="VendorX">
    <fileSender elementDn="SubNetwork=AreaN,ManagedElement=CUCP-0042" elementType="gNB-CU-CP"/>
    <traceCollec beginTime="2026-11-20T09:15:00+08:00"/>
  </fileHeader>
  <traceRecSession dnPrefix="SubNetwork=AreaN" traceRecSessionRef="1A2" stime="2026-11-20T09:15:03+08:00">
    <msg function="Uu" name="RRC SETUP REQUEST" changeTime="3.120" vendorSpecific="false">
      <ie name="Establishment Cause">mo-Data</ie>
    </msg>
    <msg function="Uu" name="RRC REESTABLISHMENT REQUEST" changeTime="41.877" vendorSpecific="false">
      <ie name="ReestablishmentCause">handoverFailure</ie>
    </msg>
    <traceSessionRef>
      <MCC>001</MCC>
      <MNC>01</MNC>
      <TRACE_ID>00A1F3</TRACE_ID>
    </traceSessionRef>
  </traceRecSession>
</traceCollecFile>
```

逐欄讀法：
- `fileSender elementType="gNB-CU-CP"`：資料來自 CU-CP，所以看到的是 RRC 與 NG-C 一類的控制面訊息，不會有使用者面資料。
- `traceCollec beginTime` 是 09:15:00；第一則訊息 `changeTime="3.120"`，代表發生在 09:15:03.120；第二則 `changeTime="41.877"`，代表發生在 09:15:41.877，兩則相隔 41.877 − 3.120 = 38.757 秒。
- 只有 `ie`、沒有 `rawMsg`，符合 Minimum 深度只記錄解碼後部分 IE 的規則（TS 32.423 V18.6.0 Annex A.1）。若要看完整訊息內容，要改用 Maximum 深度重新追蹤。
- `Establishment Cause` 只在使用小區追蹤時才是條件必備（CM）（TS 32.423 V18.6.0 Table 4.30.2），這裡有出現，和「管理面啟動的小區追蹤」相符。
- `ReestablishmentCause` 的值 `handoverFailure` 是 TS 38.331 列舉值之一（另兩個有效值是 `reconfigurationFailure`、`otherFailure`）。結論：這通連線建立約 38.8 秒後發生切換失敗，UE 嘗試重建；下一步應查同時段該小區的切換相關量測與鄰區設定（5.1.6），不能只憑這一筆就認定是哪種根因。

#### 容易搞混的地方

1. **Trace Session 和 Trace Recording Session 不同。** 前者是整個追蹤任務的期間（Trace Reference），後者是任務內實際記錄某通連線的區間（Trace Recording Session Reference）。同一個 Trace Session 下可以有很多個 `traceRecSession`。
2. **追蹤深度不是「記錄多少用戶」。** 深度只決定每則訊息記錄得多細；要追蹤哪些網元、哪些介面是另一個維度，原文稱為 trace scope（TS 32.421 V18.4.0 clause 4.1）。
3. **Maximum 才有原始訊息。** 只有 Maximum（或不含廠商擴充的版本）會有 `rawMsg`；Minimum、Medium 是解碼後的子集，看不到的 IE 不代表訊息裡沒有。
4. **管理面啟動的參數不會往下傳。** 5GS 管理面啟動時，網元不會把收到的參數轉給其他網元；需要跨網元跟著用戶走時，要用信令面啟動。

#### 和其他小節的關係

追蹤紀錄的時間要和告警（5.1.1）、績效量測（5.1.2）對齊，時間戳與時區的處理見 5.2.1；`fileSender elementDn` 的 DN 寫法見 5.2.2。MDT 資料（5.1.5）沿用同一套追蹤機制與檔案格式。逐通找出的失敗原因碼，可用於 5.5.1 排事件時間軸，再進入 6.2 由時間軸提出假設。
