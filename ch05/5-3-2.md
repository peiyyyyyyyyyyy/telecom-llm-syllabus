# 5.3.2 告警之間的關聯

所屬：[5.3 告警](5-3.md)

## 內文

#### 是什麼、什麼時候會用到

一個故障常常同時引發好幾筆告警：傳輸線路中斷，上游路由器報鏈路失效，下游基地台報連線異常，基地台底下的小區再各報一筆無法服務。告警關聯（alarm correlation）就是找出這些告警之間「由同一原因引起」的關係。TS 28.111 的說法是：單一故障可能造成多個錯誤與失效，系統可以（may）支援辨識這些關係（TS 28.111 V18.8.0 clause 6.10）。維運人員在兩種情況會讀到關聯資料：一是告警紀錄裡已經帶有系統填好的 `correlatedNotifications`；二是系統沒有填，只能自己依物件、時間與拓撲把告警分群。兩者的可信度不同，要分開看。

#### 怎麼讀

**一、規格定義的關聯欄位（3GPP）**

告警關聯在 TS 28.111 是選用的解決方案元件（optional solution component），對應兩個屬性與一個通知（TS 28.111 V18.8.0 clause 6.1 Table 6.1-1）：

| 名稱 | 型態 | 意義 |
|---|---|---|
| `correlatedNotifications` | 由 `CorrelatedNotification` 組成的清單，multiplicity * | 與本告警相關的通知清單（clause 7.4.1） |
| `CorrelatedNotification.sourceObjectInstance` | DN | 指出一個 MonitoredEntity（clause 7.3.4.1、7.4.1） |
| `CorrelatedNotification.notificationIds` | integer 清單，1..* | 該物件發出、與本告警相關的通知編號（clause 7.4.1） |
| `rootCauseIndicator` | boolean | 表示本告警紀錄是相關通知所描述事件的根因（clause 7.4.1） |
| `notifyCorrelatedNotificationChanged` | 通知 | `correlatedNotifications` 被建立、更新或刪除時送出（clause 8.7.1） |

讀法規則：

1. 支援告警關聯的 producer，`rootCauseIndicator` 與 `correlatedNotifications` 至少要支援一個（TS 28.111 V18.8.0 clause 7.3.1.3），所以可能只看到其中一個。
2. `notificationIds` 指的是「通知」不是「告警」。被引用的通知不一定是告警通知，也可能是屬性值變更等事件；若引用的是告警，那筆告警紀錄可能已被確認並清除、不在清單裡了（TS 28.111 V18.8.0 clause 7.3.4.1）。
3. 通知編號只保證在同一個受管物件內唯一（TS 28.111 V18.8.0 clause 8.2.2；X.733 clause 8.1.2.8），所以每組編號都要和 `sourceObjectInstance` 一起讀。
4. 告警紀錄的 `notificationId` 是「因更新這筆紀錄而送出的最後一個通知」的編號（TS 28.111 V18.8.0 clause 7.4.1），紀錄被更新過後就不等於當初 `notifyNewAlarm` 的編號。

**二、ITU-T X.733 的定義**

X.733 的 Correlated notifications 參數是一組通知識別碼，必要時附上所屬受管物件；若相關的事件報告來自另一個物件，就必須帶上 source object instance（X.733 clause 8.1.2.9）。X.733 明確表示：判斷關聯的演算法不在建議書範圍內（X.733 clause 7、8.1.2.9）。

**三、人工分群的線索（不是規格定義）**

系統沒有填關聯欄位時，常用下面三種線索分群；這是分析方法，規格沒有定義時間窗長度或上下游判定方式：

- **同一物件**：比對 `objectInstance`。注意四個識別屬性（`objectInstance`、`alarmType`、`probableCause`、`specificProblem`）全部相同的是「同一個告警」，不是兩個相關告警（TS 28.111 V18.8.0 clause 6.4）。同一物件上識別屬性（alarmType／probableCause／specificProblem）不完全相同的告警都是不同告警，都可以是關聯候選；例如 3GPP 指出 `QUALITY_OF_SERVICE_ALARM` 常與其他類型的告警為同一底層故障而一起產生（TS 28.111 V18.8.0 clause 6.3）。
- **同一時間窗**：比對 `alarmRaisedTime`，先把時間換成同一時區（見 5.2.1）。
- **上下游設備**：依 DN 的包含關係（例如 NRCellDU 包含在 ManagedElement 之下）與傳輸拓撲判斷依賴關係。

#### 實際例子

下表是某 SubNetwork 的 AlarmList 在 02:20 讀到的 5 筆告警紀錄（欄位依 TS 28.111 clause 7.3.1.2；DN 前綴 `SubNetwork=North,` 省略；設備名與數值虛構）：

| alarmId | objectInstance | notificationId | alarmRaisedTime | alarmType | probableCause | perceivedSeverity |
|---|---|---|---|---|---|---|
| r-0441 | ManagedElement=AGG-RTR-07 | 893 | 02:17:01Z | COMMUNICATIONS_ALARM | LINK_FAILURE | CRITICAL |
| a-1190 | ManagedElement=gNB-1001 | 5001 | 02:17:04Z | COMMUNICATIONS_ALARM | CONNECTION_ESTABLISHMENT_ERROR | MAJOR |
| a-1191 | ManagedElement=gNB-1001,GNBDUFunction=1,NRCellDU=11 | 3301 | 02:17:05Z | COMMUNICATIONS_ALARM | UNDERLYING_RESOURCE_UNAVAILABLE | MAJOR |
| a-1192 | ManagedElement=gNB-1001,GNBDUFunction=1,NRCellDU=12 | 3301 | 02:17:06Z | COMMUNICATIONS_ALARM | UNDERLYING_RESOURCE_UNAVAILABLE | MAJOR |
| a-1193 | ManagedElement=gNB-1002 | 7730 | 02:17:30Z | ENVIRONMENTAL_ALARM | TEMPERATURE_UNACCEPTABLE | WARNING |

r-0441 另帶有關聯欄位（TS 28.111 V18.8.0 clause 7.3.4.2、7.4.1）：

```json
"rootCauseIndicator": true,
"correlatedNotifications": [
  { "sourceObjectInstance": "SubNetwork=North,ManagedElement=gNB-1001", "notificationIds": [5001] },
  { "sourceObjectInstance": "SubNetwork=North,ManagedElement=gNB-1001,GNBDUFunction=1,NRCellDU=11", "notificationIds": [3301] },
  { "sourceObjectInstance": "SubNetwork=North,ManagedElement=gNB-1001,GNBDUFunction=1,NRCellDU=12", "notificationIds": [3301] }
]
```

怎麼讀：

- r-0441 的 `rootCauseIndicator` 為 true，表示 producer 判定它是三組相關通知所描述事件的根因。它的 `notificationId` 是 893，而不是當初新告警的編號，因為加入關聯時這筆紀錄被更新、送出了 `notifyCorrelatedNotificationChanged`（TS 28.111 V18.8.0 clause 6.12、7.4.1）。
- 兩個小區的通知編號都是 3301，這是合法的：編號只在各自的物件內唯一，靠 `sourceObjectInstance` 區分是哪一個小區。
- 時間差：路由器 02:17:01 到 gNB-1001 是 3 秒，到兩個小區分別是 4 秒、5 秒；gNB-1002 是 29 秒後。
- a-1193 雖然落在同一分鐘內，但不在任何 `correlatedNotifications` 裡，類型是環境告警、位置在另一個 ManagedElement，不能只因時間接近就歸到同一群。

結論：有規格欄位支持的關聯群組是 r-0441 加 a-1190～a-1192，共 4 筆；a-1193 應另案處理。

#### 容易搞混的地方

1. **「同一告警」與「相關告警」**：四個識別屬性都相同是同一告警，只會更新原紀錄；關聯指的是不同告警之間的因果或相依關係。
2. **系統標的關聯與自己推的關聯**：`correlatedNotifications`、`rootCauseIndicator` 是 producer 提供的資料；依時間窗或拓撲自己分群只是推測，寫報告時要標明依據（見 5.5.3）。
3. **`notificationIds` 不是 `alarmId`**：前者是通知編號、要配 `sourceObjectInstance` 讀；後者是告警紀錄在 AlarmList 內的識別碼。
4. **規格沒有規定關聯演算法**：X.733 與 TS 28.111 都只定義怎麼「表示」關聯，沒有定義怎麼「算出」關聯；時間窗長度沒有標準值。

#### 和其他小節的關係

本節分好的群組，是 5.3.3 合併與抑制告警、5.3.4 找最源頭告警的輸入；上下游判斷要用到 5.2.2 的 DN 與 5.1.6 的 NRM 關係；分群後的影響範圍見 5.5.2。5.3.4 → 6.2 由時間軸提出假設，再到 6.1 判斷根因類型。

```text
Fictional alarm projection. Each notification ID is interpreted with its producer scope.
Producer scope: SubNetwork=DemoCorr1
Row order: alarmId ; notificationId ; objectInstance suffix ; raise time
C01-A ; 16110 ; ManagedElement=Upstream ; 01:17:00Z
C01-B ; 16111 ; ManagedElement=BranchB ; 01:17:07Z
C01-C ; 16112 ; ManagedElement=BranchC ; 01:17:14Z
C01-D ; 16113 ; ManagedElement=Unlinked ; 01:17:21Z
C01-A.correlatedNotifications notificationId projection: 16111 | 16112
C01-A.rootCauseIndicator: true
Candidate operational dependency being investigated: transport. No physical verification supplied.
The Unlinked row has no explicit reference in this extract.
```

**1261.** What linkage does the producer evidence establish in managed-element correlation with two downstream notifications?

1. All notices must originate from the unlinked object
2. The producer associates the referenced notifications and flags the first record as their root cause.
3. The first physical repair is confirmed
4. Every temporally close alarm is directly linked

<details><summary>看答案</summary>

**答案**　2

**詳解**　Use the reference set (16111 | 16112) and the rootCauseIndicator value (true) independently. “All notices must originate from the unlinked object” does not follow from the shown references. “The first physical repair is confirmed” claims information absent from the projection. “Every temporally close alarm is directly linked” substitutes time proximity for an explicit reference.
