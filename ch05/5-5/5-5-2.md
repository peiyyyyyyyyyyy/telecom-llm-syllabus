# 5.5.2 影響範圍

所屬：[5.5 寫摘要](../5-5.md)

## 正文

In a 3GPP‑based network, every alarm that is generated by a network entity (NE) must convey not only *that* something is wrong, but also *where* the problem resides and *how far* its consequences spread.  The portion of the alarm summary that describes the **impact range** answers the questions “Which physical and logical resources are affected?” and “What capability has been lost?”  Accurately stating the impact range enables operators to assess the scope of service degradation, to plan resource‑level mitigation, and to prioritize restoration work.  Because fault detection is required to be immediate and autonomous [TS 32.111‑1 §4.1.1], the impact‑range data must be derived from the same measurements, counters and thresholds that triggered the alarm.

### Key Definitions Supplied by the Fault Detection Process

When a fault is detected, the NE must provide the following items that together constitute the impact range:

| Item | Meaning (as defined in the specification) |
|------|--------------------------------------------|
| **Device / Resource / File / Functionality / Smallest Replaceable Unit** | *“the device/resource/file/functionality/smallest replaceable unit”* – for hardware faults the smallest faulty replaceable unit, for software faults the corrupted file(s) or database, for functional faults the affected functionality, and for overload faults the reason for the overload. |
| **Physical Resources Affected** | Any *“physical … resources that are affected by the fault if applicable”*. |
| **Logical Resources Affected** | Any *“logical resources that are affected by the fault …”*. |
| **Loss of Capability Description** | A textual description of *“the loss of capability of the affected resource.”* |
| **Fault Type** | One of the ITU‑T X.733 categories: communication, environmental, equipment, processing error, QoS. |
| **Severity** | One of the ITU‑T X.733 levels: indeterminate, warning, minor, major, critical. |
| **Probable Cause** | The most likely underlying reason for the fault. |
| **Detection Time** | *“the time at which the fault was detected in the faulty network entity.”* |
| **Fault Nature** | Either **ADAC** (detectable and clearable) or **ADMC** (detectable but not automatically clearable). |
| **Additional Information** | Any *“other information that helps understanding the cause and the location of the abnormal situation.”* |

These items are not optional; the specification states that *“for each fault, the fault detection process shall supply the following information”* [TS 32.111‑1 §4.1.1].

### Representing the Impact Range

For practical documentation, the impact range is often expressed as a tuple:

$$
\mathcal{I} = \bigl( \underbrace{U}_{\text{unit}},\; \underbrace{P}_{\text{physical}},\; \underbrace{L}_{\text{logical}},\; \underbrace{C}_{\text{capability loss}},\; \underbrace{T}_{\text{type}},\; \underbrace{S}_{\text{severity}} \bigr)
$$

where  

* $U$ = smallest replaceable unit (hardware) or affected component (software/functionality).  
* $P$ = set of physical resources (e.g., chassis, line cards).  
* $L$ = set of logical resources (e.g., bearer, QoS profile).  
* $C$ = textual description of the lost capability.  
* $T$ = fault type per ITU‑T X.733.  
* $S$ = severity level per ITU‑T X.733.

No additional formulae are required; the tuple simply aggregates the data supplied by the NE.

### Worked Example

Consider a base‑station controller that detects a sudden increase in its CPU utilization counter beyond a predefined threshold. The self‑check routine classifies the event as an **ADAC fault** (detectable and clearable) of type **processing error** with **major** severity.

| Item | Value (derived from detection) |
|------|--------------------------------|
| Smallest Replaceable Unit | **CPU core 2** (hardware) |
| Physical Resources | **CPU module, power supply** |
| Logical Resources | **Scheduler process, real‑time thread** |
| Loss of Capability | **Unable to schedule downlink frames for carrier A** |
| Fault Type | **processing error** |
| Severity | **major** |
| Probable Cause | **Software loop in scheduler** |
| Detection Time | **2026‑11‑23 14:05:12 UTC** |
| Fault Nature | **ADAC** |
| Additional Info | **Counter value = 98 % (threshold = 85 %)** |

The impact‑range tuple is  

$$
\mathcal{I}= \bigl(\text{CPU core 2},\;\{\text{CPU module, power supply}\},\;\{\text{Scheduler process, real‑time thread}\},\;\text{Unable to schedule downlink frames for carrier A},\;\text{processing error},\;\text{major}\bigr)
$$

An operator reading the alarm summary can instantly see that only one core is implicated, that the physical module remains powered, and that the service impact is limited to carrier A.  Because the fault is ADAC, the NE will automatically attempt a clear once the counter falls back below threshold; if the condition persists, manual intervention may be required.

### Common Mistakes and Practical Tips

| Mistake | Why It Happens | Correct Approach |
|---------|----------------|------------------|
| **Omitting logical resources** | Engineers focus on hardware and forget that software faults also affect logical entities. | Always list both physical *and* logical resources as required by the specification. |
| **Confusing ADAC with ADMC** | Both are “detectable” and the “A” in the acronym is easy to overlook. | Remember that **ADMC faults cannot be cleared by the NE itself** and always need manual operator action. |
| **Leaving severity undefined** | Severity is sometimes treated as optional because it seems subjective. | Use the ITU‑T X.733 severity levels verbatim; the specification mandates reporting it. |
| **Providing vague loss‑of‑capability description** | “System degraded” is too generic and does not help pinpoint impact. | State the exact capability that cannot be performed (e.g., “cannot allocate QoS class 1 bearer”). |
| **Relying on a single measurement** | A threshold crossing may be transient; the spec notes short‑term faults that disappear. | Corroborate with multiple sampling intervals before finalizing the impact range. |

By systematically populating the impact‑range tuple directly from the fault detection output, alarm summaries become concise, actionable, and fully compliant with 3GPP TS 32.111‑1.

## 練習題

**1.** Which item in the fault detection information specifically addresses the scope of impact of a fault?

- A. The type of the fault (communication, environmental, equipment, processing error, QoS)
- B. The severity of the fault
- C. An indication of the physical and logical resources that are affected by the fault
- D. The probable cause of the fault

<details><summary>看答案</summary>

正解：C。The scope of impact is described by indicating which physical and logical resources are affected.

</details>

**2.** Which phrase in the specification tells us that the loss of capability of the affected resource must be described?

- A. “the smallest replaceable unit that is faulty”
- B. “a description of the loss of capability of the affected resource”
- C. “the nature of the fault, e.g. ADAC or ADMC”
- D. “the time at which the fault was detected in the faulty network entity”

<details><summary>看答案</summary>

正解：B。The specification explicitly requires a description of the loss of capability for the affected resource.

</details>

**3.** In the list of required information for each fault, which element helps understand which parts of the system are impacted?

- A. Probable cause of the fault
- B. Device/resource/file/functionality/smallest replaceable unit
- C. Physical and logical resources that are affected by the fault
- D. Severity of the fault

<details><summary>看答案</summary>

正解：C。Identifying the physical and logical resources affected directly shows the impact area.

</details>

**4.** For which category of faults does the specification require indicating the affected physical and logical resources?

- A. Only hardware faults
- B. Only software faults
- C. All faults, wherever applicable
- D. Only overload faults

<details><summary>看答案</summary>

正解：C。The requirement applies to all fault types when it is applicable.

</details>
