# 5.3.1 告警嚴重度（perceivedSeverity）

所屬：[5.3 告警](5-3.md)

## 內文

#### 是什麼、什麼時候會用到

告警嚴重度（perceived severity）是告警紀錄裡表示「這個告警有多急」的欄位。在 3GPP 的告警紀錄（alarm record）中，這個屬性叫 `perceivedSeverity`，規格把它定義為提醒維運人員注意的相對緊急程度；它的觀念來自 ITU-T X.733 的 Perceived severity 參數。維運人員幾乎每天都會用到它：監控畫面依嚴重度上色與排序、交班時先看還有多少 CRITICAL、MAJOR 沒處理、派工規則依嚴重度決定要不要立刻叫人。讀告警清單時，嚴重度是決定先看哪一筆的第一個依據，但它不是唯一依據，還要搭配告警類型、物件與時間一起判斷（見 5.3.6、5.3.4）。

#### 怎麼讀

**3GPP 的寫法**：TS 28.111 的 `perceivedSeverity` 是列舉型態（ENUM），允許值為 `CRITICAL`、`MAJOR`、`MINOR`、`WARNING`、`INDETERMINATE`、`CLEARED`，一律大寫，每筆告警紀錄必有一個值（multiplicity 1）（TS 28.111 V18.8.0 clause 7.4.1）。屬性說明只有一句：It indicates the relative level of urgency for operator attention.（TS 28.111 V18.8.0 clause 7.4.1）。各值的意義，TS 28.111 在 clause 6.3 指向 X.733 clause 8.1.2.3，所以要回到 X.733 讀定義。

**ITU-T X.733 的寫法**：X.733 定義六個嚴重度等級，ASN.1 值用小寫（`cleared`、`indeterminate`、`critical`、`major`、`minor`、`warning`）（X.733 clause 8.1.2.3、clause 11.2.7 Table 5）。其中只有四個代表「影響服務的程度」，由重到輕排序為 Critical、Major、Minor、Warning（X.733 clause 8.1.2.3）。

| 值（3GPP 寫法） | X.733 的定義重點（clause 8.1.2.3） |
|---|---|
| `CRITICAL` | 已發生影響服務的狀況，需要「立即」修正；例如物件完全停止服務 |
| `MAJOR` | 已發展出影響服務的狀況，需要「緊急」修正；例如物件能力嚴重劣化 |
| `MINOR` | 存在「不影響服務」的故障，應採取修正以免變成更嚴重（例如影響服務）的故障 |
| `WARNING` | 偵測到潛在或即將發生、會影響服務的故障，但尚未有明顯影響；應進一步診斷與修正 |
| `INDETERMINATE` | 無法判定嚴重度 |
| `CLEARED` | 表示先前回報的一個或多個告警已清除 |

讀的時候要注意三條規則：

1. **四級排序只適用前四個值**。`INDETERMINATE` 不是「介於某兩級之間」，`CLEARED` 也不是「最輕的一級」，兩者都不在 X.733 的四級排序裡（X.733 clause 8.1.2.3）。
2. **`CLEARED` 是狀態轉換，不是程度**。X.733 寫明，cleared 會清除同一受管物件上 Alarm type、Probable cause、Specific problems（若有）都相同的所有告警（X.733 clause 8.1.2.3）。3GPP 的對應做法是：條件消失時由系統把該告警紀錄的 `perceivedSeverity` 改成 `CLEARED`（自動清除，ADAC）；不會自動清除的告警（ADMC）則由 MnS consumer 把它設成 `CLEARED`（TS 28.111 V18.8.0 clause 6.8）。`perceivedSeverity` 只有在 producer 支援 consumer 清除告警時才可寫入（TS 28.111 V18.8.0 clause 7.3.1.2 NOTE）。
3. **嚴重度改變不會產生新告警**。同一告警（四個識別屬性相同）的嚴重度變化，是更新原有紀錄（TS 28.111 V18.8.0 clause 6.14）；變成 `CLEARED` 時送 `notifyClearedAlarm`，其他嚴重度變化送 `notifyChangedAlarmGeneral`（`notifyChangedAlarm` 已標為 deprecated）（TS 28.111 V18.8.0 clause 6.12、8.3.1、8.4.1、8.6.1）。

**O-RAN 的寫法（另一套模型，不可混用）**：O-RAN WG4 M-plane 的 `o-ran-fm` YANG 模組用 `fault-severity` 表示嚴重度，只有 `CRITICAL`、`MAJOR`、`MINOR`、`WARNING` 四個值，沒有 `INDETERMINATE` 與 `CLEARED`；清除與否另用布林值 `is-cleared` 表示（o-ran-fm.yang revision 2022-08-15）。

#### 實際例子

下面是向某 SubNetwork 的 AlarmList 讀回的告警紀錄（格式依 TS 28.111 OpenAPI 定義：`alarmRecords` 是以 alarmId 為鍵的 map；設備名、時間、編號均為虛構），此系統支援告警確認（acknowledgement）功能：

```json
{
  "id": "AL1",
  "attributes": {
    "operationalState": "ENABLED",
    "administrativeState": "UNLOCKED",
    "numOfAlarmRecords": 5,
    "lastModification": "2026-03-14T02:31:40Z",
    "alarmRecords": {
      "a-1201": {
        "objectInstance": "SubNetwork=North,ManagedElement=gNB-1001,GNBDUFunction=1,NRCellDU=11",
        "notificationId": 5007,
        "alarmRaisedTime": "2026-03-14T02:17:05Z",
        "alarmChangedTime": "2026-03-14T02:24:10Z",
        "alarmType": "EQUIPMENT_ALARM",
        "probableCause": "TRANSMITTER_FAILURE",
        "perceivedSeverity": "CRITICAL",
        "ackState": "UNACKNOWLEDGED"
      },
      "a-1202": {
        "objectInstance": "SubNetwork=North,ManagedElement=gNB-1001,GNBDUFunction=1,NRCellDU=12",
        "notificationId": 5003,
        "alarmRaisedTime": "2026-03-14T02:18:40Z",
        "alarmType": "QUALITY_OF_SERVICE_ALARM",
        "probableCause": "PERFORMANCE_DEGRADED",
        "perceivedSeverity": "MAJOR",
        "ackState": "UNACKNOWLEDGED"
      },
      "a-1188": {
        "objectInstance": "SubNetwork=North,ManagedElement=gNB-1002",
        "notificationId": 7712,
        "alarmRaisedTime": "2026-03-14T01:52:00Z",
        "alarmType": "ENVIRONMENTAL_ALARM",
        "probableCause": "TEMPERATURE_UNACCEPTABLE",
        "perceivedSeverity": "WARNING",
        "ackState": "ACKNOWLEDGED"
      },
      "a-1209": {
        "objectInstance": "SubNetwork=North,ManagedElement=gNB-1003",
        "notificationId": 9120,
        "alarmRaisedTime": "2026-03-14T02:29:55Z",
        "alarmType": "PROCESSING_ERROR_ALARM",
        "probableCause": "SOFTWARE_ERROR",
        "perceivedSeverity": "INDETERMINATE",
        "ackState": "UNACKNOWLEDGED"
      },
      "a-1175": {
        "objectInstance": "SubNetwork=North,ManagedElement=gNB-1001",
        "notificationId": 5011,
        "alarmRaisedTime": "2026-03-14T01:40:12Z",
        "alarmClearedTime": "2026-03-14T02:31:40Z",
        "alarmType": "COMMUNICATIONS_ALARM",
        "probableCause": "LINK_FAILURE",
        "perceivedSeverity": "CLEARED",
        "ackState": "UNACKNOWLEDGED"
      }
    }
  }
}
```

逐筆讀：

- `a-1201` 是 `CRITICAL`，而且 `alarmChangedTime` 晚於 `alarmRaisedTime`，表示這筆告警在 02:24:10 被告警來源更新過（TS 28.111 V18.8.0 clause 7.4.1）；從清單本身看不出舊值，若要知道是哪個屬性被改以及舊值，必須檢視當時的 `notifyChangedAlarmGeneral`，且僅在 producer 提供選用的 `changedAlarmAttributes` 時，該欄位才會帶有舊值（TS 28.111 V18.8.0 clause 8.4.2）。
- `a-1202` 是 `MAJOR`，類型是 `QUALITY_OF_SERVICE_ALARM`：類型說「服務品質劣化」，嚴重度說「要緊急處理」，兩個欄位各說各的。
- `a-1188` 是 `WARNING` 且已確認，屬於潛在問題，可排在後面處理。
- `a-1209` 是 `INDETERMINATE`：系統無法判定嚴重度，不能當成「不嚴重」略過，應人工判斷。
- `a-1175` 已是 `CLEARED`，卻仍在清單裡，原因是系統支援確認功能、而它尚未被確認；已清除的紀錄要等確認後才會被系統刪除（TS 28.111 V18.8.0 clause 6.14、7.3.1.1）。

結論：`numOfAlarmRecords` 為 5，但條件仍存在的只有 4 筆；排序處理時先 `a-1201`，再 `a-1202`，`a-1209` 要另外判斷，`a-1175` 只需確認。

#### 容易搞混的地方

1. **把 `CLEARED` 當成最低一級**。它表示告警條件已消失，不在 Critical→Warning 的排序裡；統計「各級告警數」時要把它分開算。
2. **大小寫混用**。3GPP 列舉值是大寫（`CRITICAL`），X.733 的 ASN.1 值是小寫（`critical`），O-RAN 的 `fault-severity` 也是大寫但只有四個值。引用時照各自原文，不要把 O-RAN 的 `is-cleared` 寫進 3GPP 的告警紀錄。
3. **以為 3GPP 只有四級加 CLEARED**。TS 28.111 clause 6.3 的敘述只點名 critical、major、minor、warning 與 cleared，但 clause 7.4.1 的允許值另有 `INDETERMINATE`；以屬性定義的允許值為準，共六個。
4. **把嚴重度和告警類型混為一談**。`QUALITY_OF_SERVICE_ALARM` 是 `alarmType` 的值，可以搭配任何嚴重度（TS 28.111 V18.8.0 clause 6.3），不代表「品質類告警一定比較輕」。
