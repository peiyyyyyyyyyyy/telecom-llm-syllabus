# 5.3.1 告警嚴重度（perceivedSeverity）

所屬：[5.3 告警](../5-3.md)

## 正文

In a 3GPP network every fault that is detected by a network entity (NE) is reported to the operation‑and‑maintenance (O&M) system as an alarm.  The **perceivedSeverity** attribute of an `AlarmInformation` object expresses *the relative level of urgency for operator attention* — it tells the alarm handling system and the human operator how quickly a corrective action is required — and therefore directly influences alarm prioritisation, escalation, and convergence strategies [TS 32.111-2 §5.5.1].

### Definition of *perceivedSeverity

`perceivedSeverity` is defined in the ITU‑T Recommendation X.733 and is carried in the alarm payload.  The legal values are  

* **Critical** – immediate operator action required to avoid service outage or major degradation.  
* **Major** – serious impact, but not an immediate service loss.  
* **Minor** – limited impact, corrective action can be scheduled.  
* **Warning** – informational, may indicate a trend toward a more severe condition.  
* **Indeterminate** – severity cannot be determined (the IRP does **not** recommend its use).  
* **Cleared** – the alarm is no longer active (see ITU‑T X.733).  

The reference table explicitly lists these values and notes the recommendation against using *indeterminate* [TS 32.111-2 §5.5.1].

### Relationship to fault severity

When a fault is detected, the detection process must supply the **severity of the fault** (indeterminate, warning, minor, major, critical) as defined in ITU‑T X.733 [TS 32.111-1 §4.1.1].  This fault severity is mapped to the alarm’s *perceivedSeverity* so that the alarm reflects the same urgency level that the NE has already determined for the underlying fault.

### Worked example

Assume a base‑station controller (BSC) detects an overload on its radio‑resource manager.  
* The fault detection routine classifies the fault as **major** because the overload leads to a measurable loss of capacity but does not cause an immediate outage.  
* An alarm is generated with the following relevant fields:

| Attribute            | Value                                 |
|----------------------|---------------------------------------|
| `alarmId`            | 10234                                 |
| `alarmRaisedTime`    | 2026‑11‑23 08:15:30 UTC                |
| `alarmChangedTime`   | 2026‑11‑23 08:20:10 UTC                |
| `perceivedSeverity`  | **Major**                             |
| `probableCause`      | Overload of Radio‑Resource Manager    |
| `eventType`          | Equipment (as per Annex A)            |

The *perceivedSeverity* of **Major** tells the O&M system to raise the alarm priority, route it to a senior operator, and possibly trigger automated load‑balancing actions.  All other attributes (e.g., `alarmId`, timestamps) are defined in the same specification [TS 32.111-2 §5.5.1].

### Practical notes and common mistakes

| Pitfall | Why it occurs | Correct practice |
|---------|---------------|------------------|
| Using **Indeterminate** as a severity level | The IRP allows the value but explicitly advises against it. | Select one of the concrete levels (Critical, Major, Minor, Warning) that matches the fault’s impact. |
| Confusing **perceivedSeverity** with **probableCause** | Both appear in the alarm payload, but they convey different information: severity describes urgency, cause describes *what* happened. | Populate `probableCause` with the ITU‑T X.733 cause code and set `perceivedSeverity` according to the fault’s urgency. |
| Forgetting to set **Cleared** when the fault disappears | Some faults have a clear condition; the alarm must be cleared to avoid stale alarms. | When the detection logic determines that the fault clearing condition is met, generate an alarm update with `perceivedSeverity` set to **Cleared**. |
| Mapping fault severity to a different alarm severity | The specification requires a direct mapping; mismatches can lead to inappropriate escalation. | Use the same level (e.g., fault *major* → alarm *Major*) unless a higher business‑policy level is explicitly defined. |

Remember that the fault detection mechanism must be able to *detect* and *clear* faults for both active and standby components, and the alarm generated must faithfully reflect the fault’s severity [TS 32.111-1 §4.1.1].
