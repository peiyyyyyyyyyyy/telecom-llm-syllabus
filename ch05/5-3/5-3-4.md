# 5.3.4 找最源頭的告警

所屬：[5.3 告警](../5-3.md)

## 正文

In a modern telecom network, a single physical fault (e.g., a fiber cut, a power supply failure, or a mis‑configuration) can generate many alarms that appear on different network elements. Operators must quickly isolate the *root‑cause alarm*—the alarm that directly corresponds to the underlying network condition—so that remediation actions address the true problem rather than its symptoms. Without correctly identifying the root cause, troubleshooting cycles lengthen, service restoration is delayed, and the risk of alarm storms increases. The specification explicitly states that, *for a set of correlated alarms, one alarm may relate to the fault which is the root cause of all the correlated alarms and events* and that the operating system (OS) should perform a Root Cause Analysis (RCA) to indicate this alarm【TS 32.111-1 §4.1.9】.

### Definition of Root‑Cause Analysis (RCA)
Root‑Cause Analysis is defined as a **process** that *determines and identifies the network condition (e.g., fault, mis‑configuration) causing the alarms*【TS 32.111-1 §4.1.9】. The process consumes several sources of information, including:

* **Information carried in alarm(s)** – attributes such as alarm identifier, severity, and timestamp.  
* **Information carried in correlated alarm sets** – the logical relationship among multiple alarms.  
* **Network notifications** – messages generated by the network that may hint at a failure.  
* **Network configuration information** – static or dynamic settings that can explain abnormal behavior.  
* **Operators' network management experience** – human expertise applied to interpret data.

The OS is expected, when possible, to invoke RCA automatically and to *identify and indicate the Root Cause Alarm*【TS 32.111-1 §4.1.9】.

### Formal View (Set Notation)
Consider a set of correlated alarms  

$$
A = \{a_1, a_2, \dots, a_n\},
$$

where each $a_i$ carries the attributes described above. RCA seeks an element  

$$
a_{rc} \in A
$$

such that $a_{rc}$ *relates to the fault which is the root cause of all the correlated alarms and events*【TS 32.111-1 §4.1.9】. In practice, the OS evaluates the five information sources listed earlier to select $a_{rc}$.

### Worked Example
A small LTE back‑haul segment reports three alarms at the same time:

| Alarm ID | Source Node | PerceivedSeverity | Timestamp | Description |
|----------|-------------|-------------------|-----------|-------------|
| A1       | Node‑X      | Major             | 12:00:05  | Interface down |
| A2       | Node‑Y      | Minor             | 12:00:07  | Loss of synchronization |
| A3       | Node‑Z      | Critical          | 12:00:06  | Power supply fault |

The OS receives these alarms and recognises them as a *correlated set* because their timestamps are within a few seconds and they share the same physical link. Applying RCA:

1. **Alarm information** – A3 reports a *Power supply fault*, a condition that can physically disable the link, whereas A1 and A2 describe symptoms.  
2. **Correlated set** – All three alarms refer to the same link, suggesting a common origin.  
3. **Network notifications** – A separate notification indicates that the power‑budget monitor on the link tripped at 12:00:04.  
4. **Configuration information** – The link is configured for redundant power; only one supply is active.  
5. **Operator experience** – Historically, power‑supply failures produce the pattern observed.

By weighting these inputs, the OS selects **Alarm A3** as the *root‑cause alarm* and highlights it for the operator. The operator can then replace the faulty power supply, restoring the link and causing A1 and A2 to clear automatically.

### Practical Notes and Common Mistakes

| Pitfall | Why It Happens | How to Avoid |
|---------|----------------|--------------|
| **Assuming the highest severity is always the root cause** | Severity reflects impact, not causality. A high‑severity symptom may be downstream of a low‑severity fault. | Follow the RCA process: examine all five information sources before designating the root‑cause alarm【TS 32.111-1 §4.1.9】. |
| **Ignoring configuration data** | Operators may focus only on alarm payloads, overlooking that mis‑configurations can generate cascaded alarms. | Include *network configuration information* as a mandatory input to RCA【TS 32.111-1 §4.1.9】. |
| **Relying solely on operator intuition** | Human expertise is valuable but can be biased by recent incidents. | Combine *operators' experience* with systematic data (alarms, notifications) as prescribed【TS 32.111-1 §4.1.9】. |
| **Skipping correlated‑set analysis** | Treating each alarm independently hides the logical relationship that points to a single fault. | Always form a *correlated alarm set* before invoking RCA【TS 32.111-1 §4.1.9】. |
| **Not indicating the root‑cause alarm** | Some systems clear alarms without marking the source, making post‑mortem analysis difficult. | The OS must *identify and indicate the Root Cause Alarm* whenever possible【TS 32.111-1 §4.1.9】. |

By adhering strictly to the sources of information defined by the specification and by letting the OS perform RCA automatically, telecom networks achieve faster fault isolation, reduced alarm noise, and more reliable service restoration.

## 練習題

**1.** Which of the following is explicitly listed as an input source for Root Cause Analysis in the specification?

- A. User interface color scheme
- B. Information carried in alarm(s)
- C. Weather forecast data
- D. Customer satisfaction surveys

<details><summary>看答案</summary>

正解：B。The specification lists information carried in alarm(s) as one of the possible inputs for RCA.

</details>

**2.** According to the specification, which entity should perform Root Cause Analysis when possible?

- A. The network operator
- B. The OS
- C. The end‑user device
- D. Third‑party monitoring software

<details><summary>看答案</summary>

正解：B。The text states that the OS should perform RCA when possible.

</details>

**3.** What is the primary purpose of Root Cause Analysis as defined in the reference?

- A. To filter out low‑severity alarms
- B. To determine and identify the network condition causing the alarms
- C. To generate performance statistics
- D. To encrypt alarm messages

<details><summary>看答案</summary>

正解：B。RCA is defined as a process that determines and identifies the network condition causing the alarms.

</details>

**4.** In a set of correlated alarms, the root‑cause alarm is the one that:

- A. Has the highest perceived severity
- B. Occurs earliest in time
- C. Relates to the fault that is the root cause of all the correlated alarms and events
- D. Was generated by the central management system

<details><summary>看答案</summary>

正解：C。The specification describes the root‑cause alarm as the one that relates to the fault causing all correlated alarms.

</details>

**5.** Which of the following items is **not** mentioned in the specification as a possible basis for Root Cause Analysis?

- A. Network notifications
- B. Operators' network management experience
- C. Information carried in correlated alarm sets
- D. Real‑time video feeds from the field

<details><summary>看答案</summary>

正解：D。Real‑time video feeds are not listed among the possible bases for RCA in the reference.

</details>
