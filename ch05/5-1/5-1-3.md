# 5.1.3 日誌

所屬：[5.1 資料的種類](../5-1.md)

## 正文

In O‑RAN the term **log** refers to any persistent record of events generated by a radio unit (O‑RU). The specification distinguishes three independent log‑management categories: **troubleshooting log**, **security log**, and **trace log**【O‑RAN MP.0 §14.2】. A troubleshooting log is used for fault diagnosis, a security log records security‑related events, and a trace log is intended for detailed protocol or timing analysis. Each category is collected independently; starting or stopping one does not affect the others.

### Log Generation and Retrieval

The O‑RU creates log files on demand through NETCONF Remote Procedure Calls (RPCs).  
* **Troubleshooting logs** are generated after the controller issues `<start-troubleshooting-logs>`; the O‑RU then records events that occur **before** this RPC and stops when a `<stop-troubleshooting-logs>` is received【O‑RAN MP.0 §14.2.2】.  
* **Trace logs** are generated after `<start-trace-logs>` and contain only events collected **after** that RPC【O‑RAN MP.0 §14.2.2】.  
* **Security logs** are always active; there is no start/stop procedure, and the O‑RU must always be capable of creating and storing them【O‑RAN MP.0 §14.2.1】.

When the O‑RU finishes generating the requested troubleshooting files it emits a `<troubleshooting‑log‑generated>` notification that lists the file names and signals that the files are ready for download【O‑RAN MP.0 §14.2.2】. The notification is optional if the controller cancels the operation with `<stop‑troubleshooting‑logs>`【O‑RAN MP.0 §14.2.2】.

The O‑RU may support the **LOG‑FILTER** feature, allowing the controller to request only a subset of log data by providing filter types and values in the `<start‑troubleshooting‑logs>` RPC【O‑RAN MP.0 §14.2.2】. If a filter is unsupported the O‑RU can either ignore it or return a **FAILURE** status【O‑RAN MP.0 §14.2.2】.

File transfer performance is a practical concern. The specification recommends that the O‑RU keep the number and size of files “reasonably small” so that the entire “Troubleshooting data upload” scenario can be completed within **15 minutes**, with a **target of 3 minutes** under ideal conditions【O‑RAN MP.0 §14.2.2】. If the total compressed size is $S$ bytes and the available bandwidth is $B$ bytes / second, the theoretical transfer time $T$ is  

$$
T = \frac{S}{B}\;.
$$

The O‑RU must compress the files using one of the extensions defined in the specification: **.gz** (DEFLATE), **.lz4** (LZ4), **.xz** (LZMA2), or **.zip** (DEFLATE)【O‑RAN MP.0 §14.2.2】.

### Security Log Requirements

Security logs are mandatory for any O‑RU that advertises the **SECURITY‑LOGGING** feature in its YANG library【O‑RAN MP.0 §14.2.1】. The format of each security‑log entry must comply with the field requirements in clause 5.3.8.8 of the O‑RAN Security Requirements Specification, and events must be mapped to the O‑RAN network functions listed in table 5.3.8.11.1‑1 of that same document【O‑RAN MP.0 §14.2.3.1】.  

Security log data must be **integrity‑protected** and stored persistently in non‑volatile memory【O‑RAN MP.0 §14.2.3.2】. The O‑RU also has to support **log‑rotation**, i.e., closing an existing log file and opening a new one based on a configured time interval【O‑RAN MP.0 §14.2.3.2】. Because logging cannot be started or stopped by an external command, the O‑RU must always be ready to record security events.

### Worked Example: Estimating Upload Time

Assume an O‑RU generates three troubleshooting log files of sizes 4 MiB, 6 MiB and 5 MiB before compression. The O‑RU compresses them with **.gz** (average 40 % size reduction).  

*Compressed sizes*:  

$$
\begin{aligned}
4\;\text{MiB} \times 0.4 &= 1.6\;\text{MiB},\\
6\;\text{MiB} \times 0.4 &= 2.4\;\text{MiB},\\
5\;\text{MiB} \times 0.4 &= 2.0\;\text{MiB}.
\end{aligned}
$$

*Total compressed size* $S = 1.6 + 2.4 + 2.0 = 6.0\;\text{MiB} = 6.0 \times 2^{20}\;\text{bytes} \approx 6.29 \times 10^{6}\;\text{bytes}$.

If the management link provides $B = 5\;\text{Mbps}$ (≈ 0.625 MiB / s), the theoretical transfer time is  

$$
T = \frac{6.0\;\text{MiB}}{0.625\;\text{MiB/s}} \approx 9.6\;\text{s}.
$$

Even accounting for protocol overhead, the upload comfortably meets the 15‑minute guideline and the 3‑minute target.

### Common Pitfalls and Practical Notes

* **Confusing start points** – Troubleshooting logs capture events *before* the `<start‑troubleshooting‑logs>` RPC, whereas trace logs capture events *after* `<start‑trace‑logs>`. Mixing the two leads to missing or duplicated data【O‑RAN MP.0 §14.2.2】.  
* **Ignoring file‑format recommendations** – Using an unsupported compression extension may cause the controller to reject the files. Always honour the listed extensions (.gz, .lz4, .xz, .zip)【O‑RAN MP.0 §14.2.2】.  
* **Assuming filters are mandatory** – The LOG‑FILTER feature is optional; an O‑RU may ignore unknown filter types without error, or return a FAILURE status【O‑RAN MP.0 §14.2.2】.  
* **Overlooking security‑log persistence** – Security logs must be stored in non‑volatile memory and protected against tampering; a failure to implement rotation or integrity protection violates the specification【O‑RAN MP.0 §14.2.3.2】.  
* **Neglecting alarm‑history storage** – Although this subsection focuses on generic logs, 3GPP TS 32.111‑1 notes that alarm history may be stored in subordinate entities and must be retrievable as files upon request【TS 32.111‑1 §5.3.2】. Ignoring this can impede coordinated fault management across network layers.

By adhering to the defined log categories, RPC procedures, compression formats, and timing guidelines, engineers can ensure that logs are both useful for troubleshooting and compliant with O‑RAN and 3GPP standards.

## 練習題

**1.** Which of the following is NOT one of the three log‑management types defined in the O‑RAN specification?

- A. Troubleshooting log
- B. Security log
- C. Trace log
- D. Configuration log

<details><summary>看答案</summary>

正解：D。The specification lists only troubleshooting, security, and trace logs; configuration log is not defined.

</details>

**2.** A trace log starts collecting events:

- A. Before the <start‑trace‑logs> RPC is issued.
- B. After the <start‑trace‑logs> RPC is issued.
- C. After the <start‑troubleshooting‑logs> RPC is issued.
- D. It never starts automatically.

<details><summary>看答案</summary>

正解：B。The trace log definition states it contains logs continuously collected after the <start‑trace‑logs> RPC.

</details>

**3.** What is the maximum recommended duration for completing a full troubleshooting data upload scenario?

- A. 3 minutes
- B. 15 minutes
- C. 30 minutes
- D. 60 minutes

<details><summary>看答案</summary>

正解：B。The specification recommends completion within 15 minutes, with a target of 3 minutes.

</details>

**4.** Which YANG feature indicates that an O‑RU supports the mandatory security‑logging procedures?

- A. LOG‑FILTER
- B. SECURITY‑LOGGING
- C. TRACE‑LOGGING
- D. ALARM‑HISTORY

<details><summary>看答案</summary>

正解：B。The SECURITY‑LOGGING feature signals support for security logging.

</details>

**5.** According to 3GPP TS 32.111‑1, where may alarm‑history information be stored?

- A. Only in the central network management system.
- B. In subordinate entities.
- C. Directly on the user equipment.
- D. Exclusively in the radio access network.

<details><summary>看答案</summary>

正解：B。The standard explicitly allows alarm history to be stored in subordinate entities.

</details>
