# 5.1.1 告警

所屬：[5.1 資料的種類](../5-1.md)

## 正文

In a live mobile network, any deviation from normal operation must be detected, reported, and acted upon before it impacts users. An **alarm** is the management‑level representation of such a deviation. It enables automated fault management, supports human operators in troubleshooting, and provides the data needed for service‑level assurance. Without a consistent alarm model, different vendors’ equipment would generate incompatible notifications, making network‑wide monitoring impossible.  

### Alarm Record Structure

The 3GPP specification defines an alarm as a **record** composed of a fixed set of attributes. Formally, an alarm record can be expressed as  

$$\text{Alarm} = \{ \text{objectDN},\ \text{type},\ \text{probableCause},\ \text{specificProblem},\ \text{perceivedSeverity} \}$$  

* **objectDN** – the Distinguished Name that identifies the managed object that is the source of the alarm. The DN may refer to an object that does not actually exist in the management system; only the string is required [TS 28.111 §6.3].  
* **type** – categorises the fault domain according to ITU‑T X.733 clause 8.1.1. The allowed values are  

| Value | Meaning |
|------|---------|
| **COMMUNICATIONS_ALARM** | Fault in procedures or processes that convey information |
| **PROCESSING_ERROR_ALARM** | Software or processing fault |
| **EQUIPMENT_ALARM** | Equipment fault |
| **ENVIRONMENTAL_ALARM** | Condition of the equipment enclosure |
| **QUALITY_OF_SERVICE_ALARM** | Degradation of a service, can be combined with any severity [TS 28.111 §6.3] |

* **probableCause** – a textual or enumerated qualifier that narrows the fault domain (ITU‑T X.733 clause 8.1.2.1) [TS 28.111 §6.3].  
* **specificProblem** – a finer refinement of the probable cause (ITU‑T X.733 clause 8.1.2.2) [TS 28.111 §6.3].  
* **perceivedSeverity** – the system’s assessment of how serious the condition is. The permitted values are **critical**, **major**, **minor**, **warning**, and **cleared** (the latter indicates that the condition no longer exists) [TS 28.111 §6.3].  

### Active and Historical Alarm Lists

O‑RAN specifies that a NETCONF server must maintain an **active‑alarm‑list**. Alarms whose *fault‑severity* is **WARNING** are excluded from this list. When the raise‑alarm criteria are satisfied, the alarm is added to the list; when the clear‑alarm condition is satisfied, the alarm is removed [O-RAN MP.0 §11.1].  

Optionally, a **historical‑alarm‑list** can be kept. Cleared alarms are inserted here with the attribute *is‑cleared* set to “true”, again omitting alarms of severity **WARNING** [O-RAN MP.0 §11.1].  

### Subscription and Notification

Network‑management applications (the NETCONF client) subscribe to alarm notifications by issuing a `<create-subscription>` RPC as defined in RFC 5277. The subscription may include a subtree filter that selects alarms by **fault‑severity** (e.g., CRITICAL, MAJOR, MINOR) [O-RAN MP.0 §11.3].  

When a new alarm is added to the active‑alarm‑list, or an existing alarm is removed (including removal caused by deletion of the *fault‑source* element), the O‑RU sends an `<alarm-notif>` to every subscriber that matches the filter [O-RAN MP.0 §11.2]. The notification contains the full alarm record, including the *fault‑source* leaf that identifies the origin (e.g., fan, module, PA, port) [O-RAN MP.0 §11.4].  

Because the O‑RU only sends notifications for state changes, the client must read the current *active‑alarm‑list* immediately after the subscription is established to obtain any alarms that were already active [O-RAN MP.0 §11.3].  

### Worked Example

Consider a macro‑cell base station where the power‑amplifier (PA) module overheats. The equipment generates an alarm with the following attributes:

| Attribute | Value |
|-----------|-------|
| **objectDN** | `siteA/eNodeB=1/module=PA1` |
| **type** | `EQUIPMENT_ALARM` |
| **probableCause** | `hardwareFailure` |
| **specificProblem** | `overTemperature` |
| **perceivedSeverity** | `critical` |

1. **Raise** – The O‑RU evaluates the condition, creates the alarm record, and adds it to the *active‑alarm‑list* (since severity is not WARNING) [O-RAN MP.0 §11.1].  
2. **Notify** – All NETCONF clients subscribed with a filter that includes **CRITICAL** receive an `<alarm-notif>` containing the above record [O-RAN MP.0 §11.2].  
3. **Clear** – After the cooling system restores normal temperature, the O‑RU clears the alarm. The record’s *perceivedSeverity* becomes **cleared**, the entry is removed from the *active‑alarm‑list*, and, if a historical list is configured, the cleared record is appended with `is-cleared="true"` [O-RAN MP.0 §11.1].  

### Common Mistakes and Practical Notes

* **Ignoring the “WARNING” exclusion** – Engineers sometimes assume that all alarms appear in the active list. The specifications explicitly exclude alarms with *fault‑severity* **WARNING** from both active and historical lists [O-RAN MP.0 §11.1].  
* **Assuming the DN must resolve** – The alarm record only requires a DN string; the referenced object does not need to be reachable via CRUD operations [TS 28.111 §6.3].  
* **Filtering only by severity** – While severity filters are common, the *fault‑source* leaf can be used to narrow notifications to specific hardware (e.g., fan) [O-RAN MP.0 §11.4].  
* **Missing pre‑existing alarms** – Because the O‑RU does not resend notifications for alarms that were already active, the client must issue a `get` operation on *active‑alarm‑list* right after subscription establishment [O-RAN MP.0 §11.3].  
* **Confusing “QUALITY_OF_SERVICE_ALARM” with fault domains** – This type does not indicate where the fault occurs; it merely signals a service‑quality impact and can be combined with any severity [TS 28.111 §6.3].  

Understanding these nuances ensures that fault‑management systems remain synchronized with the network state and that operators can react promptly to genuine service‑affecting events.

## 練習題

**1.** Which attribute in an alarm record uniquely identifies the object that generated the alarm?

- A. probableCause
- B. objectDN
- C. specificProblem
- D. perceivedSeverity

<details><summary>看答案</summary>

正解：B。The object instance attribute, identified by its Distinguished Name (DN), identifies the alarmed entity.

</details>

**2.** According to the specifications, which alarm types are excluded from the active‑alarm‑list?

- A. CRITICAL
- B. MAJOR
- C. MINOR
- D. WARNING

<details><summary>看答案</summary>

正解：D。Alarms with fault‑severity set to WARNING are explicitly excluded from the active‑alarm‑list.

</details>

**3.** A NETCONF client wants to receive only alarms of severity CRITICAL, MAJOR, and MINOR. Which mechanism does the specification provide for this?

- A. Use a different NETCONF port
- B. Apply a subtree filter in the <create-subscription> RPC
- C. Change the alarm’s perceivedSeverity attribute
- D. Modify the objectDN value

<details><summary>看答案</summary>

正解：B。The client can define a subtree filter in the <create-subscription> RPC to select alarms by severity.

</details>

**4.** When an alarm is cleared, what happens to it in a system that maintains a historical‑alarm‑list?

- A. It is removed permanently
- B. It is added with is‑cleared set to "true"
- C. Its perceivedSeverity changes to warning
- D. It is moved to the active‑alarm‑list

<details><summary>看答案</summary>

正解：B。Cleared alarms are appended to the historical list with the attribute is‑cleared set to true.

</details>

**5.** Which alarm type conveys a degradation in service quality and can be combined with any perceived severity?

- A. EQUIPMENT_ALARM
- B. PROCESSING_ERROR_ALARM
- C. QUALITY_OF_SERVICE_ALARM
- D. ENVIRONMENTAL_ALARM

<details><summary>看答案</summary>

正解：C。The specification defines QUALITY_OF_SERVICE_ALARM as indicating service degradation and combinable with any severity.

</details>
