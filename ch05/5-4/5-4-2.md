# 5.4.2 門檻與異常判斷

所屬：[5.4 指標趨勢](../5-4.md)

## 正文

In modern mobile core networks, each Network Function (NF) generates performance measurements such as CPU load, memory usage, or packet processing latency. Operators use **thresholds** to define the boundary between normal operation and a potential fault. When a measurement crosses its configured threshold, an alarm is raised, prompting corrective actions before the degradation impacts users. This proactive approach is essential for maintaining service level agreements (SLAs) and for automating fault‑management workflows.

### Core Capabilities Defined by the Management Service

The 3GPP TS 28.550 specification defines three mandatory capabilities for the **management service producer** that handles NF performance threshold monitoring:

1. **Create a threshold monitoring instance** – The producer must be able to satisfy a consumer’s request to start monitoring a specific performance measurement of one or more NFs.  
2. **Terminate a threshold monitoring instance** – The producer must be able to stop an existing monitoring session upon request from an authorized consumer.  
3. **Deliver crossing notifications** – The producer must allow the designated notification target to receive alerts when a measured value exceeds (or falls below) the configured threshold.  

These capabilities are the only functional requirements stipulated for threshold handling in the reference text [TS 28.550 §5.2.14]【TS 28.550 §5.2.14】.

### Defining a Threshold Monitoring Request

A **threshold monitoring request** consists of three elements:

| Symbol | Meaning | Unit / Type |
|--------|---------|-------------|
| $M$ | Identifier of the performance measurement (e.g., “CPU utilisation”) | String |
| $T$ | Threshold value set by the consumer | Same unit as $M$ |
| $N$ | Notification target that will receive crossing alerts | URI or identifier |

The request is sent to the management service producer, which creates an internal monitoring entity that periodically samples $M$ and compares each sample $m_i$ to $T$:

$$
\text{Crossing event} = 
\begin{cases}
\text{true} & \text{if } m_i \ge T \\
\text{false} & \text{otherwise}
\end{cases}
$$

When the condition evaluates to **true**, the producer forwards a **threshold crossing notification** to $N$.

### Worked Example

Assume an operator wants to monitor the **CPU utilisation** of an NF called *NF‑A*. The consumer defines a threshold $T = 80\%$ and designates a monitoring dashboard as the notification target $N$.

1. **Create request** – The operator issues a create‑monitoring request specifying $M = \text{CPU\_utilisation}$, $T = 80\%$, and $N = \text{dashboard\_uri}$. The management service producer acknowledges the request and starts sampling CPU utilisation every minute.  
2. **Sampling** – After three minutes the sampled values are $m_1 = 72\%$, $m_2 = 78\%$, $m_3 = 85\%$.  
3. **Threshold crossing** – At $m_3 = 85\%$, the condition $m_3 \ge T$ becomes true, so the producer generates a crossing notification and sends it to the dashboard.  
4. **Terminate request** – After the issue is resolved, the operator sends a terminate‑monitoring request. The producer stops sampling and releases the monitoring resources.  

Steps 1 and 4 correspond to the creation and termination capabilities, while step 3 demonstrates the notification capability, all of which are mandated by the specification [TS 28.550 §5.2.14]【TS 28.550 §5.2.14】.

### Practical Notes and Common Mistakes

| Mistake | Why it Happens | Correct Practice |
|---------|----------------|------------------|
| **Omitting the notification target** | Assuming the producer will log alerts automatically. | Explicitly specify $N$ in the create request; the producer only *allows* the target to receive notifications. |
| **Assuming automatic threshold adjustment** | Believing the system will adapt $T$ based on trends. | The reference only requires static threshold creation; any dynamic adaptation must be implemented by the consumer. |
| **Using unauthorized consumers** | Sending create/terminate requests from unverified entities. | Only *authorized* consumers may invoke these operations, as stated in the functional requirements. |
| **Neglecting termination** | Leaving monitoring sessions running indefinitely. | Always issue a terminate request when monitoring is no longer needed to free resources. |

By adhering strictly to the three capabilities defined in TS 28.550, engineers can design robust threshold‑based alarm systems that are both compliant and interoperable across different vendor implementations.
