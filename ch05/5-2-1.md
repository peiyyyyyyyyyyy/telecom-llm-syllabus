# 5.2.1 時間與時區

所屬：[5.2 對齊資料](5-2.md)

## 內文

#### 是什麼、什麼時候會用到

維運資料來自不同系統：基地台或網管產生的量測結果檔、告警清單、日誌伺服器、工單系統。每個來源記錄時間的方式不一定相同，有的用協調世界時（Coordinated Universal Time, UTC），有的用當地時間，有的在當地時間後面附上與 UTC 的時差（offset）。另外，同樣是「一個時間」，有時代表區間的開始，有時代表區間的結束。排上同一條時間軸之前，要先確認每個時間戳的時區與意義。最常碰到的情況有三種：判斷某筆告警落在哪一個量測期；網管系統和設備不在同一時區；以及實施夏令時間（daylight saving time）的地區，在切換當天出現「重複」或「消失」的一小時。

#### 怎麼讀

**一、量測結果 XML 檔裡的時間欄位（3GPP）**

TS 32.435 定義量測結果的 XML 檔（根元素 `measCollecFile`），它和 TS 32.432 的抽象檔案內容項目逐一對應（TS 32.435 V18.0.0 clause 4.1 Table 4.1）：

| XML 位置與屬性 | 型態（schema） | 對應 TS 32.432 項目 | 意義 |
|---|---|---|---|
| `fileHeader/measCollec@beginTime` | dateTime，required | `collectionBeginTime` | 檔案內**第一個**量測期（granularity period）的開始 |
| `measInfo/granPeriod@duration` | duration，required | `granularityPeriod` | 量測期長度，以秒計 |
| `measInfo/granPeriod@endTime` | dateTime，required | `measTimeStamp` | 該量測期的**結束** |
| `measInfo/repPeriod@duration` | duration | `reportingPeriod` | 回報週期，以秒計 |
| `fileFooter/measCollec@endTime` | dateTime，required | `timestamp` | 檔案涵蓋的**最後一個**量測期的結束 |

（schema 見 TS 32.435 V18.0.0 clause 4.2.2；各項目的意義見 TS 32.432 V18.0.0 clause 4.1 Table 4.1。）

讀法規則：

1. **時間戳格式**：TS 32.432 規定量測檔的所有時間戳要採用 ISO 8601 允許的表示法；依所用的表示法，時間戳可以指 UTC、當地時間，或「當地時間加上與 UTC 的時差」三者之一（TS 32.432 V18.0.0 clause 4.1）。TS 28.532 對新式效能資料檔也有同樣的規定（TS 28.532 V18.8.0 clause 11.3.2.1.2）。所以讀到沒有時差的時間戳，不能自行假設它是 UTC。
2. **兩個 `duration` 要用 `PTnS` 簡寫**，例如 15 分鐘寫成 `PT900S`（TS 32.435 V18.0.0 clause 4.1 Table 4.1）。
3. **檔名中的時間**：命名規則是 `<Type><Startdate>.<Starttime>-[<Enddate>.]<Endtime>[_-<jobId>][_<UniqueId>][_-_<RC>]`。`Startdate` 為 YYYYMMDD；`Starttime` 為 `HHMMshhmm`，其中 HHMM 是**當地時間**，`s` 是正負號，`hhmm` 是當地時間與 UTC 的時差（TS 32.432 V18.0.0 clause 5.1.2）。Type 為 A、B 時代表單一量測期，C、D 時代表多個量測期並且要寫 `Enddate`。TS 32.432 規定分鐘只能是 5 的倍數；TS 28.532 的新版規則允許 00～59，並把欄位改為 `jobIdList`、`UniqueIdList`（TS 28.532 V18.8.0 clause 11.3.2.1.4）。
4. **時差的方向**：ISO 8601 為付費標準（非免費公開），RFC 3339 是它供網際網路使用的剖面。它的格式為 `date-time = full-date "T" full-time`，時差寫成 `Z` 或 `+hh:mm`／`-hh:mm`（RFC 3339 clause 5.6）。時差的定義是「當地時間減 UTC」，所以 **UTC＝當地時間－時差**（RFC 3339 clause 4.2）。
5. **補收檔案時的時間條件**：TS 28.532 的 `listAvailableFiles` 操作用 `beginTime`、`endTime` 篩選檔案，這兩個參數以 UTC 表示，篩選的是檔案的就緒時間（file ready time），不是量測期（TS 28.532 V18.8.0 clause 11.6.1.5.2）。

#### 實際例子

某 gNB 的 15 分鐘量測檔（設備名、廠商名、數值虛構；格式依 TS 32.435 clause 4.2.2 與 TS 32.432 clause 5.1.2）：

```
檔名：A20261124.1400+0800-1415+0800_gNB-TPE-0412

<fileHeader fileFormatVersion="32.435 V18.0" vendorName="VendorX"
            dnPrefix="DC=op.example,SubNetwork=TW-North">
  <fileSender localDn="ManagedElement=gNB-TPE-0412" elementType="gNB"/>
  <measCollec beginTime="2026-11-24T14:00:00+08:00"/>
</fileHeader>
  ...
  <granPeriod duration="PT900S" endTime="2026-11-24T14:15:00+08:00"/>
  ...
<fileFooter>
  <measCollec endTime="2026-11-24T14:15:00+08:00"/>
</fileFooter>
```

同一時段，網管告警清單裡有一筆告警，`alarmRaisedTime` 為 `2026-11-24T06:07:30Z`（TS 28.111 V18.8.0 clause 7.3.1.2）。

怎麼讀：

- 檔名開頭 `A` 表示單一 NE、單一量測期。`1400+0800-1415+0800` 是當地 14:00 到 14:15，時差 +8 小時。換成 UTC：14:00－8 小時＝06:00Z，14:15－8 小時＝06:15Z。
- `beginTime` 14:00 是量測期開始；`granPeriod@endTime` 與頁尾 `endTime` 都是 14:15，是結束時間。`PT900S`＝900 秒＝15 分鐘，和起訖相符。
- 告警時間 06:07:30Z 加 8 小時是當地 14:07:30，落在這個檔案的量測期內。若誤把 `06:07:30` 當成當地時間，就會去找 06:00～06:15 的檔案，整整錯開 8 小時。

再看夏令時間切換日。假設某地當天由 +02:00 改回 +01:00，同一台設備會產生兩個當地時間相同的檔案：

```
A20261025.0200+0200-0215+0200_gNB-X   → 00:00Z～00:15Z
A20261025.0200+0100-0215+0100_gNB-X   → 01:00Z～01:15Z
```

兩個檔名只差在時差欄位。若處理程式丟掉時差、只留 HHMM，第二個檔會覆蓋第一個，或兩期資料被加總成一期。以 15 分鐘為一期，這一天有 25 小時，應有 100 期；夏令開始那天只有 23 小時，應有 92 期，平常是 96 期。

#### 容易搞混的地方

1. **`granPeriod@endTime` 是結束時間**：只有頁首的 `beginTime` 是開始時間。拿 `endTime` 當開始時間，所有資料會往後錯一期。
2. **檔名與補收參數的時間基準不同**：檔名裡是當地時間加時差；`listAvailableFiles` 的 `beginTime`、`endTime` 是 UTC，而且比對的是檔案就緒時間，不是量測期。
3. **`Z`、`+00:00`、`-00:00` 不完全相同**：前兩者表示以 UTC 為參考；`-00:00` 表示 UTC 時間已知、但當地時差未知（RFC 3339 clause 4.3）。
4. **沒有時差的時間戳不能直接比**：規格允許量測檔使用不帶時差的當地時間，日誌與工單系統也常如此，要先查清楚來源設定，再換成同一基準。

#### 和其他小節的關係

時間換成同一基準後，才能用 5.2.4 依檔名與 `endTime` 找出缺期，用 5.3.2 的時間窗比對告警，用 5.4.3 判斷忙時。所有來源的時間對齊後排進 5.5.1 事件時間軸，再進入 6.2 由時間軸提出假設。

**736.** What is the UTC measurement-period end in the local morning with a utc alarm export?

1. 2026-10-24T20:00:00Z
2. 2026-10-24T20:15:00Z
3. 2026-10-25T04:15:00Z
4. 2026-10-24T20:30:00Z

<details><summary>看答案</summary>

**答案**　2

**詳解**　Convert 2026-10-25T04:15:00+08:00 to UTC by subtracting its signed offset.
