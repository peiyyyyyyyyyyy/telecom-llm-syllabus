# 5.1.3 日誌

所屬：[5.1 資料的種類](5-1.md)

## 內文

#### 是什麼、什麼時候會用到

日誌（log）是軟體或作業系統逐筆寫下的事件紀錄：每一行通常帶有時間戳、來源主機、程式名稱、等級和一段訊息。和告警（5.1.1）不同，日誌沒有「產生、清除」的狀態，只會一行行往後加，細節也比告警多。業界最常用的格式是 syslog，現行規格是 IETF RFC 5424（The Syslog Protocol）。

維運人員通常在這些時候讀日誌：告警只說「鏈路中斷」，要看設備在中斷前後幾秒做了什麼；軟體異常重啟，要找最後幾行錯誤；稽核或資安事件，要查誰在什麼時間登入、做了哪些操作。前兩種看的多半是**系統日誌**（程式與作業系統的運作紀錄），後一種看的是**安全日誌**（登入、授權、稽核紀錄）。

#### 怎麼讀

**RFC 5424 的訊息結構。** 一則 syslog 訊息是「HEADER、空格、STRUCTURED-DATA，後面可再加空格與 MSG」（RFC 5424 clause 6）。HEADER 依序有 7 個欄位：

| 欄位 | 內容與規則 | 條號 |
|---|---|---|
| PRI | 角括號包住的優先值（PRIVAL），範圍 0～191，同時代表 Facility 與 Severity | 6.2.1 |
| VERSION | 協定版本，RFC 5424 使用 `1` | 6.2.2 |
| TIMESTAMP | 依 RFC 3339 的時間，例如 `2003-10-11T22:14:15.003Z` | 6.2.3 |
| HOSTNAME | 發出訊息的機器，優先順序是 FQDN、固定 IP、主機名稱、動態 IP、`-` | 6.2.4 |
| APP-NAME | 發出訊息的設備或程式，最長 48 字元 | 6.2.5 |
| PROCID | 常放程序編號；值改變代表 syslog 回報可能中斷過 | 6.2.6 |
| MSGID | 訊息類型，例如防火牆用 `TCPIN`、`TCPOUT` | 6.2.7 |

沒有值的欄位用 NILVALUE，也就是一個減號 `-`（clause 6）。

**等級（Severity）與設施（Facility）。** Severity 只能是 0～7，數字越小越嚴重：

| 值 | 名稱（RFC 5424 Table 2） |
|---|---|
| 0 | Emergency: system is unusable |
| 1 | Alert: action must be taken immediately |
| 2 | Critical: critical conditions |
| 3 | Error: error conditions |
| 4 | Warning: warning conditions |
| 5 | Notice: normal but significant condition |
| 6 | Informational: informational messages |
| 7 | Debug: debug-level messages |

Facility 只能是 0～23（Table 1），和本節有關的幾個是：0 kernel messages、3 system daemons、4 與 10 security/authorization messages、13 log audit、14 log alert、16～23 local use 0～7。RFC 原文說明這些 Facility 與 Severity 的值「are not normative but often used」（clause 6.2.1），表格是參考用途。

**PRI 的算法。** PRIVAL ＝ Facility × 8 ＋ Severity（clause 6.2.1）。原文的例子是 local use 4（Facility 20）、Notice（Severity 5），20 × 8 ＋ 5 ＝ 165，寫成 `<165>`。反過來解讀時，把 PRIVAL 除以 8，商是 Facility，餘數是 Severity。除了 `<0>` 以外，數字不可有前導 0。

**時間戳。** TIMESTAMP 的 `T` 和 `Z` 必須大寫，不可使用閏秒；秒的小數（TIME-SECFRAC）最多 6 位；時區寫成 `Z` 或 `+08:00` 這類偏移；取不到系統時間時要填 `-`（clause 6.2.3）。發送端可以用 STRUCTURED-DATA 的 `timeQuality` 說明時間可不可信：`tzKnown` 表示是否知道時區，`isSynced` 表示是否與可靠的外部時間源同步，`syncAccuracy` 是可能誤差的微秒數（clause 7.1.1～7.1.3）。

**O-RAN M-plane 的日誌功能。** O-RAN 公開的 YANG 模組 `o-ran-troubleshooting`（revision 2022-08-15）只定義了怎麼取日誌，沒有定義日誌內容的格式：`start-troubleshooting-logs` 與 `stop-troubleshooting-logs` 兩個 RPC 讓 M-plane 開始、停止收集 O-RU 的排障日誌，回傳 `status`（`SUCCESS`／`FAILURE`）和 `failure-reason`；產生新檔時送出 `troubleshooting-log-generated` 通知，`log-file-name` 列出檔案位置與名稱，例如 `o-ran/log/my_troubleshooting_log_file.zip`。本節沒有讀到 O-RAN M-plane 規格本文，日誌檔內容、取檔流程不在這裡寫。

**開源基地台的日誌不是 syslog。** srsRAN Project 的文字日誌（`contextual_text_formatter`）每行依序是：UTC 時間（`年-月-日T時:分:秒.6 位小數`，沒有時區標記）、左對齊 8 字元的元件名稱 `[RRC     ]`、一個字母的等級 `[E]`／`[W]`／`[I]`／`[D]`（error、warning、info、debug），選用的情境欄，最後是訊息。

#### 實際例子

某 DU 主機轉送到收集器的 syslog（RFC 5424 格式；主機名、程式名、IP 與訊息皆虛構，IP 用文件專用網段）：

```
<131>1 2026-11-18T02:13:07.412+08:00 du-demo-0123.example.net gnb_du 2231 LINKDOWN [timeQuality tzKnown="1" isSynced="1"] Backhaul interface eth2 link down
<30>1 2026-11-18T02:13:09.020+08:00 du-demo-0123.example.net ptp-agent 1187 - - Time source lost, clock in holdover
<84>1 2026-11-18T02:41:55.003+08:00 du-demo-0123.example.net sshd 40211 - - Failed password for invalid user admin from 192.0.2.45 port 51522
<86>1 2026-11-18T02:44:12.551+08:00 du-demo-0123.example.net sshd 40398 - - Accepted publickey for opsuser from 198.51.100.7 port 60114
```

同一台主機上 srsRAN 格式的應用日誌（訊息虛構，格式照原始碼）：

```
2026-11-17T18:13:07.415220 [F1AP    ] [W] F1-C transport lost, starting reconnection
2026-11-17T18:13:41.902113 [RRC     ] [I] Cell 1 deactivated
```

逐欄讀法：
- **PRI 拆解**：`<131>`：131 ÷ 8 ＝ 16 餘 3，Facility 16（local use 0）、Severity 3（Error）；驗算 16 × 8 ＋ 3 ＝ 131。`<30>`：3 × 8 ＋ 6 ＝ 30，system daemons、Informational。`<84>`：10 × 8 ＋ 4 ＝ 84，security/authorization、Warning。`<86>`：10 × 8 ＋ 6 ＝ 86，security/authorization、Informational（clause 6.2.1）。
- **系統日誌與安全日誌**：前兩行是系統日誌（程式與時間同步），後兩行 Facility 10 是安全日誌，收集端可以依 Facility 把它們分到不同檔案。
- **其他欄位**：第 1 行 MSGID 是 `LINKDOWN`，帶有 `timeQuality`，表示發送端知道時區且已同步；第 2～4 行 MSGID 與 STRUCTURED-DATA 都是 `-`（clause 6.2.7、6.3）。
- **時間對齊**：srsRAN 的 `18:13:07.415220` 是 UTC，加 8 小時是 2026-11-18 02:13:07.415（+08:00），與 syslog 第 1 行（02:13:07.412）只差 3 毫秒，也與 5.1.1 例子裡 02:13:07 的 LOS 告警吻合。
- **結論**：日誌確認了斷線發生在 02:13:07 左右，並多看到兩件告警清單裡沒有的事：時間同步進入 holdover，以及 02:41 有一次以 admin 帳號失敗的登入。後者和斷線有沒有關係，日誌本身無法證明，要列為待查。

#### 容易搞混的地方

1. **syslog 的 Severity 與告警的 perceivedSeverity 是兩套。** syslog 是 0～7 的數字、0 最嚴重；3GPP 告警是 `CRITICAL`、`MAJOR` 等列舉值（5.3.1）。RFC 5424 與 TS 28.111 都沒有定義兩者的對應方式，不要自行宣稱「Severity 2 等於 CRITICAL」。
2. **PRI 不是等級本身。** `<165>` 不是等級 165，而是 Facility 20 加 Severity 5；PRIVAL 最大是 23 × 8 ＋ 7 ＝ 191。
3. **安全類 Facility 有兩個。** 4 與 10 在 RFC 5424 的表裡都叫 security/authorization messages（9 與 15 也都是 clock daemon），而且這些值只是參考用；哪個程式用哪個 Facility，要看設備的設定。
4. **時區要看清楚。** RFC 5424 的時間一定帶 `Z` 或時區偏移；srsRAN 的時間是 UTC 但沒有標記。把兩種日誌放在一起時，若沒換算，會誤以為相差 8 小時的兩件事無關。

#### 和其他小節的關係

時間戳換算與時區見 5.2.1，主機名稱與設備命名見 5.2.2。日誌常用來補足 5.1.1 告警與 5.1.4 信令追蹤看不到的細節，和告警一起排進 5.5.1 的事件時間軸；寫報告時，「日誌看到的」與「推測的」要依 5.5.3 分開，再進到 6.2 推理與 6.5 交接。
