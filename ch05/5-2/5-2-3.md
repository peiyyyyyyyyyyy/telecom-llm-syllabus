# 5.2.3 指標單位

所屬：[5.2 對齊資料](../5-2.md)

## 正文

In 3GPP TS 28.552 §4.3 the *measurement type* is defined as a structured string that uniquely identifies the metric, its granularity, and any applied filters. The string is built from a *family name* and a *measurement name*, optionally followed by one or more *subcounters* and/or *filters*. The generic forms are:

* `"<familyName>.<measurementName>.<Subcounter1>.<...>.<SubcounterM>_<Filter1>_..._<FilterN>"` – a combination of subcounters **and** filters.  
* `"<familyName>.<measurementName>.<Subcounter1>.<...>.<SubcounterM>"` – subcounters **only**.  
* `"<familyName>.<measurementName>_<Filter1>_..._<FilterN>"` – filters **only**.  
* `"<familyName>.<measurementName>"` – no subcounters, no filters.  
* `"<familyName>"` – a list of all measurement results for the family.  

These patterns constitute the *unit identifier* for every KPI that appears in alarm and performance data. By parsing the string, a management system can determine the physical meaning of the numeric value (e.g., whether it is a per‑cell counter, a filtered average, or a raw aggregate) without any additional metadata. Consequently, correct construction of the measurement type string is essential for data alignment across vendors and for automated analysis pipelines. [TS 28.552 §4.3]

### Building a Metric Identifier

The components have the following roles:

| Symbol | Meaning |
|--------|---------|
| `familyName` | High‑level category (e.g., *radio*, *core*, *transport*). |
| `measurementName` | Specific KPI within the family (e.g., *throughput*, *errorRate*). |
| `SubcounterX` | An additional dimension that further qualifies the KPI (e.g., *cellId*, *queueId*). |
| `FilterY` | A selection predicate that limits the KPI to a subset of the data (e.g., *qci=5*, *direction=DL*). |

When a KPI is reported, the measurement type string is assembled by concatenating the components in the order shown above. Dots (`.`) separate the hierarchical parts (family, measurement, subcounters) while underscores (`_`) separate filters. No other delimiters are used.

Formally, a measurement type $MT$ can be expressed as  

$$
MT = 
\begin{cases}
\text{familyName}.\text{measurementName}.\displaystyle\prod_{i=1}^{M}\text{Subcounter}_i\; \_ \displaystyle\prod_{j=1}^{N}\text{Filter}_j, & M>0,\,N>0\\[6pt]
\text{familyName}.\text{measurementName}.\displaystyle\prod_{i=1}^{M}\text{Subcounter}_i, & M>0,\,N=0\\[6pt]
\text{familyName}.\text{measurementName}\; \_ \displaystyle\prod_{j=1}^{N}\text{Filter}_j, & M=0,\,N>0\\[6pt]
\text{familyName}.\text{measurementName}, & M=0,\,N=0\\[6pt]
\text{familyName}, & \text{requesting list of all measurements}.
\end{cases}
$$

All products are interpreted as concatenations with the appropriate delimiter (dot or underscore).  

### Worked Example

Suppose a radio node reports the downlink (DL) packet loss rate per cell, filtered to only high‑priority QoS flows (QCI = 5). The relevant components are:

* `familyName` = **radio**  
* `measurementName` = **packetLoss**  
* `Subcounter1` = **cellId** (identifies the cell)  
* `Filter1` = **qci=5** (selects QCI 5 traffic)  
* `Filter2` = **direction=DL** (selects downlink direction)

Because both a subcounter and filters are present, we use the first pattern. The resulting measurement type string is  

```
radio.packetLoss.cellId_qci=5_direction=DL
```

If the same KPI were reported without any filter, the string would collapse to  

```
radio.packetLoss.cellId
```

And if the operator wanted a list of all radio KPIs, the request string would simply be  

```
radio
```

These examples illustrate how the same numeric value (e.g., 0.023 % loss) can be interpreted differently depending on the measurement type string. A downstream analytics engine must therefore treat the string as part of the metric’s *unit* definition.  

### Practical Tips and Common Pitfalls

* **Do not mix delimiters.** Dots are reserved for hierarchical components; underscores are reserved for filters. Using a dot before a filter (e.g., `radio.packetLoss.cellId.qci=5`) violates the specification and will cause parsing failures.  
* **Avoid empty subcounter or filter fields.** The patterns assume that if a delimiter appears, a non‑empty token follows. Strings like `radio.packetLoss._qci=5` are invalid.  
* **Consistent naming.** The same `familyName` and `measurementName` must be used across all reports from a given network element; otherwise, aggregation tools will treat them as distinct metrics.  
* **Versioning is out of scope.** The reference does not define version tags; if a network operator introduces a new KPI, a new `measurementName` should be added rather than overloading an existing one.  
* **Filtering semantics are not defined here.** The reference only specifies the syntax; the meaning of each filter (e.g., the exact QCI value) must be documented elsewhere.  

By adhering strictly to the naming rules in TS 28.552 §4.3, engineers ensure that metric units are unambiguous, machine‑readable, and interoperable across heterogeneous equipment vendors.

## 練習題

**1.** Which naming pattern is used when a measurement includes both subcounters and filters?

- A. "<familyName>.<measurementName>.<Subcounter1>.<...>.<SubcounterM>"
- B. "<familyName>.<measurementName>_<Filter1>_..._<FilterN>"
- C. "<familyName>.<measurementName>.<Subcounter1>.<...>.<SubcounterM>_<Filter1>_..._<FilterN>"
- D. "<familyName>"

<details><summary>看答案</summary>

正解：C。The pattern with both subcounters and filters concatenates subcounters with dots and filters with underscores.

</details>

**2.** If a KPI is reported without any subcounters or filters, which string form correctly represents it?

- A. "<familyName>"
- B. "<familyName>.<measurementName>"
- C. "<familyName>.<measurementName>_<Filter1>"
- D. "<familyName>.<measurementName>.<Subcounter1>"

<details><summary>看答案</summary>

正解：B。The specification defines this exact form for a measurement result without subcounters or filters.

</details>

**3.** What does the string "<familyName>" represent according to TS 28.552 §4.3?

- A. A single measurement result with no subcounters or filters.
- B. A list of measurement results of all applicable measurementNames without any Subcounter or Filter.
- C. A measurement result that includes only filters.
- D. An invalid measurement type.

<details><summary>看答案</summary>

正解：B。The specification explicitly states that a lone family name requests a list of all measurements in that family.

</details>
