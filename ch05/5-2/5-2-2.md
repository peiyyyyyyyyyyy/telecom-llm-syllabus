# 5.2.2 設備代碼與命名

所屬：[5.2 對齊資料](../5-2.md)

## 正文

In a telecommunications network every physical or logical element – antennas, base‑band units, routers, etc. – is modelled as a **Managed Object (MO)**.  Operations such as alarm notification, performance reporting, or configuration exchange must refer to the exact MO that is concerned.  The **Distinguished Name (DN)** provides a globally unique identifier for each MO, allowing different management applications and Integration Reference Points (IRPs) to exchange data without ambiguity [TS 32.300 §3.1.7].

### Distinguished Name Structure
A DN is defined in ITU‑T X.500 and is built from an ordered list of **Relative Distinguished Names (RDNs)**.  In ASN.1 notation the relevant types are  

$$
\text{DistinguishedName} ::= \text{RDNSequence}
$$  

$$
\text{RDNSequence} ::= \text{SEQUENCE OF RelativeDistinguishedName}
$$  

$$
\text{RelativeDistinguishedName} ::= \text{SET SIZE (1..MAX) OF AttributeTypeAndValue}
$$  

$$
\text{AttributeTypeAndValue} ::= \text{SEQUENCE}\{\,\text{type AttributeType},\; \text{value AttributeValue}\,\}
$$  

Only **single‑valued** RDNs are permitted in the IRP naming convention; multi‑valued RDNs are expressly forbidden [TS 32.300 §3.1.7][TS 32.300 §5].  The containment hierarchy (e.g., a cell belonging to a node) is expressed by the order of RDNs: the DN of a child MO can be derived by appending its own RDN to the DN of the parent MO [TS 32.300 §3.1.7].

### String Representation Rules
For transport across any IRP Service Specific (SS) technology the DN is encoded as a **string** that complies with IETF RFC 2253, with additional IRP‑specific restrictions [TS 32.300 §7.A].  The key rules are:

* **Allowed characters** – any character from the ISO/IEC 646 International Reference Version (the ASCII set) and any character from Unicode extensions that also include ISO/IEC 646 [TS 32.300 §7.B].
* **Wildcard prohibition** – the asterisk ‘*’ is reserved for wildcard use and must **not** appear in a DN [TS 32.300 §7.A].
* **No multi‑valued RDN** – each RDN contains exactly one AttributeTypeAndValue pair [TS 32.300 §5].

Because the string form is technology‑neutral, each SS may apply its own escaping rules, but the underlying character set and structural constraints remain unchanged.

### Worked Example
Consider a simplified network where a base station (Network Element, **NE**) named *NodeA* contains a radio cell (Network Resource, **NR**) named *Cell01*.  Using attribute types `neName` and `nrName` (the actual OIDs are defined elsewhere in the operator’s MOC), the DN is built as follows:

1. **RDN for the cell** – `nrName=Cell01`
2. **RDN for the node (parent)** – `neName=NodeA`

The ordered DN string is  

```
nrName=Cell01,neName=NodeA
```

Because only single‑valued RDNs are used, the string complies with the IRP restriction.  All characters belong to the ISO/IEC 646 set, and no asterisk appears, satisfying the allowed‑character rule.  If a management system receives this DN, it can uniquely locate the MO representing *Cell01* under *NodeA* and, by stripping the leading RDN, derive the parent DN `neName=NodeA` [TS 32.300 §3.1.7].

### Practical Tips & Common Pitfalls
* **Do not concatenate multiple attribute/value pairs in a single RDN.**  Attempting `nrName=Cell01+cellId=1` creates a multi‑valued RDN, which the IRP naming convention rejects [TS 32.300 §5].
* **Avoid the asterisk character** inside any attribute value; it will be interpreted as a wildcard and is explicitly forbidden in a DN [TS 32.300 §7.A].
* **Stay within the ASCII (ISO/IEC 646) range** for ease of interoperability.  While Unicode is allowed, using non‑ASCII characters can introduce encoding mismatches in some SS technologies.
* **Validate the hierarchy** by confirming that the child DN ends with the parent DN.  This is the only relationship the DN conveys; no other semantic links (e.g., logical grouping) are implied [TS 32.300 §3.1.7].

By adhering to these rules, engineers ensure that device codes (i.e., the attribute values in the DN) are globally unique, parsable by any TMN‑compliant system, and safe from naming collisions that could corrupt alarm correlation or performance aggregation.

## 練習題

**1.** What is the purpose of a Distinguished Name (DN) according to the specification?

- A. To identify a network protocol
- B. To uniquely identify a MO within a name space
- C. To specify the IRP version
- D. To define service quality levels

<details><summary>看答案</summary>

正解：B。The DN is defined as the identifier for a Managed Object in the naming hierarchy.

</details>

**2.** Which type of Relative Distinguished Name (RDN) is supported by the IRP naming convention?

- A. Multi-valued RDN
- B. Single-valued RDN
- C. Optional RDN
- D. No RDN at all

<details><summary>看答案</summary>

正解：B。The document explicitly restricts RDNs to a single value.

</details>

**3.** Which character is prohibited from being used in a DN string?

- A. Underscore (_)
- B. Asterisk (*)
- C. Hyphen (-)
- D. Plus (+)

<details><summary>看答案</summary>

正解：B。The asterisk is reserved for wildcard usage and must not appear in a DN.

</details>

**4.** How can the DN of a containing Managed Object be obtained?

- A. It cannot be derived from any other DN
- B. By deriving it from the DN of the contained MO
- C. By consulting an external registry only
- D. By hashing the MO’s attributes

<details><summary>看答案</summary>

正解：B。The specification states that the containing MO’s DN can be derived from its child’s DN.

</details>
