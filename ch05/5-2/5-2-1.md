# 5.2.1 時間與時區

所屬：[5.2 對齊資料](../5-2.md)

## 正文

In performance‑measurement (PM) reporting, every record is tied to a specific **granularity period** – the time slice over which counters are accumulated. Down‑stream analytics, alarm correlation, and cross‑system audits all assume that the start and end of that period are known unambiguously. If the timestamps are misinterpreted, a 15‑minute counter may be aligned to the wrong hour, leading to false alarms or missed capacity violations. The 3GPP TS 32.432 specification therefore embeds the full date, local time, and the offset to UTC directly in the measurement‑result file name, making the temporal context self‑contained and machine‑readable.  

### Key fields defined in the file name

| Field | Meaning | Format | Example |
|-------|---------|--------|---------|
| **Type** | Indicates whether the file contains data for a single or multiple Network Elements (NEs) and whether it covers one or many granularity periods. | One character: **A**, **B**, **C**, **D** | `C` |
| **Startdate** | Date on which the first granularity period begins. | `YYYYMMDD` (year 4‑digit, month 01‑12, day 01‑31) | `20000626` |
| **Starttime** | Local time of the start of the first granularity period, together with the UTC offset. | `HHMMshhmm`  <br>• `HH` – hour 00‑23 (24‑h clock) <br>• `MM` – minute (00, 05, 10 … 55) <br>• `s` – sign of the offset (+ or –) <br>• `hhmm` – offset hours (00‑23) and minutes (00‑59) | `2315+0200` |
| **Enddate** *(optional)* | Date on which the **last** granularity period ends. Present only for Types **C** or **D**. | Same format as Startdate | `20050909` |
| **Endtime** | Local time of the end of the last granularity period, with the same offset syntax as Starttime. For Types **C** or **D** the minute values allowed are 05, 10, 15 … 55, 00. | Same format as Starttime | `1500+0000` |
| **UniqueId** *(optional)* | Distinguished name of the NE, EM, or domain that generated the file. | Alphanumeric string | `NodeBId` |
| **jobId** *(optional)* | Identifier of the measurement job when PMIRP is used. | Prefixed by “job” | `job10` |
| **RC** *(optional)* | Running count that makes the filename unique when all other components are identical. Prefixed by the delimiter `_‑_`. | Integer starting at 1 | `_‑_2` |

The **sign** (`s`) together with the hour‑minute offset (`hhmm`) expresses the *local time differential from UTC*. A positive sign means the local clock is ahead of UTC, a negative sign means it is behind. When the offset is zero, the sign may be either “+” or “‑” without changing the meaning.  

### Converting to UTC (practical note)

Although the specification does not prescribe a formula, the definition of the offset makes the conversion straightforward:  

$$
\text{UTC time} = \text{Local time} \;-\; (\text{sign}\times\text{offset})
$$

where the offset is expressed in hours and minutes. For example, a local time of 23:15 with an offset of **+02:00** corresponds to 21:15 UTC.  

### Worked example

Consider the file name  

```
A20000626.2315+0200-2330+0200_NodeBId
```

| Component | Extracted value | Interpretation |
|-----------|----------------|----------------|
| Type | `A` | Single NE, single granularity period |
| Startdate | `20000626` | 26 June 2000 |
| Starttime | `2315+0200` | 23:15 local, offset **+02:00** |
| Endtime | `2330+0200` | 23:30 local, same offset |
| UniqueId | `NodeBId` | Identifier of the generating NodeB |

**Step 1 – Local timestamps**  
- Start: 2000‑06‑26 23:15 (local)  
- End:   2000‑06‑26 23:30 (local)

**Step 2 – Convert to UTC** (offset = +02:00)  
- Start UTC = 23:15 − 02:00 = 21:15 UTC  
- End   UTC = 23:30 − 02:00 = 21:30 UTC  

Thus the granularity period covered by this file is **21:15 – 21:30 UTC on 26 June 2000**.  

### Common mistakes and practical tips

| Mistake | Why it happens | How to avoid |
|---------|----------------|--------------|
| **Using a minute value not listed** (e.g., 07) | The specification only permits 00, 05, 10 … 55 for Starttime and Endtime. | Validate the minute field against the allowed set before accepting a file name. |
| **Omitting Enddate for Type C/D** | Engineers may think Enddate is optional for any file. | Remember that Enddate *shall only be included* for Types **C** or **D**; its absence indicates a single‑period file (Types A/B). |
| **Confusing sign when offset is zero** | Belief that “+0” is mandatory. | The spec explicitly allows either “+” or “‑” when the offset is 0. |
| **Mis‑placing the RC delimiter** | The three‑character delimiter `_‑_` is easy to mistype. | Use the exact sequence underscore, hyphen, underscore when appending RC. |
| **Assuming the offset applies to the whole file** | Some think the offset changes between start and end. | Both Starttime and Endtime carry their own sign and offset; they must be identical for a given file, as shown in the examples. |

By rigorously parsing each component according to the TS 32.432 rules, automation scripts can reliably translate file‑name timestamps into UTC‑aligned series, enabling accurate alarm correlation and performance analytics.
