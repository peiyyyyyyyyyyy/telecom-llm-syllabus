# 9.3.1 結構化設定檔

所屬：[9.3 草案格式](9-3.md)

## 內文

結構化設定草案把人類讀得懂的變更要求寫成可檢查的欄位和結構。YAML、JSON 和 XML 可以表達巢狀資料，但有各自的語法與型別規則。送交審查時，先標明草案格式、適用的資料模型與目標介面。可解析只是第一步，還要檢查欄位名稱、可寫性、目標是否存在、資料相依，以及機器可接受的請求和組織核准的操作是否一致。

撰寫前先將審核資訊和設備實際接收的資料分開。內部草案可含理由、舊值、驗收條件和限制，轉成設備請求時則要用介面規則映射。對 YAML 要確認縮排和型別解析，對 JSON 要確認字串、布林與整數的差別，對 XML 則要核對命名空間。若介面使用 YANG 模型，可以依據模型檢查清單鍵、必要葉節點、型別、值域與相依限制。即使工具接受資料結構，也應對照變更前讀回資料，此時仍可能發現操作目標或適用版本不符。[RFC 7950 §7](https://www.rfc-editor.org/rfc/rfc7950.html#section-7)

使用 NETCONF 時，edit-config 的 target 指定資料存放區，config 則可裝載符合設備模型的設定內容。應先確認伺服器宣告的 capability 以及能否使用該資料存放區。以 3GPP 通用管理服務為例，createMOI 用於建立物件，須核對父物件存在。modifyMOIAttributes 修改指定物件屬性，不能直接套用建立請求的欄位。attributeListOut 是建立操作的回應欄位，且其出現取決於規格描述的條件及對應協定支援情況。拿到一份 JSON 草案不代表它就是 NETCONF RPC，也不表示同一組欄位可直接送往各種服務介面。[RFC 6241 §7.2](https://www.rfc-editor.org/rfc/rfc6241.html#section-7.2) · [3GPP TS 28.532 V18.8.0 §§11.1.1.2–11.1.1.3](https://www.etsi.org/deliver/etsi_ts/128500_128599/128532/18.08.00_60/ts_128532v180800p.pdf)

假設虛構的谷湖測試站要評估接入型錄項目的觀察窗，現行值是 10 分鐘，候選是 15 分鐘。先以本地 YAML 草案記錄實例、舊值、新值、單位和理由。接著用虛構模型檢查 observationMinutes 是整數且適用於目標版本。審查者再確認 10 來自最近的同一設備讀回。若日後採用 NETCONF，需把候選值映射到該版本 YANG 路徑及正確的命名空間，並確認設備提供的目標資料存放區。沒有相符介面或核可時，草案保留為待審資料。前後兩步各自產生驗證紀錄，分別說明內部草案能解析，以及介面負載符合設備模型。

```yaml
# Fictional review draft
target: lake-lab-07
parameter: observationMinutes
oldValue: 10
proposedValue: 15
unit: minutes
reason: retain a longer matched measurement window
```

容易混淆的地方包括將字串數字當整數、把理由或舊值塞進設備模型未定義的節點，以及只用一般語法檢查取代模型驗證。設定草案的可移植性來自明確的模型與映射。若同一份內部草案用於多個介面，應分別記錄轉換後的對象、資料存放區與操作種類。測試時可準備一份含不合法值的資料，確認檢查程式確實能辨認錯誤，也應保留合法範例的驗證結果，讓審查者能以相同資料重做。

9.3.2 說明必要的審查欄位。9.4.2 和 9.4.3 會把草案的相依與原值用於衝突檢查及退回規劃。
