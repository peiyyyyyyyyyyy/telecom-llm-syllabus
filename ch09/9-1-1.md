# 9.1.1 把一句要求拆成要改的參數

所屬：[9.1 拆解意圖](9-1.md)

## 內文

維運要求經常只寫想改善的結果，例如「讓甲區晚上省電」或「改善乙小區邊緣速率」。要把它變成可審查的設定草案，得先說清楚服務對象、時段、衡量方式和必須維持的條件，再查哪些受管理物件及可寫參數可能影響結果。意圖（intent）描述網路要達成的狀態或成效，實現方式由後續設計決定。同一意圖可能有多種做法，而直接指定某個參數值，也可能還缺少要改善的結果與驗證方式。[3GPP TS 28.312 V18.6.0 §4.1.1](https://www.etsi.org/deliver/etsi_ts/128300_128399/128312/18.06.00_60/ts_128312v180600p.pdf) · [RFC 9315 §3.1](https://www.rfc-editor.org/rfc/rfc9315.html#section-3.1)

先保留請求原句，再把內容拆成幾項。第一項是**目標**，包含指標、改善方向、基線和合格門檻。例如要改善邊緣用戶的下行速率，應先訂清楚邊緣用戶的分群方式、要看的速率分位數，以及比較前後兩次量測的時間窗。第二項是**範圍**，以資產清冊將地區、小區別名、服務及方向落到可核對的物件，並標示排除對象。第三項是**限制**，如必須保留覆蓋、不得影響特定服務，或只允許在某段時間內生效。少一項足以改變候選物件或驗收結論的資料時，要指出缺哪一筆及應向誰取得。

接著把各項要求映射到候選做法，記錄每個候選影響哪個指標、要查哪種物件、可能調高或調低什麼，以及需要哪些證據。先比對現行組態、設備版本和參數表的可寫性，再決定是否有足夠資料填入舊值及候選新值。若以 3GPP 的 NRCellDU 為例，屬性表將 `operationalState` 和 `cellState` 的寫入旗標列為 F。這兩個欄位可供觀察，不能填成要求寫入的參數。即使其他屬性可寫，仍須確認該動作符合原目標及當前變更授權。將查證結果與候選做法分開記錄，有助審查者看出方案為何成立、哪些假設尚未查實。[3GPP TS 28.541 V18.8.0 §4.3.5.2](https://www.etsi.org/deliver/etsi_ts/128500_128599/128541/18.08.00_60/ts_128541v180800p.pdf)

例如虛構的青汀電信收到「讓北橋站晚上省電，但急診入口要保持服務」的要求。先向請求人確認夜間為當地時間 01:00 至 05:00，並約定用同一個設備計量邊界的耗電量比較。假設清冊中北橋容量小區 B7 服務站前廣場，基礎覆蓋小區 B0 則覆蓋急診入口。B7 可納入候選，B0 列為受保護物件。接著查 B0 能否承接移入的使用者與尖峰流量，以及 B7 可否在預定窗口結束前恢復服務。3GPP 的同無線接取技術節能案例涵蓋由候選小區承接覆蓋和流量後，讓容量增補小區進入節能模式的做法。這不等於現場支援某個特定參數。暫定草案可以先寫「搜尋 B7 的定時節能功能及其受支援設定，候選方向為允許在核准窗口啟用」。若缺該版本的參數表，草案保留待查項目，待名稱、舊值、新值和承接檢查齊備後再送核可。[3GPP TS 28.310 V18.5.0 §5.1.3.2.2](https://www.etsi.org/deliver/etsi_ts/128300_128399/128310/18.05.00_60/ts_128310v180500p.pdf)

| 青汀電信的虛構案例 | 草案整理結果 |
| --- | --- |
| 預期結果 | 降低 01:00–05:00 站點相關設備用電 |
| 候選與排除 | B7 為候選，B0 保持急診入口覆蓋 |
| 前置證據 | B0 的覆蓋、承接餘裕、B7 的版本支援與恢復時程 |
| 待查欄位 | 確認候選參數名稱、舊值、新值及可寫性 |
| 驗收方式 | 比對同口徑夜間耗電與急診入口服務 |

容易混淆的地方有三項。指標下降的意思要依指標定義判讀，不能直接推成參數也該調低。小區平均改善時，原本服務較差的用戶仍可能沒有受益，因此需要相符的量測分群。設定完成也只表示組態變更到了預期值，是否達成維運意圖，還需要服務量測證據。草案中應清楚標示這些不同的驗證工作。

下一步在 9.2 檢查值域、相依條件與版本，再於 9.3 把證據及候選值整理成結構化草案。9.4 逐項確認影響、衝突、退回與變更後驗證，最後依 9.5 的工單流程核可與留存紀錄。
