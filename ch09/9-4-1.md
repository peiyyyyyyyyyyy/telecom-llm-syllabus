# 9.4.1 影響範圍

所屬：[9.4 變更前檢查](9-4.md)

## 內文

影響範圍描述變更期間及之後，哪些網路物件、使用者、服務和作業會受到直接或間接影響。寫入範圍只描述請求會修改的位置。即使只改一個小區，流量、共同時鐘、傳輸路徑或鄰區移動性也可能影響其他服務。審查人員用這份資訊決定是否需要另排維護窗口、通知服務負責人或停止提案。

先從設定草案取出目標物件及參數，依清冊查父子物件、共用資源和相鄰關係。以覆蓋類變更為例，要檢查相鄰小區能否接收移動中的用戶，以及受保護地點是否仍有服務。若改傳輸資源，則追查所有使用共用匯聚路徑的應用。列出每個關聯項及理由、預期影響時段、觀察指標與資料來源。直接必改、間接受影響、僅需觀察和明確排除的項目都應能追溯到清冊或量測。對於尚未確認的關聯，先標記待查，再決定是否可縮小範圍試行。

再把運行狀態和資源保護方式分開。若設備必須進入維護狀態、停用服務或改變行政狀態，依該介面與設備能力查明影響。NETCONF 的 lock 操作是對設定資料存放區取得排他鎖，用以限制其他設定活動，不能據此推論會停止無線服務。3GPP 修改物件屬性的操作也要求修改後符合資料模型約束，但這一層的成功不能代替服務影響驗證。草案要另外說明鎖定範圍、預估持續時間及解除條件，讓網管和服務團隊按各自職責驗證。[RFC 6241 §7.5](https://www.rfc-editor.org/rfc/rfc6241.html#section-7.5) · [3GPP TS 28.532 V18.8.0 §11.1.1.3](https://www.etsi.org/deliver/etsi_ts/128500_128599/128532/18.08.00_60/ts_128532v180800p.pdf)

假設虛構的川北展場想讓臨時容量小區 C2 在夜間使用新的排程設定。草案只寫 C2，現場清冊顯示 C2 與既有 C1 共用回傳，而戶外巡檢終端在交界處可能由 C2 移到 C1。先把 C1 記為間接受影響對象，再核對兩小區合計流量是否超出共用上限。使用者方面，展場訪客是改善對象，巡檢通報則為必須維持的服務。若晚間試行，仍應保留界面處的切換紀錄、回傳使用率及巡檢事件成功率。若測試資料不足以判斷巡檢路徑，草案要標示待補證據與試行限制，不能只因 C1 不會被直接寫入就從審查刪除。

| 川北展場虛構項目 | 查核方式 |
| --- | --- |
| 直接目標 C2 | 查參數、生效時點與讀回值 |
| 鄰區 C1 | 查交界切換及承接能力 |
| 共用回傳 | 查同時窗的合計負荷 |
| 巡檢通報 | 同窗驗證服務結果 |

常見誤判包括以物件數衡量全部影響、把資料存放區鎖解讀成業務停機，以及把同站的所有使用者一律列成受影響。影響範圍應由實際相依關係支持。對可能有中斷的動作，要另計中斷窗口和適用的服務驗收條件。若只做小範圍試行，應同時記錄何時停止、何時評估擴大，以及擴大後是否會新增共用資源。這些條件不同時，不能直接沿用小規模測試的影響結論。

本節結果交給 9.4.2 查同對象或同服務的競合，並由 9.4.3 與 9.4.4 設計退回及變更後的驗證項目。
