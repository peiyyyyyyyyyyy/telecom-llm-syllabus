# 9.4.3 出錯怎麼退回

所屬：[9.4 變更前檢查](9-4.md)

## 內文

退回是變更結果不符合要求時，用已準備的方式恢復可接受的設定或服務。設備可能提供特定操作的回復能力，整體維運仍需要保留基線、確認適用範圍、定義觸發條件，以及為不同失敗模式準備替代措施。這些工作在開始變更前完成，才能在連線中斷、部分寫入或品質下降時快速判斷。

先保存同一目標與版本的變更前設定、讀回時間以及與其他工單相依的狀態。紀錄備份所在位置、復原順序和可操作人員。每一項退回動作要明示還原哪些欄位，以及哪些其他物件仍維持最新值。變更後查到差異時，先確認實際寫入結果；較早的完整備份若涵蓋其他人的已核准變更，未必適合整份覆寫。退回結束還應驗證設備讀回與服務量測，否則只能知道復原命令已回覆，不能確認用戶已恢復。

NETCONF 的 candidate capability 提供暫存設定，commit 將候選提交到 running，discard-changes 則捨棄未提交的候選。confirmed-commit 是另一項能力。使用確認式提交而未在指定時間內確認時，設備按 RFC 規則回復相關設定。在有 persist 的情況下，原工作階段終止後仍可依機制處理確認，具體條件要讀規格。rollback-on-error 又不同，它指 edit-config 選用該錯誤選項時，若該操作出錯，把目標資料存放區還原至該操作開始前。這些能力都有各自範圍，不能把它們合併成跨設備、跨工單或跨服務的原子保證。[RFC 6241 §§8.3–8.5](https://www.rfc-editor.org/rfc/rfc6241.html#section-8.3)

假設虛構的南埠測試控制器宣告 candidate 與 confirmed commit 能力。在核可計畫中，團隊先保存原始設定，只把兩個相關欄位準備到 candidate 並驗證。受權人員再用已設定的確認窗口試行。其中一項服務在試行後出現超門檻的連線失敗。因為未確認，團隊依照預定程序取消或等待確認期限，接著讀回 running 並執行服務測試。若同一工單也涉及另一台由不同介面控制的設備，仍須根據該設備的獨立退回步驟恢復；本台的回復機制不涵蓋另一台。最後將實際失敗時點、已採取的動作和檢驗結果記錄到工單。

| 南埠虛構退回查核 | 判定 |
| --- | --- |
| 基線 | 核對兩欄位及同版本快照 |
| 試行 | 明訂確認窗口與失敗門檻 |
| 本機回復後 | 讀回 running，驗證服務 |
| 其他設備 | 各自執行已核可的退回程序 |

「放棄候選」適用於未提交修改。「確認式提交逾時」和「編輯出錯回復」處理不同階段。服務品質退回條件也不能只靠管理操作回應。清楚區分這些條件，才能在異常時選到適當步驟。如果操作回應因連線中斷而遺失，應將設備狀態記為待查，先用核准的方式讀回已知欄位，再決定要不要退回。恢復作業所需時間也應列入維護窗口，以免有足夠時間套用設定，卻沒有時間確認回復後的服務。

9.3.2 的舊值用於比對與還原，9.4.4 的服務門檻提供觸發條件，9.5.1 保留核可和執行紀錄。
