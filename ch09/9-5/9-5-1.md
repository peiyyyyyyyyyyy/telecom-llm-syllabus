# 9.5.1 工單、核可、紀錄

所屬：[9.5 異動流程](../9-5.md)

## 正文

In any mobile network, a **work order** (工單) is the formal request that initiates a configuration change. The work order must travel through an **approval** (核可) step before the change is executed, and the whole process is captured in a **record** (紀錄). These three artifacts together enforce the operator’s responsibility for network security by ensuring that only personnel with the proper authority can modify logical or physical settings, and that every modification is traceable — a requirement explicitly stated in the 3GPP security guidance [TS 32.600 §4.2.1.1].

### Core definitions
| Term | Definition (as used in this subsection) |
|------|------------------------------------------|
| **Work order (工單)** | A documented request that describes the intended network‑configuration change, the affected element(s), and the reason for the change. |
| **Approval (核可)** | The explicit permission granted by an operator who holds an **authorisation profile** that matches the change scope. |
| **Record (紀錄)** | An immutable log entry that stores the work order identifier, the approving operator, timestamps, and the outcome of the change. |
| **Authorisation profile** | A set of rights assigned to an operator that determines which configuration changes the operator may perform. |

The reference text makes clear that *“Changes of the network configuration shall be possible only for operators with appropriate authorisation profiles”* [TS 32.600 §4.2.1.1]. Consequently, the **approval** step is essentially a check that the requesting operator’s profile includes the required rights.

### Logical flow of a configuration change
1. **Create work order** – The initiating engineer fills a template that includes the target node, the parameter to be modified, and the desired value.  
2. **Validate authorisation** – The system queries the operator’s profile. If the profile contains the needed privilege, the work order proceeds to the approval stage; otherwise it is rejected.  
3. **Grant approval** – An authorised manager signs off, creating an approval flag in the work order.  
4. **Execute change** – The network management system applies the new configuration.  
5. **Generate record** – All steps, timestamps, and identities are written to a tamper‑evident log.  

Each step supports the operator’s overall duty *“to ensure the network security by employing the appropriate mechanisms for control of logical and physical access”* [TS 32.600 §4.2.1.1].

### Simple numeric example
Assume a small LTE RAN consists of a base station (eNodeB) whose transmit power needs to be increased from 40 dBm to 45 dBm.

| Step | Actor | Action | Authorisation check |
|------|-------|--------|---------------------|
| 1 | Engineer E1 | Opens work order WO‑101, requests power change | – |
| 2 | System | Looks up E1’s profile; profile includes “RAN‑Power‑Modify” | ✅ |
| 3 | Supervisor S2 | Approves WO‑101 (adds approval flag) | – |
| 4 | OSS | Applies new power setting | – |
| 5 | System | Writes record R‑101: WO‑101, E1, S2, timestamps, result *Success* | – |

If Engineer E3, whose profile lacks “RAN‑Power‑Modify”, had submitted the same request, step 2 would have failed and the work order would be automatically rejected. This illustrates the direct link between **authorisation profiles** and the ability to effect configuration changes.

### Common pitfalls and practical notes
| Pitfall | Why it happens | Mitigation |
|---------|----------------|------------|
| Skipping the approval step because the requestor also holds an authorisation profile. | Misunderstanding that profile possession alone is sufficient. | Enforce a policy that *all* changes, even those made by highly privileged users, must be recorded with a separate approval entry. |
| Storing records in mutable databases. | Belief that a conventional relational DB is “good enough”. | Use write‑once, append‑only logging or cryptographic hash chaining to satisfy the operator’s duty to control access and retain evidence. |
| Using a single generic authorisation profile for many roles. | Convenience in small teams. | Separate profiles for logical (software configuration) and physical (hardware access) domains to align with the “control of logical and physical access” requirement. |

**Note:** The reference specification does not prescribe a particular format for work orders, approvals, or records; it only mandates that configuration changes be limited to operators with appropriate authorisation profiles and that the operator must ensure security through suitable control mechanisms [TS 32.600 §4.2.1.1]. Any additional procedural details are therefore outside the scope of this subsection.

## 練習題

**1.** Which condition must be satisfied before a network configuration change can be performed?

- A. The change must be documented in a public forum.
- B. The operator must have an appropriate authorisation profile.
- C. The hardware must be replaced.
- D. The change must be approved by the regulator.

<details><summary>看答案</summary>

正解：B。The reference explicitly links configuration changes to operator authorisation profiles.

</details>

**2.** Which of the following best describes a record (紀錄) in the context of configuration management?

- A. A temporary cache of the new settings.
- B. An immutable log entry that captures who approved the change and when.
- C. A verbal summary spoken at a shift hand‑over.
- D. A copy of the device’s firmware.

<details><summary>看答案</summary>

正解：B。Records must retain evidence of the change, aligning with the operator’s duty to control access.

</details>

**3.** If an engineer’s authorisation profile does not include the required privilege, what does the reference imply will happen to their change request?

- A. The request will be automatically approved.
- B. The request will be ignored but logged.
- C. The request cannot be executed.
- D. The request will be sent to the regulator.

<details><summary>看答案</summary>

正解：C。The specification limits configuration changes to operators with appropriate profiles; lacking that, the change is not permitted.

</details>
