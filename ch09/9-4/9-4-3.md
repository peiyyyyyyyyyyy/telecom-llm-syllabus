# 9.4.3 出錯怎麼退回

所屬：[9.4 變更前檢查](../9-4.md)

## 正文

When a network engineer applies a configuration change, the network must remain operable even if the new settings contain errors. In a live PLMN, a faulty change can trigger service degradation, alarm storms, or even a complete outage. Therefore the management system must provide a deterministic way to restore the last known good state without manual re‑configuration of each Managed Object Instance (MOI). This “fallback” capability is a core requirement of **Active CM** on the Itf‑N interface and is explicitly defined for **Bulk CM** operations [TS 32.600 §7.1]​.

### Definition of the rollback operation

In the context of Bulk CM, a *rollback* (or *fallback*) is a **single active operation** that instructs the subordinate entity (EM or NE) to replace the currently active configuration with the previously stored stable configuration.  

Let  

- $C_{new}$ be the configuration that has just been activated,  
- $C_{old}$ be the last stable configuration saved in the subordinate entity,  
- $R_{fallback}$ be the rollback operation.  

The effect of $R_{fallback}$ can be expressed as  

$$ C_{active} \leftarrow C_{old} $$  

where $C_{active}$ denotes the configuration that the network element uses for its runtime behavior. The operation does **not** require the NM to resend the entire $C_{old}$ file; the subordinate entity already holds it and can apply it atomically.

### How the rollback is triggered

1. **Error detection** – After a Bulk CM activation, the NM monitors alarms and status notifications (passive CM). If an alarm indicating a configuration error is raised, the NM may decide to rollback.  
2. **Invocation of $R_{fallback}$** – The NM issues a single active command over Itf‑N, “fallback to previous stable configuration”. The command is part of the Bulk CM functional set.  
3. **Atomic replacement** – The subordinate entity swaps the active configuration with the stored $C_{old}$ in one step, guaranteeing that no intermediate partially‑applied state is visible to the traffic.  

The reference text states that Bulk CM “offers … the ability to fallback to a previous stable configuration through a single operation” [TS 32.600 §7.1]​.

### Worked example

Suppose a Radio Access Network (RAN) operator wants to update the Transmission Power Control (TPC) parameters for 200 cells. The operator prepares a bulk file **TPC\_v2.cfg** containing 200 parameter rows.  

| Step | Action | Result |
|------|--------|--------|
| 1 | NM issues *Bulk Download* of **TPC\_v2.cfg** to the EM. | EM stores the file as *candidate* configuration. |
| 2 | NM issues *Network‑wide activation* of the candidate. | $C_{new}$ becomes active. |
| 3 | Alarms are generated: “TPC out‑of‑range on cell 57”. | NM detects error. |
| 4 | NM sends $R_{fallback}$ command. | EM replaces $C_{new}$ with the previously stored $C_{old}$ (e.g., **TPC\_v1.cfg**). |
| 5 | Service resumes with the known‑good TPC settings. | No further alarms. |

In this scenario the rollback required **one** active command, regardless of the 200‑parameter size, illustrating the efficiency promised by Bulk CM.

### Practical notes and common pitfalls

| Pitfall | Explanation |
|---------|-------------|
| **Assuming rollback restores *all* previous changes** | The fallback only restores the *last* stable configuration saved by the subordinate entity. If multiple successful changes were made consecutively, only the most recent one can be undone in a single operation. |
| **Triggering rollback before the error is confirmed** | Premature rollback may discard a configuration that is actually functional, leading to unnecessary service disruption. Use passive CM alarms to verify the fault. |
| **Neglecting to verify that $C_{old}$ is indeed stable** | The subordinate entity must have successfully stored a stable configuration before the new activation. If $C_{old}$ itself is corrupted, the rollback will not recover the network. |
| **Treating rollback as a “save‑point” in Basic CM** | Basic CM does not define a bulk fallback operation; only Bulk CM provides the single‑operation fallback capability. Attempting to emulate it with Basic CM would require manual retrieval and re‑application of each MOI, which is error‑prone. |

**Key take‑away:** In a 3GPP PLMN, the only standardized, efficient way to revert a bulk configuration after an error is to invoke the *fallback* operation defined for Bulk CM. This operation is atomic, single‑step, and relies on the subordinate entity’s internal storage of the previous stable configuration [TS 32.600 §7.1]​.

## 練習題

**1.** 哪一項描述屬於 Bulk CM 的「主動」面向？

- A. 單一操作檢索單個 NE 的組態
- B. 透過單一操作進行全網路組態的啟用
- C. 設定過濾機制以控制通知
- D. 只提供組態概覽的被動資訊

<details><summary>看答案</summary>

正解：B。全網路組態的單一操作啟用是 Bulk CM 的主動特徵之一。

</details>

**2.** 哪一種 CM 功能提供了「真正改變目前網路組態」的能力？

- A. Passive CM
- B. Active CM
- C. Basic CM
- D. Bulk CM

<details><summary>看答案</summary>

正解：B。文件明確指出 Active CM 能讓 NM 操作者真正改變目前的網路組態。

</details>

**3.** 哪一項屬於 Passive CM 的主要特徵？

- A. 允許 NM 直接修改組態參數
- B. 主要提供 NM 目前組態變更的通知資訊
- C. 以檔案方式批次下載組態
- D. 透過單一操作回復至先前組態

<details><summary>看答案</summary>

正解：B。Passive CM 的描述強調它提供組態變更的通知資訊給 NM。

</details>
