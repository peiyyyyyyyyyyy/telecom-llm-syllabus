# 9.2.1 允許範圍

所屬：[9.2 參數](../9-2.md)

## 正文

The **allowed range** (sometimes called *scope* or *permitted values*) of a configuration attribute tells a network operator exactly which symbolic or numeric values may be written into the management database. In a live 5G deployment the OAM (Operations, Administration, and Maintenance) system validates every write request against these ranges; a mismatch is rejected before it can affect the radio stack. Consequently, a precise understanding of allowed values is essential for both fault‑free commissioning and for automated tools that generate configuration artefacts.

### Enumerated attributes
Three attributes of the **NRCellDU** object are defined as enumerations (type = ENUM). Their allowed values are listed explicitly in TS 28.541 §4.4.1:

| Attribute | Allowed values | Meaning |
|-----------|----------------|---------|
| **administrativeState** | **LOCKED**, **SHUTTING DOWN**, **UNLOCKED** | Permission to use or prohibition against using the cell, imposed through the OAM services. |
| **operationalState** | **ENABLED**, **DISABLED** | Whether the resource is installed and operable (Enabled) or not installed / not operable (Disabled). |
| **cellState** | **IDLE**, **INACTIVE**, **ACTIVE** | Usage state of the cell: idle (not in use), inactive (known but not serving UEs), active (known and able to serve UEs). |

The enumeration for **administrativeState** follows the definitions in ITU‑T Recommendation X.731 [18] and its default is **LOCKED**. The **operationalState** attribute has no default value (i.e. it must be set explicitly). The **cellState** definitions are aligned with TS 38.401 [4]; note that *Inactive* and *Active* describe the cell’s visibility to both the gNB‑DU and the gNB‑CU and whether it may serve user equipment (UE)【TS 28.541 §4.4.1】.

### Integer attributes
Two attributes carry numeric values that are constrained by the NR‑ARFCN (Absolute Radio Frequency Channel Number) tables defined in TS 38.104 §5.4.2.3:

* **arfcnDL** – downlink NR‑ARFCN (type = Integer, multiplicity = 1, not nullable)
* **arfcnUL** – uplink NR‑ARFCN (type = Integer, multiplicity = 1, not nullable)

The specifications state that “allowed values of NR‑ARFCN are specified for each band in subclause 5.4.2.3”【TS 28.541 §4.4.1】. Because the attribute is not nullable, a value must always be present; the OAM shall reject a missing entry.

### Default values and nullability
* **administrativeState** – default **LOCKED**, `isNullable: False`.
* **operationalState** – default **None** (i.e. no implicit value), `isNullable: False`.
* **cellState** – default **None**, `isNullable: False`.
* **arfcnDL / arfcnUL** – default **None**, `isNullable: False`.

The `isOrdered` and `isUnique` flags are marked **N/A** for all attributes, indicating that ordering and uniqueness are not enforced by the data model itself but are handled by higher‑level processes (e.g., network planning tools).

### Worked example
Consider a newly deployed gNB‑DU that must expose a single NRCellDU instance with the following configuration:

| Attribute | Desired value |
|-----------|---------------|
| administrativeState | UNLOCKED |
| operationalState | ENABLED |
| cellState | ACTIVE |
| arfcnDL | 527500 |
| arfcnUL | 497500 |

Step 1 – Verify allowed values: *UNLOCKED* belongs to the enumeration for **administrativeState**; *ENABLED* belongs to **operationalState**; *ACTIVE* belongs to **cellState**. All three are permitted per the table above.

Step 2 – Verify numeric ranges: The chosen ARFCN numbers must belong to a band listed in TS 38.104 §5.4.2.3. Assuming band n78 (downlink 617 000 – 642 000, uplink 592 000 – 617 000), the selected values (527 500 – 497 500) fall **outside** the allowed band and would be rejected. A correct choice would be, for example, `arfcnDL = 620 000` and `arfcnUL = 595 000`, both of which are within the n78 band.

Step 3 – Apply defaults: Since **operationalState** and **cellState** have no default, the OAM must receive explicit values (ENABLED and ACTIVE). The **administrativeState** default of LOCKED would be overridden by the explicit UNLOCKED value.

If the OAM receives the corrected set `{administrativeState=UNLOCKED, operationalState=ENABLED, cellState=ACTIVE, arfcnDL=620000, arfcnUL=595000}`, the request passes validation because every attribute respects its allowed range, multiplicity, and nullability constraints.

### Common mistakes and practical notes
1. **Confusing administrative and operational states** – Operators sometimes set **administrativeState** to UNLOCKED expecting the cell to become active immediately; however, the cell will remain non‑operational until **operationalState** is set to ENABLED and **cellState** to ACTIVE.  
2. **Omitting mandatory ARFCN values** – Because `isNullable` is **False**, any omission triggers a validation error. Automation scripts must always populate both **arfcnDL** and **arfcnUL** with band‑compatible numbers.  
3. **Assuming defaults where none exist** – The lack of a default for **operationalState** and **cellState** means the OAM may reject a partially filled object; always provide explicit values during creation.  
4. **Ignoring band‑specific NR‑ARFCN limits** – The reference to TS 38.104 §5.4.2.3 is essential; using numbers outside the band’s range leads to a “value out of range” fault even though the number itself is syntactically valid.  
5. **Treating ENUM strings as case‑insensitive** – The specification lists the literals in upper‑case; implementations typically perform case‑sensitive matching, so “locked” would be rejected.

By rigorously applying the allowed ranges defined in TS 28.541, engineers can avoid configuration rejections, reduce OAM‑level alarms, and ensure that the radio layer receives consistent, standards‑compliant parameters.
