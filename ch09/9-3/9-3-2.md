# 9.3.2 必填欄位：目標物件、參數、舊值、新值、理由

所屬：[9.3 草案格式](../9-3.md)

## 正文

In the 3GPP Managed Network Services (MnS) framework a *target object* is the managed entity that a configuration change concerns. The object is uniquely identified by a **Distinguished Name (DN)**, which is conveyed in the **managedObjectInstance** parameter for creation requests or the **baseObjectInstance** parameter for modification and deletion requests. The DN follows the syntax defined in TS 32.300 and must reference an existing parent object; otherwise the operation is rejected as an error [TS 28.532 §11.1.1.1.2] [TS 28.532 §11.1.1.4.2].

### Parameter (Attribute)

The *parameter* that is changed is an attribute defined in the managed object class. In a **createMOI** request the attribute name/value pairs are placed in **attributeListIn**; in a **modifyMOIAttributes** request the attribute is identified by **nodeIdentifier**. The MnS producer uses the attribute name (and, when necessary, a path or identifier) to locate the exact field to be altered [TS 28.532 §11.1.1.1.2] [TS 28.532 §11.1.1.3.1].

### Old and New Values

The specification does not require the *old value* to be transmitted; the MnS consumer is expected to know the current state or retrieve it beforehand. The *new value* is supplied in the **nodeValue** field of a modification entry when the **modifyOperator** is *replace* or *add*. For a *replace* operation the new value completely substitutes the existing one [TS 28.532 §11.1.1.3.1].

### Reason (Audit Information)

A textual *reason* for the change is useful for audit trails but is **outside the scope of the mandatory fields defined in TS 28.532**. No parameter named “reason” appears in the create, modify, or delete operation definitions, so inclusion of such a field is optional and protocol‑specific.

### Worked Example

Assume an operator wants to increase the maximum uplink bitrate of a radio node from 100 Mbps to 150 Mbps. The managed object class is `RadioNode`, and the attribute to modify is `maxUplinkBitRate`. The DN of the instance is `ManagedElement=1/2/3,RadioNode=4`.  

The **modifyMOIAttributes** request would contain:

| Parameter            | Value                                                  |
|----------------------|--------------------------------------------------------|
| baseObjectInstance   | `ManagedElement=1/2/3,RadioNode=4` (target object)    |
| modificationList[1]  | `modifyOperator = replace`                             |
|                      | `nodeIdentifier = maxUplinkBitRate`                    |
|                      | `nodeValue = 150000000`  (150 Mbps in bits per second) |

No **old value** or **reason** field is mandatory; the operator may keep a separate log noting “increase capacity for sector A”. The request is accepted only if the parent `ManagedElement=1/2/3` exists and the new value respects the data‑type constraints of the attribute [TS 28.532 §11.1.1.3.1] [TS 28.532 §11.1.1.1.1].

If the protocol supports returning the post‑change state, the response may include **attributeListOut** with the updated value; otherwise this element may be omitted [TS 28.532 §11.1.1.1.3].

### Common Mistakes and Practical Notes

1. **Omitting the DN** – Forgetting to supply `managedObjectInstance` (creation) or `baseObjectInstance` (modification/deletion) makes the request invalid because the target object cannot be resolved [TS 28.532 §11.1.1.1.2] [TS 28.532 §11.1.1.4.2].  
2. **Wrong attribute identifier** – Using only the attribute name when the attribute field is ambiguous can lead to mis‑identification; the spec requires a *nodeIdentifier* that may include a path or local identifier [TS 28.532 §11.1.1.3.1].  
3. **Expecting attributeListOut when the protocol does not support it** – Some stage‑2 protocols cannot return `attributeListOut`; in those cases the producer must not modify the request list before creating the object [TS 28.532 §11.1.1.1.3].  
4. **Providing a value for a read‑only attribute** – The attribute’s property (read‑only, mandatory, optional) determines whether a value may be supplied; violating this leads to operation failure [TS 28.532 §11.1.1.1.1] (see reference to TS 32.156 for attribute properties).  
5. **Assuming “reason” is mandatory** – Since the spec does not define a reason field, implementations that require one must extend the protocol beyond the baseline definition; relying on it for basic compliance will cause interoperability issues.

By strictly adhering to the mandatory fields—target object DN, attribute identifier, and new value (with appropriate modifyOperator)—engineers ensure that configuration drafts and change checks are processed reliably across heterogeneous MnS producers.

## 練習題

**1.** Which parameter in a **createMOI** request uniquely identifies the managed object to be created?

- A. managedObjectClass
- B. managedObjectInstance
- C. attributeListIn
- D. status

<details><summary>看答案</summary>

正解：B。The DN of the object is carried in the managedObjectInstance field.

</details>

**2.** Which **modifyOperator** value indicates that the supplied nodeValue must replace the current attribute value?

- A. add
- B. remove
- C. replace
- D. setToDefault

<details><summary>看答案</summary>

正解：C。The replace operator substitutes the existing value with the new one.

</details>

**3.** Is the **attributeListOut** parameter mandatory in every **createMOI** response?

- A. Yes, it must always be present.
- B. No, it is optional and only appears when the producer assigns unknown values.
- C. It is mandatory only for failure responses.
- D. It is never used in createMOI responses.

<details><summary>看答案</summary>

正解：B。attributeListOut is included only if the producer adds values unknown to the consumer; otherwise it may be omitted.

</details>

**4.** Which mandatory parameter in a **deleteMOI** request defines the starting point for object selection?

- A. scopeLevel
- B. filter
- C. baseObjectInstance
- D. deletionList

<details><summary>看答案</summary>

正解：C。baseObjectInstance supplies the full DN that serves as the selection root.

</details>
