# 9.3.1 結構化設定檔

所屬：[9.3 草案格式](../9-3.md)

## 正文

In a telecom network, a *structured configuration file* is the textual or binary representation that a Management and Orchestration (MnS) consumer uses to invoke provisioning operations on an MnS producer.  By arranging the required fields—managed object class, distinguished name, and attribute list—in a predictable hierarchy, the file can be parsed automatically and mapped to the **createMOI** operation defined in TS 28.532 §11.1.  This deterministic format reduces human error, enables batch provisioning, and supports audit trails for change management [TS 28.532 §11.1.1.1.1].

### Parameters of the **createMOI** Operation

The **createMOI** request consists of three mandatory parameters:

* **managedObjectClass** – a string that identifies the class name of the object to be created.  
* **managedObjectInstance** – a distinguished name (DN) that uniquely identifies the new instance in the network resource model.  
* **attributeListIn** – a list of *attribute name/value* pairs supplied by the consumer.  

These parameters are defined in the reference table under *Input parameters* and are all marked **M** (mandatory) [TS 28.532 §11.1.1.1.2].

### Naming the Instance and Building the DN

The MnS consumer must first assign a value to the *naming attribute* of the new object, then construct its DN according to TS 32.300.  The resulting DN is placed in **managedObjectInstance**.  No further processing of the DN occurs inside the **createMOI** operation; the producer uses it directly to locate the parent and to store the new instance [TS 28.532 §11.1.1.1.1].

### Attribute Handling and Default Values

The **attributeListIn** may contain *none*, *some*, or *all* of the attributes defined for the class.  Whether an attribute *shall*, *shall not*, or *may* be provided is dictated by the attribute’s property in the object class definition (see TS 32.156 §5.2.1, but the rule is summarised in the reference).  If an attribute is omitted and a *default value* is defined, the MnS producer assigns that default **after** returning the **createMOI** response when the underlying protocol does not support an *attributeListOut* [TS 28.532 §11.1.1.1.1].

When the producer assigns a value that was not supplied by the consumer, it includes an **attributeListOut** section in the response.  If the protocol cannot convey this list, the producer must not modify the request‑side attribute list before creation, and the consumer learns of the default assignment only via an *attribute value change notification* [TS 28.532 §11.1.1.1.1].

### Model Constraints and Parent Existence

A creation request succeeds only if the parent object already exists; otherwise the producer must reject the request as an error.  Moreover, after applying the request the model must satisfy *cardinality, multiplicity, allowed values, and data type* constraints; violation of any constraint causes the operation to fail [TS 28.532 §11.1.1.1.1].

### Worked Example

Assume a network element needs a new **PolicyControlFunction** (PCF) instance.  

1. **Naming attribute**: `pcfId = 101`  
2. **DN construction** (per TS 32.300): `pcfId=101,managedElement=ME-01` → `managedObjectInstance = "pcfId=101,managedElement=ME-01"`  
3. **managedObjectClass** = `"PolicyControlFunction"`  

The consumer prepares the **attributeListIn** with two attributes:  

* `maxSessions = 5000` (explicitly provided)  
* `defaultQoS` omitted – the class definition specifies a default of `"bronze"`  

The **createMOI** request is therefore:

```
managedObjectClass = "PolicyControlFunction"
managedObjectInstance = "pcfId=101,managedElement=ME-01"
attributeListIn = [
    {name: "maxSessions", value: 5000}
]
```

The MnS producer receives the request, verifies that the parent `managedElement=ME-01` exists, and creates the PCF object immediately.  Because `defaultQoS` was not supplied, the producer assigns `"bronze"` after sending the response and notifies the consumer via an attribute‑value‑change notification.  The **createMOI** response may contain `attributeListOut = [{name:"defaultQoS", value:"bronze"}]` if the protocol permits [TS 28.532 §11.1.1.1.1].

### Common Pitfalls and Practical Notes

| Pitfall | Why it Happens | Remedy |
|---------|----------------|--------|
| Omitting the naming attribute | The DN cannot be built, leading to an invalid **managedObjectInstance** | Always assign the naming attribute before DN construction |
| Supplying an attribute that is *shall not* be provided | The producer will reject the request due to class‑level constraints | Consult the class definition (TS 32.156) for attribute properties |
| Assuming default values are applied before the response | Some protocols do not return **attributeListOut**, so defaults appear only via notifications | Listen for attribute‑value‑change notifications if your protocol lacks **attributeListOut** |
| Attempting to create an object under a non‑existent parent | The producer treats this as an error per the parent‑existence rule | Verify parent existence with a prior **readMOI** or similar query |
| Ignoring model constraints after creation | The request may succeed but later operations may fail if constraints are violated | Validate cardinality, allowed values, and data types before sending the request |

By adhering to the structured format prescribed in TS 28.532 and respecting the attribute and model rules, engineers can reliably automate provisioning while minimizing the risk of configuration drift. [TS 28.532 §11.1.1.1.1]

## 練習題

**1.** 在「createMOI」請求中，哪兩個參數共同構成了結構化設定檔的基本識別資訊？

- A. managedObjectClass 與 attributeListIn
- B. managedObjectInstance 與 attributeListOut
- C. managedObjectClass 與 managedObjectInstance
- D. attributeListIn 與 attributeListOut

<details><summary>看答案</summary>

正解：C。這兩個參數分別提供類別名稱與完整的 DN，構成了物件的唯一識別。

</details>

**2.** 在結構化設定檔（attributeListIn）中，使用者可以提供哪些屬性值？

- A. 必須提供所有屬性的值
- B. 只能提供必須屬性的值
- C. 可以提供零個、部分或全部屬性的值
- D. 只能提供預設值的屬性

<details><summary>看答案</summary>

正解：C。使用者可自行決定提供多少屬性，系統會自行補足未提供的部分。

</details>

**3.** 若「createMOI」請求的結構化設定檔中未包含某些屬性值，MnS 產生者在建立物件後會如何回應？

- A. 直接忽略這些屬性，不回傳任何資訊
- B. 必須在回應中加入 attributeListOut，列出系統分配的屬性值
- C. 必須在回應中返回錯誤碼
- D. 必須要求使用者重新提交完整的設定檔

<details><summary>看答案</summary>

正解：B。系統會在回應中提供已自動分配的屬性值，以補足缺失的資訊。

</details>

**4.** 結構化設定檔（attributeListIn）在送出前，MnS 產生者會對其內容做什麼處理？

- A. 會先更新或刪除其中的屬性值
- B. 會在建立物件前直接修改屬性值
- C. 不會在建立物件前修改任何提供的屬性值
- D. 會自動加入所有預設屬性值

<details><summary>看答案</summary>

正解：C。產生者在建立物件之前必須保持請求中提供的屬性值不變。

</details>

**5.** 若在結構化設定檔中指定的物件父層不存在，MnS 產生者會如何處理「createMOI」請求？

- A. 自動建立缺失的父層後再建立物件
- B. 視為成功，僅回傳空的 attributeListOut
- C. 將請求視為錯誤，返回失敗
- D. 仍建立物件，但不保證屬性完整性

<details><summary>看答案</summary>

正解：C。只有在父層已存在的情況下才允許建立新物件，否則視為錯誤。

</details>
