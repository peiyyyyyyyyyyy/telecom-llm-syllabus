# 9.1.1 把一句要求拆成要改的參數

所屬：[9.1 拆解意圖](../9-1.md)

## 正文

In an Intent‑driven Management and Orchestration (MnS) system, a **consumer** states *what* it wants – for example “the RAN shall consume less energy” – without prescribing *how* to achieve it. The **producer** must translate that natural‑language or high‑level statement into concrete **parameters** that can be applied to managed objects (network slices, radio cells, etc.) [TS 28.312 §4.5.1]. This “splitting” step is the first part of *intent translation* and is essential because only by identifying the exact parameters to modify can downstream MnS layers (Intent‑CSP, Intent‑NOP) enforce the request while still being able to resolve conflicts [TS 28.312 §4.2.3].

### Key definitions
- **Object $O$** – a 3GPP‑managed entity such as a network slice, sub‑network, or service.  
- **Characteristics $S$** – the set of requirements, goals, and contexts associated with $O$. In the intent language $S$ is what the consumer wishes to achieve (e.g., a target power level, latency bound).  
- **Intent Expectation** – the combination of $S$ for a given $O$ (or for a list of objects) that the consumer communicates to the producer [TS 28.312 §4.5.1].  
- **Parameter set $\mathbf{P}$** – the concrete configuration items derived from $S$ that can be written to the managed object (e.g., $P_{\text{tx\_power}}$, $P_{\text{sleep\_mode}}$).  

The translation can be expressed as a function  

$$
\mathbf{P}=f(O,S)
$$  

where $f$ extracts each element of $S$ that corresponds to a configurable attribute of $O$.

### Step‑by‑step splitting process
1. **Identify the object(s)** – parse the sentence for nouns that match known managed object types (slice, cell, service).  
2. **Extract characteristics** – locate adjectives, quantitative expressions, or goal statements (e.g., “reduce energy consumption by 20 %”).  
3. **Map each characteristic to a parameter** – using a pre‑defined catalogue that links high‑level goals to low‑level attributes (e.g., “energy consumption” → $P_{\text{tx\_power}}$, $P_{\text{sleep\_mode}}$).  
4. **Form the Intent Expectation** – group the parameters per object (or per list of objects) as required by the specification [TS 28.312 §4.5.1].  

The producer may also need to **detect conflicts** between the extracted parameters and other active intents or non‑intent requirements before proceeding [TS 28.312 §4.2.3].

### Worked example
**Natural‑language request:** “Decrease the transmit power of cell C12 by 3 dB while keeping the user‑plane latency below 10 ms.”  

| Step | Action | Result |
|------|--------|--------|
| 1️⃣ Identify object | “cell C12” matches a RAN equipment object $O$ | $O = \text{Cell C12}$ |
| 2️⃣ Extract characteristics | “decrease transmit power by 3 dB” → $S_1$; “latency < 10 ms” → $S_2$ | $S = \{S_1,S_2\}$ |
| 3️⃣ Map to parameters | $S_1 \rightarrow P_{\text{tx\_power}} = -3\text{ dB}$; $S_2 \rightarrow P_{\text{latency}} \le 10\text{ ms}$ | $\mathbf{P}= \{P_{\text{tx\_power}}=-3\text{ dB},\;P_{\text{latency}}\le10\text{ ms}\}$ |
| 4️⃣ Form Intent Expectation | One object, two parameters | “object {Cell C12} with characteristics $\{P_{\text{tx\_power}}=-3\text{ dB}, P_{\text{latency}}\le10\text{ ms}\}$” [TS 28.312 §4.5.1] |

The Intent‑CSP producer can now forward $\mathbf{P}$ to the Intent‑NOP layer, which will apply the configuration to the radio equipment.

### Common mistakes and practical notes
- **Confusing “what” with “how.”** The consumer must not embed implementation details (e.g., “set the amplifier gain to 5 dB”). Doing so limits the producer’s optimisation freedom and violates the intent principle [TS 28.312 §4.2.3].  
- **Omitting the object identifier.** If the request only states “reduce energy consumption,” the producer cannot map $S$ to a concrete $O$, leading to ambiguity.  
- **Over‑splitting when multiple objects share the same characteristics.** The specification permits a single Intent Expectation for a list of objects with identical $S$ [TS 28.312 §4.5.1]; creating separate expectations unnecessarily increases processing load.  
- **Neglecting conflict detection.** Before committing $\mathbf{P}$, the producer must verify that the new parameters do not clash with other intents or non‑intent constraints [TS 28.312 §4.2.3].  

By systematically applying the splitting function $f(O,S)$ and respecting the rules above, engineers can ensure that high‑level service wishes are faithfully transformed into actionable configuration changes while preserving the flexibility that Intent‑driven management promises.

## 練習題

**1.** 在規格中，對於「每組具有相同屬性的物件」所組合的需求、目標與情境稱為什麼？

- A. Intent Requirement
- B. Intent Expectation
- C. Intent Specification
- D. Intent Parameter

<details><summary>看答案</summary>

正解：B。規格明確定義此組合為 Intent Expectation。

</details>

**2.** 當消費者想要對多個具有相同屬性的物件表達相同的需求時，應如何在意圖中寫出？

- A. 為每個物件寫一個獨立的意圖
- B. 使用 \"object O with characteristics S\" 單一描述
- C. 使用 \"objects {O1,O2,…,ON} with characteristics S\" 的列表形式
- D. 只列出物件名稱，不需說明特性

<details><summary>看答案</summary>

正解：C。規格提供了以列表方式同時描述多個物件的寫法。

</details>

**3.** 若消費者希望對「屬性不同」的物件群組設定不同的需求、目標與情境，規格指出必須區分什麼？

- A. 物件的唯一識別碼
- B. 需求、目標與情境的組合
- C. 網路切片的類型
- D. 服務的優先順序

<details><summary>看答案</summary>

正解：B。必須區分每組具有相同屬性的物件所對應的需求、目標與情境。

</details>

**4.** 在最基本的形式下，消費者使用意圖向生產者表達需求時，會說「an object O with characteristics S」。此句中的「characteristics S」代表什麼？

- A. 物件的唯一編號
- B. 物件的屬性、需求、目標與情境
- C. 物件的位置信息
- D. 物件的安全等級

<details><summary>看答案</summary>

正解：B。「characteristics S」涵蓋了需求、目標與情境等所有特性。

</details>

**5.** 根據 TS 28.310，意圖主要關注哪一個層面？

- A. 「How」要如何實現
- B. 「What」需要達成的目標
- C. 「When」何時執行
- D. 「Who」誰來執行

<details><summary>看答案</summary>

正解：B。規格指出意圖更著重於描述「要達成什麼」而非「如何」達成。

</details>
