# 2.4.7 由變更請求（CR）內容判斷所屬規格與工作組

所屬：[2.4 文件歸類](../2-4.md)

## 正文

In 3GPP development, every modification to a normative document is submitted as a **Change Request (CR)**. By inspecting the CR we can immediately tell which **specification clause** is being touched, and consequently which **working group** owns that clause. This is essential for routing the CR to the correct experts, avoiding duplicated effort, and ensuring that the change is evaluated under the appropriate **stage‑3** or **stage‑2** process.  

### Key definitions dictated by TS 21.900 §4.6.3

| Symbol / Term | Definition | Unit / Note |
|----------------|------------|-------------|
| **CR form** | The standardized cover page that initiates a change request. | – |
| **Clause** | A numbered paragraph of a 3GPP specification (e.g., 5.2.1). | – |
| **Major version** | The first digit of a specification version (e.g., *38* in *38.331*). The CR must reference the **latest version of the major version**. | – |
| **Revision mode** | A word‑processor feature that marks insertions, deletions and moved text. All proposed changes must be visible through this mode. | – |
| **Forge repository** | The Git‑based storage used for stage‑3 normative files, referenced by clause 5C of the specification. | – |
| **Merge‑Request (MR)** | A Forge construct that bundles a set of file modifications; the CR cover page must list the MR in the “*Other comments:*” field. | – |

### Mandatory content of a CR

1. **List of affected clauses** – The CR must attach **the clauses of the specification that are affected**, and it must use the **latest version of the major version**. This guarantees that reviewers work on the most up‑to‑date text [TS 21.900 §4.6.3].  

2. **Revision‑mode markings** – Inside each attached clause the proposed modifications must be **clearly marked** using the word‑processor’s revision mode. This visual cue lets the working‑group members see exactly what is being added, removed or altered [TS 21.900 §4.6.3].  

3. **Independence of concurrent CRs** – If several independent CRs target the **same part of the specification**, each CR **must not contain** the modifications proposed by the others. Any possible interaction must be resolved **before** the CRs are presented to the working group. This rule prevents contradictory changes from being merged inadvertently [TS 21.900 §4.6.3].  

4. **Stage‑3 files in the Forge repository** – When a CR proposes changes to **stage‑3 specification files** that are stored in the Forge repository (as defined in clause 5C), the modifications **must be documented in the Forge repository**. The CR cover page then includes a reference to a **Forge Merge‑Request**; the MR identifier is placed in the “*Other comments:*” field, and **excerpts of all affected stage‑3 files** showing the proposed changes are appended to the cover page [TS 21.900 §4.6.3].  

### Determining the owning work group from a CR

Each 3GPP specification is owned by a specific work group (e.g., RAN2, SA3, CT4). The **clause number** uniquely identifies the document and the work‑group responsible for it. By reading the list of clauses attached to a CR, a reviewer can map the clause to its work group using the **specification‑to‑work‑group matrix** (maintained in the 3GPP documentation catalogue). Consequently, the **CR routing** process can be automated:  

$$
\text{WorkGroup}(CR) = \bigcup_{i=1}^{N} \text{Owner}\bigl(\text{Clause}_i\bigr)
$$

where $N$ is the number of attached clauses, and $\text{Owner}(\cdot)$ returns the work group that maintains the clause.  

### Worked example

A telecom operator wishes to add a new optional feature to the **NR RRC** configuration. The engineering team prepares a CR with the following data:

| Item | Value |
|------|-------|
| Specification | TS 38.331 (RRC) |
| Latest major version | **38** (the most recent 38.x release) |
| Affected clause | **5.2.1** – “RRC Connection Reconfiguration” |
| Revision‑mode change | Insert a new IE “newFeatureSupported” with type **BOOLEAN** |
| Forge MR | MR #12345 (referenced in “Other comments”) |
| Excerpts attached | The full text of clause 5.2.1 with the new IE highlighted in revision mode |

From the clause number **5.2.1** the operator’s change manager consults the catalogue and sees that **TS 38.331** is owned by **RAN2**. Therefore the CR is automatically routed to the **RAN2** working group. Because the change touches a stage‑3 file, the MR reference and the excerpt are appended to the cover page, satisfying the Forge‑related requirement.  

### Common pitfalls and practical notes

| Pitfall | Why it matters | Remedy |
|---------|----------------|--------|
| **Omitting the clause list** | Reviewers cannot identify the responsible work group, leading to delays. | Always attach the exact clause numbers and ensure they belong to the latest major version. |
| **Using an outdated major version** | The change may be applied to an obsolete text, causing version drift. | Verify the current major version before filling the CR form. |
| **Mixing modifications from multiple independent CRs** | Duplicate or conflicting edits can corrupt the specification. | Keep each CR self‑contained; resolve interactions in a separate coordination meeting before submission. |
| **Failing to include the Forge MR reference for stage‑3 files** | The change will be rejected by the Forge review workflow. | Add the MR identifier to the “Other comments” field and attach the file excerpts. |
| **Neglecting revision‑mode markings** | Reviewers may miss the intended change, increasing the risk of misinterpretation. | Use the word‑processor’s revision mode consistently for every insertion, deletion, or move. |

By adhering strictly to the content rules defined in TS 21.900 §4.6.3, engineers can reliably determine the correct work group for any CR, streamline the approval process, and maintain the integrity of the 3GPP specification set.  

[TS 21.900 §4.6.3]

## 練習題

**1.** 當變更請求（CR）提出對已於 3GPP Forge 倉庫中以第 5C 條規範的 stage 3 規格檔案的修改時，應將提議的修改記錄於何處？

- A. 只在 CR 表格內說明
- B. 在 3GPP Forge 倉庫中
- C. 以電子郵件附件方式
- D. 發佈於 3GPP 官方網站

<details><summary>看答案</summary>

正解：B。依規範，對 stage 3 檔案的修改必須記錄於 Forge 倉庫。

</details>

**2.** 若 CR 影響 stage 3 規格檔案，CR 表單的封面頁必須包含哪項資訊？

- A. 完整的規格原文
- B. 參考的 Forge Merge‑Request
- C. 所有工作組的名單
- D. 會議主持人的簽名

<details><summary>看答案</summary>

正解：B。封面頁需要列出對應的 Forge Merge‑Request 作為參考。

</details>

**3.** CR 必須以何種方式標示受影響條款的提議修改？

- A. 手寫標註
- B. PDF 附件
- C. 使用文字處理器的「revision mode」
- D. 口頭說明

<details><summary>看答案</summary>

正解：C。規範要求使用文字處理器的修訂模式來清楚標示修改。

</details>

**4.** 若有多個獨立的 CR 同時針對同一規格部分提出變更，這些 CR 之間的內容應如何處理？

- A. 每個 CR 必須包含其他 CR 的所有提議修改
- B. 彼此不應包含對方的提議修改
- C. 必須合併為單一 CR
- D. 必須分別提交給不同的工作組

<details><summary>看答案</summary>

正解：B。規範規定，各獨立 CR 不得包含其他 CR 的提議修改。

</details>
