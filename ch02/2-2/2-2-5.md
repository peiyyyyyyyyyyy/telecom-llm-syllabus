# 2.2.5 ASN.1 與資訊元素

所屬：[2.2 規格文件的結構](../2-2.md)

## 正文

Abstract Syntax Notation One (ASN.1) is one of the computer languages that may be used to describe *information elements* – the structured data exchanged between network entities. In a 3GPP Technical Specification (TS) or Technical Report (TR), such language fragments appear alongside prose to give an exact, machine‑readable definition of a data structure. Because the same document also contains normative text, it is essential that any code fragment be visually and semantically separated from the surrounding narrative so that readers can instantly recognise the boundary between natural language and formal syntax.  

The 3GPP standard TS 21.801 explicitly permits the inclusion of code fragments such as ASN.1, GDMO, C, or C++ in a TS or TR, **provided they are clearly marked** and presented in the *PL* style [TS 21.801 §7].

### Marking Rules and the PL Style

The *PL* (Presentation Language) style is the prescribed formatting convention for all code excerpts. In practice this means:

* The fragment is enclosed in a dedicated block (often a shaded or boxed area) that is labelled with the language name, e.g. “**ASN.1**”.
* The block is set in a monospaced font, distinct from the surrounding proportional‑type paragraph text.
* A caption such as “**Code fragment**” or “**ASN.1 definition**” may be added, but the key requirement is that the fragment be *clearly marked as such*.

These visual cues satisfy the normative requirement that “Portions of code … can be included … but should be clearly marked as such” [TS 21.801 §7].

### Worked Example

Below is a simple illustration of how an ASN.1 snippet would be inserted into a 3GPP document following the PL style.

```
--- BEGIN ASN.1 CODE (PL style) ---
MyMessage ::= SEQUENCE {
    transactionId   INTEGER (0..65535),
    payload         OCTET STRING (SIZE (1..256))
}
--- END ASN.1 CODE ---
```

*Explanation*: The block is surrounded by a clear start/end delimiter and labelled “ASN.1 CODE”. The monospaced font distinguishes it from the narrative. Although the example does not explain the semantics of `MyMessage`, the reader can immediately identify the fragment as an ASN.1 definition, satisfying the marking rule.

### Why Marking Matters in Real Networks

When a network element implements a protocol defined in a TS, engineers often copy the ASN.1 definition directly into development tools (e.g., ASN.1 compilers) to generate encoding/decoding functions. If the code fragment is not clearly marked, there is a risk that:

1. **Human error** – a developer may misinterpret a prose description as a formal definition, leading to incompatible implementations.
2. **Tooling error** – automated documentation parsers may fail to extract the code, causing missing or outdated generated source files.

Both situations can compromise interoperability, which is the core purpose of 3GPP specifications.

### Common Mistakes and Practical Tips

| Mistake | Why it violates the rule | Remedy |
|---------|--------------------------|--------|
| Embedding ASN.1 inline with normal paragraphs without a distinct block. | The code is not *clearly marked*; readers cannot differentiate it from prose. | Use a separate PL‑style block, as shown in the example. |
| Using proportional fonts for the code fragment. | Violates the visual distinction required by the PL style. | Switch to a monospaced font (e.g., Courier New) for the block. |
| Omitting the language label (“ASN.1”) before the block. | The fragment is not explicitly identified, breaching the “clearly marked” requirement. | Prefix the block with a label such as “**ASN.1**”. |
| Including code that is not part of the normative specification (e.g., pseudo‑code). | May cause confusion about what is normative; the TS only permits *code fragments* that are meant to be used. | Ensure only official ASN.1 definitions appear, and annotate any illustrative pseudo‑code as non‑normative. |

A practical tip is to adopt a template for all code insertions: a boxed area, a language label, and monospaced text. Many document‑authoring tools (e.g., LaTeX with the `listings` package) provide built‑in support for the PL style, reducing the chance of accidental formatting errors.

### Summary

* ASN.1 is a permitted language for describing information elements in 3GPP TS/TR documents.
* The specification mandates that any such code fragment be **clearly marked** and presented in the **PL style**.
* Proper marking prevents misinterpretation by engineers and tooling, safeguarding the interoperability that 3GPP standards aim to guarantee.
* Common pitfalls include missing visual separation, wrong fonts, and absent language labels; these can be avoided with a consistent template.

By adhering to the concise rules in TS 21.801 §7, authors ensure that their specifications remain both human‑readable and machine‑processable, a cornerstone of reliable telecom system design.
