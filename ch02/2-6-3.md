# 2.6.3 找不到就說找不到

所屬：[2.6 引用規則](2-6.md)

## 內文

查核時應把「已證實的部分」和「現有證據尚未回答的部分」寫清楚。找不到可能是版本未確定、附件沒有取得、原始引文號有誤，或公開登錄只顯示摘要。工程師在填寫缺陷單、答覆規格疑問或清點技術文件時，可以據此標記這項結論所及的文件、版次及欄位，也可以記下需要交接查找的材料。下一位讀者能直接接續查同一個缺口。 [3GPP TR 21.900 V19.1.0](https://www.etsi.org/deliver/etsi_tr/121900_121999/121900/19.01.00_60/tr_121900v190100p.pdf) [ITU-T，3GPP-LS7 往返信函紀錄](https://www.itu.int/net/itu-t/ls/ls.aspx?isn=28296)

找資料時先把問題改寫成可查核的項目，例如「哪一版已收錄這份 CR」，或「聯絡函登錄有無標出回覆期限」。確認號碼及發文單位，再從官方規格入口、變更紀錄或會議附件查找。先看引文能否定位原件，再確認打開的是正式發布版、工作稿或登錄紀錄。交叉比對標題、日期、參照欄、版本和對應段落。對同號文件，還要核對文種、年份與修訂。若只取得摘要，先寫明摘要確認的欄位，再說目前無法據此核對的內容。若資料庫無對應項，保留查找的入口、關鍵字、查閱日期及涵蓋範圍。可詢問持有原件的人提供精確檔名、完整版本號或附件，也可從登錄中的前件與後件繼續查。待原件取得後，補上精確引註及更正結論，讓任何後續引用都能沿用同一份證據。 [3GPP TR 21.900 V19.1.0](https://www.etsi.org/deliver/etsi_tr/121900_121999/121900/19.01.00_60/tr_121900v190100p.pdf) [3GPP Portal，TS 38.215](https://portal.3gpp.org/desktopmodules/Specifications/SpecificationDetails.aspx?specificationId=3217) [ITU-T，3GPP-LS7 往返信函紀錄](https://www.itu.int/net/itu-t/ls/ls.aspx?isn=28296)

例子可看 ITU-T 的 3GPP-LS7 公開登錄。它列出題名、文件號、收件資訊，以及 In response to 所指的 SG15-LS348。讀者可以依此確認它是一份回函，並循參照欄追前件。若待查的是回覆期限，該登錄的期限欄顯示空缺符號，可紀錄「在 ITU-T 的 3GPP-LS7 公開登錄中，未見列出回覆期限」。若必須確定郵件或附件是否有其他約定，要再找原始附件或相應會議文件，並標明是否已查到全文。這段敘述給了來源、欄位與證據上限。即使後來取得同一議題的其他文件，也要先核對該文件的識別和回函關係，再更新欄位判讀。 [ITU-T，3GPP-LS7 往返信函紀錄](https://www.itu.int/net/itu-t/ls/ls.aspx?isn=28296) [ITU-T，SG15 聯絡函登錄](https://www.itu.int/net/itu-t/ls/ols.aspx?after=2021-09-03&before=2022-01-06&from=8275)

常見混淆包括把查無結果解讀成文件從未存在、把登錄缺項解讀成當事方從未提出該資訊，以及用相近版次中的條款補齊原本欠缺的引文。前兩種應限定查核範圍，第三種應為相近版本另立引註。遇到受到存取限制的附件，可說明已查到公開索引、附件尚未核讀，並具體列出還要核對的內容。這樣即使先回答部分問題，也不會讓後手誤以為整份材料都已確認。 [3GPP TR 21.900 V19.1.0](https://www.etsi.org/deliver/etsi_tr/121900_121999/121900/19.01.00_60/tr_121900v190100p.pdf) [ITU-T，3GPP-LS7 往返信函紀錄](https://www.itu.int/net/itu-t/ls/ls.aspx?isn=28296)

本節以 2.6.1 的完整引註作為查到後要填補的資訊。查國際組織的往返文件時，可用 2.4.6 的收件方與回覆欄定位前件。若先找到的只是檔名，依 2.6.4 初核版本，並在能核對封面後再引用正文。 [3GPP TR 21.900 V19.1.0](https://www.etsi.org/deliver/etsi_tr/121900_121999/121900/19.01.00_60/tr_121900v190100p.pdf) [ITU-T，3GPP-LS7 往返信函紀錄](https://www.itu.int/net/itu-t/ls/ls.aspx?isn=28296)

> 4.3.2 Slots
>
> 「OFDM symbols in a slot in a downlink or uplink frame can be classified as 'downlink', 'flexible', or 'uplink'. Signaling of slot formats is described in clause 11.1 of [5, TS 38.213].」

**356.** 依這段資料，UE 在上行訊框（uplink frame）的一個 slot 裡，可以在哪幾類符元發送？

<details><summary>看答案</summary>

**答案**　只能在 'uplink' 或 'flexible' 符元發送。依據是資料的第三段引句。

**詳解**　資料寫「In a slot in an uplink frame, the UE shall only transmit in 'uplink' or 'flexible' symbols.」用的是 shall only，所以 'downlink' 符元不在可發送之列。資料已有明確答案，直接回答並指出是哪一句即可。
出處：3GPP TS 38.211 V18.10.0 clause 4.3.2；https://www.3gpp.org/ftp/Specs/archive/38_series/38.211/38211-ia0.zip

**357.** 不支援全雙工的 UE，在同一個 cell 收完最後一個下行符元後，最快要隔多久才能開始上行發送？請給出時間長度。

<details><summary>看答案</summary>

**答案**　能確定的部分：這類 UE 不會被期待在「最後一個收到的下行符元結束後 N_Rx-Tx × T_c」之前於同一 cell 發送上行，也就是至少要隔 N_Rx-Tx × T_c（資料第四段引句）。不能確定的部分：這段時間實際是多長。N_Rx-Tx 的值在 Table 4.3.2-3，T_c 的定義在 clause 4.1，兩者資料都沒有摘錄，所以算不出秒數。要取得 TS 38.211 V18.10.0 的 Table 4.3.2-3（依頻率範圍取值）和 clause 4.1 的 T_c 才能換算：https://www.3gpp.org/ftp/Specs/archive/38_series/38.211/

**詳解**　資料給了關係式，沒有給數值。引句明說「where NRx-Tx is given by Table 4.3.2-3」，而資料末尾註明沒有包含這張表；T_c 是整份規格的基本時間單位，定義在 clause 4.1，也不在摘錄裡。缺兩個量就不能給出時間長度，所以回答要停在「N_Rx-Tx × T_c」，並說清楚缺的是哪張表、哪一條。
出處：3GPP TS 38.211 V18.10.0 clause 4.3.2；https://www.3gpp.org/ftp/Specs/archive/38_series/38.211/38211-ia0.zip

</details>

**359.** 資料提到 slot format。slot format 0 的 14 個符元各是 downlink、flexible 還是 uplink？

<details><summary>看答案</summary>

**答案**　能確定的部分：MDBV 只適用於 Delay-critical GBR resource type（資料 5.7.3.2 第二段最後一句「the MDBV parameter applies only to the Delay-critical GBR resource type」）。不能確定的部分：預設值。資料沒有任何 MDBV 的數值，也沒有摘錄 MDBV 的定義條文和 5QI 對照表。缺的是 TS 23.501 clause 5.7.3.7「Maximum Data Burst Volume」與 Table 5.7.4-1 中各 Delay-critical GBR 5QI 的 Default Maximum Data Burst Volume 欄；而且預設值是每個 5QI 各自一個，要先確定問的是哪個 5QI。請取得 TS 23.501 V18.12.0 查該表：https://www.3gpp.org/ftp/Specs/archive/23_series/23.501/

**364.** 資料說 GBR 與 Delay-critical GBR 兩種 resource type 的 PDB 定義不同。兩者的 PDB 定義差在哪裡？

**365.** 依這段資料，一條 GBR QoS Flow 的 GFBR 應該設成多少？GFBR 和 MFBR 的關係是什麼？

<details><summary>看答案</summary>

**答案**　資料中沒有這項資訊。資料只在 5.7.3.2 第一段提到 resource type 決定是否永久配置與 GFBR 值相關的專用網路資源，沒有給 GFBR 的數值，也沒有提到 MFBR。缺的有兩樣：一是 GFBR、MFBR 的定義條文，在 TS 23.501 clause 5.7.2.5「Flow Bit Rates」；二是這條 QoS Flow 實際要設的位元率，這是個別網路的設定值，資料裡沒有，要問負責核心網路 QoS 政策設定的人員。規格原文下載：https://www.3gpp.org/ftp/Specs/archive/23_series/23.501/
