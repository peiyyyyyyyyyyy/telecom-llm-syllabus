# 3.7.2 信源編碼：霍夫曼、算術編碼

所屬：[3.7 資訊理論與編碼](3-7.md)

## 內文

#### 為什麼要學

信源編碼（source coding）的工作是把資料裡的冗餘拿掉，用比較少的位元表示同樣的內容。行動網路的空中介面資源昂貴，語音、影像編碼器，以及封包標頭壓縮，都要先把要送的位元數壓下來，再交給通道編碼加上保護用的冗餘。霍夫曼編碼（Huffman coding）與算術編碼（arithmetic coding）是兩種最基本的無失真熵編碼方法，許多影音壓縮標準的最後一級都採用這類技術。學這一節的目的，是能由符號機率算出平均碼長，並和熵比較，判斷一個編碼離理論極限還有多遠。

#### 定義與符號

| 符號 | 意思 | 單位 |
|---|---|---|
| $p_i$ | 第 $i$ 個符號出現的機率 | 無 |
| $l_i$ | 第 $i$ 個符號的碼字長度 | bit |
| $\bar{L}$ | 平均碼長，$\sum p_i l_i$ | bit／符號 |
| $H$ | 信源的熵 | bit／符號 |
| $\eta$ | 編碼效率，$H/\bar{L}$ | 無（或 %） |
| $[\text{low},\ \text{high})$ | 算術編碼目前的區間 | 無 |

#### 公式與推導

**前綴條件與 Kraft 不等式。** 可變長度碼要能不加分隔符號就唯一解出來，最常用的做法是讓任何一個碼字都不是另一個碼字的開頭，稱為前綴碼（prefix code）。二元前綴碼的碼長必須滿足 Kraft 不等式：

$$\sum_i 2^{-l_i}\le 1$$

反過來，只要一組碼長滿足這個不等式，就一定找得到對應的前綴碼。

**平均碼長的界限。** 對無記憶信源逐符號編碼時，任何唯一可解的碼都有 $\bar{L}\ge H$；而最佳前綴碼滿足

$$H\le \bar{L} < H+1$$

編碼效率定義為 $\eta = H/\bar{L}$，最大為 1。只有當每個機率都是 2 的負整數次方時，逐符號編碼才能做到 $\eta=1$。

**霍夫曼編碼。** 做法是：把機率最小的兩個符號合併成一個新節點，機率相加；重複這個動作直到只剩一個節點；再由根往下，每個分支標上 0 或 1，葉節點的路徑就是碼字。在「符號機率已知、逐符號、整數碼長」的條件下，霍夫曼碼的平均碼長最短。合併時若有機率相同的節點，選法不同會得到不同的樹，但平均碼長相同。

**算術編碼。** 算術編碼不替單一符號指定碼字，而是把整段訊息對應到 $[0,1)$ 裡的一個小區間。先依累積機率把 $[0,1)$ 切成每個符號的子區間；每讀進一個符號，就把目前區間依同樣比例再切一次，留下該符號對應的那一段：

$$\text{low}' = \text{low} + (\text{high}-\text{low})\,F_{\text{low}}(s),\qquad \text{high}' = \text{low} + (\text{high}-\text{low})\,F_{\text{high}}(s)$$

其中 $F_{\text{low}}(s)$、$F_{\text{high}}(s)$ 是符號 $s$ 的累積機率下界與上界。最後區間的寬度等於整段訊息的機率 $P$，輸出一個落在區間內的二進位小數即可；所需位元數不超過 $\lceil \log_2(1/P)\rceil + 1$。因為不必把每個符號的碼長取成整數，訊息夠長時每符號的平均位元數可以逼近熵。

#### 算例

**算例 1（霍夫曼編碼）** 已知五個符號的機率：A 0.35、B 0.25、C 0.20、D 0.12、E 0.08。

建樹：
1. 最小的兩個是 D（0.12）與 E（0.08），合併為 DE（0.20）。
2. 剩下 0.35、0.25、0.20、0.20，最小的兩個是 C 與 DE，合併為 CDE（0.40）。
3. 剩下 0.40、0.35、0.25，最小的兩個是 A 與 B，合併為 AB（0.60）。
4. AB（0.60）與 CDE（0.40）合併為根（1.00）。

指定位元（上分支 0、下分支 1）：AB 為 0、CDE 為 1；A＝00、B＝01；C＝10、DE＝11；D＝110、E＝111。

| 符號 | 機率 | 碼字 | 碼長 |
|---|---|---|---|
| A | 0.35 | 00 | 2 |
| B | 0.25 | 01 | 2 |
| C | 0.20 | 10 | 2 |
| D | 0.12 | 110 | 3 |
| E | 0.08 | 111 | 3 |

平均碼長：$\bar{L} = 2\times(0.35+0.25+0.20)+3\times(0.12+0.08) = 1.60+0.60 = 2.20$ bit／符號。

熵：$H = 0.5301+0.5000+0.4644+0.3671+0.2915 = 2.1531$ bit／符號。

效率：$\eta = 2.1531/2.20 = 0.9787$，約 97.9%。

檢查：沒有任何碼字是另一個碼字的開頭（00、01、10 都不是 110、111 的開頭），滿足前綴條件；Kraft 和為 $3\times 2^{-2}+2\times 2^{-3}=1$。$H\le\bar{L}<H+1$ 也成立。若用固定長度碼，五個符號需要 3 bit，霍夫曼碼省了約 27%。

**算例 2（算術編碼的區間）** 已知三個符號 A、B、C 的機率為 0.5、0.3、0.2，子區間依序為 A：$[0,\,0.5)$、B：$[0.5,\,0.8)$、C：$[0.8,\,1)$。對序列「B A C」編碼。

1. 讀 B：區間變成 $[0.5,\ 0.8)$，寬度 0.3。
2. 讀 A：取目前區間的前 50%，$[0.5,\ 0.5+0.3\times 0.5) = [0.5,\ 0.65)$，寬度 0.15。
3. 讀 C：取目前區間的 80%～100%，$[0.5+0.15\times 0.8,\ 0.65) = [0.62,\ 0.65)$，寬度 0.03。

檢查：最後寬度 $0.03 = 0.3\times 0.5\times 0.2$，正是這段訊息的機率。$\log_2(1/0.03)=5.06$，所以最多 $\lceil 5.06\rceil+1 = 7$ bit 就能表示這段訊息。二進位小數 $0.101_2 = 0.625$ 落在 $[0.62,\ 0.65)$ 內，是區間裡的一個點；解碼端依同樣的切法，由這個數值所在的子區間依序判出 B、A、C（解碼端還需要知道訊息長度或結束符號）。

#### 常見錯誤

- 把平均碼長算成碼長的算術平均（本例 $(2+2+2+3+3)/5=2.4$），沒有用機率加權。
- 霍夫曼建樹時沒有每次都重新排序，把剛合併出來的節點固定放在最後，結果合併到的不是最小的兩個。
- 效率寫成 $\bar{L}/H$，得到大於 1 的數字。效率是 $H/\bar{L}$，不會超過 1。
- 算術編碼更新區間時，用原始的 $[0,1)$ 比例直接取，而沒有乘上目前區間的寬度。

#### 和其他小節的關係

平均碼長的下限來自 3.7.1 的熵。信源編碼去掉冗餘之後，3.7.3 到 3.7.6 的通道編碼再加上有結構的冗餘來對抗錯誤，兩者的方向相反。壓縮後的位元率是 3.4 訊務量估算的輸入之一。

#### 單題：Huffman code average length

**3.7.2G001**　A memoryless source emits five symbols with probabilities 0.4, 0.2, 0.2, 0.1 and 0.1. A binary Huffman code is designed for it. Determine the average codeword length in bits per symbol, rounded to two decimal places. (Ties in the merging may be broken arbitrarily; the average length does not depend on the choice.)

<details><summary>看答案</summary>

**答案**　2.20

**詳解**　Merges: $0.1 + 0.1 = 0.2$; then $0.2 + 0.2 = 0.4$; then $0.2 + 0.4 = 0.6$; then $0.4 + 0.6 = 1.0$.
One resulting set of lengths is (1, 2, 3, 4, 4) for (0.4, 0.2, 0.2, 0.1, 0.1):
$\bar L = 0.4 \times 1 + 0.2 \times 2 + 0.2 \times 3 + 0.1 \times 4 + 0.1 \times 4 = 0.4 + 0.4 + 0.6 + 0.4 + 0.4 = 2.20$ bit/symbol.
Check: $\bar L$ equals the sum of the merged-node probabilities, $0.2 + 0.4 + 0.6 + 1.0 = 2.2$.
\boxed{2.20}

**3.7.2G006**　A source emits five symbols with probabilities 0.45, 0.25, 0.15, 0.10 and 0.05. Determine the coding efficiency $\eta = H/\bar L$ of a binary Huffman code for this source, in percent, using base-2 logarithms, rounded to two decimal places.

<details><summary>看答案</summary>

**答案**　98.86

**詳解**　Huffman merges: $0.05 + 0.10 = 0.15$; $0.15 + 0.15 = 0.30$; $0.25 + 0.30 = 0.55$; $0.45 + 0.55 = 1.00$; $\bar L = 0.15 + 0.30 + 0.55 + 1.00 = 2.00$ bit/symbol (lengths 1, 2, 3, 4, 4).
$H = 0.5184 + 0.5000 + 0.4105 + 0.3322 + 0.2161 = 1.97724$ bit/symbol.
$\eta = 1.97724/2.00 = 0.98862 = 98.86\,\%$.

**3.7.2S003**　Under what conditions is the Huffman code guaranteed to have the smallest average length of all codes the probe could use, and which kind of coder could still do better?

<details><summary>看答案</summary>

**答案**　It is optimal among uniquely decodable codes that encode one message type at a time with an integer number of bits, when the probabilities are known and the messages are independent. Coding blocks of messages, arithmetic coding, or exploiting dependence between messages can do better.

**詳解**　Huffman's construction minimises $\sum p_i l_i$ over all integer length sets satisfying the Kraft inequality. **答案**　Step 3 is wrong: the variance is $\sum p_i l_i^2 - \bar L^2$ (the second moment minus the squared mean), not the second moment itself. Correct: $5.0 - 2.2^2 = 5.0 - 4.84 = 0.16$ bit².

**詳解**　$\mathrm{Var}(l) = E[l^2] - (E[l])^2 = 5.0 - 4.84 = 0.16$ bit², which matches the direct sum $\sum p_i (l_i - 2.2)^2$.

**出處**　Cover & Thomas, Elements of Information Theory; definition of variance

</details>

#### 情境題：Coding efficiency and the entropy bound

**Scenario | Frame-type indicator of a voice service**

Each voice frame on a VoIP bearer carries a frame-type indicator with four values: speech (probability 0.55), comfort-noise update (0.25), no data (0.15) and other (0.05). The indicator is to be coded with a binary Huffman code; frame types are treated as independent.

**3.7.2S011**　What is the entropy of the frame-type indicator? Give the answer in bits (base-2 logarithm), rounded to four decimal places.

<details><summary>看答案</summary>

**答案**　1.6010 bit

**詳解**　Terms $-p\log_2 p$: $0.55 \to 0.47437$, $0.25 \to 0.50000$, $0.15 \to 0.41054$, $0.05 \to 0.21610$.
$H = 1.60101$ bit $\approx 1.6010$ bit.

**出處**　Cover & Thomas, Elements of Information Theory (entropy)

</details>

**3.7.2S012**　What is the coding efficiency $H/\bar L$ of the Huffman code? Give the answer in percent, rounded to two decimal places.

<details><summary>看答案</summary>

**答案**　97.03 %

**詳解**　Merges: $0.05 + 0.15 = 0.20$; $0.20 + 0.25 = 0.45$; $0.45 + 0.55 = 1.00$; $\bar L = 0.20 + 0.45 + 1.00 = 1.65$ bit (lengths 1, 2, 3, 3).
$\eta = 1.60101/1.65 = 0.97031 = 97.03\,\%$.

**出處**　Cover & Thomas, Elements of Information Theory (Huffman codes)

</details>

**3.7.2S013**　Why does the Huffman code not reach 100 % efficiency for this indicator, and what property of the probabilities would allow it?

<details><summary>看答案</summary>

**答案**　Because codeword lengths must be integers, and $-\log_2 p_i$ is not an integer for 0.55, 0.15 and 0.05. Efficiency 100 % is possible only if every probability is a negative integer power of 2 (a dyadic distribution).

**詳解**　$\bar L = H$ requires $l_i = -\log_2 p_i$ for all $i$. For example, $-\log_2 0.55 = 0.86$ bit, but the shortest codeword is 1 bit. With dyadic probabilities (1/2, 1/4, 1/8, ...) the ideal lengths are integers and Huffman achieves them exactly.

**出處**　Cover & Thomas, Elements of Information Theory (optimal codes; dyadic distributions)

</details>

**3.7.2S014**　Check whether the Huffman average length satisfies the source-coding bounds. Could any symbol-by-symbol prefix code for this indicator have an average length of 1.55 bit?

<details><summary>看答案</summary>

**答案**　$H = 1.6010 \le \bar L = 1.65 < H + 1 = 2.6010$, so the bounds hold. No uniquely decodable code can have $\bar L = 1.55$ bit, because that is below the entropy 1.6010 bit.

**詳解**　For any uniquely decodable code $\bar L \ge H$; for an optimal code $\bar L < H + 1$. A claimed average below $H$ is impossible regardless of construction; it would mean the code violates the Kraft–McMillan inequality.

**出處**　Cover & Thomas, Elements of Information Theory (Kraft–McMillan inequality; bounds on optimal code length)

</details>

**3.7.2S015**　A designer reports the efficiency:
1. $H = 1.6010$ bit.
2. $\bar L = 1.65$ bit.
3. Efficiency $= \bar L/H = 1.65/1.6010 = 103.06\,\%$.

Which step is wrong, and what is the correct result?

<details><summary>看答案</summary>

**答案**　Step 3 is wrong: efficiency is $H/\bar L$, which can never exceed 100 %. Correct: $1.6010/1.65 = 97.03\,\%$.

**詳解**　$\eta = 1.60101/1.65 = 0.97031 = 97.03\,\%$. A value above 100 % should be recognised as impossible, because $\bar L \ge H$.

**出處**　Cover & Thomas, Elements of Information Theory (coding efficiency)

</details>

**Scenario | Alarm code designed on dyadic statistics**

A base-station alarm source was characterised with probabilities 0.5, 0.25, 0.125 and 0.125 for its four alarm classes, and a prefix code with lengths 1, 2, 3 and 3 was deployed. A later traffic study gives updated probabilities 0.45, 0.30, 0.15 and 0.10 for the same classes in the same order. The deployed code is kept.

**3.7.2S016**　For the original statistics, what is the average codeword length of the deployed code? Give the answer in bits per alarm, rounded to three decimal places.

<details><summary>看答案</summary>

**答案**　1.750 bit per alarm

**詳解**　$\bar L = 0.5 \times 1 + 0.25 \times 2 + 0.125 \times 3 + 0.125 \times 3 = 0.5 + 0.5 + 0.375 + 0.375 = 1.750$ bit. This equals the entropy (1.75 bit), so the efficiency is 100 %.

**3.7.2S017**　With the updated probabilities, what is the efficiency $H/\bar L$ of the deployed code? Give the answer in percent (base-2 logarithm), rounded to two decimal places.

<details><summary>看答案</summary>

**答案**　99.01 %

**詳解**　$\bar L = 0.45 \times 1 + 0.30 \times 2 + 0.15 \times 3 + 0.10 \times 3 = 0.45 + 0.60 + 0.45 + 0.30 = 1.80$ bit.
$H = 0.51840 + 0.52109 + 0.41054 + 0.33219 = 1.78223$ bit.
$\eta = 1.78223/1.80 = 0.99013 = 99.01\,\%$.

**出處**　Cover & Thomas, Elements of Information Theory (coding efficiency)

</details>

**3.7.2S018**　Why does the deployed code achieve exactly 100 % efficiency on the original statistics?

<details><summary>看答案</summary>

**答案**　Because each original probability is a power of 1/2 and each codeword length equals $-\log_2 p_i$ (1, 2, 3, 3), so $\bar L = \sum p_i(-\log_2 p_i) = H$ exactly.

**詳解**　$-\log_2 0.5 = 1$, $-\log_2 0.25 = 2$, $-\log_2 0.125 = 3$. When lengths match the ideal values, every term of $\bar L$ equals the corresponding term of $H$, and the Kraft sum is exactly 1.

**出處**　Cover & Thomas, Elements of Information Theory (dyadic distributions)

**3.7.2S019**　Would rerunning the Huffman algorithm on the updated probabilities reduce the average length below 1.80 bit?

**答案**　No. Huffman on (0.45, 0.30, 0.15, 0.10) merges 0.10 + 0.15 = 0.25, then 0.25 + 0.30 = 0.55, then 0.45 + 0.55, giving lengths 1, 2, 3, 3, the same as the deployed code, so 1.80 bit is already optimal.

**詳解**　Sum of merged nodes: $0.25 + 0.55 + 1.00 = 1.80$ bit. The ranking of the probabilities has not changed in a way that alters the tree, so redesign brings nothing; only block coding or arithmetic coding could approach $H = 1.7822$ bit more closely.

**出處**　Huffman, Proc. IRE, 1952

**3.7.2S020**　An analyst checks the deployed code after the traffic study:

#### 情境題：Prefix codes and the Kraft inequality

**Scenario | Decoding a prefix code on a control link**

A controller sends four commands A, B, C, D with probabilities 0.50, 0.25, 0.15 and 0.10, coded as A = 0, B = 10, C = 110, D = 111. Codewords are sent back to back without separators. One received bit string is 0110100111.

**3.7.2S026**　What is the average codeword length of this code? Give the answer in bits per command, rounded to two decimal places.

<details><summary>看答案</summary>

**答案**　1.75 bit per command

**詳解**　$\bar L = 0.50 \times 1 + 0.25 \times 2 + 0.15 \times 3 + 0.10 \times 3 = 0.50 + 0.50 + 0.45 + 0.30 = 1.75$ bit.

**出處**　Cover & Thomas, Elements of Information Theory (expected code length)

</details>

**3.7.2S027**　Decode the bit string 0110100111. How many commands does it contain, and which are they?

<details><summary>看答案</summary>

**答案**　Five commands: A C B A D.

**詳解**　Read from the left and stop as soon as a codeword is complete: 0 → A; 110 → C; 10 → B; 0 → A; 111 → D. Total bits $1 + 3 + 2 + 1 + 3 = 10$, matching the string length.

**出處**　Cover & Thomas, Elements of Information Theory (instantaneous codes)

</details>

**3.7.2S028**　Why can the receiver split the bit string into codewords without any separator, and why can it decide each command as soon as its last bit arrives?

<details><summary>看答案</summary>

**答案**　Because the code is a prefix code: no codeword is the beginning of another, so the first complete codeword found while reading is the only possible one. Such codes are instantaneous: no look-ahead is needed.

**詳解**　0 is not a prefix of 10, 110 or 111; 10 is not a prefix of 110 or 111; 110 and 111 differ in the last bit. Walking down the code tree from the root, reaching a leaf identifies the command immediately, and the next bit starts at the root again.

**出處**　Cover & Thomas, Elements of Information Theory (prefix / instantaneous codes)

</details>

**3.7.2S029**　A colleague proposes the reversed codewords A = 0, B = 01, C = 011, D = 111 (same lengths). Is this code uniquely decodable, and is it instantaneous?

<details><summary>看答案</summary>

**答案**　It is uniquely decodable (it is a suffix code, decodable from the end of the string), but not instantaneous: 0 is a prefix of 01 and 011, so the receiver must look ahead before deciding.

**詳解**　Reversing every codeword of a prefix code gives a suffix code with the same Kraft sum and average length (1.75 bit). It can be decoded uniquely by reading backwards, but a forward decoder that has received "0" cannot yet tell whether A, B or C was sent, which adds delay and buffering.

**出處**　Cover & Thomas, Elements of Information Theory (uniquely decodable vs instantaneous codes)

</details>

**3.7.2S030**　An engineer studies the effect of one bit error on the string 0110100111:
1. Flip the first bit: 1110100111.
2. Parse: 111 | 0 | 10 | 0 | 111 = D A B A D.
3. Compared with the original A C B A D, only the first command is wrong, so one bit error corrupts exactly one command.

Which step is wrong, and what is the correct result?

<details><summary>看答案</summary>

**答案**　Step 3 is wrong: comparing position by position, D A B A D differs from A C B A D in the first two commands (D instead of A, A instead of C). The error shifted the codeword boundaries, so two commands are corrupted before the decoder resynchronises.

**詳解**　Original boundaries: 0 | 110 | 10 | 0 | 111. Corrupted: 111 | 0 | 10 | 0 | 111. The first two parses differ; from bit 5 onward the boundaries coincide again. In variable-length codes a single bit error can affect several codewords (and can even change the number of decoded symbols).

#### 情境題：Coding of extended (block) sources

**Scenario | Binary motion-detector stream**

A motion detector reports one bit per second: 1 (motion) with probability 0.05 and 0 otherwise, independently. The bits are sent over a narrowband link, and the designer compares sending them uncoded with Huffman coding of blocks of 2 bits.

**3.7.2S031**　What is the entropy of the detector output? Give the answer in bits per source bit (base-2 logarithm), rounded to four decimal places.

<details><summary>看答案</summary>

**答案**　0.2864 bit per source bit

**3.7.2S032**　With Huffman coding of 2-bit blocks, what is the average number of code bits per source bit? Round to three decimal places.

<details><summary>看答案</summary>

**答案**　0.574 code bit per source bit

**詳解**　Block probabilities: 00 → 0.9025, 01 → 0.0475, 10 → 0.0475, 11 → 0.0025.

**3.7.2S033**　Why does Huffman coding of single detector bits give no compression at all?

<details><summary>看答案</summary>

**答案**　With a binary alphabet each symbol needs at least a 1-bit codeword, so the Huffman code is just 0 and 1 and $\bar L = 1$ bit, no matter how skewed the probabilities are; the efficiency is only 28.6 %.

**詳解**　Codeword lengths are integers $\ge 1$. For two symbols the only optimal code is one bit each. The gap $\bar L - H = 1 - 0.2864 = 0.7136$ bit can be reduced only by grouping bits into blocks (or by arithmetic or run-length coding).

**3.7.2S034**　What happens to the code bits per source bit as the block length $n$ increases, and what limits it?

<details><summary>看答案</summary>

**答案**　It decreases toward the entropy, 0.2864 bit, because $H \le \bar L_n/n < H + 1/n$; for example 3-bit blocks give 0.433 bit per source bit. The cost is a codebook of $2^n$ entries and $n$ seconds of delay before a block can be coded.

**詳解**　Applying the single-symbol bound to the block source gives $nH \le \bar L_n < nH + 1$; dividing by $n$ gives the stated bound. With $n = 3$, Huffman on the eight block probabilities gives $\bar L_3 = 1.29975$ bit, i.e. 0.43325 bit per source bit. The codebook size grows exponentially and the coding delay linearly with $n$.

<details><summary>看答案</summary>

**3.7.2S043**　Why is the width of the final interval equal to the probability of the message, and why does that link the code length to the self-information?

<details><summary>看答案</summary>

**答案**　Each step multiplies the width by the probability of the coded symbol, so after the message the width is the product of the symbol probabilities, i.e. the message probability $P$. Identifying a point in an interval of width $P$ needs about $\log_2(1/P)$ bits, which is the self-information of the message.

**詳解**　$\text{width}' = \text{width} \times p(s)$ at every step. A binary fraction with $k$ bits locates a point to within $2^{-k}$, so roughly $k \approx \log_2(1/P)$ bits (plus at most 2) suffice. On average over messages, $E[\log_2(1/P)] = nH$ for $n$ independent symbols.

**3.7.2S044**　For this source a Huffman code for single trend indications averages 1.3 bit per symbol while the entropy is 1.157 bit. Why can arithmetic coding approach 1.157 bit per symbol on long messages when the Huffman code cannot?

<details><summary>看答案</summary>

**答案**　Huffman must give each symbol an integer number of bits (at least 1 bit for N, whose ideal length is only 0.515 bit). Arithmetic coding codes the whole message as one number, so fractional bit costs accumulate and the overhead is at most about 2 bits per message, not per symbol.

**詳解**　Huffman lengths (1, 2, 2) give $\bar L = 0.7 + 0.4 + 0.2 = 1.3$ bit. With arithmetic coding the message cost is about $\sum \log_2(1/p_i) + 2$ bits; per symbol this tends to $H = 1.157$ bit as the message grows.

#### 情境題：Source coding in a transmission chain

**Scenario | Telemetry over a coded QPSK link**

A telemetry unit produces 4000 independent symbols per second with probabilities 0.4, 0.3, 0.2 and 0.1. The symbols are Huffman-coded; the resulting bits are protected by a rate-2/3 channel code and transmitted with QPSK (2 coded bits per modulation symbol).

**3.7.2S056**　What modulation symbol rate is needed on average? Give the answer in symbols per second, rounded to the nearest integer.

<details><summary>看答案</summary>

**答案**　5700 symbol/s

**詳解**　Huffman merges: $0.1 + 0.2 = 0.3$; $0.3 + 0.3 = 0.6$; $0.4 + 0.6 = 1.0$; $\bar L = 0.3 + 0.6 + 1.0 = 1.9$ bit/symbol (lengths 1, 2, 3, 3).

**3.7.2S057**　Why are variable-length (Huffman) coded bits especially sensitive to residual bit errors after channel decoding?

<details><summary>看答案</summary>

**答案**　A single residual bit error can shift the codeword boundaries, so the decoder mis-parses several following symbols (and may even output a different number of symbols) until it happens to resynchronise; with fixed-length codes an error stays inside one symbol.

**詳解**　The decoder finds codeword boundaries only from the bits themselves. Corrupting one bit can make a long codeword look like a short one or vice versa, and every later boundary may move. This is why compressed data is protected by strong channel codes and CRCs, and why some codecs add resynchronisation markers.

**出處**　Cover & Thomas, Elements of Information Theory (prefix codes); error propagation in variable-length codes

</details>

**3.7.2S058**　The source coder removes redundancy and the channel coder then adds redundancy. Why not skip both and rely on the natural redundancy of the source?

<details><summary>看答案</summary>

**答案**　The natural redundancy is not structured for error correction, and its amount depends on the source statistics. Removing it and adding designed redundancy lets the channel code be matched to the channel; by Shannon's separation theorem this is optimal for long blocks.

**詳解**　The source redundancy (here $2 - 1.846 = 0.154$ bit per symbol against a 2-bit fixed code) is spread unevenly and is not designed to correct errors. A channel code adds redundancy with a known minimum distance or decoding threshold. The separation theorem states that, asymptotically, separate source and channel coding loses nothing.

**出處**　Shannon, "A Mathematical Theory of Communication," 1948 (source–channel separation); Cover & Thomas, Elements of Information Theory

</details>

**3.7.2S059**　A planner computes the channel bit rate:
1. Huffman output: $4000 \times 1.9 = 7600$ bit/s.
2. After the rate-2/3 channel code: $7600 \times 2/3 = 5066.7$ bit/s.
3. QPSK symbol rate: $5066.7/2 = 2533$ symbol/s.

Which step is wrong, and what is the correct result?

<details><summary>看答案</summary>

**答案**　Step 2 is wrong: a rate-2/3 code outputs 3 coded bits for every 2 information bits, so the bit rate must be divided by 2/3 (multiplied by 1.5). Correct: 11400 bit/s, giving 5700 QPSK symbols per second.

**詳解**　$7600/(2/3) = 11400$ bit/s; $11400/2 = 5700$ symbol/s.

**出處**　Proakis & Salehi, Digital Communications (code rate)

</details>

**3.7.2S060**　Another planner computes:
1. Huffman output: 7600 bit/s.
2. After the channel code: $7600 \times 1.5 = 11400$ bit/s.
3. QPSK carries 4 bits per symbol: $11400/4 = 2850$ symbol/s.

Which step is wrong, and what is the correct result?

<details><summary>看答案</summary>

**答案**　Step 3 is wrong: QPSK has 4 constellation points and therefore carries $\log_2 4 = 2$ bits per symbol, not 4. Correct: $11400/2 = 5700$ symbol/s.

**詳解**　Bits per symbol $= \log_2 M = \log_2 4 = 2$. $11400/2 = 5700$ symbol/s.

**出處**　Proakis & Salehi, Digital Communications (M-ary modulation)

**Scenario | Compressing a highly skewed log stream**

A network element writes one log code per event: "OK" with probability 0.90, and three warning codes with probabilities 0.05, 0.03 and 0.02. Codes are independent. The operator considers a binary Huffman code for single codes.

**3.7.2S061**　What is the efficiency $H/\bar L$ of the Huffman code? Give the answer in percent (base-2 logarithm), rounded to two decimal places.

<details><summary>看答案</summary>

**答案**　53.70 %

**詳解**　Merges: $0.02 + 0.03 = 0.05$; $0.05 + 0.05 = 0.10$; $0.10 + 0.90 = 1.00$; $\bar L = 0.05 + 0.10 + 1.00 = 1.15$ bit (lengths 1, 2, 3, 3).
$H = 0.13682 + 0.21610 + 0.15177 + 0.11288 = 0.61754$ bit.
$\eta = 0.61754/1.15 = 0.53699 = 53.70\,\%$.

**出處**　Cover & Thomas, Elements of Information Theory (Huffman codes)

</details>

**3.7.2S063**　Name two ways to get much closer to the entropy for this stream, and why they help.

<details><summary>看答案</summary>

**答案**　(1) Arithmetic coding, which spends about 0.152 bit on each "OK" instead of a whole bit; (2) coding runs of "OK" (run-length coding) or blocks of several codes with Huffman, so the probability mass of long "OK" runs is coded with a single codeword.

**詳解**　Both approaches remove the 1-bit-per-symbol floor. Arithmetic coding approaches $H = 0.618$ bit per event on long messages; block or run-length coding spreads one codeword over many events, with $\bar L_n/n < H + 1/n$ for blocks of $n$ events.

**出處**　Cover & Thomas, Elements of Information Theory (arithmetic coding; extended sources); Witten, Neal & Cleary, 1987

</details>

**3.7.2S064**　A designer proposes a "better" code:
1. Use lengths 1, 2, 2, 3 for probabilities 0.90, 0.05, 0.03, 0.02.
2. $\bar L = 0.90 \times 1 + 0.05 \times 2 + 0.03 \times 2 + 0.02 \times 3 = 1.12$ bit.
3. This beats the Huffman code (1.15 bit).

Which step is wrong, and what is the correct result?

<details><summary>看答案</summary>

**答案**　Step 1 is wrong: lengths 1, 2, 2, 3 violate the Kraft inequality ($2^{-1} + 2 \times 2^{-2} + 2^{-3} = 1.125 > 1$), so no prefix code with these lengths exists. The best achievable symbol-by-symbol average remains the Huffman value, 1.15 bit.

**詳解**　Kraft sum $= 0.5 + 0.25 + 0.25 + 0.125 = 1.125 > 1$. No uniquely decodable code can have these lengths, so the 1.12 bit figure is not achievable. Huffman lengths 1, 2, 3, 3 have Kraft sum exactly 1 and $\bar L = 1.15$ bit.

**出處**　Cover & Thomas, Elements of Information Theory (Kraft–McMillan inequality)

</details>

**3.7.2S065**　A trainee builds the Huffman tree:
1. Merge the two smallest: $0.02 + 0.03 = 0.05$.
2. Merge the new node with "OK": $0.05 + 0.90 = 0.95$.
3. Merge $0.05 + 0.95 = 1.00$; lengths: 0.05 → 1, 0.90 → 2, 0.03 → 3, 0.02 → 3; $\bar L = 0.05 + 1.80 + 0.09 + 0.06 = 2.00$ bit.

Which step is wrong, and what is the correct result?

<details><summary>看答案</summary>

**答案**　Step 2 is wrong: after the first merge the two smallest nodes are 0.05 (merged) and 0.05 (warning code), not 0.05 and 0.90. Correct merges give lengths 1, 2, 3, 3 and $\bar L = 1.15$ bit.

**詳解**　Correct: $0.02 + 0.03 = 0.05$; $0.05 + 0.05 = 0.10$; $0.10 + 0.90 = 1.00$. $\bar L = 0.90 \times 1 + 0.05 \times 2 + 0.03 \times 3 + 0.02 \times 3 = 0.90 + 0.10 + 0.09 + 0.06 = 1.15$ bit.

**出處**　Huffman, Proc. IRE, 1952

</details>
