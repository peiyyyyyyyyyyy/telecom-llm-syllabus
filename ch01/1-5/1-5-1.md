# 1.5.1 O-RAN 架構與元件：O-CU、O-DU、O-RU、SMO

所屬：[1.5 開放與虛擬化](../1-5.md)

## 正文

The Open Radio Access Network (O‑RAN) initiative defines a disaggregated, interoperable RAN that can be assembled from components supplied by different vendors. By separating the traditional monolithic base‑station into distinct network functions (NFs) that may be deployed on generic compute (the O‑Cloud) or on dedicated hardware, operators gain flexibility in scaling, upgrading, and cost‑optimising their networks. The four logical building blocks that are the focus of this subsection are the Service Management and Orchestration framework (SMO), the Centralized Unit (split into control‑plane O‑CU‑CP and user‑plane O‑CU‑UP), the Distributed Unit (O‑DU) and the Radio Unit (O‑RU). Understanding the exact responsibilities, interfaces and management relationships of each block is essential for designing, integrating and operating an O‑RAN deployment.

---

### 1. Service Management and Orchestration (SMO)

The SMO is the “brain” of the O‑RAN domain. It provides RAN‑wide management, orchestration and lifecycle services for all O‑RAN NFs except the O‑RU, which is managed only through the Open Fronthaul M‑Plane (see §5.3.1 and §5.1) [O-RAN OAD §5.3.1][O-RAN OAD §5.1].  

* **Southbound interfaces** – The SMO talks to the NFs via four standardized interfaces:  

  * **A1** – policy, enrichment and machine‑learning model exchange with the Near‑RT RIC.  
  * **O1** – FCAPS (fault, configuration, accounting, performance, security) management for O‑CU‑CP, O‑CU‑UP, O‑DU and, in hybrid mode, the O‑RU.  
  * **Open Fronthaul M‑Plane** – management of the O‑RU in hierarchical or hybrid mode.  
  * **O2** – resource and workload management of the O‑Cloud.  

All O‑RAN NFs, *except* the O‑RU, are managed via the O1 interface [O-RAN OAD §5.1].

---

### 2. Centralized Unit – Control Plane (O‑CU‑CP)

The O‑CU‑CP implements the higher‑layer control functions of a 5G gNB‑CU. According to the 3GPP specification it terminates the following *control‑plane* interfaces and protocols towards the UE and the core network [O-RAN OAD §5.3.3]:  

* **NG‑c**, **X2‑c**, **Xn‑c**, **F1‑c**, **E1** – standard 3GPP control‑plane links.  
* **RRC** and **PDCP (for SRB)** – radio‑resource control and data‑link protocols for signalling radio‑bearer (SRB) traffic.  

It also terminates the **E2** interface towards the Near‑RT RIC [O-RAN OAD §5.3.3] and is managed by the SMO via **O1** [O-RAN OAD §5.3.3].

---

### 3. Centralized Unit – User Plane (O‑CU‑UP)

The O‑CU‑UP hosts the user‑plane processing of a gNB‑CU. It terminates the corresponding *user‑plane* interfaces and protocols [O-RAN OAD §5.3.4]:  

* **NG‑u**, **X2‑u**, **S1‑u**, **Xn‑u**, **F1‑u**, **E1** – standard 3GPP user‑plane links.  
* **PDCP** and **SDAP** – protocols that handle data segmentation, reassembly and QoS mapping.  

Like the O‑CU‑CP, it also terminates **E2** towards the Near‑RT RIC and is managed via **O1** [O-RAN OAD §5.3.4].

---

### 4. Distributed Unit (O‑DU)

The O‑DU bridges the split between the CU and the radio. It implements the lower‑layer PHY, MAC and RLC functions and presents the following interfaces [O-RAN OAD §5.3.5]:  

* **E2** – for analytics and control from the Near‑RT RIC.  
* **F1** – the split interface towards the O‑CU (both CP and UP).  
* **Open Fronthaul (LLS) C‑Plane** – the C‑plane of the Open Fronthaul (as defined in the Open FH CUS‑Plane).  
* **Open Fronthaul M‑Plane** – for O‑RU management (hierarchical or hybrid mode).  
* **D2** – inter‑O‑DU carrier‑aggregation link (D2‑u and D2‑c services).  

The O‑DU can be deployed as a virtualised NF or on dedicated hardware, and it is managed via **O1** [O-RAN OAD §5.3.5].

---

### 5. Radio Unit (O‑RU)

The O‑RU is a *pure hardware* node (PNF) that hosts the Low‑PHY functions and the RF front‑end. It terminates the **Open Fronthaul (LLS) C‑Plane** towards the O‑DU and the **Open Fronthaul M‑Plane** towards both the O‑DU and the SMO for management [O-RAN OAD §5.3.6]. Virtualisation of the O‑RU is **not** supported in the current specification [O-RAN OAD §5.1].

---

### Worked Example: Mapping Interfaces in a Minimal O‑RAN Deployment  

Consider a single‑cell deployment that uses one O‑RU, one O‑DU, one O‑CU‑CP, one O‑CU‑UP and a Near‑RT RIC. The SMO resides in the O‑Cloud and manages all NFs. The required logical connections are:

| From → To | Interface (Purpose) | Direction |
|-----------|----------------------|-----------|
| O‑RU → O‑DU | Open Fronthaul **LLS C‑Plane** (radio data) | UE ↔ Radio |
| O‑RU ↔ SMO | Open Fronthaul **M‑Plane** (management) | Hierarchical/Hybrid |
| O‑DU → O‑CU‑CP / O‑CU‑UP | **F1‑c / F1‑u** (split) | Control / User |
| O‑DU → Near‑RT RIC | **E2** (analytics/control) | Near‑RT RIC |
| O‑CU‑CP → 5GC | **NG‑c**, **X2‑c**, **Xn‑c**, **E1** | Core signalling |
| O‑CU‑UP → 5GC | **NG‑u**, **X2‑u**, **S1‑u**, **E1** | User data |
| O‑CU‑CP / O‑CU‑UP / O‑DU → SMO | **O1** (FCAPS) | Management |
| SMO → O‑Cloud | **O2** (resource/workload) | Orchestration |
| SMO → Near‑RT RIC | **A1** (policy/ML) | Optimization |

All NFs except the O‑RU are managed via **O1**; the O‑RU receives management commands over the **Open Fronthaul M‑Plane** from either the O‑DU (hierarchical) or directly from the SMO (hybrid) [O-RAN OAD §5.1][O-RAN OAD §5.3.5][O-RAN OAD §5.3.6].

---

### Common Mistakes and Practical Notes  

| Mistake | Why it Happens | Correct Practice |
|---------|----------------|------------------|
| **Confusing O‑CU‑CP and O‑CU‑UP responsibilities** – assuming both terminate the same set of interfaces. | The specification separates control‑plane and user‑plane functions. | Refer to §5.3.3 for O‑CU‑CP (NG‑c, X2‑c, etc.) and §5.3.4 for O‑CU‑UP (NG‑u, X2‑u, etc.). |
| **Assuming the O‑RU can be virtualised** – designing cloud‑native O‑RU images. | Virtualisation of O‑RU is explicitly **not** supported. | Treat the O‑RU as a physical network function (PNF) [O-RAN OAD §5.1]. |
| **Using O1 to manage the O‑RU** – configuring radio parameters via O1. | Only the Open Fronthaul M‑Plane provides O‑RU management. | Use the Open Fronthaul M‑Plane (hierarchical or hybrid) for O‑RU management [O-RAN OAD §5.1]. |
| **Omitting the D2 interface** – overlooking inter‑O‑DU carrier aggregation. | D2 is required for carrier aggregation across O‑DUs. | Include D2‑u / D2‑c services when multiple O‑DUs are deployed [O-RAN OAD §5.3.5]. |
| **Mis‑labeling the Open Fronthaul C‑Plane as “M‑Plane”** – mixing up data and management planes. | The C‑Plane carries radio samples; the M‑Plane carries management messages. | Keep the distinction clear: **LLS C‑Plane** for radio data, **M‑Plane** for O‑RU management [O-RAN OAD §5.3.6]. |

By respecting these definitions and interface relationships, engineers can build interoperable O‑RAN deployments that fully exploit the benefits of openness and virtualization.

## 練習題

**1.** Which O‑RAN network function is *not* managed via the O1 interface?

- A. O‑CU‑CP
- B. O‑DU
- C. O‑RU
- D. O‑CU‑UP

<details><summary>看答案</summary>

正解：C。The O‑RU is managed through the Open Fronthaul M‑Plane, not O1.

</details>

**2.** In a hybrid management model, which two interfaces does the SMO use to manage the O‑RU?

- A. O1 and E2
- B. Open Fronthaul M‑Plane and O1
- C. Open Fronthaul C‑Plane and A1
- D. O2 and A1

<details><summary>看答案</summary>

正解：B。In hybrid mode the SMO provides FCAPS over Open Fronthaul M‑Plane and also over O1 to the O‑DU.

</details>
