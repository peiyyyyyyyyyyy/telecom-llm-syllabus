# 1.5.4 網路功能虛擬化（NFV）

所屬：[1.5 開放與虛擬化](../1-5.md)

## 正文

Network Function Virtualization (NFV) is the systematic migration of traditional, hardware‑bound network functions (NFs) to software components that run on generic compute, storage and networking resources, collectively called the NFV Infrastructure (NFVI). In contemporary mobile networks, NFV enables operators to scale capacity on‑demand, to place functions close to the user (edge computing), and to reduce CAPEX/OPEX by avoiding dedicated appliances [TS 28.500 §4.2.1].

A **Network Element (NE)** is the physical or logical entity that hosts one or more NFs. An NF is “a processing function in a network which has defined functional behaviour and defined interfaces” [TS 28.500 §4.2.1]. The NE may be a rack‑mount server, a base‑band unit, or any other dedicated hardware platform that implements the NF.

A **Virtualised Network Function (VNF)** is an NF (or a set of NFs) that is instantiated as software on the NFVI [TS 28.500 §4.2.1].  
A VNF consists of three logical parts:

* **Set‑a (application part)** – the functionality of the NF(s) plus supporting elements such as libraries, databases and protocol stacks.  
* **Set‑b (supporting part)** – additional software that assists the NF functionality (also part of the application part).  
* **Set‑c (virtualisation‑specific part)** – the components that enable the VNF to run on the NFVI (e.g., hypervisor drivers, container runtimes) [TS 28.500 §4.2.1].

Management of these parts is split between two orchestrators:

* The **Element Manager (EM)** controls set‑a and set‑b via the *Type 1* interface [TS 28.500 §4.2.1].  
* The **VNF Manager (VNFM)** controls set‑c through the ETSI‑defined *Ve‑Vnfm‑vnf* reference point [TS 28.500 §4.2.1].

### Virtualised Deployment Scenarios

3GPP TS 23.501 §5.21 defines several generic patterns for deploying virtualised NFs:

| Scenario | Key properties |
|----------|----------------|
| **Distributed, redundant, stateless, scalable** | Instances may be placed at multiple locations; they do not keep locally‑persistent state; scaling is achieved by adding/removing identical instances. |
| **Set‑based redundancy** | A *NF set* contains several instances that together provide redundancy and scalability; addition/removal of instances is explicitly supported. |
| **Special‑case functions (e.g., SEPP, SCP)** | Although not NFs per se, they may also be deployed in a distributed, redundant, scalable fashion. |

For deployments of the **Access and Mobility Management Function (AMF)**, the specification distinguishes two concrete cases [TS 23.501 §5.21]:

1. **Stateless, non‑additive deployment** – the AMF is deployed as a single logical instance that does **not** require dynamic addition or removal of transport network layer associations (TNLA) for redundancy.  
2. **Set‑based deployment** – several AMF instances form an *AMF set*; the network may add or remove AMFs and their associated TNLA to achieve redundancy or load‑balancing [TS 23.501 §5.21].

Both approaches rely on the Network Resource Function (NRF) to publish mappings between Global UE‑Identifier (GUAMI) values and the serving AMF(s). When a new AMF is introduced, it **updates the NRF with the new GUAMI(s)**, and the NRF subsequently includes this information in discovery responses [TS 23.501 §5.21.2.1].

### Worked Example: Dimensioning a Virtualised AMF

An operator expects a peak of **20 000 concurrent UE sessions** in a metropolitan area. Each AMF VNF instance can sustain **5 000 sessions** (as determined by performance testing).  

The required number of VNF instances $N$ is  

$$
N = \left\lceil \frac{\text{Peak Sessions}}{\text{Sessions per Instance}} \right\rceil
   = \left\lceil \frac{20\,000}{5\,000} \right\rceil = 4 .
$$

Thus the operator provisions **four AMF VNF instances** on the NFVI. Because the AMF is defined as *stateless* in this scenario, any UE can be re‑bound to any of the four instances without session loss, satisfying the *distributed, redundant, stateless and scalable* criteria [TS 23.501 §5.21].

If the operator later observes a 30 % traffic growth, an additional VNF instance can be instantiated on the NFVI without hardware changes, illustrating the **elastic scaling** capability of NFV.

### Common Pitfalls and Practical Notes

| Pitfall | Why it occurs | Mitigation |
|---------|---------------|------------|
| **Confusing a VNF with the underlying NF** | The VNF contains both the NF logic (set‑a/b) **and** virtualization glue (set‑c). Treating them as interchangeable can lead to missing the need for hypervisor or container updates. | Keep the three‑part model in mind; verify that the VNFM manages set‑c while the EM handles set‑a/b [TS 28.500 §4.2.1]. |
| **Assuming a VNF is always stateless** | Some NFs retain session state (e.g., a stateful SMF). Deploying them as stateless may break service continuity. | Identify the statefulness of each NF; if stateful, ensure state replication or use of a state‑synchronisation mechanism. |
| **Neglecting the Type 1 interface** | The EM‑to‑VNF management channel is required for lifecycle actions on set‑a/b. Skipping it prevents configuration updates. | Implement the Type 1 interface as defined in the specification [TS 28.500 §4.2.1]. |
| **Over‑provisioning NFVI resources** | Deploying more VNFs than needed wastes compute/storage and may increase latency due to resource contention. | Use the sizing formula (as in the example) and monitor utilisation to adjust the number of instances dynamically. |
| **Forgetting to update the NRF after adding a VNF** | New AMF instances must publish their GUAMI(s) to the NRF; otherwise, UE‑to‑AMF mapping fails. | Follow the AMF addition procedure: update the NRF with new GUAMI(s) and verify DNS publication [TS 23.501 §5.21.2.1]. |

By adhering to the definitions, management interfaces, and deployment patterns documented in the 3GPP specifications, engineers can design robust, scalable, and maintainable virtualised network architectures.
