# 1.5.5 雲端平台：O-Cloud 與雲原生網路功能

## 正文

The O‑Cloud is the physical‑to‑virtual substrate on which all O‑RAN functions are instantiated. In an O‑RAN deployment the cloud is *open* (vendor‑agnostic interfaces, standardized APIs) and *virtualized* (functions run as software rather than dedicated hardware). When the functions are built according to cloud‑native principles—containerisation, micro‑service decomposition, declarative orchestration—they are called **Cloud‑Native Network Functions (CNFs)**.  

Why does this matter?  
* **Scalability** – CNFs can be elastically scaled in or out (horizontal scaling) or up/down (vertical scaling) in response to traffic variations, without swapping hardware.  
* **Agility** – New features or bug‑fixes are delivered as container images; the O‑Cloud can roll them out with zero‑downtime using blue‑green or canary deployments.  
* **Cost efficiency** – Shared compute, storage, and networking resources reduce CAPEX and OPEX, especially when the same pool serves multiple functions (e.g., O‑DU, O‑CU‑CP, O‑CU‑UP).  
* **Inter‑operability** – Open interfaces (e.g., A1, E2) allow CNFs from different vendors to coexist, fostering a multi‑vendor ecosystem.

### Key Definitions  

| Symbol | Definition | Unit |
|--------|------------|------|
| $P$ | Total processing capacity required for a function (CPU cores) | cores |
| $\lambda$ | Traffic load presented to the function (average bitrate) | Mbps |
| $c$ | Processing intensity, i.e., CPU cores required per Mbps of traffic for the function | cores/Mbps |
| $R$ | Aggregate resource demand of a set of functions | cores |
| $\mu$ | Service rate of a processing element (e.g., a vCPU) | Mbps |
| $L_{\text{proc}}$ | Expected processing latency (queueing + execution) | ms |
| $n$ | Number of parallel replicas (pods) of a CNF | – |
| $U_{\text{CPU}}$ | CPU utilisation per replica (0‑1) | – |

#### Resource Estimation Formula  

A first‑order estimate for the CPU cores needed by a CNF is  

$$
P = \lambda \times c
\tag{1}
$$

If the function is horizontally scaled to $n$ identical replicas, the per‑replica load becomes $\lambda/n$, and the required cores per replica are  

$$
P_{\text{rep}} = \frac{\lambda}{n} \times c
\tag{2}
$$

The total allocated cores must satisfy  

$$
P_{\text{total}} = n \times P_{\text{rep}} \ge P
\tag{3}
$$

#### Queueing‑Based Latency Approximation  

Assuming each replica behaves like an M/M/1 queue, the average processing latency is  

$$
L_{\text{proc}} = \frac{1}{\mu - \lambda/n}
\tag{4}
$$

where $\mu$ is the service rate of a vCPU (e.g., 10 Gbps per core for a modern Intel Xeon). This simple model helps verify that scaling decisions keep latency within the radio‑level budget (typically < 1 ms for the DU).

### Worked Example  

**Scenario**: An O‑DU is to be deployed as a CNF on an O‑Cloud. The expected peak traffic on the DU is $\lambda = 2\,\text{Gbps}$ (i.e., 2000 Mbps). Vendor documentation states that the DU needs $c = 0.025$ cores per Mbps of traffic. The O‑Cloud provides vCPUs with $\mu = 10\,\text{Gbps}$ per core.

1. **Compute total CPU cores (no scaling).**  
   Using (1):  
   $$
   P = 2000\ \text{Mbps} \times 0.025\ \frac{\text{cores}}{\text{Mbps}} = 50\ \text{cores}
   $$

2. **Choose a horizontal scaling factor** $n = 5$ (five identical pods).  
   Per‑replica traffic: $\lambda/n = 2000/5 = 400$ Mbps.  
   Per‑replica cores from (2):  
   $$
   P_{\text{rep}} = 400\ \text{Mbps} \times 0.025\ \frac{\text{cores}}{\text{Mbps}} = 10\ \text{cores}
   $$

   Total allocated cores: $P_{\text{total}} = 5 \times 10 = 50$ cores, satisfying (3).

3. **Check processing latency** using (4):  
   $$
   L_{\text{proc}} = \frac{1}{\mu - \lambda/n} = \frac{1}{10\,\text{Gbps} - 0.4\,\text{Gbps}} = \frac{1}{9.6\,\text{Gbps}} \approx 0.104\ \text{µs}
   $$  
   Converting to milliseconds, $L_{\text{proc}} \approx 0.000104$ ms, well below the 1 ms budget.  

Thus, five replicas each with 10 CPU cores comfortably meet both capacity and latency requirements.

### Practical Notes & Common Mistakes  

| Mistake | Why it Happens | Corrective Action |
|---------|----------------|-------------------|
| **Over‑provisioning CPU** | Using worst‑case $c$ values for all traffic conditions. | Profile the CNF with realistic traffic mixes; apply dynamic scaling policies (e.g., HPA in Kubernetes). |
| **Ignoring network I/O** | Focusing only on CPU while forgetting that CNFs also need NIC bandwidth and SR‑IOV lanes. | Include a parallel bandwidth estimate $B = \lambda \times b$, where $b$ is NIC utilisation per Mbps (often ≈ 1 Gbps per 10 Gbps NIC). |
| **Mis‑configuring pod affinity** | Placing all replicas on the same physical host, eliminating redundancy. | Use anti‑affinity rules so that replicas are spread across failure domains (rack, zone). |
| **Neglecting latency budgets** | Relying solely on average CPU utilisation; bursty traffic can cause queue buildup. | Simulate burst scenarios or apply a safety factor (e.g., keep $U_{\text{CPU}} < 0.7$). |
| **Hard‑coding container images** | Tying the O‑Cloud to a single vendor’s image format, breaking openness. | Adopt OCI‑compatible images and store them in a neutral registry; use Helm charts or Kustomize for declarative deployment. |

**Best practice checklist**  

1. **Define service level objectives (SLOs)** for throughput, latency, and availability.  
2. **Model resource needs** using (1)–(4) and validate with on‑site measurements.  
3. **Deploy with Kubernetes** (or an equivalent CNCF‑certified orchestrator) and enable **Horizontal Pod Autoscaler (HPA)** based on custom metrics (e.g., per‑pod bitrate).  
4. **Implement observability**: Prometheus metrics for $U_{\text{CPU}}$, $L_{\text{proc}}$, and NIC utilisation; Grafana dashboards for real‑time monitoring.  
5. **Test fail‑over** by injecting host failures and verifying that the O‑Cloud re‑schedules pods without service interruption.

By adhering to these principles, engineers can realise the full promise of O‑Cloud: a flexible, cost‑effective substrate that supports multi‑vendor, cloud‑native RAN deployments while meeting the stringent performance demands of 5G and beyond.
