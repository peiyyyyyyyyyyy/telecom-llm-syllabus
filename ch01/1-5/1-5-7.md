# 1.5.7 E2 服務模型：KPM、RC

所屬：[1.5 開放與虛擬化](../1-5.md)

## 正文

The **E2 interface** is the logical link between the Near‑Real‑Time RAN Intelligent Controller (Near‑RT RIC) and the O‑CU/O‑DU cluster. Its purpose is to transport *service‑model‑specific* messages that enable the RIC to (i) collect performance data from the radio access network and (ii) issue control actions that affect radio resources on a sub‑second time‑scale. Two service models are defined in the O‑RAN specification and are widely implemented in commercial O‑RAN deployments:

* **KPM (Key Performance Measurement)** – a telemetry service model that delivers KPI (Key Performance Indicator) measurements from the O‑CU/O‑DU to the Near‑RT RIC.
* **RC (RAN Control)** – a command‑and‑control service model that carries *control policies* (actions) from the Near‑RT RIC to the O‑CU/O‑DU and reports execution status.

Both models share a common **E2AP (E2 Application Protocol)** transport, but each defines its own set of Information Elements (IEs), encoding rules, and procedural flows (subscription, indication, control, and acknowledgement).

### KPM Service Model

| Symbol | Meaning | Unit |
|--------|---------|------|
| $M_i$ | Measured raw value of KPI *i* (e.g., number of transmitted bits) | varies (bits, packets, etc.) |
| $T$ | Measurement interval length | seconds (s) |
| $K_i$ | Normalised KPI *i* (e.g., throughput) | bits · s⁻¹, % , etc. |
| $w_i$ | Weight assigned to KPI *i* in a composite metric | dimension‑less |

A KPI is typically derived from raw counters using a linear transformation:

$$
K_i = \frac{M_i}{T} \times w_i
\tag{1}
$$

*Example*: PRB (Physical Resource Block) utilization is expressed as a percentage:

$$
K_{\text{PRB}} = \frac{N_{\text{used\_PRB}}}{N_{\text{total\_PRB}}} \times 100\%
\tag{2}
$$

**Procedural flow**

1. **Subscription Request** – The Near‑RT RIC sends an *E2SM‑KPM‑Subscription‑Request* specifying the list of KPIs, measurement period $T$, and reporting mode (periodic or event‑triggered).
2. **Subscription Response** – The O‑CU/O‑DU acknowledges with *E2SM‑KPM‑Subscription‑Response*.
3. **Indication** – At each interval $T$, the O‑CU/O‑DU packages the computed $K_i$ values into an *E2SM‑KPM‑Indication* message and transmits it to the RIC.
4. **Indication Acknowledgement** – The RIC replies with *E2SM‑KPM‑Indication‑Ack* (optional, used for flow‑control).

The KPM model supports *granular* reporting (per‑cell, per‑UE, per‑slice) by nesting *measurement objects* within the indication.

### RC Service Model

The RC model enables the RIC to **steer** radio behavior. Control actions are defined by *action definitions* (AD) that map to O‑CU/O‑DU configurable parameters (e.g., scheduling weight, handover thresholds).

| Symbol | Meaning | Unit |
|--------|---------|------|
| $a$ | Action identifier (unique per subscription) | – |
| $p$ | Parameter to be modified (e.g., scheduling weight) | – |
| $v$ | New value for $p$ | depends on $p$ (e.g., integer, float) |
| $t_{\text{exec}}$ | Execution deadline for the action | milliseconds (ms) |
| $s$ | Status code returned after execution | – (e.g., 0 = success) |

**Typical RC flow**

1. **Control Policy Definition** – The Near‑RT RIC creates an *E2SM‑RC‑Control‑Message* containing one or more actions $\{a\}$, each with a target parameter $p$, desired value $v$, and deadline $t_{\text{exec}}$.
2. **Control Request** – The RIC sends the control message via *E2AP‑Control‑Request* to the O‑CU/O‑DU.
3. **Execution** – The O‑CU/O‑DU applies the new configuration, respecting the deadline.
4. **Control Acknowledgement** – The O‑CU/O‑DU returns *E2AP‑Control‑Response* containing a *Control‑Outcome* IE with status $s$ for each action.

RC also defines *policy‑triggered* actions: the Near‑RT RIC can subscribe to a KPI (via KPM) and, when a threshold is crossed, automatically issue a corresponding RC control message. This *closed‑loop* operation underpins many O‑RAN use‑cases such as dynamic load balancing and slice‑aware scheduling.

### Worked Example

A mobile operator wants to keep the **average PRB utilization** per cell below **70 %**. The Near‑RT RIC will:

1. Subscribe to the PRB utilization KPI using KPM with $T = 100\ \text{ms}$.
2. When the reported $K_{\text{PRB}}$ exceeds 70 %, issue an RC control action that reduces the *scheduling weight* $w_{\text{sched}}$ of the most congested slice by 10 %.

Assume the following numbers for a single cell during one measurement interval:

* Total PRBs in the cell: $N_{\text{total\_PRB}} = 100$.
* Used PRBs: $N_{\text{used\_PRB}} = 78$.
* Current scheduling weight for Slice A: $w_{\text{sched}}^{\text{A}} = 5$.

**Step 1 – KPI calculation (Eq. 2):**

$$
K_{\text{PRB}} = \frac{78}{100} \times 100\% = 78\%
$$

Since $78\% > 70\%$, the RIC triggers an RC action.

**Step 2 – RC action definition:**

$$
a = 1,\quad p = \text{“sched\_weight\_SliceA”},\quad v = w_{\text{sched}}^{\text{A}} - 0.1 \times w_{\text{sched}}^{\text{A}} = 5 - 0.5 = 4.5,\quad t_{\text{exec}} = 50\ \text{ms}
$$

The control message is sent; the O‑DU applies $w_{\text{sched}}^{\text{A}} = 4.5$ and replies with $s = 0$ (success). In the next interval, the KPI is recomputed; the loop continues until $K_{\text{PRB}} \le 70\%$.

### Common Mistakes & Practical Notes

| Pitfall | Why it occurs | Remedy |
|---------|---------------|--------|
| **Mismatched measurement periods** – The Near‑RT RIC assumes $T = 100\ \text{ms}$ while the O‑DU is configured for $T = 200\ \text{ms}$. | The subscription request does not enforce $T$; the O‑DU may ignore an unsupported period. | Verify the *E2SM‑KPM‑Subscription‑Response* contains the accepted $T$ and log any deviation. |
| **Over‑loading the RC channel** – Sending a burst of control actions (e.g., per‑UE handover) without pacing. | RC actions are processed synchronously; excessive load can cause missed deadlines ($t_{\text{exec}}$). | Implement a back‑pressure mechanism using *E2SM‑RC‑Control‑Outcome* status codes and respect the *Control‑Rate‑Limit* IE (if present). |
| **Incorrect KPI normalization** – Forgetting the weight $w_i$ in Eq. (1), leading to misleading values (e.g., raw bits reported as throughput). | Engineers sometimes treat raw counters as already normalized. | Always apply the transformation defined in the KPI’s *measurement definition* part of the subscription. |
| **Ignoring granularity** – Subscribing only at the cell level when a slice‑specific policy is required. | The subscription may default to cell‑wide objects. | Explicitly include *slice‑ID* in the *Measurement‑Object‑List* of the KPM subscription. |
| **Assuming RC is instantaneous** – Expecting $t_{\text{exec}}$ = 0 ms. | The O‑CU/O‑DU must serialize configuration changes; hardware limits introduce latency. | Set realistic $t_{\text{exec}}$ values (e.g., 10–50 ms) and monitor actual execution times via the *Control‑Outcome* timestamp. |

**Practical tip:** When building a closed‑loop KPM → RC workflow, start with *event‑triggered* KPM reporting (threshold crossing) rather than periodic reporting. This reduces traffic on the E2 interface and lowers reaction latency.

**Summary**

The E2 service models KPM and RC together enable *real‑time* intelligence in O‑RAN. KPM supplies the RIC with timely, normalized performance metrics; RC lets the RIC enforce policies that adapt radio behavior within tight deadlines. Mastery of the subscription/indication and control request/response flows, along with careful KPI definition and action parameterisation, is essential for building robust, low‑latency O‑RAN deployments.

## 練習題

**1.** In the KPM service model, which formula correctly converts a raw counter $M_i$ into a normalised KPI $K_i$ over a measurement interval $T$?

- A. $K_i = M_i \times T$
- B. $K_i = \dfrac{M_i}{T} \times w_i$
- C. $K_i = M_i + w_i$
- D. $K_i = \dfrac{T}{M_i}$

<details><summary>看答案</summary>

正解：B。Equation (1) defines KPI normalisation as the raw value divided by the interval and multiplied by a weight.

</details>

**2.** Which of the following statements about the RC service model is FALSE?

- A. An RC action can include a deadline $t_{\text{exec}}$ that the O‑CU/O‑DU must respect.
- B. The RC model uses the same subscription procedure as KPM.
- C. The RC control message contains one or more action definitions.
- D. The O‑CU/O‑DU returns a status code $s$ for each action in the Control‑Outcome IE.

<details><summary>看答案</summary>

正解：B。RC does not require a subscription; it is a pure request‑response model, unlike KPM which uses subscriptions.

</details>

**3.** A Near‑RT RIC subscribes to PRB utilisation with $T = 100\,$ms. The O‑DU reports $N_{\text{used\_PRB}} = 78$ and $N_{\text{total\_PRB}} = 100$. What is the reported KPI $K_{\text{PRB}}$?

- A. 0.78 %
- B. 78 %
- C. 100 %
- D. 0.78

<details><summary>看答案</summary>

正解：B。Using Eq. (2), $K_{\text{PRB}} = 78/100 \times 100\% = 78\%$.

</details>

**4.** In a closed‑loop KPM → RC workflow, which of the following is the most appropriate way to minimise latency?

- A. Use periodic KPM reporting with the shortest possible interval.
- B. Subscribe to event‑triggered KPM reports that fire when a KPI exceeds a threshold.
- C. Send RC actions for every KPI measurement, regardless of magnitude.
- D. Increase the size of the RC control message to include all possible actions.

<details><summary>看答案</summary>

正解：B。Event‑triggered reports reduce unnecessary traffic and allow the RIC to react only on significant changes, lowering overall latency.

</details>

**5.** When an RC control action fails to execute within its deadline, which status code should the O‑DU return in the Control‑Outcome IE?

- A. $s = 0$ (success)
- B. $s = 1$ (partial success)
- C. $s = 2$ (deadline missed)
- D. $s = 255$ (unknown error)

<details><summary>看答案</summary>

正解：C。Status code 2 is defined for “deadline missed” in the RC outcome specification.

</details>
