## 正文

Edge computing (also called Multi‑Access Edge Computing, MEC) brings IT‑service capabilities—compute, storage, and networking—closer to the end‑user devices by locating them at the radio access network (RAN) edge, e.g., at a base‑station (gNB/eNB) or at a centralized‑unit (CU) site. In a 5G or LTE network the edge node is typically co‑located with the UPF (User Plane Function) or the edge cloud platform. By processing data locally instead of sending every packet to a distant data centre, edge computing reduces round‑trip latency, saves back‑haul bandwidth, and enables new use‑cases such as augmented reality (AR), tactile‑internet control loops, and real‑time analytics for IoT sensors.

---

### Key Definitions

| Symbol | Definition | Unit |
|--------|------------|------|
| $T_{\text{prop}}$ | Propagation delay between UE and edge node (speed of light in fiber or radio) | s |
| $T_{\text{tx}}$ | Transmission time for a packet of size $L$ over a link of rate $R$ | $L/R$ (s) |
| $T_{\text{queue}}$ | Queuing delay at the edge server (depends on load) | s |
| $T_{\text{proc}}$ | Processing time for the application at the edge | s |
| $T_{\text{E2E}}$ | End‑to‑end latency experienced by the UE | s |
| $C$ | Number of CPU cycles required by the task | cycles |
| $f_{\text{loc}}$ | Local CPU frequency (UE) | Hz |
| $f_{\text{edge}}$ | Edge CPU frequency (edge server) | Hz |
| $L_{\text{up}}$, $L_{\text{down}}$ | Uplink and downlink payload sizes | bits |
| $R_{\text{up}}$, $R_{\text{down}}$ | Uplink and downlink data rates | bit/s |
| $E_{\text{loc}}$, $E_{\text{edge}}$ | Energy consumption per CPU cycle locally and at the edge | J/cycle |

**End‑to‑End Latency Model**

A common analytical model for the latency of a task that may be offloaded to the edge is  

$$
\boxed{
T_{\text{E2E}} = T_{\text{prop}} + T_{\text{tx}} + T_{\text{queue}} + T_{\text{proc}} + T_{\text{tx}}^{\text{down}} + T_{\text{prop}}^{\text{down}}
}
\tag{1}
$$

For a purely local execution the latency reduces to  

$$
T_{\text{loc}} = \frac{C}{f_{\text{loc}}}.
\tag{2}
$$

When the task is offloaded, the total time becomes  

$$
\boxed{
T_{\text{off}} = \frac{L_{\text{up}}}{R_{\text{up}}} + \frac{C}{f_{\text{edge}}} + \frac{L_{\text{down}}}{R_{\text{down}}} + T_{\text{prop}}^{\text{up}} + T_{\text{prop}}^{\text{down}} + T_{\text{queue}}.
}
\tag{3}
$$

A decision rule is therefore  

$$
\text{Offload if } T_{\text{off}} < T_{\text{loc}}.
\tag{4}
$$

**Energy Model (optional)**  

Local energy consumption  

$$
E_{\text{loc}} = C \, E_{\text{cycle,loc}}
\tag{5}
$$

Offloading energy (radio only)  

$$
E_{\text{off}} = L_{\text{up}} \, P_{\text{tx}}/R_{\text{up}} + L_{\text{down}} \, P_{\text{rx}}/R_{\text{down}} .
\tag{6}
$$

### Worked Example

A smartphone runs a video‑frame enhancement algorithm that requires $C = 2 \times 10^{9}$ CPU cycles.

| Parameter | Value |
|-----------|-------|
| $f_{\text{loc}}$ | $1.5$ GHz |
| $f_{\text{edge}}$ | $10$ GHz |
| $L_{\text{up}}$ | $4$ Mbit (0.5 MiB) |
| $L_{\text{down}}$ | $1$ Mbit (0.125 MiB) |
| $R_{\text{up}}$ | $10$ Mbps |
| $R_{\text{down}}$ | $20$ Mbps |
| $T_{\text{prop}}^{\text{up}} = T_{\text{prop}}^{\text{down}}$ | $5$ ms (typical RAN‑edge distance) |
| $T_{\text{queue}}$ | $2$ ms (lightly loaded edge) |

1. **Local execution time** (Eq. 2)  

$$
T_{\text{loc}} = \frac{2 \times 10^{9}}{1.5 \times 10^{9}} = 1.33\ \text{s}.
$$

2. **Uplink transmission time**  

$$
\frac{L_{\text{up}}}{R_{\text{up}}}= \frac{4 \times 10^{6}}{10 \times 10^{6}} = 0.4\ \text{s}.
$$

3. **Edge processing time**  

$$
\frac{C}{f_{\text{edge}}}= \frac{2 \times 10^{9}}{10 \times 10^{9}} = 0.20\ \text{s}.
$$

4. **Downlink transmission time**  

$$
\frac{L_{\text{down}}}{R_{\text{down}}}= \frac{1 \times 10^{6}}{20 \times 10^{6}} = 0.05\ \text{s}.
$$

5. **Total offload latency** (Eq. 3)  

$$
\begin{aligned}
T_{\text{off}} &= 0.4 + 0.20 + 0.05 + 0.005 + 0.005 + 0.002 \\
&= 0.662\ \text{s}.
\end{aligned}
$$

Since $T_{\text{off}} = 0.662\,$s $<$ $T_{\text{loc}} = 1.33\,$s, the optimal decision is to offload the task to the edge node.

### Practical Notes & Common Pitfalls

| Pitfall | Why it matters | Mitigation |
|---------|----------------|------------|
| **Ignoring queuing delay** | $T_{\text{queue}}$ can dominate when many users share the same MEC host, turning an apparently beneficial offload into a latency penalty. | Monitor MEC load via the 3GPP **TS 23.287** “Service requirements for MEC” and incorporate dynamic $T_{\text{queue}}$ estimates. |
| **Assuming static radio rates** | $R_{\text{up}}$ and $R_{\text{down}}$ fluctuate with channel quality, causing $T_{\text{off}}$ to vary wildly. | Use adaptive bitrate or a margin (e.g., 20 % lower than the measured peak) in the decision logic. |
| **Over‑looking security & privacy** | Sensitive data may be regulated (e.g., GDPR) and cannot be sent to a public edge node without proper encryption and consent. | Deploy **private MEC** (SNPN) or enforce end‑to‑end encryption before offloading. |
| **Neglecting energy trade‑offs** | For battery‑constrained IoT devices, radio transmission can consume more energy than local compute, even if latency improves. | Evaluate Eq. (5) vs. Eq. (6) and set a combined latency‑energy cost function. |
| **Mismatched task granularity** | Very small tasks incur fixed radio overhead that outweighs any edge‑processing gain. | Batch multiple tasks or use “compute‑at‑the‑edge” only for tasks exceeding a minimum cycle count (often > 10⁸ cycles). |

Edge computing is now a cornerstone of 5G service architecture. Properly modeling latency, load, and energy, and respecting regulatory constraints, enables telecom operators to deliver ultra‑low‑latency services while preserving network efficiency.
