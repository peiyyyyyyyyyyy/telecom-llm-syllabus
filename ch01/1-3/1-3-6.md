# 1.3.6 企業專網：非公眾網路（SNPN、PNI-NPN）與 5G LAN

所屬：[1.3 服務與多媒體](../1-3.md)

## 正文

Enterprise private networks (often called *non‑public networks*) are logical or physical 5G deployments that are owned, operated, and managed by a single enterprise rather than a public‑operator. They are used for industrial automation, campus connectivity, or dedicated services where the operator wants full control over radio resources, security policies, and service exposure. In 3GPP terminology two main flavours exist:

* **SNPN (Standalone Non‑Public Network)** – a completely independent 5G core (5GC) that does **not** rely on the public‑operator’s core.  
* **PNI‑NPN (Public‑Network Integrated Non‑Public Network)** – a private slice that runs on top of the public 5GC but is isolated from public traffic by network slicing.

Both SNPN and PNI‑NPN can host the same IMS‑based services that are offered to public subscribers, such as VoLTE/VoNR or multimedia telephony. The 3GPP specifications therefore describe how the *IMS voice over PS* (packet‑switched) indication, resource reservation, and telephony application server (TAS) behaviour are handled when the UE is attached to a non‑public network.

### Key definitions drawn from the standards

| Symbol / term | Definition (as per 3GPP TS) |
|---------------|-----------------------------|
| **IMS voice over PS session** | A voice call carried over the packet‑switched domain of the IP Multimedia Subsystem, using SIP signalling and RTP media streams. |
| **SNPN** | A non‑public network where the serving PLMN AMF indicates IMS voice support based on local policy, UE capabilities, IP‑address preservation and NR coverage. |
| **TAS (Telephony Application Server)** | A SIP Application Server that provides network support for the multimedia telephony service (TS 22.173). It may be collocated with the Media Resource Function Controller (MRFC). |
| **IP‑CAN bearer** | An IP‑based connectivity‐access‑network bearer used for user‑plane traffic (e.g., voice, video). |
| **SDP (Session Description Protocol)** | The protocol used in SIP messages to describe media capabilities; the UE receives an SDP *answer* and may reserve IP‑CAN bearers accordingly. |
| **Resource reservation** | The act of requesting QoS resources (e.g., guaranteed bitrate, latency) from the PCRF/PCF for a media flow. |
| **Attestation** | Verification of subscriber identity, RCD (Remote Credential Data) information, or signatures, performed by the TAS or another AS when configured by operator policy. |

No explicit formula is required for the concepts above; however, the resource‑reservation logic can be expressed as a simple Boolean decision:

$$
\text{ReserveBearer} = 
\begin{cases}
\text{True}, & \text{if UE is aware of allowed media (voice/video) and policy permits reservation at INVITE/SDP answer} \\
\text{False}, & \text{otherwise}
\end{cases}
$$

### How IMS voice support is indicated in SNPN

When a UE registers on a **stand‑alone non‑public network**, the serving PLMN AMF sends an *IMS voice over PS* indication to the UE. This indication is derived from:

* local SNPN policy,
* the UE’s advertised capabilities,
* whether the network can preserve the UE’s IP address,
* the extent of NR (New Radio) coverage.

The indication is **per Registration Area** – i.e., it applies to the specific geographic area where the UE performed the registration. If the indication is “supported”, the UE may select the IMS domain for voice calls; otherwise it must fall back to circuit‑switched (CS) voice or another RAT. The specification notes that in SNPN there is **only NR**; therefore a “voice‑centric” UE cannot re‑select another RAT within the same SNPN if the first Registration Area cannot support IMS voice, and homogeneous support across the SNPN is recommended [TS 23.501 §5.16.3.2]​.

### Telephony Application Server (TAS) role in private networks

The **Telephony Application Server** provides the SIP signalling backbone for multimedia telephony, whether the service runs on a public network or a private one. The TAS may be collocated with the **Media Resource Function Controller (MRFC)** when media interaction is required [TS 23.228 §4.16.1]​.

Key behaviours that are relevant for enterprise private networks:

1. **Service identification** – The multimedia telephony service is associated with a *communication service identifier* so that calls originating from the PSTN/CS domain are marked accordingly [TS 23.228 §4.16.2]​.
2. **Session setup** – The UE may reserve IP‑CAN bearers **at the reception of the SDP answer**; if the UE already knows the operator’s media policy, it may reserve at the **sending of the SIP INVITE**. The UE should only request reservation for voice and video streams [TS 23.228 §4.16.3]​.
3. **Attestation and signature verification** – When configured, the TAS (or another AS) may attest the subscriber’s identity, verify RCD information, or check signatures for both originating and terminating requests. Only **one network element** performs attestation for an originating subscriber in the originating network [TS 23.228 §4.16.3]​.

These functions can be deployed inside an SNPN or a PNI‑NPN slice, providing the same service level as the public network while keeping traffic isolated.

### Worked example: Resource reservation for a multimedia call in an SNPN

**Scenario**  
An enterprise deploys an SNPN that supports IMS voice over PS. A UE with voice‑and‑video capabilities registers in Registration Area A. The UE initiates a video call to a remote user on the public network.

| Parameter | Value |
|-----------|-------|
| UE capability flag for video | `true` |
| Operator policy – allowed media for SNPN | voice + video |
| QoS flow for voice: 64 kbps, 20 ms latency |
| QoS flow for video: 2 Mbps, 30 ms latency |

**Steps**

1. **Registration** – The AMF sends the *IMS voice over PS supported* indication because the SNPN policy, UE capabilities, and NR coverage satisfy the conditions [TS 23.501 §5.16.3.2]​.
2. **SIP INVITE** – The UE knows that video is allowed, so it **reserves IP‑CAN bearers at the INVITE** stage for both voice and video (per §4.16.3).  
3. **SDP exchange** – The network returns an SDP *answer* confirming the media parameters. Since the UE already reserved the bearers, no further action is required.  
4. **Attestation** – The TAS performs subscriber identity attestation (only one element does this) as configured by the operator [TS 23.228 §4.16.3]​.

Result: The call proceeds with guaranteed QoS for both voice (64 kbps) and video (2 Mbps), illustrating how an enterprise SNPN can deliver the same IMS‑based multimedia experience as the public network.

### Common pitfalls and practical notes

| Pitfall | Why it occurs | Mitigation |
|---------|---------------|------------|
| **Assuming IMS voice is always available** | The AMF indication is *per Registration Area* and depends on local policy, UE capabilities, and NR coverage. | Verify the IMS voice indication after each registration, especially when moving between areas. |
| **Reserving bearers too early** | If the UE reserves before knowing the operator’s allowed media, it may request unnecessary resources. | Follow the recommendation: reserve at **SDP answer** unless the UE is already aware of the policy. |
| **Multiple attestation points** | The spec allows only one network element to attest the originating subscriber; deploying two can cause conflicts. | Design the private‑network IMS core so that attestation is centralized in the TAS (or a dedicated AS). |
| **Expecting PNI‑NPN to behave like SNPN** | PNI‑NPN runs on the public 5GC; the SNPN indication rules do not apply. | Treat PNI‑NPN as a slice of the public network and use the public‑operator’s IMS indications. |
| **Neglecting homogeneous support in SNPN** | Heterogeneous support can lead to call drops when the UE moves to a Registration Area without IMS voice. | Deploy SNPN coverage homogeneously for IMS voice or ensure fallback mechanisms (e.g., CS fallback) are in place. |

**Scope note** – The detailed architecture of *5G LAN* (e.g., local breakout, edge‑computed services) is not covered in the cited 3GPP specifications; therefore this subsection limits itself to the aspects of IMS support, TAS behaviour, and SNPN indication that are explicitly defined in the references.

## 練習題

**1.** According to TS 23.501, what factors does the serving SNPN consider when providing the IMS voice‑over‑PS indication?

- A. Only the UE’s battery level
- B. Local policy, UE capabilities, IP address preservation and extended NR coverage
- C. The number of active video streams
- D. The current temperature of the base station

<details><summary>看答案</summary>

正解：B。The SNPN bases the indication on policy, UE abilities, address preservation and NR coverage.

</details>

**2.** When may the AMF indicate that IMS voice‑over‑PS is supported over non‑3GPP access?

- A. Whenever the UE is registered in any area
- B. Only if the network can provide a successful IMS voice‑over‑PS session over N3IWF/TNGF with a 5G QoS Flow that supports voice
- C. When the UE requests video services
- D. If the UE is using Wi‑Fi only

<details><summary>看答案</summary>

正解：B。The indication is allowed only if the network can establish a voice‑supporting QoS flow via N3IWF/TNGF.

</details>

**3.** According to the specifications, how many network elements may perform attestation of the originating subscriber in the originating network?

- A. Zero – attestation is not required
- B. One only
- C. Two, the Telephony AS and the PCRF
- D. All ASes involved in the call

<details><summary>看答案</summary>

正解：B。The standard limits attestation to a single network element in the originating network.

</details>

**4.** What impact does NRF‑based P‑CSCF discovery have on the UE?

- A. The UE must store multiple P‑CSCF addresses
- B. It requires the UE to run additional cryptographic checks
- C. It has no impact; the UE does not need to know how the address is discovered
- D. The UE must select the P‑CSCF manually

<details><summary>看答案</summary>

正解：C。The UE is unaware of the discovery mechanism; it operates transparently.

</details>

**5.** Which statement best reflects the relationship between CS fallback and IMS‑based services as defined in TS 23.272?

- A. They are mutually exclusive and cannot operate in the same network
- B. CS fallback replaces IMS‑based services completely
- C. CS fallback and IMS‑based services shall be able to co‑exist in the same operator’s network
- D. IMS‑based services are only used when CS fallback fails

<details><summary>看答案</summary>

正解：C。The specification explicitly states that both can operate together.

</details>
