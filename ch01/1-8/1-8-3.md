# 1.8.3 角色與資料權限

所屬：[1.8 維運組織](../1-8.md)

## 正文

In a modern telecommunications network, the Network Management Center (NMC) must enforce who can see or modify which pieces of information—alarms, performance counters, work‑order details, or configuration data. The mechanism that decides “who may do what” is called **access control**. It is built on two complementary capabilities defined in 3GPP TS 28.533: **authentication** (proving the identity of a requester) and **authorization** (granting concrete permissions once the identity is known) [TS 28.533 §4.9].

### Key Definitions

| Symbol | Meaning | Unit / Note |
|--------|---------|-------------|
| **MnS consumer** | An entity (person, process, or device) that requests a Management‑Network Service (MnS). | – |
| **MnS producer** | The network element or software that provides the MnS. | – |
| **Authentication Service producer** | Provides identity‑management and authentication functions for MnS consumers/producers. | – |
| **Authorization Service producer** | Provides permission‑management for MnS consumers (or groups). | – |
| **Explicit authentication** | Direct interaction of the consumer with the authentication service to obtain an authentication assertion. | – |
| **Implicit authentication** | Authentication occurs indirectly via the MnS producer, establishing a secure session. | – |
| **Explicit authorization** | Consumer obtains an access token from the authorization service; the producer validates the token. | – |
| **Implicit authorization** | Producer enforces locally stored or synchronised policies without a token exchange. | – |
| **Access token** | A digitally signed data structure that may contain a list of permissions $P = \{p_1, p_2, \dots\}$ and conditions. | – |
| **Certificate (CA‑signed)** | Public‑key credential used to authenticate the opposite party over TLS/SSH. | – |

### How Roles Map to Permissions

1. **Identity establishment** – A *MnS consumer* (e.g., a NMC operator, a field‑engineer terminal, or an automated alarm‑correlation service) first authenticates.  
   - If the consumer uses **explicit authentication**, it contacts the *Authentication Service producer* directly and receives an authentication assertion.  
   - If the consumer uses **implicit authentication**, the *MnS producer* mediates the authentication, typically by establishing a TLS session whose server certificate is verified.  

2. **Permission granting** – After successful authentication, the consumer must be authorized.  
   - In **explicit authorization**, the consumer asks the *Authorization Service producer* for an *access token* containing the permitted actions (e.g., “read‑alarm”, “write‑work‑order”). The *MnS producer* checks the token’s digital signature before honoring the request.  
   - In **implicit authorization**, the *MnS producer* already holds local or synchronised policies and decides whether to allow the operation without a token.  

Because the same consumer can belong to a *group* of consumers, the authorization service may grant permissions to the entire group, simplifying role‑based access control (RBAC) in the NMC.

### Deployment Levels and Cross‑Domain Considerations

Both the authentication and authorization service producers can be instantiated **at domain level** (e.g., inside a Radio Access Network (RAN) or Core Network (CN) domain) or **in a centralized manner** at the PLMN level [TS 28.533 §4.9].  

- **Domain‑level deployment** is optimal when the consumer and producer reside in the same logical domain; it reduces latency and limits the scope of credentials.  
- **Centralized deployment** (also called *Cross‑Domain Authorization Service producer*) is required when a consumer in one domain needs to access a producer in another domain; the central service can issue tokens that are recognised across domains [TS 28.533 §4.9.2].

### Worked Example

Assume a field‑engineer terminal (consumer) needs to read the alarm list of a base‑station (producer) that belongs to a different domain.

| Step | Action | Relevant Service | Outcome |
|------|--------|------------------|---------|
| 1 | The terminal initiates a TLS connection to the *Authentication Service producer* (centralized). | Authentication Service (explicit) | The terminal validates the producer’s CA‑signed certificate (as described in Note 3). |
| 2 | The terminal sends its own certificate (also CA‑signed) and receives an authentication assertion. | Authentication Service | Identity of the terminal is now proven. |
| 3 | The terminal requests an access token for permission “read‑alarm” from the *Authorization Service producer* (centralized). | Authorization Service (explicit) | The service returns a token that includes the permission list $\{ \text{read‑alarm} \}$ and a digital signature. |
| 4 | The terminal presents the token to the base‑station’s management interface. | MnS Producer (implicit authorization) | The base‑station verifies the token’s signature and, seeing the required permission, returns the alarm list. |

No numerical values are required by the specification, but the token could, for instance, be a JSON Web Token (JWT) with a 5‑minute validity—this is an implementation detail, not mandated by the reference.

### Common Mistakes and Practical Notes

| Mistake | Why it Happens | Correct Practice |
|---------|----------------|------------------|
| **Confusing explicit and implicit authentication** – assuming the same flow applies to both. | The specification distinguishes “direct interaction” (explicit) from “indirect via producer” (implicit). | Verify whether the consumer contacts the authentication service *directly* (explicit) or only through the MnS producer (implicit). |
| **Assuming certificates are only for the consumer** – ignoring that the consumer also validates the producer’s certificate. | Note 3 and Note 4 describe mutual certificate validation. | Always validate the certificate of the party you are connecting to (producer or authentication service). |
| **Deploying a single domain‑level authorization service for cross‑domain work** – leading to denied access. | Cross‑domain access requires a centralized (Cross Domain) Authorization Service producer. | Use a centralized authorisation service when consumers and producers belong to different domains. |
| **Granting permissions directly in the MnS producer without a token** – violating the explicit‑authorization model. | Explicit authorization requires a token with a signed permission list. | When explicit authorization is required, ensure the token is present and verified before granting access. |
| **Over‑looking group‑based permissions** – managing each user individually. | The reference allows “group of MnS consumers” to be provisioned with the same policies. | Define roles as groups and assign permissions at the group level to simplify administration. |

By adhering strictly to the authentication and authorization mechanisms defined in TS 28.533, a network operation centre can guarantee that each role—whether an operator, automated system, or field engineer—accesses only the data it is entitled to, thereby preserving both operational efficiency and security.

## 練習題

**1.** Which deployment option for the Authorization Service producer is intended to support access control between a MnS consumer and producer that reside in different domains?

- A. Deployment at the RAN level
- B. Deployment at the CN level
- C. Deployment at the domain level only
- D. Deployment in a centralized manner (e.g., PLMN level)

<details><summary>看答案</summary>

正解：D。A centralized deployment, such as at the PLMN level, enables cross‑domain authorization.

</details>

**2.** In the context of the specification, what characterises **explicit authorization**?

- A. The MnS producer enforces access control using locally pre‑configured policies.
- B. The MnS consumer obtains an access token from the authorization service producer before contacting the MnS producer.
- C. The MnS consumer authenticates the producer by validating its TLS certificate.
- D. The MnS producer automatically grants all requested permissions.

<details><summary>看答案</summary>

正解：B。Explicit authorization requires the consumer to interact with the authorization service to receive a signed token.

</details>

**3.** Which note explains the use of a certificate issued by a trusted CA to authenticate the **authentication service producer**?

- A. Note 1
- B. Note 2
- C. Note 3
- D. Note 4

<details><summary>看答案</summary>

正解：C。Note 3 specifically states that a trusted CA certificate is used to authenticate the authentication service producer.

</details>

**4.** How is **implicit authentication** defined in the reference text?

- A. The MnS consumer directly contacts the authentication service producer to obtain an assertion.
- B. The MnS consumer interacts indirectly with authentication via the MnS producer to establish a secure session.
- C. The MnS consumer validates the producer’s certificate without contacting any service.
- D. The MnS consumer uses a one‑time password supplied by the producer.

<details><summary>看答案</summary>

正解：B。Implicit authentication occurs when the consumer’s authentication is performed indirectly through the MnS producer.

</details>

**5.** According to the specification, which component may be deployed **together with the management service producer** at the domain level?

- A. Authentication Service producer
- B. Cross‑Domain Authorization Service producer
- C. Domain Authorization Service producer
- D. Network Slice selection function

<details><summary>看答案</summary>

正解：C。The domain‑level Authorization Service producer can be co‑located with the management service producer.

</details>
