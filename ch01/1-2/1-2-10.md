# 1.2.10 網路介面：NG、Xn、F1、E1 與 N4（PFCP）

所屬：[1.2 通訊協定](../1-2.md)

> 本頁正文與練習題由本機模型 gpt-oss-120b 撰寫，經程式驗算與另一個模型（Gemma-4-31B）交叉驗題，尚待專家審閱。

## 正文

In a 5G System (5GS) the radio access network (RAN) is no longer a monolithic base station. Instead it is split into logical functions that may be deployed on separate hardware, possibly in different geographic locations. The split introduces a set of standardized **reference points**—NG, Xn, F1, E1, and N4—that carry control‑plane (CP) and user‑plane (UP) traffic between the functions. Understanding these interfaces is essential for network dimensioning, troubleshooting, and for designing any custom element (e.g., a proprietary UPF) that must interoperate with the rest of the 5GS.

---

### 1. NG Interface (NG‑AP)

| Endpoints | AMF ↔ gNB (or ng‑eNB) |
|-----------|----------------------|
| Plane     | Control (NG‑AP)      |
| Protocol  | SCTP (Stream Control Transmission Protocol) over IP |
| Main purpose | Mobility management, session establishment, security context handling |

The NG‑AP (NG Application Protocol) is carried over SCTP streams. Each SCTP association can host up to 65535 streams, but 3GPP recommends using at most 4 for NG‑AP to keep ordering predictable.  

Key messages (simplified):

- **NG‑Setup‑Request / NG‑Setup‑Response** – establishes the SCTP association.
- **Initial‑Context‑Setup‑Request / Response** – transfers UE context from AMF to gNB.
- **UE‑Context‑Release‑Request / Response** – releases UE resources.

A useful formula for estimating the **control‑plane latency** over NG is:

$$
L_{\text{NG}} = T_{\text{SCTP\_setup}} + N_{\text{msg}} \times (T_{\text{proc}} + T_{\text{prop}})
$$

where  

* $T_{\text{SCTP\_setup}}$ – time to establish the SCTP association (ms),  
* $N_{\text{msg}}$ – number of NG‑AP messages exchanged,  
* $T_{\text{proc}}$ – processing time per message at each node (ms),  
* $T_{\text{prop}}$ – one‑way propagation delay between AMF and gNB (ms).

---

### 2. Xn Interface (Xn‑AP)

| Endpoints | gNB ↔ gNB (or gNB ↔ ng‑eNB) |
|-----------|----------------------------|
| Plane     | Control (Xn‑AP) and optionally User (Xn‑U) |
| Protocol  | SCTP for Xn‑AP; GTP‑U for Xn‑U |
| Main purpose | Handover, load balancing, inter‑gNB coordination |

Xn replaces the legacy X2 interface of LTE. It carries handover preparation messages (e.g., **Handover‑Request**) and can transport user data directly when low latency is required (Xn‑U).  

Latency over Xn‑U is governed by the GTP‑U tunnel performance:

$$
\text{Throughput}_{\text{Xn‑U}} = \frac{\text{MTU}_{\text{GTP}}}{\text{RTT}_{\text{Xn}} + \frac{\text{MTU}_{\text{GTP}}}{C_{\text{link}}}}
$$

where  

* $\text{MTU}_{\text{GTP}}$ – maximum transmission unit of the GTP tunnel (bytes),  
* $\text{RTT}_{\text{Xn}}$ – round‑trip time between the two gNBs (ms),  
* $C_{\text{link}}$ – physical link capacity (bits s$^{-1}$).

---

### 3. F1 Interface (F1‑AP)

The F1 interface connects the **gNB‑Centralized Unit (CU‑CP)** to the **gNB‑Distributed Unit (DU)**. It is defined for the 5G‑RAN split option 2 (or higher).

| Endpoints | CU‑CP ↔ DU |
|-----------|-----------|
| Plane     | Control (F1‑AP) and User (F1‑U) |
| Protocol  | SCTP for F1‑AP; Ethernet (or NG‑U) for F1‑U |
| Main purpose | Transport of radio‑bearer configuration (control) and user data (user) between CU and DU |

F1‑AP messages include **Setup Request/Response**, **Radio‑Resource‑Management‑Config**, and **UE‑Context‑Setup**. The user‑plane part (F1‑U) uses GTP‑U encapsulation similar to Xn‑U.

A practical performance metric is the **split‑delay budget**:

$$
D_{\text{split}} = D_{\text{CU‑proc}} + D_{\text{F1‑latency}} + D_{\text{DU‑proc}}
$$

All terms are in milliseconds and must satisfy the end‑to‑end Radio Access Network (RAN) latency requirement (e.g., ≤ 10 ms for URLLC).

---

### 4. E1 Interface (E1‑AP)

E1 links the **CU‑Control Plane (CU‑CP)** to the **CU‑User Plane (CU‑UP)** within the same gNB‑CU logical entity.

| Endpoints | CU‑CP ↔ CU‑UP |
|-----------|--------------|
| Plane     | Control (E1‑AP) |
| Protocol  | SCTP |
| Main purpose | Transfer of session‑level control information (e.g., QoS, flow binding) between the two CU parts |

E1‑AP messages mirror NG‑AP but are scoped to the CU. Because CU‑CP and CU‑UP often run on the same host, the SCTP association may be loopback, reducing $T_{\text{prop}}$ to near‑zero. Nonetheless, the **processing latency** remains a design variable.

---

### 5. N4 Interface (PFCP)

N4 is the **User‑Plane Function (UPF) ↔ Session Management Function (SMF)** reference point. It uses the **Packet Forwarding Control Protocol (PFCP)**, a UDP‑based protocol defined in 3GPP TS 29.244.

| Endpoints | SMF ↔ UPF |
|-----------|----------|
| Plane     | Control (PFCP) |
| Transport | UDP over IPv4/IPv6 |
| Main purpose | Create, modify, delete PDRs (Packet Detection Rules) and FARs (Forwarding Action Rules), report statistics, and manage session heart‑beats |

#### PFCP Message Overview
- **PFCP‑Session‑Establishment‑Request/Response** – creates a PDR/FAR set for a new UE session.
- **PFCP‑Session‑Modification‑Request/Response** – updates QoS parameters.
- **PFCP‑Heartbeat‑Request/Response** – keeps the SMF‑UPF association alive.
- **PFCP‑Report‑Response** – carries usage statistics (bytes, packets, timestamps).

#### Key PFCP Parameters

- **PDR ID** – 16‑bit identifier of a detection rule.
- **FAR ID** – 16‑bit identifier of a forwarding rule.
- **UE IP** – IPv4/IPv6 address of the UE.
- **QoS Flow Identifier (QFI)** – 6‑bit value indicating the QoS profile.

#### Heartbeat Interval Calculation  

To avoid session timeout, the SMF must send a **Heartbeat Request** before the **Heartbeat Timer** expires. If the measured round‑trip time (RTT) on N4 is $RTT_{N4}$ and the timer is set to $T_{\text{HB}}$, a safe interval $I_{\text{HB}}$ is:

$$
I_{\text{HB}} = T_{\text{HB}} - \alpha \times RTT_{N4}
$$

where $0 < \alpha < 1$ is a safety factor (commonly 0.8).  

---

#### Worked Example: Determining a PFCP Heartbeat Interval  

A mobile operator configures the SMF‑UPF heartbeat timer to **30 seconds**. The measured one‑way propagation delay on N4 is **5 ms**, and processing at each end adds **2 ms**.  

1. Compute RTT:  

$$
RTT_{N4} = 2 \times (5\ \text{ms} + 2\ \text{ms}) = 14\ \text{ms}
$$

2. Choose $\alpha = 0.8$.  

$$
I_{\text{HB}} = 30\,\text{s} - 0.8 \times 0.014\,\text{s}
               = 30\,\text{s} - 0.0112\,\text{s}
               \approx 29.99\,\text{s}
$$

Thus the SMF should transmit a PFCP Heartbeat Request at least every **29.9 seconds** to guarantee that the UPF receives it before the timer expires, even under worst‑case processing jitter.

### 6. Common Mistakes and Practical Tips  

| Mistake | Why it Happens | Remedy |
|---------|----------------|--------|
| **Confusing NG with N2** | Both are control‑plane interfaces; NG links AMF↔gNB, N2 links AMF↔gNB‑CU in LTE‑evolved architecture. | Remember that NG is **5G‑only**; N2 exists only in the LTE‑NR interworking scenario. |
| **Treating Xn as pure user‑plane** | Xn‑AP (control) and Xn‑U (user) are separate; many engineers configure only Xn‑AP and forget Xn‑U, causing handover data loss. | Verify that both Xn‑AP and Xn‑U are provisioned when using inter‑gNB data forwarding. |
| **Mixing up F1‑C and F1‑U messages** | F1‑AP (control) and F1‑U (user) share the same reference point name, leading to mis‑routed packets. | Use distinct SCTP streams for F1‑AP and separate Ethernet tunnels for F1‑U; label them clearly in configuration. |
| **Setting N4 heartbeat timer too low** | Over‑frequent heartbeats increase UDP load and may trigger rate‑limiting on the UPF. | Choose the timer based on measured RTT and add a safety margin; avoid values < 5 s unless required by the network slice. |
| **Ignoring PFCP cause codes** | When a PFCP Session Modification fails, engineers often look only at the UDP payload size, missing the **Cause Value** that explains the error (e.g., “Insufficient resources”). | Log the full PFCP response, parse the Cause IE, and correlate with UPF resource tables. |

**Practical tip:** In a split‑RAN deployment, keep the **F1 latency** below 2 ms and the **E1 latency** below 1 ms to meet the 5G URLLC target of ≤ 4 ms air‑interface latency. Use network‑time protocol (NTP) or PTP synchronization across CU‑CP, CU‑UP, and DU to avoid jitter that would otherwise inflate $D_{\text{split}}$.

---

By mastering the NG, Xn, F1, E1, and N4 interfaces—and the protocols that run over them—engineers can design scalable, low‑latency 5G networks, troubleshoot cross‑functional issues, and extend the core with custom functions that still interoperate with the standardized 5GS.
