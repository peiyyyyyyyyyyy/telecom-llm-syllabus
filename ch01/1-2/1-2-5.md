# 1.2.5 MPLS 與 VPN

所屬：[1.2 通訊協定](../1-2.md)

## 正文

### What MPLS and VPNs Are, and Why They Matter  

Multiprotocol Label Switching (MPLS) is a packet‑forwarding mechanism that inserts a short, fixed‑length **label** (typically 20 bits) between the Layer 2 header and the Layer 3 payload.  Each MPLS‑enabled router—called a **Label Switching Router (LSR)**—uses the label to make a **forwarding equivalence class (FEC)** decision without consulting the IP routing table.  By chaining FECs across a provider’s core, MPLS builds **label‑switched paths (LSPs)** that guarantee deterministic forwarding, traffic engineering (TE) capabilities, and fast reroute.

A **Virtual Private Network (VPN)** on top of MPLS isolates customers’ traffic while sharing the same physical infrastructure.  The provider’s core carries many customers’ packets, each distinguished by MPLS labels (and by **VPN identifiers** such as Route Distinguishers).  MPLS‑based VPNs are the dominant solution for **Layer 3 IP VPNs (BGP/MPLS VPNs)** and **Layer 2 VPNs (VPLS, EVPN)** in carrier networks because they combine scalability, QoS, and service‑level guarantees.

---

### Key Definitions  

| Symbol | Meaning | Unit / Size |
|--------|---------|-------------|
| $L$ | MPLS label value (20 bits) | bits |
| $TTL$ | Time‑to‑Live field in MPLS header | hops |
| $S$ | Stack depth (number of MPLS headers) | integer |
| $H_{L2}$ | Original Layer 2 header length (e.g., Ethernet) | bytes |
| $H_{IP}$ | Original IP header length (without options) | bytes = 20 |
| $H_{MPLS}$ | MPLS header length per label | 4 bytes |
| $O_{MPLS}$ | Total MPLS overhead | $S \times H_{MPLS}$ |
| $MTU_{eff}$ | Effective MTU after MPLS encapsulation | $MTU - O_{MPLS}$ |
| $VRF$ | Virtual Routing and Forwarding instance (per‑VPN routing table) | – |
| $RD$ | Route Distinguisher (unique 64‑bit value) | – |
| $RT$ | Route Target (extended BGP community used for import/export) | – |
| $B_{LSP}$ | Bandwidth reserved for an LSP (e.g., 100 Mbps) | bps |

**MPLS Header (per label)**  

```
+-------------------+-------------------+
| Label (20 bits)   | Exp (3 bits)      |
+-------------------+-------------------+
| S (1 bit) | TTL (8 bits)                |
+--------------------------------------+
```

* **Label** – identifies the FEC.  
* **Exp** – experimental field, commonly used for QoS (3 bits → 8 priority levels).  
* **S** – “bottom of stack” flag; S = 1 for the last label.  
* **TTL** – decremented at each hop, preventing label loops.

**Label Operations**  

| Operation | Description |
|-----------|-------------|
| **Push** | Insert one or more new labels on top of the existing stack (used at PE ingress). |
| **Swap** | Replace the top label with a new label (common on transit LSRs). |
| **Pop** | Remove the top label (used at PE egress before delivering the original packet). |

**VPN Constructs**  

* **VRF** – a separate routing table per VPN; packets are forwarded based on the VRF rather than the global routing table.  
* **Route Distinguisher (RD)** – concatenates a 16‑bit administrator field with a 48‑bit customer field to make IP prefixes globally unique: $RD = (admin\_id, customer\_id)$.  
* **Route Target (RT)** – a BGP extended community (type 2) that indicates which VRFs should import/export a route.  

**BGP/MPLS IP VPN (RFC 4364)**  

1. **Customer edge (CE)** advertises routes to its **Provider Edge (PE)** via iBGP or eBGP.  
2. PE **adds an RD** to each prefix, creating a **VPN‑IP** address: $RD:IP\_prefix$.  
3. PE **injects** these VPN‑IP routes into the provider’s **MP‑iBGP** table, tagging them with one or more **RTs**.  
4. Other PEs **import** routes whose RTs match their VRF import list, populating the VRF routing tables.  
5. When forwarding, the egress PE **pushes** a **VPN label** (usually the **bottom‑of‑stack** label) onto the packet; the core LSPs forward based on the **transport label** only.  

---

### Formulas  

1. **Total MPLS overhead** for a packet that traverses $N$ LSPs and carries $V$ VPN‑specific labels:  

   $$
   O_{MPLS}= (N + V) \times H_{MPLS}
   $$

   where $H_{MPLS}=4\ \text{bytes}$.  

2. **Effective MTU** after MPLS encapsulation:  

   $$
   MTU_{eff}= MTU_{orig} - O_{MPLS}
   $$

3. **Label space per LSR** (assuming 20‑bit label field, reserved values for special purposes):  

   $$
   L_{max}=2^{20} - \text{reserved}
   $$

   Typically $\text{reserved}=2^{8}$, leaving $L_{max}\approx 1{,}048{,}576$ usable labels.

---

### Worked Example  

A service provider offers a 100 Mbps MPLS‑L3VPN to Customer A. The provider network consists of:

* **PE‑in** (ingress) → **LSR‑1** → **LSR‑2** → **PE‑out** (egress).  

The provider reserves **one transport label** per hop (swap) and **one VPN label** at the egress. The customer’s Ethernet frames have an original MTU of 1500 bytes.

1. **Determine stack depth $S$**:  
   * Transport labels: 3 hops (PE‑in → LSR‑1, LSR‑1 → LSR‑2, LSR‑2 → PE‑out) → $N=3$  
   * VPN label at egress: $V=1$  
   * $S = N + V = 4$  

2. **Compute MPLS overhead**:  

   $$
   O_{MPLS}=4 \times 4\ \text{bytes}=16\ \text{bytes}
   $$

3. **Effective MTU**:  

   $$
   MTU_{eff}=1500\ \text{bytes} - 16\ \text{bytes}=1484\ \text{bytes}
   $$

4. **Result**: The provider must ensure that the customer’s devices do not exceed 1484 bytes, or the provider must enable **MPLS‑aware Path MTU Discovery** to fragment or drop oversized packets.

### Common Mistakes and Practical Notes  

| Mistake | Why It Happens | Remedy |
|---------|----------------|--------|
| **Using the same label range on adjacent LSRs** | Labels are locally significant; reusing a label that is still present in the downstream stack can cause premature pop. | Verify that each LSR clears or swaps the top label before forwarding; use distinct label pools per LSR. |
| **Forgetting to set the Bottom‑of‑Stack (S) bit** | Without S = 1 the egress PE cannot know where the label stack ends, leading to mis‑interpretation of the payload. | Ensure PE‑out pushes the VPN label with S = 1; transit LSRs must preserve the S bit on swap. |
| **Mismatched Route Targets (RTs) between VRFs** | Import/export policies rely on RTs; a missing RT prevents routes from populating the correct VRF. | Double‑check RT import/export lists on all PEs; use a consistent naming convention. |
| **Neglecting MPLS overhead in MTU calculations** | Overhead can cause unexpected fragmentation, especially on low‑MTU links (e.g., PPPoE). | Apply the $MTU_{eff}$ formula when configuring customer-facing interfaces. |
| **Confusing L2VPN (VPLS/EVPN) with L3VPN** | Both use MPLS but differ in how customer MAC/IP information is carried. | Choose the appropriate VPN type early in design; L2VPN carries Ethernet frames, L3VPN carries IP prefixes. |

**Operational tip:** When deploying TE LSPs, reserve bandwidth ($B_{LSP}$) using RSVP‑TE or Segment Routing (SR‑TE). The bandwidth reservation must be greater than the sum of all VPN traffic that will traverse the LSP to avoid congestion and packet loss.

## 練習題

**1.** In an MPLS label stack, which field indicates that the current label is the last (bottom) label?

- A. The Exp field
- B. The S (Bottom‑of‑Stack) bit
- C. The TTL field
- D. The Label field

<details><summary>看答案</summary>

正解：B。The S bit is defined as the Bottom‑of‑Stack flag; when set to 1, it marks the last label in the stack.

</details>

**2.** A provider edge (PE) router receives a customer packet and needs to forward it across the MPLS core to the egress PE. Which sequence of label operations is typically performed at the ingress PE?

- A. Pop → Swap → Push
- B. Push → Swap → Pop
- C. Push → Push → Swap
- D. Swap → Swap → Swap

<details><summary>看答案</summary>

正解：C。The ingress PE usually pushes a transport label (for the LSP) and a VPN label, then swaps the inner label as the packet enters the core.

</details>

**3.** In a BGP/MPLS IP VPN, what purpose does the Route Distinguisher (RD) serve?

- A. It defines the import/export policy between VRFs.
- B. It uniquely identifies a VPN‑IP prefix across the provider.
- C. It carries QoS priority information.
- D. It specifies the MPLS label space size.

<details><summary>看答案</summary>

正解：B。The RD is prepended to an IP prefix, making it globally unique within the provider’s MP‑iBGP table.

</details>

**4.** If a packet traverses three MPLS LSP hops and receives one VPN label at egress, what is the total MPLS overhead in bytes?

- A. 8 bytes
- B. 12 bytes
- C. 16 bytes
- D. 20 bytes

<details><summary>看答案</summary>

正解：C。Four labels × 4 bytes per MPLS header = 16 bytes of overhead.

</details>

**5.** Which of the following is a common cause of label‑related forwarding errors in an MPLS network?

- A. Using a 24‑bit label field instead of 20 bits.
- B. Not clearing the Bottom‑of‑Stack bit on transit LSRs.
- C. Assigning the same label value on two non‑adjacent LSRs.
- D. Forgetting to decrement the MPLS TTL field.

<details><summary>看答案</summary>

正解：D。MPLS TTL must be decremented at each hop; failure to do so can cause loops and excessive label propagation.

</details>
