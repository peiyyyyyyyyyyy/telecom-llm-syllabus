# 1.2.9 控制面與用戶面協定堆疊

## 正文

In any packet‑switched network the *control plane* (CP) and the *user (or data) plane* (UP) form two logical, and often physically distinct, processing pipelines. The control plane is responsible for network management, session establishment, mobility handling, and routing decisions. The user plane carries the actual payload—voice, video, IoT telemetry, etc.—from source to destination. Keeping these planes separate allows operators to scale forwarding capacity independently of signaling capacity, to introduce new services without touching the fast‑path datapath, and to apply different reliability or latency guarantees to each.

---

### 1.2.1 Logical Stack Overview

| Layer (OSI‑like) | Control‑Plane Protocols (examples) | User‑Plane Protocols (examples) |
|------------------|------------------------------------|---------------------------------|
| Application      | Network Management (NETCONF, REST‑CONF), Service Orchestration (SBI) | Application payload (HTTP, RTP, MQTT) |
| Transport        | SCTP (for NG‑AP, GTP‑C), TCP (for Diameter, NETCONF) | UDP/TCP (for user traffic) |
| Network          | Routing protocols (OSPF, BGP), Signalling tunnels (GTP‑C) | IP forwarding, MPLS label swapping, GTP‑U |
| Data Link        | SDN control channel (OpenFlow), LLDP for topology discovery | Ethernet, Wi‑Fi MAC, LTE/5G MAC |
| Physical         | – (signalling is encapsulated in the same physical media) | PHY (NR, LTE, Ethernet PHY) |

In 5G NR the control‑plane stack is anchored in the **NG Application Protocol (NGAP)** over SCTP, which in turn sits on IP. The user‑plane stack begins with **GTP‑U** (User‑Plane Tunnel) over UDP/IP, then traverses the radio protocol stack PDCP → RLC → MAC → PHY. A similar separation exists in legacy LTE (S1‑AP / S1‑MME vs. GTP‑U) and in MPLS‑based backbone networks (OSPF/BGP for control, LSP forwarding for data).

---

### 1.2.2 Key Definitions and Quantitative Relationships

1. **Control‑Plane Load (CPL)** – the average number of signalling bits transmitted per second on a given link.  
   $$\text{CPL} = \frac{\sum_{i=1}^{N} S_i}{\Delta t}$$  
   where $S_i$ (bits) is the size of the $i^{\text{th}}$ signalling message during observation interval $\Delta t$ (seconds).

2. **User‑Plane Throughput (UPT)** – the effective payload rate delivered to the application layer.  
   $$\text{UPT} = \frac{L_{\text{payload}}}{T_{\text{frame}}} \times \eta_{\text{eff}}$$  
   - $L_{\text{payload}}$ (bits) = user data per transmission unit (e.g., per TTI in NR).  
   - $T_{\text{frame}}$ (seconds) = duration of the transmission unit (e.g., $1\,$ms for a sub‑frame).  
   - $\eta_{\text{eff}}$ (unitless) = efficiency factor accounting for protocol overhead (header, retransmission, coding rate).

3. **Control‑to‑User Ratio (C/U)** – a useful metric for dimensioning signalling channels (e.g., NR PUCCH).  
   $$\frac{C}{U} = \frac{\text{CPL}}{\text{UPT}}$$  
   A low C/U (e.g., $<0.01$) indicates a data‑heavy flow, whereas a high C/U (e.g., $>0.1$) signals a signalling‑intensive session such as a massive‑IoT device attachment.

4. **Latency Budgets** – separate maximum allowable delays for CP and UP. In 5G the *Control‑Plane latency* $\tau_{\text{CP}}$ must be ≤ 10 ms for handover, while *User‑Plane latency* $\tau_{\text{UP}}$ may be as low as 1 ms for URLLC services.

### 1.2.3 Worked Example: Estimating Effective Downlink Rate in a 5G Cell

A 5G NR gNB serves a UE with the following parameters:

| Parameter                              | Value |
|----------------------------------------|-------|
| Sub‑frame duration $T_{\text{frame}}$  | $1\,$ms |
| Modulation order (bits per symbol)     | 4 (16‑QAM) |
| Number of allocated PRBs (N\_PRB)      | 50 |
| OFDM symbol count per sub‑frame        | 14 |
| CP overhead per OFDM symbol            | 7 % |
| PDCP header size $H_{\text{PDCP}}$     | 12 bytes |
| RLC Acknowledged Mode (AM) header      | 4 bytes |
| MAC sub‑header                         | 2 bytes |
| Average retransmission factor $\rho$   | 1.05 |

1. **Calculate raw physical bits per sub‑frame**  
   $$B_{\text{raw}} = N_{\text{PRB}} \times 12\ \text{subcarriers} \times 14\ \text{symbols} \times 4\ \text{bits/sym} \times (1-0.07)$$  
   $$B_{\text{raw}} = 50 \times 12 \times 14 \times 4 \times 0.93 = 39{,}312\ \text{bits}$$

2. **Subtract protocol overhead**  
   Total header per Transport Block (TB):  
   $$H_{\text{total}} = (H_{\text{PDCP}} + H_{\text{RLC}} + H_{\text{MAC}}) \times 8 = (12+4+2) \times 8 = 144\ \text{bits}$$  

   Effective payload bits per sub‑frame:  
   $$L_{\text{payload}} = (B_{\text{raw}} - H_{\text{total}}) \times \rho = (39{,}312 - 144) \times 1.05 \approx 41{,}280\ \text{bits}$$  

3. **Compute user‑plane throughput**  
   $$\text{UPT} = \frac{L_{\text{payload}}}{T_{\text{frame}}} = \frac{41{,}280\ \text{bits}}{1\ \text{ms}} = 41.28\ \text{Mbps}$$  

Thus, despite a nominal 50 PRB allocation (≈ 50 Mbps raw), the actual downlink throughput observed by the application is about **41 Mbps** after accounting for control‑plane protocol headers and a modest retransmission overhead.

If the same UE generates a typical RRC connection request of 300 bytes every 10 seconds, the control‑plane load is:  
$$\text{CPL} = \frac{300 \times 8}{10} = 240\ \text{bits/s}$$  
Resulting C/U ratio:  
$$\frac{C}{U} = \frac{240}{41.28 \times 10^{6}} \approx 5.8 \times 10^{-6}$$  
which is negligible for this data‑heavy scenario.

### 1.2.4 Practical Notes & Common Pitfalls

| Pitfall | Why it Happens | Corrective Action |
|---------|----------------|-------------------|
| **Mixing CP and UP metrics** (e.g., reporting latency of GTP‑U as control‑plane latency) | The same packet trace often carries both signalling and data fields, leading to ambiguous measurements. | Separate measurement points: use NG‑AP/SCTP for CP latency, GTP‑U/IP forwarding counters for UP latency. |
| **Under‑estimating header overhead** in high‑layer protocols (e.g., ignoring PDCP sequence numbers) | Engineers may assume only MAC/PHY overhead matters. | Include every mandatory header from the top of the UP stack down to the transport layer when computing $\eta_{\text{eff}}$. |
| **Assuming CP traffic is negligible** | In massive‑IoT or URLLC scenarios, frequent RRC re‑configurations or handovers can dominate link usage. | Compute C/U ratio periodically; if $C/U > 0.05$, revisit control‑channel dimensioning (e.g., increase PUCCH resources). |
| **Violating latency budgets by placing CP functions on congested CPUs** | Control‑plane functions (NGAP, Diameter) are often hosted on general‑purpose servers; queuing delays can exceed the 10 ms budget. | Deploy CP functions on low‑latency cores, enable priority queuing, and monitor $\tau_{\text{CP}}$ end‑to‑end. |
| **Using the same QoS class for CP and UP** | CP messages require reliable delivery but low bandwidth, whereas UP may need high bandwidth with best‑effort loss tolerance. | Map CP signalling to a dedicated QoS Identifier (e.g., 5QI = 71 in 5G) and enforce strict ERAB policies. |

Finally, remember that the separation of control and user planes is a design principle, not a strict physical partition. In some low‑cost deployments (e.g., small cells or edge routers) the same ASIC may process both planes, but the logical distinction—and the associated protocol stacks—must still be respected in software design, performance testing, and standards compliance.
