# 1.2.6 無線介面協定：RRC、SDAP、PDCP、RLC、MAC、PHY

所屬：[1.2 通訊協定](../1-2.md)

## 正文

In 5G NR the radio interface is realised as a strict layered protocol stack that separates control‑plane signalling from user‑plane data transport.  The separation enables independent optimisation of latency, reliability and throughput for signalling (e.g., hand‑over, bearer set‑up) and for user traffic (e.g., video, massive IoT).  All layers above the physical (PHY) layer are defined in 3GPP TS 38.300; the stack is split between the *user plane* and the *control plane* as shown in the specifications.

---

### User‑Plane Stack  

The user‑plane protocol stack consists of four sub‑layers that are terminated in the gNB on the network side:

| Sub‑layer | Position in the stack | Role (as defined in clause 6) |
|-----------|----------------------|------------------------------|
| **SDAP**  | Topmost (above PDCP) | Provides service‑data‑adaptation functions |
| **PDCP**  | Below SDAP           | Performs header compression, encryption and integrity protection |
| **RLC**   | Below PDCP           | Handles segmentation, concatenation and retransmission |
| **MAC**   | Below RLC            | Schedules radio resources and multiplexes logical channels |

These layers together transport user payload from the UE to the gNB (and vice‑versa) before the signal is handed to the PHY for over‑the‑air transmission.  The specification explicitly lists SDAP, PDCP, RLC and MAC as the sub‑layers of the user plane [TS 38.300 §4.4.1].

> *“The figure below shows the protocol stack for the user plane, where SDAP, PDCP, RLC and MAC sublayers (terminated in gNB on the network side) perform the functions listed in clause 6.”*  

---

### Control‑Plane Stack  

The control‑plane stack shares three sub‑layers with the user plane (PDCP, RLC, MAC) and adds the **RRC** (Radio Resource Control) layer on top:

| Sub‑layer | Position | Function (as defined in clause 7) |
|-----------|----------|-----------------------------------|
| **RRC**   | Topmost  | Manages radio resources, connection state, and mobility |
| **PDCP**  | Below RRC| Same functions as in the user plane (header compression, security) |
| **RLC**   | Below PDCP| Same segmentation/retransmission duties |
| **MAC**   | Below RLC| Same scheduling and multiplexing duties |

All four sub‑layers are terminated in the gNB on the network side, while the RRC terminates in the gNB and interacts with the NAS protocol in the AMF.  The specification states that PDCP, RLC and MAC are present in the control plane, and that RRC “performs the functions listed in clause 7” [TS 38.300 §4.4.2].

> *“The figure below shows the protocol stack for the control plane, where: – PDCP, RLC and MAC sublayers (terminated in gNB on the network side) perform the functions listed in clause 6; – RRC (terminated in gNB on the network side) performs the functions listed in clause 7; – NAS control protocol (terminated in AMF on the network side) performs the functions listed in TS 23.501 …”*  

---

### PHY Layer (Outside the Scope of the Reference)

The PHY (Physical) layer sits below MAC and is responsible for modulation, coding, and radio‑frequency transmission.  The TS 38.300 excerpts used for this subsection do **not** describe PHY functions or its placement; therefore a detailed description is omitted here.  Readers should consult TS 38.211 (Physical channels and modulation) for the complete PHY definition.

---

### Worked Example  

A UE sends a 1 kB (1024 bytes) user payload over the NR uplink.  The payload traverses the user‑plane stack as follows:

| Layer | Typical overhead (illustrative) | Resulting size |
|-------|----------------------------------|----------------|
| SDAP  | 0 bytes (no additional header)   | 1024 bytes |
| PDCP  | 2 bytes (ciphering header)       | 1026 bytes |
| RLC   | 3 bytes (segmentation header)    | 1029 bytes |
| MAC   | 2 bytes (MAC header)             | 1031 bytes |
| PHY   | (modulation, coding – not counted) | – |

The total size presented to the PHY is **1031 bytes**, i.e., the original payload plus the cumulative overhead of the four sub‑layers.  This simple arithmetic illustrates how each sub‑layer adds protocol‑specific headers, a fact implied by the “functions listed in clause 6” for each layer.

### Common Mistakes & Practical Notes  

| Mistake | Why it occurs | Correct practice |
|---------|---------------|------------------|
| **Treating RRC as a user‑plane layer** | RRC is only present in the control plane. | Remember that RRC terminates in the gNB and handles signalling, not user data. |
| **Omitting SDAP when analysing uplink data** | SDAP is sometimes overlooked because it has no header in many deployments. | Include SDAP in the stack diagram; even if it adds no bytes, it defines service‑data mapping. |
| **Assuming PDCP, RLC, MAC are different between planes** | The same sub‑layers exist in both planes but serve different traffic (signalling vs. payload). | Recognise that PDCP/RLC/MAC share the same implementation; only the uppermost layer (SDAP vs. RRC) differs. |
| **Confusing termination points** | NAS runs in the AMF, not in the gNB, leading to placement errors. | Keep NAS separate from the NR radio stack; only NAS is mentioned in the control‑plane description. |
| **Attempting to derive PHY behaviour from this subsection** | The reference does not describe PHY. | Consult the dedicated PHY specification (TS 38.211) for modulation, coding, and radio‑frequency details. |

Understanding the exact composition of the NR protocol stack is essential for performance modelling, troubleshooting, and for designing network functions that interact with specific sub‑layers (e.g., implementing a custom RLC retransmission policy).  The clear separation of user‑plane and control‑plane layers, as defined in TS 38.300, provides a solid foundation for all higher‑level radio‑access engineering tasks.
