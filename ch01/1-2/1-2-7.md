# 1.2.7 核心網信令：NAS、NGAP、GTP、Diameter、SBI

所屬：[1.2 通訊協定](../1-2.md)

## 正文

The control plane of a mobile packet core is a collection of signalling protocols that set up, maintain and tear down user‑plane resources. Accurate exchange of these messages is essential for subscriber mobility, session continuity and efficient resource utilisation. In 3GPP systems the principal protocols are:

* **NAS (Non‑Access Stratum)** – signalling between the UE and the core network.  
* **NGAP (NG Application Protocol)** – control‑plane signalling on the N2 interface between the gNB and the AMF.  
* **GTP (GPRS Tunnelling Protocol)** – both control‑plane (GTP‑C) and user‑plane (GTP‑U) messages that create and manage tunnels across the EPC/5GC.  
* **Diameter** – the AAA protocol used on the S6a/S6d interfaces to exchange subscriber data with the HSS.  
* **SBI (Service‑Based Interface)** – HTTP/2 based API used in the 5G Core.  

The reference excerpts supplied cover **GTP** and **Diameter** in detail; the other three protocols are mentioned only to state that their specifications are outside the scope of the present references.

### GTP – Control Plane (GTP‑C)

GTP‑C messages are used to negotiate user‑plane tunnels. The most basic path‑management messages are **Echo Request**, **Echo Response** and **Version Not Supported Indication**.

| Message | Mandatory IE | Optional IE |
|---------|--------------|-------------|
| Echo Request | **Recovery** (contains the local Restart Counter) | Private Extension |
| Echo Response | **Recovery** (contains the local Restart Counter) | Private Extension |

The **Recovery** IE carries a *Restart Counter* that is incremented each time the node restarts, allowing a peer to detect a reset of state [TS 29.274 §7.1.1] [TS 29.274 §7.1.2]. The **Private Extension** may contain vendor‑specific data but is not required.

A GTP‑C node must include the Recovery IE when it contacts a peer **for the first time** or after a recent restart [TS 29.274 §7.2.0]. If the peer receives a Recovery IE with a higher counter than it has seen, it treats the message as if it were an Echo Response for state‑synchronisation purposes.

**Create Session Request** is the cornerstone tunnel‑setup message. Its direction depends on the involved entities:

* **MME → SGW** on the **S11** interface,  
* **SGW → PGW** on the **S5/S8** interface,  

and similarly for SGSN‑based procedures on **S4** [TS 29.274 §7.2.1].

The message is triggered by procedures such as *E‑UTRAN Initial Attach* or *PDN Connectivity* and carries the TEID that will identify the tunnel.

> **Worked example**  
> An MME restarts and sets its Restart Counter to 5. It sends an **Echo Request** on the S11 interface. The Echo Request includes the **Recovery** IE with value 5. The SGW receives it, notes the counter is higher than the previous value 3, and replies with an **Echo Response** containing **Recovery** 5. The exchange confirms both nodes are aware of the restart and can safely proceed with a **Create Session Request** that carries TEID $0x12345678$ (hexadecimal 305,419,896 decimal). The TEID is a 32‑bit unsigned identifier that multiplexes user packets on the GTP‑U tunnel [TS 29.281 §7.1].

### GTP – User Plane (GTP‑U)

GTP‑U transports user payload in **G‑PDU** packets. Each G‑PDU carries a **TEID** field that uniquely identifies the tunnel for a given endpoint pair [TS 29.281 §7.1]. The TEID is negotiated during the control‑plane Create Session procedure.

Path‑management on the user plane also uses **Echo Request** and **Echo Response**. An implementation must not send Echo Requests more frequently than **once every 60 seconds** on a given path [TS 29.281 §7.2.1]. Even when no user traffic is present, a node must be ready to answer an Echo Request with an Echo Response that contains a **Recovery** IE set to zero (the value is ignored) [TS 29.281 §7.2.2].

For multicast distribution (MBMS) the Echo and Error‑Indication messages are omitted because of the point‑to‑multipoint nature of the traffic [TS 29.281 §7.2.1].

### Diameter on the S6a / S6d Interface

Diameter provides AAA services between the **MME (or SGSN)** and the **Home Subscriber Server (HSS)**. The primary procedure for location management is **Update‑Location**. It is carried out by the **Update‑Location‑Request (ULR)** and **Update‑Location‑Answer (ULA)** command pair [TS 29.272 §5.2.1.1.1].

The **ULR** contains mandatory AVPs such as **IMSI** (the subscriber identifier) and **ULR‑Flags**, and optional AVPs like **Supported‑Features** and **Terminal‑Info** [TS 29.272 §5.2.1.1.1]. The HSS responds with a **ULA** that returns the subscriber’s profile, including APN configuration and security parameters.

### NAS, NGAP, SBI – Scope Note

The supplied specifications do not describe **NAS**, **NGAP**, or **SBI**. Consequently this subsection does not detail their message structures or procedures; readers should consult the corresponding 3GPP TS 24.501 (NAS), TS 38.413 (NGAP) and TS 29.502 (SBI) for authoritative definitions.

### Common Pitfalls and Practical Tips

| Pitfall | Why it matters | Remedy |
|---------|----------------|--------|
| **Omitting the Recovery IE** on the first contact after a restart | Peer cannot detect that its state has been cleared, leading to stale TEID usage | Always include Recovery with the current Restart Counter on the first message [TS 29.274 §7.2.0] |
| **Sending Echo Requests more frequently than 60 s** on a GTP‑U path | May cause unnecessary processing load and violate the spec [TS 29.281 §7.2.1] | Implement a timer that respects the 60‑second minimum interval |
| **Using TEID 0 (all zeros) for user traffic** | The spec treats TEID 0 as a special case; error indications are not generated for it [TS 29.281 §7.3.1] | Allocate a non‑zero TEID for every bearer; reserve TEID 0 only for signalling or control messages |
| **Neglecting Private Extension when required by vendor** | May break interoperability with equipment that expects vendor‑specific parameters | Include Private Extension only when the peer signals support for it; otherwise omit |
| **Confusing Diameter ULR with GTP‑C Create Session** | Both are “setup” messages but belong to different planes; mixing them leads to protocol mismatches | Keep clear separation: use Diameter for subscriber data (S6a/S6d) and GTP‑C for tunnel creation (S11, S5/S8) |

By adhering to the exact IE composition, timing constraints, and directionality defined in the 3GPP specifications, engineers can ensure robust signalling across the core network.

## 練習題

**1.** In the GTP-C Echo Request and Echo Response messages, which Information Element is mandatory?

- A. Sending Node Features
- B. Private Extension
- C. Recovery
- D. Recovery Time Stamp

<details><summary>看答案</summary>

正解：C。The Recovery IE is listed as mandatory (M) in both messages.

</details>

**2.** According to the GTP-U specifications, how frequently may an Echo Request be sent on a path?

- A. No more than every 30 seconds
- B. No more than every 60 seconds
- C. No more than every 5 minutes
- D. There is no limit

<details><summary>看答案</summary>

正解：B。The standard restricts Echo Requests to at most one per 60 seconds per path.

</details>

**3.** What does the Version Not Supported Indication message contain?

- A. A full set of GTP-C IEs
- B. Only the GTPv2 header
- C. The Recovery IE and Private Extension
- D. An Echo Request payload

<details><summary>看答案</summary>

正解：B。The message is defined to consist solely of the GTPv2 header.

</details>

**4.** In a GTP-U Echo Response, how must the Restart Counter value in the Recovery Information Element be set?

- A. To the current Restart Counter of the sender
- B. To the Restart Counter received in the request
- C. To zero
- D. It must be omitted

<details><summary>看答案</summary>

正解：C。For backward compatibility the field is mandatory but must be zeroed.

</details>

**5.** Which Information Element is optional in a GTP-U Echo Request?

- A. Recovery (mandatory)
- B. Sending Node Features (conditional)
- C. Recovery Time Stamp
- D. TEID

<details><summary>看答案</summary>

正解：C。The table lists Recovery Time Stamp as optional for Echo Request.

</details>
