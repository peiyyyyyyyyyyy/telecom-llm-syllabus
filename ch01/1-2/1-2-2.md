# 1.2.2 IP 定址與子網路

所屬：[1.2 通訊協定](../1-2.md)

## 正文

In a mobile core network the user plane function (UPF) is the point where the 5G System (5GS) meets external data networks (DNs) that use the Internet Protocol (IP). Correct IP addressing is essential because it determines how user‑plane packets are routed between the user equipment (UE) and the Internet or a private intranet, and it influences the ability to apply quality‑of‑service (QoS) and security policies.

---

### 5GS support for IPv4 and IPv6  

The 5GS is defined to interwork with data networks that use either IPv4, IPv6, or both. This dual‑stack capability is expressed in the specification as “the 5GS can operate IPv4 and/or IPv6” [TS 29.561 §8.2.1]. Consequently, the UPF must be able to handle both address families when forwarding packets to the external IP network.

---

### The N6 reference point  

The logical interface that connects the UPF to the external IP network is called the **N6 reference point**. It is described as “the N6 reference point is between the UPF and the external IP network” [TS 29.561 §8.2]. From the viewpoint of the external network the UPF appears as a conventional IP router; the lower‑layer (L1/L2) technologies are operator‑specific and not covered by the specification.

---

### Transparent IP access  

In the **transparent access** model the UE receives an IP address that belongs to the operator’s own addressing space. The specification states:

* “the UE is given an IPv4 address and/or an IPv6 prefix belonging to the operator addressing space. The IPv4 address and/or IPv6 prefix is assigned either at subscription in which case it is a static address or at PDU session establishment in which case it is a dynamic address” [TS 29.561 §8.2.2.1].

* For IPv6 the UE uses **Stateless Address Autoconfiguration** to form its IPv6 address [TS 29.561 §8.2.2.1].

Because the address is part of the operator’s pool, the UPF can forward packets without additional authentication steps: “the UE need not send any authentication request at PDU session establishment procedure and the SMF/UPF need not take any part in the user authentication/authorization process” [TS 29.561 §8.2.2.1].

Transparent access provides at least a basic ISP service and may also support a QoS‑controlled tunnel to a private intranet. Security between the UE and the intranet is expected to be provided end‑to‑end by an “Intranet Protocol”. An example given is **IPsec**, which can supply both authentication and confidentiality [TS 29.561 §8.2.2.1].

---

### Non‑transparent IPv4 access  

When the network operates in a **non‑transparent IPv4** mode, the UE is allocated an address that belongs to the external ISP or intranet’s own address space. The specification outlines the process:

* “a static or a dynamic IPv4 address belonging to the Intranet/ISP addressing space is allocated to a UE at PDU session establishment” [TS 29.561 §8.2.2.2].

* The address may be drawn from a **local address pool** provisioned in the SMF, from the UPF, or obtained from external allocation servers such as **DHCPv4, RADIUS DN‑AAA, or Diameter DN‑AAA** [TS 29.561 §8.2.2.2].

* As part of session setup the SMF (or SMF+PGW‑C) may request user authentication from an external DN‑AAA server (RADIUS or Diameter) belonging to the ISP [TS 29.561 §8.2.2.2].

* The communication between the 5GS and the ISP may traverse any transport, even an insecure network; any required security protocol is defined by mutual agreement between the PLMN operator and the ISP [TS 29.561 §8.2.2.2].

Thus, non‑transparent access gives the operator the ability to hand over full ISP‑level control (addressing, authentication, policy) to the external network.

---

### Subnetting considerations  

Typical IP subnetting (e.g., calculating network prefixes, host counts, and mask lengths) is a fundamental topic in IP networking, but the 3GPP specification that defines the interworking model does **not** prescribe specific subnetting formulas or address‑size details. Consequently, detailed subnet calculations are outside the scope of this subsection and should be consulted in dedicated IP‑addressing references (e.g., IETF RFCs).

---

### Practical notes and common pitfalls  

| Pitfall | Why it occurs | Remedy |
|---|---|---|
| Assuming the UPF must perform AAA for transparent sessions | The spec explicitly says no authentication is required in transparent access [TS 29.561 §8.2.2.1] | Trust the operator‑assigned address and rely on end‑to‑end security if needed |
| Using an ISP‑owned address pool in transparent mode | Transparent mode requires addresses **belonging to the operator’s addressing space** [TS 29.561 §8.2.2.1] | Verify address pool ownership before configuration |
| Forgetting to configure a security protocol for insecure N6 links in non‑transparent mode | The spec allows insecure transport but recommends a mutually‑agreed security protocol [TS 29.561 §8.2.2.2] | Establish IPsec, TLS, or another tunnel as per inter‑operator agreement |
| Mixing static and dynamic allocation without clear policy | Both static (subscription) and dynamic (session‑establishment) assignments are permitted [TS 29.561 §8.2.2.1] | Define clear policy in the SMF/UPF for each subscriber type |

By adhering to the allocation and interworking rules defined in TS 29.561, network designers can ensure that IP addressing works seamlessly across the 5GS and external data networks, whether the service model is transparent or non‑transparent.
