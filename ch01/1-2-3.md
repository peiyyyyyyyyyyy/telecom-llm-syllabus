# 1.2.3 傳輸層：TCP、UDP、SCTP

所屬：[1.2 通訊協定](1-2.md)

## 內文

傳輸層把不同應用的資料交給正確的端點，並按協定提供重傳、排序或流量控制等服務。TCP 提供可靠、有序的位元組流，UDP 保持個別資料報，SCTP 提供可分成多個串流的可靠訊息傳遞。挑選傳輸方式時，先問應用如何界定一份訊息、對延遲與遺失能容忍多少，以及網路或產業規格是否已指定承載協定。 [IETF RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html) [IETF RFC 768](https://www.rfc-editor.org/rfc/rfc768.html) [IETF RFC 9260](https://www.rfc-editor.org/rfc/rfc9260.html)

| 協定 | 傳遞及排序方式 | 判讀重點與出處 |
| --- | --- | --- |
| TCP | 應用持續讀寫位元組流，協定追蹤序號及確認 | 接收端須依應用格式切出個別訊息。 [IETF RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html) |
| UDP | 每次傳遞保留資料報邊界，基本協定沒有確認及重傳程序 | 若應用需要可靠交付或順序，應檢查其自身機制。 [IETF RFC 768](https://www.rfc-editor.org/rfc/rfc768.html) |
| SCTP | 在關聯內傳送有邊界的訊息，依串流管理有序傳送 | 一個關聯可容納多串流及端點多個位址，須查實際配置。 [IETF RFC 9260](https://www.rfc-editor.org/rfc/rfc9260.html) |

TCP 的傳送端以序號追蹤位元組，接收端以確認資訊回報進度，必要時重傳。UDP 每個資料報有來源及目的端口等欄位，接收端可逐報交付。SCTP 把資料放進區塊並在關聯中處理確認、重傳與串流序列。5G N2 的 NGAP 由 SCTP 承載，因此 N2 斷線時可先找出關聯的位址及狀態，再往上查接取控制訊息。三種協定都要依實際 IP 路徑確認資料走哪個端點。 [IETF RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html) [IETF RFC 768](https://www.rfc-editor.org/rfc/rfc768.html) [IETF RFC 9260](https://www.rfc-editor.org/rfc/rfc9260.html) [3GPP TS 38.412 Release 18](https://www.etsi.org/deliver/etsi_ts/138400_138499/138412/18.01.00_60/ts_138412v180100p.pdf)

常見混淆包括把每次 TCP 寫入當作對端的一筆訊息、把 UDP 的簡單設計當作應用必定無重傳，以及把 SCTP 的多位址當作並行使用所有路徑的保證。實作應按應用格式處理 TCP 位元組流。UDP 應用可另做傳輸控制，SCTP 則需看主要路徑、備援與對端能力。 [IETF RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html) [IETF RFC 768](https://www.rfc-editor.org/rfc/rfc768.html) [IETF RFC 9260](https://www.rfc-editor.org/rfc/rfc9260.html)

工單記下收發位址、端口、協定、測試時段及在哪一側查到封包。應用團隊可核對邊界與逾時處理，IP 團隊查正反向路由與介面，N2 案件再由無線及核心控制團隊查看 SCTP 關聯及 NGAP 程序。比較多條 SCTP 串流時以同一關聯識別連起紀錄，再看異常是集中在個別訊息程序，還是所有傳輸都受影響。 [IETF RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html) [IETF RFC 768](https://www.rfc-editor.org/rfc/rfc768.html) [IETF RFC 9260](https://www.rfc-editor.org/rfc/rfc9260.html) [3GPP TS 38.412 Release 18](https://www.etsi.org/deliver/etsi_ts/138400_138499/138412/18.01.00_60/ts_138412v180100p.pdf)
