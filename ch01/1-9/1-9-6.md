# 1.9.6 AI 用在網路：機器學習、深度學習、強化學習、聯邦學習

所屬：[1.9 電信研究前沿](../1-9.md)

## 正文

**AI in the 5G/6G Core Network – Machine Learning, Deep Learning, Reinforcement Learning, and Federated Learning**

Artificial intelligence (AI) techniques are increasingly embedded in the 5G/6G core network to enable data‑driven optimisation, anomaly detection, and self‑organising functions. By analysing massive amounts of operational data, AI can adapt radio resource management, predict traffic load, and enforce security policies without human intervention. Among the AI paradigms, **machine learning (ML)**, **deep learning (DL)**, **reinforcement learning (RL)**, and **federated learning (FL)** are the most relevant for network‑level automation. The 3GPP specifications describe the management of ML models and the concrete procedures for FL among network functions (NFs) such as the Network Data Analytics Function (NWDAF). This subsection summarises the standards‑based view of FL and the associated ML model lifecycle, while noting that detailed definitions of ML, DL, and RL lie outside the scope of the cited references.

### Machine Learning, Deep Learning, and Reinforcement Learning (Scope Note)

The 3GPP documents referenced here focus on the *application* of AI rather than the mathematical foundations of ML, DL, or RL. Consequently, this text does **not** provide formal definitions or formulas for these techniques; readers are referred to external AI literature for such background. What matters for network engineers is how these techniques are *operationalised* within the core network, i.e., how models are trained, validated, tested, deployed, and invoked. The standard‑defined lifecycle is described in TS 28.105 §6.1.

### ML Model Lifecycle Management (TS 28.105 §6.1)

The 3GPP ML model lifecycle comprises several managed steps, each exposed through a dedicated AI/ML management capability:

| Capability | Primary Function |
|------------|------------------|
| **ML model training management** | Request, control, and monitor training (including validation). |
| **ML model testing management** | Request testing, receive performance metrics, and trigger re‑training if needed. |
| **AI/ML inference emulation** | Emulate inference before deployment on the target network. |
| **ML model loading management** | Trigger, control, and monitor loading of a trained model into the runtime environment. |
| **AI/ML inference management** | Activate/deactivate inference, configure output ranges, monitor performance, and trigger updates. |

Each capability enables a *MnS consumer* (e.g., a network‑level orchestrator) to interact with a *MnS producer* (e.g., an NWDAF) for a given analytic ID. Validation of the trained model is mandatory before the model proceeds to testing; if the variance between training and validation performance exceeds an acceptable threshold, the model must be re‑trained [TS 28.105 §6.1].

### Horizontal Federated Learning (H‑FL) among NWDAFs (TS 23.288 §5.3)

**Horizontal Federated Learning** (H‑FL) is a collaborative training technique in which multiple NWDAFs (the *FL client* NFs) each hold a local dataset that shares the same feature space (e.g., UE identifiers) but contains different samples. No raw data leaves the local NF; only model updates are exchanged with a designated **FL server NWDAF**.

### Roles and Responsibilities

* **FL server NWDAF**
  * Discovers and selects FL client NWDAFs for participation.
  * Sends an initial global model to each client and requests local training.
  * Aggregates the received local model information to generate a new global model.
  * Returns the global model to clients for possible further training iterations.

* **FL client NWDAF**
  * Performs local training on its own dataset, respecting privacy, security, and access‑right constraints.
  * Reports the resulting local model information back to the FL server.
  * Receives the updated global model and may continue training.

Both server and client register their FL capabilities with the Network Repository Function (NRF) as described in clause 5.2 of TS 23.288 [TS 23.288 §5.3].

### Procedure Overview

1. **Discovery** – The FL server queries the NRF to discover eligible FL client NWDAFs.
2. **Initial Model Distribution** – The server provides an initial model to each client.
3. **Local Training** – Each client trains the model on its own data set.
4. **Aggregation** – The server aggregates the local model information (e.g., weights) to produce a new global model.
5. **Iteration** – Steps 3–4 may repeat until convergence criteria are met.
6. **Completion** – The final global model is stored and can be loaded for inference.

The aggregation step is defined as “generates global ML Model by aggregating local model information from FL client NWDAFs” [TS 23.288 §5.3].

### Worked Example (Illustrative)

Assume three NWDAF clients (C1, C2, C3) each train a linear regression model on their local UE‑throughput data. After one local epoch, the clients produce weight vectors:

* $w_{C1}=0.8$, $w_{C2}=1.0$, $w_{C3}=0.6$.

The FL server aggregates them by simple averaging (the standard approach defined in many FL frameworks, consistent with “aggregating local model information”) to obtain the global weight:

$$
w_{\text{global}} = \frac{w_{C1}+w_{C2}+w_{C3}}{3}= \frac{0.8+1.0+0.6}{3}=0.8.
$$

The server distributes $w_{\text{global}}=0.8$ back to the clients for the next training round. This cycle repeats until the weight change falls below a predefined threshold.

*Citation*: The server “generates global ML Model by aggregating local model information from FL client NWDAFs” [TS 23.288 §5.3].

### Vertical Federated Learning (V‑FL) (TS 23.288 §5.4)

**Vertical Federated Learning** (V‑FL) addresses the scenario where participating NFs possess *different feature spaces* for the *same* set of samples (e.g., the same UE ID but distinct measurement types). V‑FL may involve multiple NWDAFs, Access Functions (AFs), or a combination thereof, within a single PLMN or across PLMNs.

### Roles

* **VFL server** – An NWDAF or a trusted AF that discovers VFL clients, assigns a correlation ID, requests local training, optionally performs its own training, and combines intermediate results (e.g., gradients, loss) to update all participants’ models.
* **VFL client** – An NWDAF or AF that locally trains on its own feature set, computes intermediate results, reports them to the server, and updates its model based on the server’s feedback.

When an *untrusted* AF acts as VFL server, the NEF mediates discovery and message forwarding [TS 23.288 §5.4].

### Procedure Summary

1. **Registration** – NFs register VFL capability with the NRF.
2. **Discovery & Sample Alignment** – The server discovers clients and aligns common sample identifiers (e.g., UE IDs).
3. **Local Training & Reporting** – Each client trains on its own feature set and sends intermediate results (gradients, loss) to the server.
4. **Server Aggregation** – The server combines received information, optionally using its own data, and computes model updates.
5. **Model Update** – The server sends update information back to each client, which applies it locally.
6. **Inference** – After training, the server coordinates inference by combining local inference results from clients.

The server “combines intermediate training results from VFL client(s) and VFL server and computes intermediate model training information (e.g. gradient information, loss information)” [TS 23.288 §5.4].

### Practical Notes and Common Pitfalls

| Pitfall | Why it Happens | Mitigation |
|--------|----------------|------------|
| **Assuming data can be shared** | FL (both H‑FL and V‑FL) explicitly forbids raw data exchange; designers may inadvertently design interfaces that leak data. | Enforce strict API contracts; rely on the standard’s “without exchanging/sharing local data set” clause. |
| **Mismatched feature spaces in H‑FL** | H‑FL requires identical feature spaces across clients; using heterogeneous features leads to aggregation errors. | Verify that all participating NWDAFs share the same analytic ID and feature definition before initiating FL. |
| **Neglecting security authorisation** | FL procedures require authorisation steps defined in TS 33.501 (Annex X). Skipping them can expose the network to attacks. | Follow the security procedures for authorising FL server and client interactions as mandated. |
| **Skipping validation after training** | The ML model lifecycle demands validation; deploying an unvalidated model can degrade network performance. | Use the “ML model training management” capability to run validation and only proceed when variance is acceptable. |
| **Overlooking VFL client discovery** | When an untrusted AF acts as VFL server, NEF must forward messages; failing to involve NEF breaks the flow. | Ensure NEF participation for untrusted AF‑based VFL servers as stipulated. |

### Summary

AI‑driven network automation relies on a well‑defined ML model lifecycle (TS 28.105) and on collaborative learning techniques that preserve data privacy. Horizontal FL enables multiple NWDAFs with the same feature set to co‑train a model without sharing raw data, while Vertical FL allows participants with complementary features to jointly learn. Both paradigms are supported by explicit 3GPP procedures for discovery, registration, training, aggregation, and inference, ensuring interoperable and secure deployment across the 5G/6G core network.
