# 1.9.2 非地面網路：UAV、衛星

所屬：[1.9 電信研究前沿](../1-9.md)

## 正文

*Why UAV connectivity matters*  
Unmanned Aerial Vehicles (UAVs) are increasingly used for logistics, inspection, public‑safety, and remote‑sensing missions. To support these services, a UAV must obtain reliable, secure, and controllable radio access, often through the same 5G Core (5GC) that serves terrestrial User Equipments (UEs). The 3GPP specification TS 23.256 §4 defines a set of architectural enhancements that enable the network to authenticate, authorize, and manage UAVs throughout their flight lifecycle, while also providing hooks for air‑traffic‑control functions such as geofencing and Detect‑and‑Avoid (D‑A A).

*Key definitions*  

| Symbol / Term | Meaning (as defined by 3GPP) | Unit / Type |
|---------------|------------------------------|-------------|
| **UAV** | Aerial user equipment that may operate in flight or on the ground before take‑off. | – |
| **USS** | Unmanned‑Aircraft System Service – a backend that issues flight authorizations and Remote ID. | – |
| **UUAA** | UAV Authentication & Authorization procedure performed by the USS. | – |
| **CAA‑Level UAV ID** | Identifier assigned by the Civil Aviation Authority, used for regulatory tracking. | – |
| **3GPP UAV ID** | Identifier assigned by the Mobile Network Operator (MNO) and stored in the subscriber’s GPSI. | – |
| **PDU session** | User‑plane session that carries application data (e.g., payload, C2). | – |
| **PDN connection** | LTE counterpart of a PDU session. | – |
| **C2** | Command‑and‑Control communication between a UAV and a UAV‑Control Centre (UAVC). | – |
| **Geofencing / Geocaging** | Air‑traffic‑control functions that restrict UAV operation to predefined 3‑D volumes (in‑flight) or ground areas (pre‑flight). | – |
| **Broadcast Remote ID** | Periodic transmission of UAV identification information over the air (via MBS or PC5). | – |
| **Detect‑and‑Avoid (D‑A A)** | Mechanisms that prevent collisions, supported via PC5 reference point or ground‑based assistance. | – |

*UAV registration and authentication flow*  

1. **USS registration (optional)** – During 5G registration, the UAV may be authenticated and authorized by the USS (UUAA). This step is optional and depends on PLMN policies, USS requirements, and geographic regulations [TS 23.256 §4].  
2. **PDU session establishment** – When the UAV requests user‑plane resources (e.g., to start a payload transmission), the network must perform UUAA again if it was not completed earlier. The UAV must include its CAA‑Level UAV ID in the request [TS 23.256 §4].  
3. **PDN connection (LTE)** – In EPS, the analogous procedure occurs during the attach and PDN connection establishment phases [TS 23.256 §4].

*UAV identifiers*  

- The **CAA‑Level UAV ID** is supplied by the regulatory authority and must be presented both during registration and PDU session establishment in 5GS, or during PDN connection establishment in EPS [TS 23.256 §4].  
- The **3GPP UAV ID** is derived from at least one GPSI stored in the subscriber database (UDM) and is used internally by the 3GPP system [TS 23.256 §4].

*Location tracking and geofencing*  

The specification defines three UAV tracking modes:  

- **UAV location reporting mode** – the UAV periodically sends its GNSS coordinates to the USS.  
- **UAV presence monitoring mode** – the network monitors the UAV’s attachment state.  
- **List of aerial UEs in a geographic area** – the USS can query which UAVs are present within a defined region [TS 23.256 §4].  

Geofencing (in‑flight) and geocaging (pre‑flight) are *air‑traffic‑control* functions that the USS implements, while the 3GPP system only provides enablers such as location services and event notifications [TS 23.256 §4].

*Remote ID and C2 support*  

- **Broadcast Remote ID** can be transmitted over the Multicast‑Bicast Service (MBS) or via the PC5 reference point [TS 23.256 §4].  
- **Direct C2 communication** is explicitly supported, allowing a UAV to talk directly with a UAVC without traversing the core network [TS 23.256 §4].  
- **Detect‑and‑Avoid** mechanisms may rely on the PC5 reference point or on network‑assisted, ground‑based solutions [TS 23.256 §4].

*Mission planning and handover*  

The 3GPP system assists the UAV with pre‑mission flight planning and in‑mission monitoring. When a UAV’s flight path traverses multiple USS coverage areas, the network must support seamless change‑over from one USS to another [TS 23.256 §4]. Network‑assisted D‑A A and enforcement of “No Transmit Zone” restrictions are also defined, although the latter is left to implementation [TS 23.256 §4].

*Worked example*  

Assume a UAV **U1** has been assigned the regulatory identifier **CAA‑ID = 987654321** and the MNO has stored the GPSI **3GPP‑ID = 00101‑001‑1234567890** in the UDM. The UAV wishes to start a video‑streaming payload:

1. **Registration** – U1 initiates 5G registration. Because the operator’s PLMN policy requires UUAA at registration, the network forwards the UAV’s CAA‑ID to the USS. The USS validates the flight plan and returns an authorization token.  
2. **PDU session request** – U1 requests a PDU session with APN *uav‑data*. The request includes the same CAA‑ID. Since UUAA was already completed, the network only checks that the token is still valid.  
3. **Remote ID broadcast** – While in flight, U1 periodically sends its CAA‑ID and 3GPP‑ID over PC5 as part of Broadcast Remote ID.  
4. **Detect‑and‑Avoid** – A nearby manned aircraft triggers a D‑A A event via PC5; the network forwards an avoidance command to U1.  

All steps are directly traceable to the functional blocks described in TS 23.256 §4.

*Common pitfalls and practical notes*  

| Pitfall | Reason | Mitigation |
|---------|--------|------------|
| **Skipping UUAA at registration** | Some operators assume UUAA is only needed during PDU session, but the specification allows (and sometimes requires) it at registration [TS 23.256 §4]. | Verify PLMN policy and implement both optional paths. |
| **Omitting CAA‑Level UAV ID in PDU session** | The network expects the identifier in both registration and PDU session establishment; omission leads to session rejection [TS 23.256 §4]. | Ensure the UAV firmware always includes the CAA‑ID in the SM‑PCO field. |
| **Relying on 3GPP for geofencing enforcement** | Geofencing is an *air‑traffic‑control* function outside the scope of 3GPP; the network only supplies location services and event notifications [TS 23.256 §4]. | Integrate with a USS that implements geofencing logic. |
| **Assuming “No Transmit Zone” is automatically blocked** | Enforcement is implementation‑specific; the spec does not mandate automatic suppression [TS 23.256 §4]. | Implement local checks in the UAV firmware or in the USS policy. |
| **Neglecting USS change‑over** | When crossing USS boundaries, failure to trigger handover can cause loss of flight authorization [TS 23.256 §4]. | Monitor geographic area and trigger USS re‑authentication proactively. |

*Satellite component* – The reference specification does not cover satellite‑based non‑terrestrial networks; therefore satellite‑specific mechanisms are outside the scope of this subsection.

## 練習題

**1.** Which of the following statements about UAV Authentication & Authorization (UUAA) is correct according to TS 23.256 §4?

- A. UUAA must always be performed only during the PDU session establishment.
- B. UUAA may be performed either during 5G registration or during PDU session establishment, depending on PLMN policy.
- C. UUAA is performed exclusively by the UAVC, not by the USS.
- D. UUAA is optional and can be omitted entirely for all UAVs.

<details><summary>看答案</summary>

正解：B。The specification allows UUAA either as a separate procedure during registration or when the UAV requests user‑plane resources, based on PLMN policies.

</details>

**2.** What identifier must a UAV provide during both 5G registration and PDU session establishment?

- A. The 3GPP UAV ID only.
- B. The CAA‑Level UAV ID only.
- C. Both the CAA‑Level UAV ID and the 3GPP UAV ID.
- D. No identifier is required if the UAV is pre‑registered.

<details><summary>看答案</summary>

正解：B。The CAA‑Level UAV ID is required in both registration and PDU session establishment.

</details>

**3.** Which of the following mechanisms is *outside* the scope of the 3GPP specification, even though enablers are provided?

- A. Broadcast Remote ID over PC5.
- B. Direct C2 communication.
- C. Geofencing/geocaging enforcement.
- D. Detect‑and‑Avoid based on PC5.

<details><summary>看答案</summary>

正解：C。Geofencing/geocaging are air‑traffic‑control functions performed by the USS and are explicitly out of scope.

</details>

**4.** When a UAV crosses from the coverage area of one USS to another, what does the 3GPP system need to support?

- A. Immediate termination of the PDU session.
- B. Seamless change‑over to the new USS.
- C. Automatic downgrade to LTE only.
- D. No action; the UAV continues using the original USS.

<details><summary>看答案</summary>

正解：B。The architecture includes support for multiple USS serving different geographical areas and change‑over of the UAV.

</details>

**5.** Which of the following statements about Broadcast Remote ID is accurate?

- A. It can only be transmitted via the Multicast‑Bicast Service (MBS).
- B. It can be transmitted via either MBS or the PC5 reference point.
- C. It is optional and not defined in the specification.
- D. It must be sent on the PDU session control plane.

<details><summary>看答案</summary>

正解：B。The spec lists both MBS and PC5 as possible transports for Broadcast Remote ID.

</details>
