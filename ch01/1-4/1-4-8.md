# 1.4.8 用戶身分隱私：SUPI 與 SUCI

所屬：[1.4 網管、計費、安全與密碼學](../1-4.md)

> 本頁正文與練習題由本機模型 gpt-oss-120b 撰寫，經程式驗算與另一個模型（Gemma-4-31B）交叉驗題，尚待專家審閱。

## 正文

In modern mobile networks the subscriber’s permanent identifier is a highly sensitive piece of information. If the identifier is exposed over the radio interface, an eavesdropper can correlate traffic, infer the subscriber’s location, and build a tracking profile. The 5G system therefore introduces a two‑step mechanism: the **Subscriber Permanent Identifier (SUPI)**, which remains unchanged for the life of the subscription, and the **Subscriber Concealed Identifier (SUCI)**, a cryptographically protected version of the SUPI that is transmitted only during the initial registration. This design satisfies the privacy requirement that the network never reveals the SUPI in clear‑text on the radio link.

---

### 1. Definitions

| Symbol | Meaning | Unit / Format |
|--------|---------|---------------|
| **SUPI** | Subscriber Permanent Identifier; globally unique. It can be expressed as an IMSI, a Network Access Identifier (NAI), or a 5G‑specific format. | e.g., IMSI = “310150123456789” (decimal digits) |
| **SUCI** | Subscriber Concealed Identifier; the result of encrypting the SUPI with the Home Network’s (HN) public key. | Binary string, length depends on encryption algorithm |
| **PK\_{HN}** | Public key of the Home Network, published in the **5G System (5GS) public key repository**. | EC point (e.g., secp256r1) or RSA modulus |
| **SK\_{HN}** | Private key of the Home Network, kept secret. | Same algorithm as PK\_{HN} |
| **R** | Random nonce generated by the UE for each registration attempt. | 128‑bit random value |
| **Enc\_{PK}(·)** | Asymmetric encryption function (ECIES for EC keys, RSA‑OAEP for RSA keys). | Output = ciphertext |
| **Dec\_{SK}(·)** | Corresponding decryption function using the private key. | Output = plaintext |
| **GUTI** | Globally Unique Temporary Identifier, assigned after successful authentication. | 48‑bit identifier, used for subsequent signaling |

The relationship between SUPI and SUCI is defined in **3GPP TS 33.501, clause 5.2.2**:

$$
\text{SUCI} = \text{Enc}_{\text{PK}_{\text{HN}}}\bigl(\text{SUPI}\,\|\,R\bigr)
$$

where “$\|$” denotes concatenation. The random nonce *R* guarantees that two registrations from the same UE produce different SUCI values, thwarting replay and correlation attacks.

---

### 2. Procedure Overview

1. **Public‑Key Acquisition**: Before registration, the UE obtains the current PK\_{HN} from the **5G System public key repository** (or via a signed certificate).  
2. **SUCI Construction**: The UE concatenates its SUPI with a freshly generated 128‑bit random *R* and encrypts the pair with PK\_{HN}.  
3. **Transmission**: The UE sends the SUCI inside the **Initial Registration Request** (NAS message). No SUPI is revealed.  
4. **De‑cryption at HN**: Upon receiving the SUCI, the Home Network uses SK\_{HN} to recover SUPI and *R*. The *R* value is discarded after verification that decryption succeeded.  
5. **Authentication & Key Agreement (AKA)**: The normal 5G‑AKA procedure follows, after which the network allocates a **GUTI** for all subsequent signaling.  

Because the SUCI is a one‑way encrypted value, the serving network (SN) cannot derive the SUPI; it must forward the SUCI to the HN for de‑cryption. This separation ensures that even a compromised SN cannot learn the permanent subscriber identity.

---

### 3. Worked Example

Assume a UE with SUPI = IMSI **310150123456789** (15 decimal digits). The Home Network’s public key is an EC point on curve **secp256r1** (256‑bit). The UE generates a random nonce:

$$
R = \text{0xA1B2C3D4E5F60718293A4B5C6D7E8F90} \quad (\text{128 bits})
$$

The plaintext to encrypt is:

$$
\text{PLA} = \text{“310150123456789”} \,\|\, R
$$

Using ECIES with SHA‑256 KDF and AES‑128‑GCM, the UE obtains a ciphertext of 384 bits (48 bytes). The resulting SUCI (hexadecimal) might be:

$$
\text{SUCI} = \text{0x04B8D7E9… (48 bytes total)}
$$

The UE places this value in the **Registration Request** NAS message. The HN receives the SUCI, runs ECIES de‑cryption with its private key SK\_{HN}, and recovers the original SUPI and *R*. The HN then proceeds with the 5G‑AKA exchange, eventually allocating a GUTI such as **0x01‑23‑45‑67‑89‑AB** for ongoing sessions.

*Key observations*:

* The SUCI length does **not** reveal the SUPI length; padding or format markers are added to hide the original digit count.  
* Each registration produces a different SUCI because *R* changes, even if the same SUPI is used.

---

### 4. Practical Notes & Common Mistakes

| Issue | Why it matters | Correct practice |
|-------|----------------|------------------|
| **Re‑using the random nonce *R*** | Identical ciphertexts enable linking of multiple registrations to the same UE, breaking unlinkability. | Generate a fresh cryptographically‑secure random *R* for every registration (minimum 128 bits). |
| **Using a weak public‑key algorithm** | RSA‑1024 or EC curves with < 224 bits are vulnerable to modern factorisation or discrete‑log attacks, compromising SUPI confidentiality. | Adopt at least **secp256r1** (or higher) for EC, or RSA‑2048 with OAEP padding. |
| **Skipping certificate validation** | An attacker could inject a malicious PK\_{HN}, causing the UE to encrypt under a key controlled by the attacker (a “key‑substitution” attack). | Verify the signature chain of the public‑key certificate against the trusted root of the Home Network. |
| **Assuming SUCI is a permanent identifier** | Network functions that rely on a stable identifier (e.g., charging) might incorrectly use SUCI, leading to duplicate records. | Use SUPI only in secure back‑office processes; treat SUCI as a one‑time, transport‑level token. |
| **Failing to support fallback** | Early‑release UEs or legacy networks may not understand SUCI, causing registration failure. | Implement the **“SUPI fallback”** mode defined in 3GPP TS 33.501, where the UE may send SUPI in clear only after explicit network indication and with additional protection (e.g., via NAS security). |

Finally, operators must **rotate PK\_{HN}** periodically (e.g., yearly) and maintain backward compatibility for UEs that still hold the old key. The de‑cryption logic should accept multiple valid keys and reject any SUCI that cannot be decrypted with a known public key.
