### 1.4.4 User Authentication and Key Agreement (AKA)

#### 1.4.4.1 Why AKA matters  
In cellular and broadband access networks, every subscriber must be **authenticated** before receiving services, and a fresh set of cryptographic keys must be derived for confidentiality and integrity protection of user‑plane and control‑plane traffic. The **Authentication and Key Agreement (AKA)** protocol fulfills both goals in a single, mutually authenticated handshake. AKA is the security cornerstone of 3GPP generations (UMTS, LTE, 5G) and is also used in IMS, Wi‑Fi off‑load, and IoT access technologies that adopt the 3GPP security architecture. Without a robust AKA, an attacker could impersonate a user (fraud), hijack sessions, or force the network to reuse old keys, leading to replay attacks and loss of confidentiality.

#### 1.4.4.2 Core entities and terminology  

| Symbol | Meaning | Unit / Type |
|--------|---------|-------------|
| $U$ | User equipment (UE) | – |
| $H$ | Home network (HN) – the subscriber’s operator | – |
| $V$ | Visited network (VN) – the serving operator (e.g., LTE eNodeB) | – |
| $K$ | Long‑term secret key stored in the USIM (or SIM) at $U$ and $H$ | 128‑bit |
| $SQN$ | Sequence number, prevents replay | 48‑bit |
| $RAND$ | Random challenge generated by $H$ (or $V$) | 128‑bit |
| $XRES$ | Expected response, computed by $H$ | 128‑bit |
| $RES$ | Response computed by $U$ | 128‑bit |
| $AUTN$ | Authentication token = $(SQN \oplus AK, MAC_A, AMF)$ | 128‑bit |
| $AK$ | Anonymity key = $f5(K, RAND)$ | 48‑bit |
| $MAC_A$ | Message authentication code = $f1(K, SQN\|RAND\|AMF)$ | 64‑bit |
| $CK$ | Cipher key (confidentiality) | 128‑bit |
| $IK$ | Integrity key (integrity protection) | 128‑bit |
| $K_{eNB}$, $K_{gNB}$ | Keys derived for the radio access node | 128‑bit |
| $AMF$ | Authentication Management Field (e.g., emergency flag) | 16‑bit |

All functions $f1$–$f5$ are **MILENAGE** or **AES‑CMAC** primitives defined in 3GPP TS 35.205/35.206. They are keyed hash‑like functions that take $K$ and $RAND$ as inputs and output the values shown above.

#### 1.4.4.3 High‑level flow (EPS‑AKA, 3GPP TS 33.102)

1. **Authentication Vector (AV) generation** – The Home Network $H$ computes an AV = $(RAND, XRES, AUTN, CK, IK)$ using the subscriber’s $K$ and a fresh $SQN$.
2. **AV delivery** – $H$ sends the AV to the Visited Network $V$ over a secure back‑haul (e.g., MAP‑SEC, Diameter). $V$ forwards $RAND$ and $AUTN$ to the UE $U$.
3. **UE verification** – $U$ computes $AK = f5(K,RAND)$, recovers $SQN' = (SQN \oplus AK) \oplus AK$, verifies $SQN'$ is within the acceptable window, and checks $MAC_A = f1(K, SQN'\|RAND\|AMF)$. If both tests pass, $U$ accepts the authentication.
4. **Response generation** – $U$ calculates $RES = f2(K,RAND)$ and sends it back to $V$.
5. **Network verification** – $V$ compares $RES$ with $XRES$. A match confirms that $U$ possesses the correct $K$.
6. **Key derivation** – Both $U$ and $V$ now hold $CK$ and $IK$ (and, in LTE, $K_{eNB}=K_{ASME}$ derived from $CK$, $IK$, and $RAND$). These keys are used for NAS and radio‑link security.

The same structure appears in 5G‑AKA (TS 33.401) with additional keys ($K_{amf}$, $K_{seaf}$) and the use of **SUCI** instead of clear SUPI, but the fundamental steps—challenge, MAC verification, response, and key derivation—remain identical.

#### 1.4.4.4 Formal description  

The authentication vector is mathematically expressed as  

$$
\begin{aligned}
RAND &\xleftarrow{\$} \{0,1\}^{128} \\
SQN &\xleftarrow{\$} \{0,1\}^{48} \\
AK   &= f_5(K,RAND) \\
AUTN &= \bigl( SQN \oplus AK,\; MAC_A,\; AMF \bigr) \\
MAC_A &= f_1\bigl(K,\, SQN \parallel RAND \parallel AMF\bigr) \\
XRES  &= f_2(K,RAND) \\
CK    &= f_3(K,RAND) \\
IK    &= f_4(K,RAND)
\end{aligned}
$$

where “$\parallel$” denotes bit‑wise concatenation, and “$\xleftarrow{\$}$” means “draw uniformly at random”.

The UE side verification:

$$
\begin{aligned}
AK'   &= f_5(K,RAND) \\
SQN'  &= (SQN \oplus AK) \oplus AK' \\
\text{Check } & SQN' \in [SQN_{min}, SQN_{max}] \\
MAC_A' &= f_1\bigl(K,\, SQN' \parallel RAND \parallel AMF\bigr) \\
\text{Accept if } & MAC_A' = MAC_A
\end{aligned}
$$

Response generation:

$$
RES = f_2(K,RAND)
$$

Both parties finally compute the **Key Derivation Function (KDF)**:

$$
K_{ASME}= \text{KDF}\bigl(CK \parallel IK,\; \text{‘KASME’} \parallel RAND \parallel SQN' \parallel AMF\bigr)
$$

The exact KDF algorithm is defined in TS 33.220; it typically uses HMAC‑SHA‑256.

#### 1.4.4.5 Worked example (numerical)

Assume a subscriber’s long‑term key  

$$
K = \text{0x1F2E3D4C5B6A7988 9A7B6C5D4E3F2A1B} \; (\text{128‑bit})
$$

The Home Network generates  

$$
\begin{aligned}
RAND &= \text{0xA1B2C3D4E5F60718293A4B5C6D7E8F90} \\
SQN  &= \text{0x000001234567} \; (\text{48‑bit})
\end{aligned}
$$

Using MILENAGE (values are illustrative):

$$
\begin{aligned}
AK   &= f_5(K,RAND) = \text{0x112233445566} \\
SQN \oplus AK &= \text{0x000001234567} \oplus \text{0x112233445566} = \text{0x112232777331} \\
MAC_A &= f_1(K, SQN\|RAND\|AMF) = \text{0xAABBCCDDEEFF0011} \\
XRES  &= f_2(K,RAND) = \text{0xDEADBEEFDEADBEEF} \\
CK    &= f_3(K,RAND) = \text{0xCAFEBABECAFEBABE} \\
IK    &= f_4(K,RAND) = \text{0xFEEDFACEFEEDFACE}
\end{aligned}
$$

The network sends $RAND$ and $AUTN = (\text{0x112232777331}, \text{0xAABBCCDDEEFF0011}, \text{0x0000})$ to the UE.

The UE recomputes $AK' = f_5(K,RAND) = \text{0x112233445566}$, recovers  

$$
SQN' = (\text{0x112232777331} \oplus \text{0x112233445566}) = \text{0x000001234567}
$$

The UE checks the sequence window (e.g., $SQN_{min}=0$, $SQN_{max}=2^{48}-1$) – passes. It then computes $MAC_A'$ and finds it equal to the received $MAC_A$, so authentication succeeds.

Finally, the UE computes  

$$
RES = f_2(K,RAND) = \text{0xDEADBEEFDEADBEEF}
$$

and sends $RES$ back. The network compares $RES$ with $XRES$ – they match, completing AKA. Both sides now hold $CK$ and $IK$, from which $K_{ASME}$ is derived.

#### 1.4.4.6 Common pitfalls and practical notes  

| Pitfall | Why it occurs | Remedy |
|---------|---------------|--------|
| **Sequence number desynchronisation** | $SQN$ may drift when the UE fails to receive an authentication request (e.g., radio outage). | Implement **re‑synchronisation** using the AUTS token (contains $SQN$ and a MAC based on $K$) as defined in TS 33.102. |
| **Weak random number generation** | If $RAND$ is predictable, an attacker can pre‑compute $XRES$ and mount a replay. | Use a cryptographically secure RNG (e.g., NIST SP 800‑90A) in the HSS/AuC. |
| **Re‑use of $K$ across generations** | Some legacy networks stored $K$ in cleartext on the UE, exposing it to side‑channel attacks. | Store $K$ only in tamper‑resistant USIM hardware; migrate to 5G‑AKA where $K$ is never exposed. |
| **Incorrect MAC length** | Using a truncated $MAC_A$ can reduce security margin. | Follow the MILENAGE spec: $MAC_A$ is 64 bits; do not truncate unless a formal security analysis justifies it. |
| **Neglecting integrity protection of the authentication vector** | AVs traveling over the back‑haul may be altered. | Transport AVs over Diameter with IPsec or TLS; optionally sign them with a network‑wide certificate. |

**Practical tip:** In LTE, the key hierarchy is *rooted* at $K_{ASME}$; any compromise of $CK$ or $IK$ does **not** affect $K$ or $K_{ASME}$ because the later keys are derived with fresh $RAND$ each session. Therefore, always discard $CK$, $IK$, and $K_{ASME}$ after the session ends (or after a defined re‑key interval).  

**Performance note:** The MILENAGE functions are designed for hardware acceleration in USIM chips; a typical UE can complete the full AKA exchange within a few milliseconds, satisfying the latency requirements of real‑time services (voice, URLLC).

#### 1.4.4.7 Summary  

- AKA provides mutual authentication and fresh key material in a single protocol run.  
- It relies on a long‑term secret $K$, a random challenge $RAND$, and a sequence number $SQN$ to prevent replay.  
- The cryptographic primitives $f1\!-\!f5$ (MILENAGE) generate MACs, anonymity keys, and the response $RES$.  
- Successful verification yields $CK$, $IK$, and higher‑level keys (e.g., $K_{ASME}$) that protect user‑plane and control‑plane traffic.  
- Correct handling of $SQN$ synchronization, random number generation, and secure transport of authentication vectors is essential for a robust deployment.
