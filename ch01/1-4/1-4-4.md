# 1.4.4 用戶鑑權與金鑰協商（AKA）

所屬：[1.4 網管、計費、安全與密碼學](../1-4.md)

## 正文

In a 5G system the *primary authentication and key agreement* (AKA) procedure is the first security step that a user equipment (UE) performs when it attaches to a serving network (SN). Its twofold purpose is to **mutually authenticate** the UE and the network, and to generate **keying material** that will protect all subsequent radio and core‑network communications — from NAS signalling to user‑plane encryption — in the serving network. The anchor key produced by this run is called **$K_{\text{SEAF}}$** and is handed over from the home network’s Authentication Server Function (AUSF) to the serving network’s Security Anchor Function (SEAF) [TS 33.501 §6.1.1].

### Key definitions and derivation chain

| Symbol | Meaning | Origin |
|--------|---------|--------|
| $K$ | Long‑term subscriber key stored in the USIM (128 bits or 256 bits) | ARPF |
| $CK$, $IK$ | Cipher and integrity keys derived from $K$ (5G AKA) | ARPF |
| $CK'$, $IK'$ | Transformed $CK$, $IK$ used for **EAP‑AKA′** (generated by ARPF) | §6.1.3.1 step 1 |
| **EMSK** | EAP‑derived master session key, computed from $CK'$ and $IK'$ | §6.1.3.1 step 10 |
| $K_{\text{AUSF}}$ | Intermediate key for the home network; **most significant 256 bits of EMSK** | §6.1.3.1 step 10 |
| $K_{\text{SEAF}}$ | Anchor key for the serving network; derived from $K_{\text{AUSF}}$ and the **serving network name** | §6.1.1.3‑4 |
| $K_{\text{AMF}}$, $K_{\text{NASint}}$, $K_{\text{NASenc}}$, … | Keys further derived from $K_{\text{SEAF}}$ for specific layers (see Fig. 6.2.1‑1) | §6.2.1 |

The **key derivation hierarchy** is anchored by $K_{\text{SEAF}}$:

$$
K_{\text{SEAF}} = \operatorname{KDF}\bigl(K_{\text{AUSF}},\ \text{serving‑network‑name}\bigr)
$$

where *serving‑network‑name* is a concatenation of the serving network identifier (SN Id) and the service code “5G”. This binding “prevents one serving network from claiming to be a different serving network, and thus provides implicit serving network authentication to the UE” [TS 33.501 §6.1.1.3].

### Authentication flow (EAP‑AKA′)

The EAP framework (RFC 3748) is used for both 5G AKA and EAP‑AKA′. In the 5G system the roles are:

* **UE** – *peer*  
* **SEAF** – *pass‑through authenticator* [TS 33.501 §6.1.1.2]  
* **AUSF** – *backend authentication server*  

A condensed sequence for **EAP‑AKA′** is:

1. **AV′ generation** – The UDM/ARPF creates an authentication vector with AMF separation bit = 1, then computes $CK'$ and $IK'$ and replaces the original $CK$, $IK$ [§6.1.3.1 step 1].  
2. **AV′ delivery** – The transformed vector AV′ ($\text{RAND},\ \text{AUTN},\ X_{\text{RES}},\ CK',\ IK'$) is sent from UDM to AUSF [§6.1.3.1 step 2].  
3. **EAP‑Request** – AUSF forwards an *EAP‑Request/AKA′‑Challenge* to SEAF, which forwards it in a NAS *Authentication Request* to the UE [§6.1.3.1 steps 3‑4].  
4. **USIM verification** – The UE’s USIM checks $AUTN$ for freshness (as in TS 33.102) and, if valid, returns $RES$, $CK$, $IK$ to the ME; the ME then derives $CK'$ and $IK'$ [§6.1.3.1 step 5].  
5. **EAP‑Response** – UE sends *EAP‑Response/AKA′‑Challenge* (carrying $RES$) back to SEAF, which forwards it to AUSF [§6.1.3.1 steps 6‑7].  
6. **Verification & key derivation** – AUSF compares $X_{\text{RES}}$ with $RES$. On success it derives **EMSK** from $CK'$ and $IK'$, extracts $K_{\text{AUSF}}$, then computes $K_{\text{SEAF}}$ [§6.1.3.1 step 10].  
7. **Completion** – AUSF sends an *EAP‑Success* (carrying $K_{\text{SEAF}}$) to SEAF, which forwards it to the UE. The AMF is then triggered to run the **NAS Security Mode Command** to activate the new NAS keys [§6.1.1.1].

### Worked example (numeric illustration)

Assume the ARPF has produced the following transformed keys for a given UE:

* $CK' = \text{0x11111111111111111111111111111111}$  
* $IK' = \text{0x22222222222222222222222222222222}$  

The AUSF applies the EAP‑AKA′ KDF (as defined in RFC 5448) together with the serving‑network‑name “5G:SN‑001”. The resulting **EMSK** (512 bits) is, for illustration:

```
EMSK = 0xAAAABBBBCCCCDDDDEEEEFFFF111122223333444455556666777788889999AAAA
```

The most significant 256 bits (first half) become $K_{\text{AUSF}}$:

```
K_AUSF = 0xAAAABBBBCCCCDDDDEEEEFFFF111122223333444455556666777788889999
```

Using the serving‑network‑name as KDF input, $K_{\text{SEAF}}$ is derived (the exact KDF is defined in Annex A, not reproduced here). The resulting anchor key might be:

```
K_SEAF = 0x1234567890ABCDEF1234567890ABCDEF1234567890ABCDEF1234567890ABCD
```

All subsequent keys ($K_{\text{AMF}}$, $K_{\text{NASint}}$, …) are then derived from $K_{\text{SEAF}}$ following the hierarchy in Figure 6.2.1‑1. This example shows how a single primary authentication run yields a cascade of keys without further interaction with the home network.

### Common mistakes & practical notes

| Mistake | Why it matters | Remedy |
|---------|----------------|--------|
| **Confusing $K_{\text{AUSF}}$ with $K_{\text{SEAF}}$** – treating them as interchangeable. | $K_{\text{AUSF}}$ is an intermediate key; $K_{\text{SEAF}}$ is the anchor that is *bound* to the serving network. | Remember the derivation order: $K_{\text{AUSF}} \rightarrow K_{\text{SEAF}}$ (via serving‑network‑name). |
| **Omitting the serving‑network‑name in the KDF** – leads to a key that is not network‑specific. | The spec explicitly requires this binding to prevent a rogue SN from impersonating another SN [§6.1.1.3‑4]. | Include the exact serving‑network‑name string defined in §6.1.1.4 when calling the KDF. |
| **Using the wrong authentication method for a non‑3GPP access** – e.g., trying to use 5G AKA with a device that only supports EAP‑AKA′. | For non‑3GPP access the credentials must still reside on the USIM, and only EAP‑AKA′ or 5G AKA are supported [§6.1.1.1‑4]. | Verify the UE’s capability and select the method accordingly; the home operator decides which method is used. |
| **Skipping the NAS Security Mode Command (SMC) after primary authentication**. | The UE does not store the new $K_{\text{AUSF}}$ until it receives the NAS SMC; without it the partial native NAS security context remains inactive [§6.1.1.1 Note 6]. | Ensure the AMF always initiates the NAS SMC immediately after a successful AKA run. |
| **Assuming $K_{\text{SEAF}}$ is the same as the legacy $K_{\text{ASME}}$**. | The anchor key is *cryptographically separate* from $K_{\text{ASME}}$ used in earlier generations [§6.1.1.3]. | Treat $K_{\text{SEAF}}$ as a fresh key family; do not reuse $K_{\text{ASME}}$ values. |

Understanding the precise flow, the role of each entity, and the binding of $K_{\text{SEAF}}$ to the serving network is essential for secure 5G deployments and for troubleshooting authentication failures.

## 練習題

**1.** What is the primary purpose of the primary authentication and key agreement (AKA) procedures in 5G?

- A. To authenticate the network to the UE only.
- B. To generate keying material without authenticating any party.
- C. To enable mutual authentication between the UE and the network and provide keying material.
- D. To exchange billing information between the UE and the serving network.

<details><summary>看答案</summary>

正解：C。The procedures are defined to both mutually authenticate the UE and the network and to produce keys for subsequent security functions.

</details>

**2.** In the EAP framework used for 5G AKA/EAP‑AKA′, which network function acts as the pass‑through authenticator?

- A. UE (User Equipment)
- B. SEAF (Security Anchor Function)
- C. AUSF (Authentication Server Function)
- D. AMF (Access and Mobility Management Function)

<details><summary>看答案</summary>

正解：B。The SEAF forwards EAP messages between the UE and the AUSF without terminating the authentication itself.

</details>

**3.** During the EAP‑AKA′ authentication flow, which key is obtained by taking the most significant 256 bits of the EMSK?

- A. K_SEAF
- B. K_AUSF
- C. K_AMF
- D. K_NASint

<details><summary>看答案</summary>

正解：B。After deriving EMSK from CK′ and IK′, the AUSF extracts the upper half as the intermediate key K_AUSF.

</details>

**4.** Which parameter is explicitly included in the key‑derivation chain to bind the anchor key K_SEAF to a specific serving network?

- A. Access network type
- B. Serving network name
- C. UE IMSI
- D. Home network private key

<details><summary>看答案</summary>

正解：B。The serving‑network‑name is concatenated into the KDF input so that K_SEAF is unique to that network.

</details>

**5.** Why must the NAS Security Mode Command (SMC) be executed immediately after successful primary authentication?

- A. Because it triggers the billing session in the core network.
- B. Because the UE does not store the new derived K_AUSF until receiving the NAS SMC message.
- C. Because it updates the UE’s firmware.
- D. Because it informs the home network of the UE’s location.

<details><summary>看答案</summary>

正解：B。The UE holds off on storing K_AUSF until the NAS SMC confirms the new security context.

</details>
