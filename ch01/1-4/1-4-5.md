# 1.4.5 加密與完整性保護

所屬：[1.4 網管、計費、安全與密碼學](../1-4.md)

## 正文

In a 5G system every signalling and user‑plane exchange between the User Equipment (UE) and the network must be protected against eavesdropping, tampering and replay attacks.  The mechanisms that provide **confidentiality** (encryption) and **integrity** (message authentication) are defined in 3GPP TS 33.501.  They are applied at different protocol layers – NAS (Non‑Access Stratum) over the N1 reference point, RRC (Radio Resource Control) over the N2 reference point, and the User Plane (UP) over the data radio bearers.  Without these protections an attacker could read subscriber data, inject false control messages, or replay old messages to cause service disruption.

---

### 1. Security contexts and multiple NAS connections  

A UE may be simultaneously registered to different PLMNs (Public Land Mobile Networks) or to the same PLMN over both 3GPP and non‑3GPP access.  In each case the UE **maintains an independent 5G NAS security context** that contains keys, algorithm identifiers and two pairs of NAS COUNTs (uplink/downlink) for each access type [TS 33.501 §6.4.2.1].  

When the two active NAS connections belong to the **same PLMN**, a **common NAS security context** is created, but the context holds a **unique NAS connection identifier** (0x01 for 3GPP access, 0x02 for non‑3GPP access) together with separate COUNT pairs [TS 33.501 §6.4.2.2].  This identifier guarantees cryptographic separation and replay protection across the two links.

---

### 2. NAS protection (integrity + confidentiality)

The NAS security mechanisms protect signalling between the UE and the Access and Mobility Management Function (AMF) over the N1 interface [TS 33.501 §6.4.1].  The protection relies on the NAS keys derived from the 5G security context and on the selected integrity (NIA) and ciphering (NEA) algorithms.  The same key material is used for both directions; the direction is distinguished by the **NAS COUNT** value, which is incremented for each transmitted NAS message.  Replay protection is achieved because a receiver must accept each COUNT value only once.

---

### 3. RRC integrity protection  

RRC messages are integrity‑protected **by the PDCP layer**; no lower layer is integrity‑protected [TS 33.501 §6.5.1].  When an integrity algorithm other than **NIA0** is selected, replay protection is activated automatically.  The integrity MAC (Message Authentication Code) is computed over:

* the RRC **MESSAGE**,
* the 128‑bit integrity key **$K_{\text{RRCint}}$**,
* the 5‑bit **BEARER** identity,
* the 1‑bit **DIRECTION** (0 = uplink, 1 = downlink),
* the 32‑bit **COUNT** taken from the PDCP count.

The input set is identical to the one defined for the 128‑NIA algorithms (Annex D).  Both UE and gNB verify the MAC; a failed check leads to discarding the message [TS 33.501 §6.5.1].

---

### 4. RRC confidentiality protection  

Confidentiality for RRC is also realized **by the PDCP layer** using the 128‑NEA family of stream cipher algorithms [TS 33.501 §6.5.2].  The algorithm requires:

$$
\begin{aligned}
\text{KEY}   & = K_{\text{RRCenc}} \;(128\text{‑bit})\\
\text{COUNT} & \;(32\text{‑bit})\\
\text{BEARER}& \;(5\text{‑bit})\\
\text{DIR}   & \;(1\text{‑bit})\\
\text{LENGTH}& \;(\text{bits of keystream})
\end{aligned}
$$

The keystream generated from these inputs is XOR‑ed bit‑by‑bit with the plaintext to obtain the ciphertext; the same inputs regenerate the keystream for de‑cryption [TS 33.501 §D.2.1.1].

*Example*:  
Assume $K_{\text{RRCenc}} = \text{0x001122…FF}$ (128 bits), BEARER = 3, DIR = 0 (uplink), COUNT = 0x00000010, LENGTH = 64 bits.  The NEA algorithm produces a 64‑bit keystream, e.g. `0xA5A5A5A5A5A5A5A5`.  Plaintext `0x1122334455667788` XOR keystream yields ciphertext `0xB7 77 96 E1 F3 D3 DD D D`.  The same parameters at the receiver reproduce the keystream and recover the original plaintext.

---

### 5. User‑Plane (UP) security policy  

The Session Management Function (SMF) conveys a **UP security policy** to the gNB during PDU‑session establishment [TS 33.501 §6.6.1].  The policy indicates whether **confidentiality** and/or **integrity** protection are *Required*, *Preferred* or *Not needed* for each Data Radio Bearer (DRB).  

* If the policy is **Required** and the gNB cannot activate the indicated protection, it **rejects** the establishment of the UP resources and reports a reject‑cause to the SMF [TS 33.501 §6.6.1].  
* If the policy is **Not needed**, the session proceeds without protection.  
* For **Preferred**, the gNB may activate the protection when possible but is not forced to reject if it cannot.

During handovers (Xn, N2, inter‑working) the UP security policy is transferred together with the PDU‑session identifier so that the target gNB can enforce the same protection level [TS 33.501 §6.6.1].

---

### 6. Common pitfalls and practical notes  

| Pitfall | Why it matters | Guidance |
|---------|----------------|----------|
| **Re‑using the same NAS COUNT** across different NAS connections | Violates replay protection; the receiver may accept a replayed message | Maintain separate COUNT pairs per access as mandated [TS 33.501 §6.4.2.1] |
| **Activating confidentiality without integrity** (e.g., selecting NIA0) | Integrity attacks can go undetected while traffic is encrypted | Ensure the selected integrity algorithm is not NIA0 unless explicitly allowed [TS 33.501 §6.5.1] |
| **Neglecting to update the security context after a NAS SMC on one access** | The other active NAS connection may continue using an old key, exposing it to compromise | Follow the dual‑access re‑keying rules; trigger a NAS Security Mode Command (SMC) on the second access when needed [TS 33.501 §6.4.2.2] |
| **Skipping UP security policy check on handover** | The target gNB may inadvertently downgrade protection, violating subscriber contracts | Transfer and verify the UP security policy in the handover messages and reject if the policy cannot be honoured [TS 33.501 §6.6.1] |
| **Assuming PDCP integrity covers lower layers** | Only PDCP‑layer messages are integrity protected; lower layers remain vulnerable | Deploy additional measures (e.g., MAC‑I verification at RRC) if required by the operator [TS 33.501 §6.5.1] |

By adhering to the defined security contexts, algorithm inputs and policy handling, engineers can ensure that both signalling and user data remain confidential and tamper‑resistant throughout the 5G network life‑cycle.

## 練習題

**1.** Which layer provides RRC integrity protection in the 5G system?

- A. MAC layer
- B. PDCP layer
- C. RLC layer
- D. Physical layer

<details><summary>看答案</summary>

正解：B。RRC integrity is performed by the PDCP layer, as specified in the standard.

</details>

**2.** What parameter guarantees replay protection for RRC integrity?

- A. BEARER identity
- B. DIRECTION bit
- C. PDCP COUNT value
- D. MESSAGE length

<details><summary>看答案</summary>

正解：C。Replay protection is achieved by accepting each PDCP COUNT value only once.

</details>

**3.** Which key is used as the INPUT KEY for the 128‑NEA ciphering algorithm?

- A. $K_{\text{RRCint}}$
- B. $K_{\text{NAS}}$
- C. $K_{\text{RRCenc}}$
- D. $K_{\text{UP}}$

<details><summary>看答案</summary>

正解：C。The NEA algorithm uses the 128‑bit cipher key $K_{\text{RRCenc}}$.

</details>

**4.** If the UP security policy received by the gNB is "Required" but the gNB cannot activate confidentiality, what must the gNB do?

- A. Continue without confidentiality and log a warning
- B. Activate integrity only and ignore confidentiality
- C. Reject the establishment of UP resources and send a reject‑cause to the SMF
- D. Switch to a fallback ciphering algorithm

<details><summary>看答案</summary>

正解：C。The standard mandates a rejection when required protection cannot be provided.

</details>
