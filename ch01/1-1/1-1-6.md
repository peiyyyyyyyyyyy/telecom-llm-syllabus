## 正文

**5G Core Network (5GC) and Service‑Based Architecture (SBA)**  

The 5G Core Network (5GC) is the logical backbone that interconnects the radio access network (RAN) with external data networks, enabling the three major pillars of 5G: enhanced Mobile Broadband (eMBB), massive Machine‑Type Communications (mMTC), and ultra‑Reliable Low‑Latency Communications (URLLC). Unlike the 4G EPC, which is built around a hierarchy of point‑to‑point interfaces, the 5GC adopts a **Service‑Based Architecture (SBA)**. In SBA every network function (NF) is a *service* that offers well‑defined Application Programming Interfaces (APIs) over HTTP/2 and JSON. This decoupling yields:

* **Scalability** – NFs can be instantiated on demand (cloud‑native, micro‑service style).  
* **Flexibility** – New services (e.g., network‑slice selection, policy control) can be added without redesigning the whole core.  
* **Interoperability** – Standardized Service‑Based Interfaces (SBIs) allow multivendor deployments.

---

### 1. Core Network Functions (CNFs) in SBA  

| NF | Primary Role | Typical SBI(s) |
|----|--------------|----------------|
| **AMF** (Access and Mobility Management Function) | Handles registration, connection management, mobility, and security for the control plane. | N1 (UE‑AMF), N2 (gNB‑AMF), N11 (SMF‑AMF) |
| **SMF** (Session Management Function) | Creates, modifies and releases PDU sessions; selects UPF(s). | N11 (AMF‑SMF), N4 (SMF‑UPF) |
| **UPF** (User Plane Function) | Data plane anchor; forwards user packets, performs traffic shaping, QoS enforcement, and lawful interception. | N3 (gNB‑UPF), N4 (SMF‑UPF) |
| **NRF** (Network Repository Function) | Service discovery; maintains a registry of all available NF instances and their supported APIs. | N5 (NF‑NRF) |
| **PCF** (Policy Control Function) | Stores policy rules; provides QoS and charging rules to SMF/UPF. | N7 (PCF‑SMF), N15 (PCF‑AF) |
| **NSSF** (Network Slice Selection Function) | Determines which network slice a UE should be attached to, based on subscription and network load. | N13 (AMF‑NSSF) |
| **AF** (Application Function) | External applications (e.g., OTT, IoT platforms) that request network resources via PCF. | N11 (AF‑SMF) |
| **UDM** (Unified Data Management) | Central subscriber data store (e.g., SUPI, authentication keys). | N12 (UDM‑AMF) |
| **AUSF** (Authentication Server Function) | Performs 5G‑Aka authentication. | N12 (AUSF‑UDM) |

All NFs are **stateless** with respect to user plane data; state is either kept in a distributed data store (e.g., UDM) or in the UPF (session context).  

---

### 2. Service‑Based Interfaces (SBIs) and Message Flow  

SBIs use **HTTP/2** for transport, enabling multiplexed streams, header compression (HPACK), and TLS 1.3 for security. Each SBI is identified by a **reference URI** (e.g., `http://amf.example.com:80/n11`). The request/response payload follows **3GPP TS 23.503** JSON schema.

A typical **PDU Session Establishment** proceeds as:

1. UE → **N1** → AMF: `Initial UE Message` (registration request).  
2. AMF → **N11** → SMF: `Create Session Request` (includes *DNN*, *S-NSSAI*).  
3. SMF → **N4** → UPF: `PDU Session Establishment Request`.  
4. UPF replies with allocated **TEID** (Tunnel Endpoint Identifier) and **QoS Flow Identifier (QFI)**.  
5. SMF → **N11** → AMF: `Create Session Response`.  
6. AMF → **N2** → gNB: `RRC Connection Setup` with the TEID/QFI for user‑plane forwarding.

### 3. Key Quantitative Concepts  

#### 3.1 QoS Flow Mapping  

Each QoS Flow is identified by a **QFI** (0‑255). The mapping from QFI to **5G QoS Identifier (5QI)** determines latency, packet loss, and priority. The relationship is often expressed as:

$$
\text{Latency Budget}_{\text{QFI}} = \frac{1}{\text{Scheduling Interval}} \times \text{ARQ Retransmissions}_{\text{QFI}}
$$

where:

* **Scheduling Interval** – time between two consecutive transmission opportunities (ms).  
* **ARQ Retransmissions** – maximum number of Hybrid‑ARQ (HARQ) rounds allowed for the flow.

#### 3.2 Maximum Number of PDU Sessions per UE  

The 5G specification caps the number of concurrent PDU sessions per UE at **$N_{\text{max}} = 16$**. However, the practical limit is driven by the **UPF processing capacity**:

$$
N_{\text{UE}}^{\text{practical}} = \left\lfloor \frac{C_{\text{UPF}}}{c_{\text{session}}} \right\rfloor
$$

where:

* $C_{\text{UPF}}$ = total packet processing capacity of the UPF (packets s$^{-1}$).  
* $c_{\text{session}}$ = average processing load per active PDU session (packets s$^{-1}$ per session).

---

### 4. Worked Example  

**Scenario:** An operator deploys a cloud‑native UPF with a processing capacity of $C_{\text{UPF}} = 200$ Mpps (million packets per second). The average packet rate per active PDU session is measured as $c_{\text{session}} = 0.8$ Mpps.  

**Question:** How many simultaneous PDU sessions can the UPF support, and does this exceed the per‑UE limit?

**Solution:**  

$$
N_{\text{UE}}^{\text{practical}} = \left\lfloor \frac{200\ \text{Mpps}}{0.8\ \text{Mpps/session}} \right\rfloor = \left\lfloor 250 \right\rfloor = 250\ \text{sessions}
$$

Since the standard per‑UE limit is $N_{\text{max}} = 16$, the UPF can comfortably support the aggregate of sessions across many UEs. For a single UE, the limit remains 16, so the operator must enforce this at the SMF level (e.g., by rejecting additional session requests).

### 5. Common Mistakes and Practical Notes  

| Mistake | Why it Happens | Correct Practice |
|---------|----------------|------------------|
| **Treating AMF as a “gateway”** | Legacy 4G mindset where MME performed both control and user‑plane anchoring. | Remember AMF is *purely* control‑plane; user‑plane traffic always passes through a UPF. |
| **Hard‑coding NF IP addresses** | Early‑stage testbeds often use static configuration. | Use the NRF for dynamic discovery; store only the NRF URI in each NF. |
| **Ignoring slice selection in the SMF** | Assuming a single “default” slice suffices. | Configure NSSF to return the appropriate *S‑NSSAI* and let SMF select a slice‑specific UPF. |
| **Over‑provisioning QoS Flows** | Assigning a unique QFI per application without aggregating similar requirements. | Group flows with identical latency/priority into the same QFI to reduce state in the UPF. |
| **Neglecting latency budgets in URLLC** | Focusing only on throughput. | Verify that the sum of scheduling interval, processing delay, and propagation delay meets the URLLC target (< 1 ms). |

**Practical tip:** Deploy the 5GC as containerized micro‑services orchestrated by Kubernetes. Leverage *Horizontal Pod Autoscaling* based on CPU/packet‑processing metrics to automatically scale SMF/UPF instances as traffic fluctuates. Ensure that the NRF’s service registry is replicated across zones to avoid a single point of failure.
