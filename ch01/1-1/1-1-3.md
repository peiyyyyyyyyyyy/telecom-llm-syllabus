# 1.1.3 RAN 架構演進：CU／DU／RU 分離

所屬：[1.1 網路架構](../1-1.md)

## 正文

The radio access network (RAN) in 4 G and 5 G has evolved from a monolithic base‑station toward a disaggregated architecture in which the logical functions are split into **Centralized Units (CUs)**, **Distributed Units (DUs)** and, in the Open RAN context, **Radio Units (RUs)**. This functional split enables operators to place compute‑intensive control‑plane functions (e.g., RRC, PDCP for signaling radio‑bearer) in a data‑center‑class CU, while latency‑sensitive lower‑layer processing (MAC, RLC, High‑PHY) remains close to the antenna in the DU, and the lowest‑layer RF processing (Low‑PHY, analog front‑end) resides in the RU. The result is greater scalability, multi‑vendor interoperability, and the ability to reuse transport infrastructure (e.g., Ethernet) for the fronthaul link – a key enabler for dense 5 G deployments and network sharing [TS 38.401 §6.1.1].

### Key Logical Nodes (3GPP terminology)

| Node | Primary functions | Typical placement |
|------|-------------------|-------------------|
| **gNB‑CU‑CP** | Control‑plane (RRC, PDCP for SRB) | Centralised data‑centre or edge cloud |
| **gNB‑CU‑UP** | User‑plane (PDCP for user data) | Co‑located with CU‑CP or separate |
| **gNB‑DU** | RLC, MAC, High‑PHY (layer 2/3) | Near the antenna, often collocated with RU |
| **RU (O‑RU)** | Low‑PHY, RF front‑end | At the tower or rooftop |

A gNB may consist of a **gNB‑CU‑CP**, one or more **gNB‑CU‑UPs**, and one or more **gNB‑DUs** [TS 38.401 §6.1.2]. The same principle applies to an ng‑eNB, which uses the same logical split but with different naming.

### Interface Landscape

| Interface | Direction | Connects | Protocol layer (as defined in the reference) |
|-----------|-----------|----------|---------------------------------------------|
| **F1‑C** | Control‑plane | gNB‑CU‑CP ↔ gNB‑DU | Logical F1 interface (control) |
| **F1‑U** | User‑plane | gNB‑CU‑UP ↔ gNB‑DU | Logical F1 interface (user) |
| **E1** | Both planes | gNB‑CU‑CP ↔ gNB‑CU‑UP | Logical E1 interface |
| **W1‑C / W1‑U** | (ng‑eNB only) | ng‑eNB‑CU‑CP ↔ ng‑eNB‑DU (C) and ng‑eNB‑CU‑UP ↔ ng‑eNB‑DU (U) | Logical W1 interface |
| **Xn**, **NG**, **X2** | Inter‑gNB / core | Terminate in the CU | Logical interfaces (signalling & user) |
| **Open Fronthaul (LLS)** | Both planes | O‑DU ↔ O‑RU | Defined by O‑RAN (LLS) |

The **F1‑C** and **F1‑U** interfaces are explicitly mentioned as the links between the CU‑CP / CU‑UP and the DU [TS 38.401 §6.1.2]. The **E1** interface binds the CU‑CP and CU‑UP [TS 38.401 §6.1.2].

### Connectivity Rules (3GPP)

* **One‑to‑One CU‑CP ↔ DU**: *“One gNB‑DU is connected to only one gNB‑CU‑CP”* [TS 38.401 §6.1.2].
* **One‑to‑One CU‑CP ↔ CU‑UP**: *“One gNB‑CU‑UP is connected to only one gNB‑CU‑CP”* [TS 38.401 §6.1.2].
* **One‑to‑Many DU ↔ CU‑UP**: *“One gNB‑DU can be connected to multiple gNB‑CU‑UPs under the control of the same gNB‑CU‑CP”* [TS 38.401 §6.1.2].
* **One‑to‑Many CU‑UP ↔ DU**: *“One gNB‑CU‑UP can be connected to multiple DUs under the control of the same gNB‑CU‑CP”* [TS 38.401 §6.1.2].
* **Resiliency**: *“For resiliency, a gNB‑DU and/or a gNB‑CU‑UP may be connected to multiple gNB‑CU‑CPs by appropriate implementation”* [TS 38.401 §6.1.2].

These rules guarantee that the logical gNB remains a single entity to the 5GC (the NG, Xn‑C interfaces terminate in the CU) while allowing flexible placement of processing resources [TS 38.401 §6.1.1].

### O‑RAN Perspective

The O‑RAN Alliance adopts the same functional split but uses its own naming:

* **O‑CU‑CP** – terminates NG‑c, X2‑c, Xn‑c, F1‑c, and E1; hosts RRC and PDCP for SRB [O‑RAN OAD §5.3.3].
* **O‑CU‑UP** – terminates NG‑u, X2‑u, Xn‑u, F1‑u; hosts PDCP for user data (not explicitly quoted but implied by the split).
* **O‑DU** – implements RLC, MAC, High‑PHY, terminates the Open Fronthaul (LLS) towards one or more **O‑RUs** [O‑RAN OAD §5.3.5].
* **O‑RU** – implements Low‑PHY and RF front‑end, terminates the Open Fronthaul on the M‑Plane [O‑RAN OAD §5.3.6].

Management interfaces (O1 for SMO control, E2 for near‑RT RIC) are also defined, but they are outside the scope of this subsection.

### Worked Example

Consider a small 5 G site that deploys:

* **1** gNB‑CU‑CP (centralised in a metro‑edge data centre)
* **2** gNB‑CU‑UPs (one for enhanced mobile broadband, one for ultra‑reliable low‑latency traffic)
* **3** gNB‑DUs (each co‑located with an O‑RU)

The connectivity constraints imply:

1. Each DU connects to the single CU‑CP → **3** F1‑C links.
2. Each DU may be served by both CU‑UPs → **3 × 2 = 6** F1‑U links.
3. The CU‑CP connects to each CU‑UP via **E1** → **2** E1 links.

If the operator wishes to add resiliency by connecting DU 1 also to a backup CU‑CP, the number of F1‑C links rises to **4** (the extra link to the backup CU‑CP). The logical gNB still appears as a single entity to the 5GC because all NG‑c and Xn‑c interfaces terminate in the primary CU‑CP [TS 38.401 §6.1.1].

### Common Mistakes & Practical Notes

| Mistake | Why it Happens | Correct Practice |
|---------|----------------|------------------|
| **Confusing CU‑CP with CU‑UP** | Both share the “CU” prefix; the split is not always visible in vendor documentation. | Remember: *CP* = control‑plane (RRC, SRB PDCP); *UP* = user‑plane (PDCP for user data). |
| **Assuming a one‑to‑one DU‑CU relationship** | Early 4 G deployments were monolithic. | The specification explicitly allows one DU to attach to multiple CU‑UPs and vice‑versa [TS 38.401 §6.1.2]. |
| **Placing the F1‑U interface at the CU‑CP** | Misreading “F1” as a single interface. | F1‑C carries control information; F1‑U carries user data. |
| **Ignoring resiliency connections** | Resiliency is optional and often omitted in diagrams. | Design for multiple CU‑CP connections when high availability is required [TS 38.401 §6.1.2]. |
| **Mapping O‑RAN components to 3GPP names incorrectly** | O‑RAN uses “O‑CU‑CP/UP”, “O‑DU”, “O‑RU”. | Use the equivalence table: O‑CU‑CP ↔ gNB‑CU‑CP, O‑DU ↔ gNB‑DU, O‑RU ↔ radio front‑end. |

By adhering to the defined interfaces and connectivity rules, engineers can build flexible, carrier‑grade RANs that interoperate across vendors and support future services such as network slicing and edge computing.
