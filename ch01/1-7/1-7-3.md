# 1.7.3 換手與移動性管理

所屬：[1.7 網路優化與終端](../1-7.md)

## 正文

Mobility management in 5G NR is the set of mechanisms that keep a user equipment (UE) connected while it moves across the radio coverage of different transmission points (TRPs) or cells. Proper handover ensures uninterrupted user‑plane data, maintains QoS guarantees, and avoids radio link failures (RLF) that would otherwise trigger costly RRC re‑establishment procedures. In a network‑controlled environment, handover decisions are taken by the gNB (or distributed unit) and are signalled to the UE through the Radio Resource Control (RRC) layer [TS 38.300 §9.2.3].

### Types of Mobility

The specification distinguishes two mobility categories for a UE that is already in **RRC_CONNECTED**:

* **Cell‑level mobility** – the UE moves from a source cell to a target cell and an explicit RRC handover procedure is required.  
* **Beam‑level mobility** – the UE switches between beams (or between beams belonging to different cells) without any RRC signalling; the decision is taken locally by the physical and MAC layers [TS 38.300 §9.2.3].

Cell‑level handover may be intra‑gNB (within the same gNB) or inter‑gNB (across Xn). Beam‑level mobility can also be inter‑cell (inter‑cell beam management, ICBM) and is controlled by measurement configurations delivered by the gNB [TS 38.300 §9.2.3].

### Inter‑gNB Handover Procedure (Cell‑level)

The minimum signalling chain for an inter‑gNB handover consists of the following elemental steps (Fig. 9.2.3.1‑1 in the spec):

| Step | Action |
|------|--------|
| 1 | Source gNB sends **HANDOVER REQUEST** to the target gNB over the Xn interface. |
| 2 | Target gNB performs admission control and replies with **HANDOVER REQUEST ACKNOWLEDGE**, containing the RRC configuration for the target cell. |
| 3 | Source gNB forwards the received **RRCReconfiguration** message (contained in the ACK) to the UE. The message includes at least the target cell ID and all access information required to reach the target cell without a fresh SystemInformation acquisition. |
| 4 | UE re‑establishes the RRC connection on the target gNB and sends **RRCReconfigurationComplete**. User data may be piggy‑backed if a grant permits [TS 38.300 §9.2.3].

During a **Data‑And‑Power‑Saving (DAPS)** handover the UE continues to receive downlink data from the source gNB until the source cell is released, and continues uplink transmission to the source gNB until the random‑access (RA) procedure on the target gNB succeeds [TS 38.300 §9.2.3].

### MAC / RLC / PDCP handling at Handover

For a regular handover the UE must reset the MAC entity and re‑establish the RLC layer. In a DAPS handover the UE:

* creates a MAC entity for the target,
* instantiates an RLC entity and a dedicated logical channel (DTCH) for each DRB configured with DAPS,
* re‑configures the PDCP entity with separate security and ROHC functions for source and target,
* retains all other source‑cell configurations until the source cell is released [TS 38.300 §9.2.3].

RRC‑managed handovers may be performed **with** or **without** PDCP re‑establishment. For DRBs using RLC‑AM, the PDCP can be re‑established together with a security‑key change, or a data‑recovery procedure can be launched without a key change. Similar options exist for RLC‑UM and SRBs [TS 38.300 §9.2.3].

### Radio Link Failure (RLF) and Recovery

While in **RRC_CONNECTED**, the UE continuously performs Radio Link Monitoring (RLM) on the active Bandwidth Part (BWP) using reference signals (SSB/CSI‑RS) and thresholds supplied by the network. An RLF is declared when any of the following occurs [TS 38.300 §9.2.7]:

* Expiry of a radio‑problem timer after a physical‑layer indication,
* Expiry of a timer started by a measurement report,
* Random‑access failure,
* RLC failure,
* Consistent uplink LBT failures (shared‑spectrum operation),
* For IAB‑MT, reception of a backhaul‑RLF indication.

After RLF the UE **remains** in **RRC_CONNECTED** and follows a recovery flow that depends on the handover context (source vs. target cell, DAPS, CHO). For example, after a DAPS handover failure the UE falls back to the source cell configuration, resumes the connection, and reports the failure without triggering RRC re‑establishment if the source link is still alive [TS 38.300 §9.2.7].

### Mobility Robustness Optimisation (MRO)

MRO is a set of network‑side analytics that detect sub‑optimal handovers and trigger corrective actions. The three intra‑system handover problems defined are [TS 38.300 §15.5.2]:

* **Too Late Handover** – RLF occurs after the UE has stayed a long time in the cell; the UE re‑establishes in a *different* cell.
* **Too Early Handover** – RLF occurs shortly after a successful handover; the UE re‑establishes in the *source* cell.
* **Handover to Wrong Cell** – RLF occurs shortly after handover; the UE re‑establishes in a cell that is neither the source nor the target.

The detection relies on the UE‑reported timer **Tstore_UE_cntxt** (or equivalent) that measures the elapsed time since the last handover. If the timer is **smaller** than the configured threshold, a “too early” situation is inferred; if it is **absent** or **larger**, a “too late” situation is inferred [TS 38.300 §15.5.2].

### Worked Example (Illustrative)

Consider a UE that is served by **gNB A** (source) and needs to hand over to **gNB B** (target). The following timeline (in arbitrary time units) is observed:

| Time | Event |
|------|-------|
| t₀ | gNB A sends **HANDOVER REQUEST** to gNB B. |
| t₁ = t₀ + Δ₁ | gNB B replies with **HANDOVER REQUEST ACKNOWLEDGE** (contains RRCReconfiguration). |
| t₂ = t₁ + Δ₂ | gNB A forwards **RRCReconfiguration** to UE. |
| t₃ = t₂ + Δ₃ | UE moves the RRC connection, sends **RRCReconfigurationComplete** (user data may be included). |
| t₄ = t₃ + Δ₄ | Handover completes; source cell is released. |

Assume each Δᵢ = 10 ms, giving a total handover duration of 40 ms. The network’s **Tstore_UE_cntxt** threshold is configured to 100 ms. Because the elapsed time since the last handover (40 ms) is *smaller* than the threshold, the network classifies the handover as **successful** and not a “too early” case [TS 38.300 §15.5.2]. If, instead, the UE later declared RLF after staying 150 ms in the new cell, the timer would be *larger* than the threshold, and MRO would flag a **Too Late Handover** [TS 38.300 §15.5.2].

### Common Pitfalls and Practical Notes

| Pitfall | Why it matters | Remedy |
|---------|----------------|--------|
| **Omitting beam‑specific information in the RRCReconfiguration** | The UE would be unable to access the target cell without a fresh SystemInformation read, increasing handover latency. | Include any required beam information in the RRCReconfiguration as prescribed [TS 38.300 §9.2.3]. |
| **Releasing secondary cells (CA, DC, SUL, etc.) too early during DAPS** | Premature release can cause loss of user‑plane data before the UE completes the random‑access on the target. | Follow the rule that secondary configurations are released *before* the handover command and are only re‑configured after the source PCell is released [TS 38.300 §9.2.3]. |
| **Ignoring RLF reports in MRO** | Without the UE’s RLF report the network cannot differentiate between coverage‑related failures and handover‑related failures, leading to sub‑optimal parameter tuning. | Ensure the UE makes the latest RLF Report available to the network for up to 48 hours [TS 38.300 §15.5.2]. |
| **Assuming beam‑level mobility always avoids RRC signalling** | Inter‑cell beam management (ICBM) still requires measurement configuration that may trigger RRC updates if the UE needs to switch to a different PCI. | Distinguish intra‑cell beam mobility (no RRC) from ICBM, which involves measurement of SSBs with different PCIs [TS 38.300 §9.2.3]. |
| **Treating “Too Early” and “Too Late” as symmetric** | The thresholds and recovery actions differ; a “too early” handover often leads the UE back to the source cell, while a “too late” handover forces re‑selection of a new cell. | Use the timer‑based criteria (Tstore_UE_cntxt) to correctly classify the event [TS 38.300 §15.5.2]. |

Understanding these mechanisms enables engineers to design robust handover policies, optimise measurement configurations, and correctly interpret MRO analytics for continuous service quality.

## 練習題

**1.** Which type of mobility explicitly requires RRC signalling to be triggered according to the specification?

- A. Cell Level Mobility
- B. Beam Level Mobility
- C. Both Cell and Beam Level Mobility
- D. Neither Cell nor Beam Level Mobility

<details><summary>看答案</summary>

正解：A。Cell Level Mobility is defined as needing explicit RRC signalling such as handover.

</details>

**2.** After the source gNB receives the HANDOVER REQUEST ACKNOWLEDGE, what is its next action toward the UE?

- A. It forwards the RRCReconfiguration message to the UE.
- B. It sends a RRCConnectionRelease to the UE.
- C. It initiates a random access procedure on behalf of the UE.
- D. It directly transfers user data without further signalling.

<details><summary>看答案</summary>

正解：A。The source gNB forwards the RRC configuration contained in the HANDOVER REQUEST ACKNOWLEDGE to the UE.

</details>

**3.** Which of the following configurations are released by the source gNB before the handover command is sent in a DAPS handover?

- A. CA, DC, SUL, multi‑TRP, EHC, CHO, UDC, NR sidelink and V2X sidelink configurations
- B. Only the target PCell configuration
- C. All beam‑specific information for the target cell
- D. No configurations are released; they are retained until after the handover

<details><summary>看答案</summary>

正解：A。In DAPS handover, many secondary configurations are released prior to the handover command.

</details>

**4.** When a Radio Link Failure (RLF) occurs in the source cell during a DAPS handover, what does the UE do according to the specification?

- A. It stops any data transmission or reception via the source link and releases the source link, but maintains the source RRC configuration.
- B. It immediately initiates RRC re‑establishment with the target gNB.
- C. It switches to idle mode and performs cell reselection.
- D. It discards all PDCP entities and starts a new security context.

<details><summary>看答案</summary>

正解：A。The UE halts data on the source link while keeping the RRC state, awaiting further handover steps.

</details>

**5.** Which handover failure scenario does **not** trigger an RRC connection re‑establishment procedure?

- A. DAPS handover failure, where the UE falls back to the source cell configuration.
- B. Inter‑gNB handover failure after the UE has completed random access to the target.
- C. Initial CHO execution failure leading to cell selection.
- D. Any handover failure that results in the UE entering RRC_IDLE.

<details><summary>看答案</summary>

正解：A。In a DAPS handover failure the UE returns to the source cell without invoking RRC re‑establishment.

</details>
