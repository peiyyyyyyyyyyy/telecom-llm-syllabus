# 1.7.6 終端一致性測試（Conformance testing）

所屬：[1.7 網路優化與終端](../1-7.md)

## 正文

In a 5G NR (New Radio) deployment, *conformance testing* verifies that network elements – in particular NG‑RAN nodes – behave according to the procedures defined in the 3GPP specifications. Although the reference clause [TS 38.300 §15.5.5] does not describe a dedicated “conformance test suite”, it defines the functional expectations that must be met. A terminal (UE) or a network element that fails to follow these expectations will cause coverage‑related performance degradation, hand‑over failures, or unnecessary interference, all of which directly affect the quality of service promised to the operator and its customers. Consequently, conformance testing is a prerequisite before a node is released to live service or before a UE is certified for market.

### Key Definitions (derived from the reference)

| Symbol / Term | Definition | Unit / Remarks |
|---------------|------------|----------------|
| **NG‑RAN node** | Any gNB (or gNB‑DU/gNB‑CU) that participates in the radio access network. | – |
| **Alternative coverage configuration** | A set of radio parameters (e.g., power, beamforming weights) that can be selected by OAM to achieve a desired coverage state. | – |
| **OAM** | Operations, Administration and Management – the system that programs alternative coverage configurations. | – |
| **Dynamic coverage configuration change** | An autonomous modification of radio parameters within a node, possibly switching between alternative configurations. | – |
| **NG‑RAN NODE CONFIGURATION UPDATE** | The Xn‑based signalling message used to inform neighbour nodes of changes to coverage. | – |
| **CGI** | Cell Global Identifier – uniquely identifies a cell. | – |
| **SSB** | Synchronisation Signal Block – carries the broadcast of the cell’s reference signals. | – |
| **Coverage State Indicator (CSI)** | A binary or enumerated flag attached to a CGI/SSB in the update message that signals the current coverage status (e.g., *active* or *inactive*). | – |
| **Mobility Robustness Optimisation (MRO)** | Functions that manage hand‑over decisions to preserve service continuity. | – |

The reference stipulates that a node may be configured with *alternative coverage configurations* by OAM and that each configuration contains “relevant radio parameters” and possibly a permissible adjustment range [TS 38.300 §15.5.5.2]. When a node autonomously changes its coverage, it must *notify* its neighbours using the **NG‑RAN NODE CONFIGURATION UPDATE** message, including a list of affected cells (identified by CGI) and SSBs, together with the **coverage state indicator** [TS 38.300 §15.5.5.3].

### Conformance Criteria Derived from the Specification

A conformance test for an NG‑RAN node therefore checks the following observable behaviours:

1. **Configuration Acceptance** – The node must accept at least one *alternative coverage configuration* supplied by OAM, and must enforce any declared parameter ranges.  
2. **Autonomous Adjustment** – The node may autonomously modify its radio parameters within the allowed range and optionally switch to a different alternative configuration.  
3. **Neighbour Notification** – Upon any change, the node must generate a **NG‑RAN NODE CONFIGURATION UPDATE** that:
   - Lists every modified cell by its **CGI**.  
   - Includes the **coverage state indicator** for each listed cell.  
   - Optionally includes the **SSB index** and its coverage state indicator.  
4. **Coverage State Indicator Usage** – Receiving neighbours must:
   - Use the CSI to retrieve a previously stored **MRO** state if applicable.  
   - Align their own coverage configurations with the neighbour’s indicated state.  
   - Avoid triggering hand‑overs toward cells marked *inactive*.  

A test harness typically emulates OAM to inject alternative configurations, monitors the node’s internal parameter values, and captures Xn messages to verify the presence and correctness of the **NG‑RAN NODE CONFIGURATION UPDATE** payload.

### Worked Example

Assume a simple two‑node scenario: **Node A** (gNB‑1) and **Node B** (gNB‑2) are neighbours on the Xn interface.

| Step | Action | Expected Outcome |
|------|--------|-------------------|
| 1 | OAM configures **Node A** with two alternative coverage configurations: **C₁** (default) and **C₂** (high‑power). | Node A stores both configurations. |
| 2 | Traffic load increases; **Node A** autonomously switches from **C₁** to **C₂** (within allowed power range). | Internal radio parameters change; coverage radius expands. |
| 3 | **Node A** sends **NG‑RAN NODE CONFIGURATION UPDATE** to **Node B**. The list contains: <br> • CGI = *12345* (cell of Node A) <br> • Coverage State Indicator = *active* <br> • SSB index = 0, CSI = *active*. | **Node B** receives the update. |
| 4 | **Node B** processes the CSI: it updates its **MRO** state to reflect the neighbour’s expanded coverage and *does not* schedule hand‑overs toward any cell that would become *inactive* (none in this case). | Service continuity is maintained; no unnecessary hand‑overs occur. |

In a conformance test, the tester would verify that after step 3 the Xn message contains exactly the CGI and CSI as described, and after step 4 that **Node B** refrains from initiating a hand‑over toward any cell that the CSI marks *inactive*.

### Practical Notes & Common Mistakes

| Mistake | Why it matters | How to detect in testing |
|---------|----------------|--------------------------|
| **Ignoring the coverage state indicator** – The node treats all neighbours as *active* regardless of CSI. | May trigger hand‑overs to cells that are being de‑activated, causing call drops. | Verify that the hand‑over decision logic consults the CSI flag in the received update. |
| **Omitting SSB indices** – The update message includes only CGI entries. | Some neighbour nodes rely on SSB‑level granularity for beam‑specific optimisation. | Check the Xn payload for optional SSB entries when the specification mentions “optionally”. |
| **Sending updates for cells that are unchanged** – Flooding neighbours with unnecessary messages. | Increases signalling load and may confuse MRO state machines. | Confirm that updates are sent *only* when a coverage configuration change actually occurs. |
| **Not respecting the OAM‑defined parameter ranges** – Node adjusts power beyond the allowed interval. | Can cause interference with adjacent cells, violating the CCO objective. | Inspect the node’s internal radio parameter logs after OAM injection. |
| **Triggering hand‑overs toward cells marked *inactive*** – Contradicts the “avoid triggering hand‑overs towards cell(s) that are indicated to be inactive” rule. | Leads to connection failures during re‑configuration. | Simulate a neighbour update marking a cell *inactive* and observe hand‑over decisions. |

Finally, note that the reference clause does **not** provide a separate “conformance test specification” for terminals (UE) themselves; the described behaviours pertain to NG‑RAN nodes. Consequently, any UE‑focused conformance testing falls outside the scope of this subsection’s source material.

## 練習題

**1.** Which message must an NG‑RAN node send to its neighbours after a dynamic coverage configuration change?

- A. RRC Connection Reconfiguration
- B. NG‑RAN NODE CONFIGURATION UPDATE
- C. NAS Authentication Request
- D. X2 Handover Request

<details><summary>看答案</summary>

正解：B。The specification states that the node must notify neighbours using the NG‑RAN NODE CONFIGURATION UPDATE message.

</details>

**2.** What information is mandatory in the NG‑RAN NODE CONFIGURATION UPDATE message after a coverage change?

- A. Only the new transmit power value
- B. The CGI of each modified cell and its coverage state indicator
- C. The UE’s IMSI
- D. The complete list of all cells in the network

<details><summary>看答案</summary>

正解：B。The update must contain at least the CGI and coverage state indicator for each modified cell.

</details>

**3.** How should a receiving NG‑RAN node treat hand‑overs toward cells indicated as inactive in the update?

- A. It should prioritize them to clear the inactivity flag.
- B. It should avoid triggering hand‑overs toward those cells.
- C. It should ignore the indication and proceed normally.
- D. It must immediately shut down those cells.

<details><summary>看答案</summary>

正解：B。The specification explicitly instructs the receiving node to avoid hand‑overs to inactive cells.

</details>

**4.** Which entity is allowed to configure alternative coverage configurations for an NG‑RAN node?

- A. The UE
- B. OAM
- C. The Internet Service Provider
- D. The user’s mobile device

<details><summary>看答案</summary>

正解：B。OAM is the entity defined to configure alternative coverage configurations.

</details>

**5.** What optional element may be included in the NG‑RAN NODE CONFIGURATION UPDATE besides the CGI and coverage state indicator?

- A. The UE’s RRC state
- B. The SSB index and its coverage state indicator
- C. The core network’s IP address
- D. The device’s battery level

<details><summary>看答案</summary>

正解：B。The specification mentions that the SSB index and its coverage state indicator can be optionally included.

</details>
