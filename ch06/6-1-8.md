# 6.1.8 傳輸中斷與核心網問題

所屬：[6.1 根因的類型](6-1.md)

## 內文

#### 是什麼、什麼時候會用到

這一節處理「無線端本身沒壞，但基站和外界的連線出了問題」的障礙：gNB 與 AMF 之間的 NG-C 介面斷線、gNB 之間的 Xn-C 介面斷線、承載這些介面的 SCTP（Stream Control Transmission Protocol）偶聯（association）中斷、傳輸設備告警，以及 AMF 過載。NG-C 與 Xn-C 的傳輸層都是 IP 上的 SCTP（TS 38.412 V18.1.0 clause 7；TS 38.300 V18.11.0 clause 4.3.2.2）。維運人員通常在這些時候遇到它：同一區域很多小區在同一分鐘一起劣化或停話；告警台湧入大量通訊類告警；客服反映「有訊號但打不出去、上不了網」。這類障礙的關鍵是**從多點同時劣化推到共同的上游**，而不是逐站派人。規格頁：[TS 38.412 FTP 目錄](https://www.3gpp.org/ftp/Specs/archive/38_series/38.412/)。

#### 怎麼做／怎麼判斷

1. **先畫影響範圍。** 把劣化的小區依站點、傳輸路由、所連的 AMF 分群。TS 32.111-1 指出單一網路故障可能在大範圍產生多個告警，可依告警傳遞路徑、地理區域、特定設備等規則做關聯，並由 OS（Operations System）盡可能指出根因告警（TS 32.111-1 V18.0.0 clause 4.1.8、4.1.9）。TS 28.111 的告警紀錄為此提供 correlatedNotifications 與 rootCauseIndicator 屬性（TS 28.111 V18.8.0 clause 6.10、7.4.1）。
2. **看通訊類告警是誰發的。** 兩個 NE 之間的連線媒介出問題時，「each affected NE/OS shall detect the fault ... and generate its own associated communication alarm」，再由 OS 負責關聯定位（TS 32.111-1 clause 4.1.2）。所以十幾個 gNB 各自發 COMMUNICATIONS_ALARM 是正常現象，不代表十幾個故障點。常見 probableCause 有 Loss Of Signal（8）、Communications Receive Failure（17）、Communication Subsystem Failure（306）、Connection establishment error（566）；傳輸設備本身的問題可能出現 External transmission device failure（552，TS 28.111 Annex B 歸 Environmental）（TS 28.111 Annex B）。
3. **NG 與 SCTP 的規定要知道。** NG-RAN 節點與 AMF 之間「shall support」單一 SCTP 偶聯的組態，多個 SCTP 端點的組態「should be supported」；SCTP 偶聯由 NG-RAN 節點建立；可用 SCTP 多重歸屬（multi-homing）達成傳輸備援（TS 38.412 clause 7）。SCTP 恢復後，NG Setup「shall be the first NGAP procedure triggered after the TNL association has become operational」（TS 38.413 V18.11.0 clause 8.7.1.1），因此要確認斷線後有沒有重新完成 NG Setup。
4. **分辨 AMF 失效與 AMF 過載。** 收到 AMF STATUS INDICATION 時，NG-RAN 節點 shall 視所列 GUAMI 為不可用並執行 AMF 重選（TS 38.413 clause 8.7.6.2）。AMF 失效時，5G-AN 會把該 AMF 標為失效，對連線態 UE 釋放 NGAP UE-TNLA 綁定但保留 N3 用戶面，之後改送備援 AMF 或同一 AMF set 的其他 AMF（TS 23.501 V18.12.0 clause 5.21.2.3）。
5. **AMF 過載照 Overload Start／Stop 判讀。**
   - 收到 OVERLOAD START 的 NG-RAN 節點 shall 把發送的 AMF 視為過載（TS 38.413 clause 8.7.7.2）。
   - 若帶有 Overload Action IE，NG-RAN 節點 shall 用它辨識要處理的信令；值有四種：拒絕非緊急的 MO 資料傳輸 RRC 建立、拒絕信令的 RRC 建立、只允許緊急與 MT 服務、只允許高優先與 MT 服務（clause 8.7.7.2、9.3.1.105）。
   - 帶有 AMF Traffic Load Reduction Indication IE（INTEGER 1..99，clause 9.3.1.106）時，shall 依所示百分比減少信令；沒帶時，shall 確保只送出未被列為拒絕的信令。
   - 過載期間再收到 OVERLOAD START，shall 以新內容取代舊內容；收到 OVERLOAD STOP，shall 視過載結束並恢復對該 AMF 的正常運作（clause 8.7.7.2、8.7.8.2）。
   - AMF 可只對一部分 5G-AN 節點發送，受限制的 UE 會收到等待計時器（TS 23.501 clause 5.19.5.2）。

原文：[TS 38.412 V18.1.0](https://www.3gpp.org/ftp/Specs/archive/38_series/38.412/38412-i10.zip)、[TS 38.413 V18.11.0](https://www.3gpp.org/ftp/Specs/archive/38_series/38.413/38413-ib0.zip)、[TS 23.501 V18.12.0](https://www.3gpp.org/ftp/Specs/archive/23_series/23.501/23501-ic0.zip)。

#### 實際例子

虛構業者「Telco-X」某日上午的兩段紀錄（站名、AMF 名稱、數值均為虛構；KPI 為業者自訂）：

```
[A] 10:02 起告警（節錄）
10:02:11 GNB-K101 ... GNB-K114（14 站）
         alarmType: COMMUNICATIONS_ALARM  probableCause: Communication Subsystem Failure
         specificProblem: NG-C SCTP association down     # 廠商自訂字串
10:02:09 AGG-RTR-07  alarmType: COMMUNICATIONS_ALARM  probableCause: Loss Of Signal
         specificProblem: port 1/0/3 LOS                 # 匯聚路由器
10:31:40 AGG-RTR-07 告警清除；10:31:52 起 14 站陸續完成 NG Setup

[B] 14:00–14:15 NGAP 摘要（AMF-02 → 連到它的 gNB）
14:00:30 OVERLOAD START
         AMF Overload Response > Overload Action: Reject RRC connection establishments for Signalling
         AMF Traffic Load Reduction Indication: 40
14:13:05 OVERLOAD STOP
```

| 14:00–14:15 | 連 AMF-02 的站 | 只連 AMF-01 的站 |
|---|---|---|
| RRC 建立嘗試 | 52,000 | 18,000 |
| RRC 建立成功 | 33,800（65.0%） | 17,820（99.0%） |
| 前一日同時段成功率 | 99.0% | 99.0% |

判讀：[A] 段 14 站的通訊告警比匯聚路由器的 Loss Of Signal 晚 2 秒、都掛在同一台匯聚路由器下，路由器告警清除後 14 站恢復並重新 NG Setup，時間軸支持「共同上游傳輸中斷」，14 張站端告警應關聯成同一事件，根因告警是 AGG-RTR-07。[B] 段只有連到 AMF-02 的站成功率下降，無線端告警無異常，且起訖時間與 OVERLOAD START／STOP 一致，支持「AMF-02 過載導致 NG-RAN 依指示拒絕部分 RRC 建立」，不是無線涵蓋問題。失敗比例 35.0% 略低於指示的 40%，可以用「MT 存取不在這個 Overload Action 的拒絕範圍內」解釋，但要拿 RRC 建立原因分布才能確認。

不能下的結論：[A] 只知道路由器埠收不到信號，是光纖斷還是對端設備故障要再查；[B] 只能說明過載期間 gNB 的行為，AMF-02 **為何**過載（信令風暴、容量不足或上游 NF 問題）不在這些資料裡。參考：[TS 38.413 V18.11.0](https://www.3gpp.org/ftp/Specs/archive/38_series/38.413/38413-ib0.zip)。

#### 容易搞混的地方

- **Overload Start 不是 gNB 故障**：gNB 依 OVERLOAD START 拒絕部分 RRC 建立是規格要求的行為（TS 38.413 clause 8.7.7.2），不要把它當成 gNB 的軟硬體問題去重啟基站（[TS 23.501 FTP 目錄](https://www.3gpp.org/ftp/Specs/archive/23_series/23.501/)）。
- **百分比的意義**：Traffic Load Reduction Indication 是相對於 gNB 當下進來的、屬於 Overload Action 所指那類流量的拒絕比例（clause 9.3.1.106），不是全部流量都打 6 折。
- **很多告警 ≠ 很多故障**：連線媒介故障時兩端 NE 各自發告警是規格設計（TS 32.111-1 clause 4.1.2），要先關聯再派工。
- **AMF 過載與 AMF 失效**：過載時 AMF 還在服務，只是要求限流；失效或計畫移除時則有 AMF 重選（TS 23.501 clause 5.21.2）。

#### 和其他小節的關係

多點同時劣化的時間軸做法見 5.5.1 與 6.2.1，判斷是否為共同上游要列支持證據與反證（6.2.2）；若只有單站且有設備告警，回到 6.1.7。傳輸中斷常需跨部門協調，通報與升級見 6.4.2，交接時要寫明已關聯的告警（6.5.1）。規格：[TS 38.300 FTP 目錄](https://www.3gpp.org/ftp/Specs/archive/38_series/38.300/)。

**017.** According to TS 38.412, how can transport network redundancy be achieved for NG-C?

1. By SCTP multi-homing between two end-points, one or both of which is assigned multiple IP addresses
2. By running two NG Setup procedures towards the same AMF over the same association
3. By routing NGAP over Xn-C to a neighbouring gNB when NG-C fails
4. By carrying NGAP over GTP-U when SCTP fails

<details><summary>看答案</summary>

**答案**　1

**詳解**　TS 38.412 clause 7 states that transport network redundancy can be achieved by SCTP multi-homing between two end-points, of which one or both is assigned with multiple IP addresses. Option 2 is not a redundancy mechanism; NG Setup exchanges application-level data. Option 3 is wrong: Xn-C carries XnAP between NG-RAN nodes, not NGAP. Option 4 is wrong: SCTP shall be supported as the transport layer of the NG-C signalling bearer; GTP-U is a user-plane protocol.

**出處**　3GPP TS 38.412 V18.1.0 clause 7 (https://www.3gpp.org/ftp/Specs/archive/38_series/38.412/38412-i10.zip); 3GPP TS 38.300 V18.11.0 clause 4.3.2.2 (https://www.3gpp.org/ftp/Specs/archive/38_series/38.300/38300-ib0.zip)

</details>

**018.** What should the NOC do about this event?

<details><summary>看答案</summary>

**答案**　Raise a transport ticket to repair CSR-H51 port 1/1/2 because path redundancy for NG-C is lost, with no gNB restart or NG-C recovery action, since service is not affected.

**詳解**　The LOS on CSR-H51 port 1/1/2 (10:14:29) explains the path failure two seconds later. Service is running on the second path, so the action is a repair of the failed path to restore redundancy; a restart would cause an outage for no gain.

**出處**　Curriculum 6.1.8; 3GPP TS 32.111-1 V18.0.0 clause 4.1.3 (communication faults repaired by replacing faulty transmission equipment) (https://www.3gpp.org/ftp/Specs/archive/32_series/32.111-1/32111-1-i00.zip)
