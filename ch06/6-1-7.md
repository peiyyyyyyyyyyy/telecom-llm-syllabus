# 6.1.7 硬體故障

所屬：[6.1 根因的類型](6-1.md)

## 內文

#### 是什麼、什麼時候會用到

硬體故障（hardware failure）指網元（Network Element，NE）裡某個實體資源失常，例如射頻單元（Radio Unit）的發射路徑、基頻板、電源模組或風扇。TS 32.111-1 把網路故障分成硬體故障、軟體問題、功能故障、過載與通訊故障五類，其中硬體故障的定義是「NE 內某個實體資源的失常」（TS 32.111-1 V18.0.0 clause 4.1.0）。維運人員最常在三種情況碰到它：告警台跳出設備類告警；某個小區話務突然歸零或明顯下降；客服接到同一地點多人反映「沒訊號」。困難在於「小區不出訊號」不一定是壞掉，夜間節能關斷也會讓小區暫停服務，兩者處置完全不同，一定要先分清楚。規格頁：[TS 32.111-1 FTP 目錄](https://www.3gpp.org/ftp/Specs/archive/32_series/32.111-1/)。

#### 怎麼做／怎麼判斷

1. **先看告警類型與可能原因。** 告警紀錄（AlarmRecord）以 objectInstance、alarmType、probableCause、specificProblem 四個屬性識別同一個告警（TS 28.111 V18.8.0 clause 6.4）。alarmType 在 TS 28.111 的列舉值為 COMMUNICATIONS_ALARM、QUALITY_OF_SERVICE_ALARM、PROCESSING_ERROR_ALARM、EQUIPMENT_ALARM、ENVIRONMENTAL_ALARM 等（TS 28.111 clause 7.4.1）；它們對應 ITU-T X.733 的五種告警類型，X.733 的值參照名稱寫成 equipmentAlarm、communicationsAlarm、processingErrorAlarm 等（ITU-T X.733 clause 8.1.1、clause 11.2.5 Table 3）。X.733 對設備告警的定義是主要與設備故障相關的告警。硬體故障通常落在 EQUIPMENT_ALARM；但機房溫度、市電中斷這類「設備所在環境」的問題屬於 ENVIRONMENTAL_ALARM，不要混為一類。
2. **再看 probableCause 指到哪一種零件。** TS 28.111 Annex B 列出建議使用的字串（或整數）：例如 Transmitter Failure（67）、Receiver Failure（61）、Replaceable Unit Problem（69）、Power Problem（58）屬設備類；無線系統另有 Antenna problem（503）、Transceiver problem（529）、Power supply failure（522）、Lost redundancy（519）。規格要求產生者應（should）選用最具體的 probableCause（TS 28.111 clause 7.4.1）。
3. **看有沒有備援接手。** backedUpStatus 表示告警對象是否有備援，backUpObject 指出備援物件（TS 28.111 clause 7.4.1，定義引自 X.733 clause 8.1.2.4、8.1.2.5）。X.733 說明 backedUpStatus 為 true 時，代表服務沒有因此中斷。依 TS 32.111-1 clause 4.1.6，故障資源**沒有備援**時，NE 應隔離故障資源並將依賴它的資源移出服務；**有備援**時，NE 除隔離與通報外還要執行該備援型態的切換程序，而且「the recovery sequence shall start immediately」，切換前後短暫、有限的服務損失是可接受的。這些是 NE 自動做的，不是等人工核准才做。
4. **對照狀態變化。** 資源因故障完全無法服務時，operationalState 由 ENABLED 變為 DISABLED，依賴它的資源也跟著變（TS 32.111-1 clause 4.2.1；列舉值見 TS 28.622 V18.14.0 clause 4.4.1）。規格建議一個故障只發一個告警，其餘受影響資源以狀態變更事件呈現（TS 32.111-1 clause 4.1.2），所以「一個設備告警＋好幾個小區 DISABLED」是硬體故障的典型樣子。
5. **排除節能關斷。** TS 28.310 V18.8.0 clause 4.3.2 寫明，處於 energySaving 狀態的小區「is not considered as a cell outage or a fault condition」，且因此產生的狀況不應（should not）發告警。集中式節能的小區節能狀態可查 energySavingState（IS_ENERGY_SAVING／IS_NOT_ENERGY_SAVING），由 energySavingControl 觸發（TS 28.541 V18.15.0 clause 4.4.1，所屬類別 CESManagementFunction 見 clause 4.3.63）。原文：[TS 28.111 V18.8.0](https://www.3gpp.org/ftp/Specs/archive/28_series/28.111/28111-i80.zip)、[TS 28.310 V18.8.0](https://www.3gpp.org/ftp/Specs/archive/28_series/28.310/28310-i80.zip)。

#### 實際例子

下列為虛構業者「甲電信」的告警與狀態紀錄（格式依 TS 28.111 clause 7.3.1 的屬性名稱；DN、數值、廠商字串均為虛構）：

```
alarmId: 880417
objectInstance: SubNetwork=TelcoX-North,ManagedElement=GNB-A0421
alarmRaisedTime: 2026-11-18T02:13:07+08:00
alarmType: EQUIPMENT_ALARM
probableCause: Transmitter Failure
specificProblem: RU-2 TX branch output power loss   # 廠商自訂字串
perceivedSeverity: CRITICAL
backedUpStatus: false

02:13:08 state change  NRCellDU=2  operationalState ENABLED -> DISABLED
# NRCellDU=1、NRCellDU=3 沒有狀態變更通知，operationalState 維持 ENABLED
同站另一筆（02:40）：
alarmType: EQUIPMENT_ALARM  probableCause: Lost redundancy
specificProblem: PSU-B fail   perceivedSeverity: MAJOR
backedUpStatus: true  backUpObject: ManagedElement=GNB-A0421,PowerUnit=PSU-A  # 虛構 DN，由 PSU-A 承載
```

判讀步驟：第一，告警類型是設備類、可能原因指向發射路徑，時間點與第 2 小區轉為 DISABLED 只差 1 秒，同站其他兩小區不受影響，支持「RU-2 單一硬體故障」。第二，backedUpStatus 為 false，表示沒有備援接手，第 2 小區確實停止服務；反觀 02:40 的電源告警 backedUpStatus 為 true，嚴重度 MAJOR，符合 TS 32.111-1 clause 4.1.2「冗餘元件失效」列為 major 的範例，服務未中斷但已失去備援，應排入維修而非當成斷站。第三，該小區沒有任何節能狀態變化，排除節能關斷。

不能下的結論：告警只說明發射路徑失常，**不能**據此斷定是 RU 本體壞，也可能是饋線或連接器；要等現場測試或更換結果才能確認（TS 32.111-1 clause 4.3 測試管理）。參考：[TS 28.111 V18.8.0](https://www.3gpp.org/ftp/Specs/archive/28_series/28.111/28111-i80.zip)。

#### 容易搞混的地方

- **alarmType 的寫法**：TS 28.111 用 EQUIPMENT_ALARM 這種大寫列舉；X.733 的值參照名稱是 equipmentAlarm。兩者指同一類別，寫報告時照資料來源的實際值，不要自創第三種寫法（[ITU-T X.733](https://www.itu.int/rec/T-REC-X.733-199202-I/en)）。
- **設備類與環境類**：Cooling Fan Failure、Commercial Power Failure 在 TS 28.111 Annex B 列為 Environmental，不是 Equipment。
- **節能不是故障**：小區暫停服務但沒有設備告警、且 energySavingState 為 IS_ENERGY_SAVING，應判為節能；反之若有設備告警而小區 DISABLED，就不能用「可能是節能」帶過。
- **備援切換不是人工動作**：故障觸發的備援切換由 NE 依 TS 32.111-1 clause 4.1.6 自動執行；人工以管理命令鎖定主用資源讓備用接手，則屬預防性維護（clause 4.2.0），要走異動流程。

#### 和其他小節的關係

告警欄位的讀法見 5.1～5.5；把告警與狀態變更排成時間軸見 5.5.1、6.2.1。若同時出現多站傳輸告警，改看 6.1.8；更換板卡、鎖定／解鎖資源屬 6.3.2 需批准的處置，並依第 9 章異動流程辦理；換件後要寫進 6.5.2 障礙報告。規格：[TS 28.310 FTP 目錄](https://www.3gpp.org/ftp/Specs/archive/28_series/28.310/)。

**001.** An engineer edits the incident report and changes alarm 55101 (Cooling Fan Failure) to EQUIPMENT_ALARM "because a fan is a piece of hardware". Which statement is correct?

1. No; the type is Environmental, not Equipment.
2. The edit is right: any alarm raised by a physical component must be typed EQUIPMENT_ALARM.
3. The edit is right but should be written equipmentAlarm, because TS 28.111 takes its alarm types from X.733.
4. The alarm should be QUALITY_OF_SERVICE_ALARM, because the fan failure ultimately degraded cell throughput.

<details><summary>看答案</summary>

**答案**　1

**詳解**　TS 28.111 Annex B Table B.1 gives Cooling Fan Failure the integer 107 and the alarm type Environmental, and the record already carries ENVIRONMENTAL_ALARM, so the original value is correct. Option 2 is wrong because the alarm type follows the area of the problem (an enclosure condition here), not whether the reporting object is physical. Option 3 is wrong because a TS 28.111 record uses the enumeration EQUIPMENT_ALARM, not the X.733 value reference, and Equipment is the wrong category anyway. Option 4 is wrong because QUALITY_OF_SERVICE_ALARM conveys service degradation and is a separate alarm (55104 already does that), it does not reclassify the fan alarm.
