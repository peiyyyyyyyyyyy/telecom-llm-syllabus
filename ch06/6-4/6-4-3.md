# 6.4.3 工單

所屬：[6.4 流程](../6-4.md)

## 正文

In a 3GPP network, the moment an alarm is raised the operating personnel must decide whether the condition warrants a concrete corrective activity. When the alarm is verified as valid and its impact is assessed, the operator creates a **work order** (also referred to as a trouble report) to record the required actions, assign responsibility, and track the resolution timeline. This documented hand‑off guarantees that every alarm that *requires an operator response* is acted upon in a controlled manner, thereby limiting the degradation of Quality of Service (QoS) perceived by users [TS 32.111-1 §4.4].

### Definition and Core Elements
A work order is a structured record that contains at least the following fields:

| Symbol | Meaning | Unit / Type |
|--------|---------|--------------|
| $W_{\text{id}}$ | Unique work‑order identifier | integer |
| $A_{\text{id}}$ | Alarm identifier that triggered the order | integer |
| $P$ | Priority class (derived from alarm severity) | enum |
| $R_{\text{ass}}$ | Assigned responsible party (e.g., 1st‑line, 2nd‑line) | text |
| $T_{\text{open}}$ | Timestamp when the work order is opened | UTC |
| $T_{\text{close}}$ | Timestamp when the work order is closed | UTC |
| $S$ | Status (Open, In‑Progress, Closed) | enum |
| $A_{\text{act}}$ | List of actions to be performed (reset, replace, etc.) | text |

The **creation** of $W_{\text{id}}$ follows directly after the operator has *acknowledged* and *verified* the alarm, i.e., after the steps “Recognizing the alarm; Acknowledging the alarm; Verifying that the alarm is valid …” [TS 32.111-1 §4.4]. The work order then becomes the primary vehicle for “Taking actions which may include … creating trouble reports, etc.” [TS 32.111-1 §4.4].

### Workflow Integration
The work‑order lifecycle is tightly coupled with the alarm handling loop:

1. **Alarm detection** – Surveillance system raises an alarm.  
2. **Operator acknowledgement** – Operator marks the alarm as seen.  
3. **Validation** – Operator confirms the alarm is not a false positive.  
4. **Information enrichment** – Additional performance counters or logs are attached.  
5. **Cause analysis & impact assessment** – Operator decides on the required remediation.  
6. **Work‑order generation** – A new $W_{\text{id}}$ is created, populated with $A_{\text{id}}$, $P$, $R_{\text{ass}}$, and $A_{\text{act}}.  
7. **Execution** – Assigned personnel perform the listed actions (reset, replace equipment, etc.).  
8. **Closure** – After verification that the fault is corrected, $T_{\text{close}}$ is recorded and the status set to *Closed*.  

Each step is designed to satisfy the expectation that “Each alarm requires a needed action; Each action is taken by the operator” [TS 32.111-1 §4.4].

### Worked Example
Consider a LTE eNodeB that raises a *Radio Link Failure* alarm with identifier $A_{\text{id}} = 1024$ and severity *Critical*. The operator follows the loop:

| Step | Action | Result |
|------|--------|--------|
| 1 | Alarm appears on the console. | $A_{\text{id}} = 1024$ displayed. |
| 2 | Operator acknowledges (ACK). | Alarm status changes to *Acknowledged*. |
| 3 | Validation: cross‑check with KPI dashboard shows loss of throughput, confirming the alarm is genuine. |
| 4 | Enrichment: attach recent RRC logs (size = 2 MB). |
| 5 | Analysis: suspect faulty RF module; impact is loss of service for 150 users. |
| 6 | Work‑order creation: $W_{\text{id}} = 5678$, $P$ = *High*, $R_{\text{ass}}$ = *2nd‑line RF team*, $A_{\text{act}}$ = “reset RF module, if failure persists replace module”. |
| 7 | Execution: RF team performs a remote reset at $T = 10:15$ UTC; service restores. |
| 8 | Closure: verification at $T = 10:20$ UTC confirms KPI normalisation; $S$ set to *Closed*, $T_{\text{close}} = 10:20$ UTC. |

The work order provides a traceable record that the alarm was handled, the actions taken, and the time taken to restore service.

### Practical Notes and Common Pitfalls

| Mistake | Why it hurts | How to avoid |
|---------|--------------|--------------|
| Creating a work order for every alarm, regardless of relevance | Leads to “alarm flooding” and dilutes focus on truly impactful events. | Apply the key criterion: *alarms must require an operator response* [TS 32.111-1 §4.4]. |
| Missing the *acknowledge* step before work‑order creation | Breaks the human‑machine interface contract that operators should never miss actionable alarms. | Ensure the console forces an ACK before $W_{\text{id}}$ can be generated. |
| Assigning the wrong priority class $P$ | May delay high‑impact remediation. | Derive $P$ directly from alarm severity as defined in the FM specification. |
| Not updating the status $S$ during execution | Reduces visibility for supervisors and may cause duplicate effort. | Enforce status transitions (Open → In‑Progress → Closed) in the ticketing system. |
| Ignoring alarm suppression guidelines | Can cause saturation of the alarm management system, risking loss of control. | Use built‑in suppression methods to filter out non‑operationally relevant alarms [TS 32.111-1 §4.4]. |

By adhering to these guidelines, work orders become a reliable bridge between **alarm detection** and **service restoration**, ensuring that the network remains resilient and that QoS degradation is minimized.

## 練習題

**1.** Which of the following is NOT listed as an operator response step that could lead to a work order?

- A. Recognizing the alarm
- B. Analyzing the situation
- C. Suppressing alarms
- D. Taking actions such as creating trouble reports

<details><summary>看答案</summary>

正解：C。Alarm suppression is mentioned as a method to avoid flooding, not as a step that creates a work order.

</details>

**2.** What is the key criterion for an alarm to be considered for operator handling, which also justifies creating a work order?

- A. The alarm must be acknowledged
- B. The alarm must be validated
- C. The alarm must require an operator response
- D. The alarm must be suppressed

<details><summary>看答案</summary>

正解：C。Only alarms that need an operator action—such as issuing a work order—are considered relevant.

</details>
