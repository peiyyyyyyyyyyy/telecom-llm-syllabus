# 6.3.1 可以先查證的動作

所屬：[6.3 處置](6-3.md)

## 內文

#### 是什麼、什麼時候會用到

「可以先查證的動作」指的是只讀取、不改變網路元件（Network Element, NE）狀態、不影響使用者服務的動作：查告警、查效能指標（KPI）、讀組態並和規劃值比對、看日誌與變更紀錄、調閱既有的量測檔。維運人員接到告警或客訴、還沒確定根因之前，第一步都應該是這一類動作；它們沒有服務風險，做錯了也不會讓障礙擴大，所以不需要等批准就能先做。3GPP 在 TS 32.111-1 clause 4.4 中以「may consist of many different steps such as」說明告警處理流程，列出的順序為：Recognizing the alarm → Acknowledging the alarm → Verifying that the alarm is valid and not a malfunction → Getting enhanced information → Analysing the situation … decide upon actions → Taking actions → Continuing the surveillance（TS 32.111-1 V18.0.0 clause 4.4）。本節說明有哪些讀取操作、各自能回答什麼問題，以及「讀」和「寫」的界線在哪裡。

#### 怎麼做／怎麼判斷

在 3GPP 的服務化管理架構裡，讀取管理資料主要靠下面幾種操作或通知（名稱照原文；[TS 28.532 規格檔](https://www.3gpp.org/ftp/Specs/archive/28_series/28.532/28532-i80.zip)、[TS 28.111 規格檔](https://www.3gpp.org/ftp/Specs/archive/28_series/28.111/28111-i80.zip)）：

| 要查什麼 | 用什麼 | 依據 |
|---|---|---|
| 物件的屬性（組態、狀態） | `getMOIAttributes`：向 MnS producer 讀取受管物件（managed object）的屬性名稱與值，可用 `scope`／`filter` 或 `dataNodeSelector` 指定範圍，`attributeListIn` 指定要回傳哪些屬性 | TS 28.532 V18.8.0 clause 11.1.1.2 |
| 同上，REST 版本 | `getMOIAttributes` 對應 HTTP GET `{MnSRoot}/ProvMnS/{MnSVersion}/…/{className}={id}` | TS 28.532 V18.8.0 table 12.1.1.1.1-1、clause 12.1.1.1.3 |
| 目前的告警 | 告警存在 `AlarmList` 的 `alarmRecords` 裡，消費端用 `getMOIAttributes` 讀取，可只取某嚴重度或某個 ManagedElement 的告警 | TS 28.111 V18.8.0 clause 6.5、6.6、7.3.2 |
| 新告警、清除、變化 | 訂閱 `notifyNewAlarm`、`notifyClearedAlarm`、`notifyChangedAlarmGeneral` 等通知 | TS 28.111 V18.8.0 clause 8.2～8.4 |
| 效能量測檔 | `listAvailableFiles`：以 `fileDataType`（例如 `PERFORMANCE`、`TRACE`）和 `beginTime`／`endTime` 列出可上傳的檔案 | TS 28.532 V18.8.0 clause 11.6.1.5 |
| 門檻跨越 | `notifyThresholdCrossing`：`ThresholdMonitor` 偵測到效能指標跨越門檻時送出 | TS 28.532 V18.8.0 clause 11.3.1.3 |

建議的查證順序（一般實務，不是規格要求）：

1. **讀告警**：先看 `AlarmList`，記下 `objectInstance`、`alarmType`、`probableCause`、`specificProblem`、`perceivedSeverity`、`alarmRaisedTime`（TS 28.111 clause 7.3.1）。同一個故障可能讓多個資源各出現狀態變化，但 NE 原則上對每個故障只發一個告警（TS 32.111-1 clause 4.1.2，原文用 should）。
2. **讀狀態**：用 `getMOIAttributes` 讀 `operationalState`（ENABLED／DISABLED，唯讀，由物件或 producer 設定）和 `administrativeState`（TS 28.622 V18.14.0 clause 4.4.1）；小區另有 `cellState`（IDLE、INACTIVE、ACTIVE，TS 28.541 V18.15.0 clause 4.4.1）。
3. **讀 KPI**：調閱障礙前後的量測檔，對照正常時段。
4. **比對組態**：把讀回來的屬性值和規劃值、上次備份比較，並查變更紀錄裡最近有沒有人動過。
5. **看日誌**：NE 與管理系統的日誌、告警歷史，排成時間軸（見 5.5.1）。

每一步都要把查到的值、查詢時間和查詢範圍記下來，之後寫工單和交接單才有依據；查不到或沒查的項目也要寫明，避免下一班誤以為已經查過。如果讀回的資料彼此矛盾（例如告警說故障，狀態卻是正常），先懷疑資料的時間點或告警清單本身是否可靠，再往下推。

判斷一個動作算不算「先查證」，看它會不會改變任何受管物件的值：GET、讀檔、收通知屬於讀；`createMOI`、`modifyMOIAttributes`、`deleteMOI`（TS 28.532 clause 11.1.1.1、11.1.1.3、11.1.1.4）屬於寫。

#### 實際例子

甲電信（虛構）監控中心 02:14 收到客服回報某區上網很慢，值班人員先做讀取查證（告警欄位依 [TS 28.111 clause 7.3.1](https://www.3gpp.org/ftp/Specs/archive/28_series/28.111/28111-i80.zip)，REST 讀取格式依 [TS 28.532 clause 12.1.1.1.3](https://www.3gpp.org/ftp/Specs/archive/28_series/28.532/28532-i80.zip)；`{MnSRoot}`、`{MnSVersion}` 保留原文的佔位寫法）：

```
# 1) 讀 AlarmList（getMOIAttributes，只取 ManagedElement=gNB-TPE-0417 的告警）
alarmId=A-88213  objectInstance=SubNetwork=TW-N,ManagedElement=gNB-TPE-0417,
                 GNBDUFunction=1,NRCellDU=3
  alarmType=EQUIPMENT_ALARM  probableCause=(略)
  perceivedSeverity=MAJOR    alarmRaisedTime=2026-11-25T01:58:42+08:00
  ackState=UNACKNOWLEDGED

# 2) GET {MnSRoot}/ProvMnS/{MnSVersion}/SubNetwork=TW-N/ManagedElement=gNB-TPE-0417/
#        GNBDUFunction=1/NRCellDU=3?scopeType=BASE_ONLY
#        &attributes=administrativeState,operationalState,cellState
administrativeState=UNLOCKED  operationalState=ENABLED  cellState=ACTIVE

# 3) 量測檔（listAvailableFiles, fileDataType=PERFORMANCE）
時段          下行平均吞吐(Mbps)  RRC 連線建立成功率
01:30-01:45   142.6               99.1%
02:00-02:15    38.9               98.8%
```

逐步判斷：

1. 告警時間 01:58 早於客訴 02:14，然而因缺少 01:45-02:00 時段的量測資料，僅能說劣化在 01:45～02:15 之間開始。
2. 小區 `operationalState=ENABLED`、`cellState=ACTIVE`，表示小區沒有停止服務；吞吐下降約 (142.6－38.9)÷142.6≈72.7%，但連線成功率幾乎不變，比較像「能連上但慢」。
3. 告警類型是 `EQUIPMENT_ALARM`、嚴重度 `MAJOR`，可以提出「某個硬體元件劣化」的假設，交給 6.2 推理。

不能下的結論：還沒讀射頻單元的狀態與告警詳細欄位，也沒比對組態變更紀錄，所以**不能**說是哪一塊板卡壞掉，更不能直接決定重啟或鎖定——那些屬於 6.3.2 要批准的處置。

#### 容易搞混的地方

- **確認告警、清除告警不是純讀取**：設定 `ackState`、把 ADMC 告警的 `perceivedSeverity` 設為 cleared，都是寫入告警記錄（TS 28.111 V18.8.0 clause 6.7、6.8，[規格檔](https://www.3gpp.org/ftp/Specs/archive/28_series/28.111/28111-i80.zip)）。它們不影響使用者服務，但會改變告警清單，業者通常有自己的權限規定。
- **啟動追蹤或量測工作也是寫入**：新建量測或追蹤工作要建立物件（`createMOI`），不是 `getMOIAttributes`；是否要登記，看業者規定。
- **測試分兩種**：不侵入的測試可以先做；侵入式（intrusive）測試可以使用 `administrativeState` 把資源移出服務來執行（TS 32.111-1 clause 4.2.0、4.3），那就屬於 6.3.2。
- **`operationalState=ENABLED` 不等於一切正常**：資源沒有完全失去服務能力時，原文規定 operational state 仍是 enabled，另以 availability status 標 degraded（TS 32.111-1 clause 4.2.0）。

#### 和其他小節的關係

本節產出的告警、狀態、KPI 是 5.1～5.5 判讀的對象，排進時間軸用 5.5.1，寫結論時區分事實與推測用 5.5.3；查證結果再交給 6.2 提出與檢驗假設。查證完才輪到 6.3.2 需要批准的處置，過程與結果要記進 6.4.3 的工單與 6.5.1 的交接單（[TS 28.532 規格檔](https://www.3gpp.org/ftp/Specs/archive/28_series/28.532/28532-i80.zip)）。

**002.** Which attributes of an alarm record are the "alarm identifying attributes", that is, the attributes whose equal values make two alarms the same alarm?

<details><summary>看答案</summary>

**答案**　objectInstance, alarmType, probableCause and specificProblem.

**詳解**　TS 28.111 states that alarms with the same values for object instance, alarm type, probable cause and specific problem are the same alarm; the alarmId is a shortcut for these four attributes. Severity and times are not identifying attributes.

**出處**　3GPP TS 28.111 V18.8.0 clause 6.4 (https://www.3gpp.org/ftp/Specs/archive/28_series/28.111/)

</details>

**004.** According to TS 28.111, which operation does an MnS consumer use to retrieve the alarm records of an AlarmList?

1. listAvailableFiles with fileDataType set to the alarm list
2. getMOIAttributes, defined in TS 28.532 clause 11.1.1.2
3. notifyNewAlarm, sent on request of the consumer
4. modifyMOIAttributes with an empty modificationList

<details><summary>看答案</summary>

**答案**　2

**詳解**　TS 28.111 says a consumer retrieves alarm records with getMOIAttributes (TS 28.532 clause 11.1.1.2), ideally with conditional selection such as severity or managed element. Option 1 is wrong: listAvailableFiles lists files of type PERFORMANCE, TRACE, ANALYTICS or PROPRIETARY. Option 3 is wrong: notifyNewAlarm is a notification sent by the producer when a new record is added, not a retrieval operation. Option 4 is wrong: modifyMOIAttributes is a write operation.

**出處**　3GPP TS 28.111 V18.8.0 clause 6.6 (https://www.3gpp.org/ftp/Specs/archive/28_series/28.111/); 3GPP TS 28.532 V18.8.0 clause 11.1.1.2 and clause 11.6.1.5 (https://www.3gpp.org/ftp/Specs/archive/28_series/28.532/)

</details>

**005.** The day engineer asks whether the cabinet High Temperature alarm also occurred earlier in the night, before 01:12:08. Can this be answered from the snapshot?

<details><summary>看答案</summary>

**答案**　Cannot be determined: the AlarmList holds only the current (active) alarm records, not historical ones; the alarm history (NE alarm history or the notifications received during the night) is needed.

**詳解**　TS 28.111 states that historical alarm records are not stored in an alarm list, and the same alarm identity can have only one record at a time. An earlier occurrence that was cleared and removed would leave no trace in this read. TS 32.111-1 requires the NE to keep alarm history information separately.

**出處**　3GPP TS 28.111 V18.8.0 clause 6.5 (https://www.3gpp.org/ftp/Specs/archive/28_series/28.111/); 3GPP TS 32.111-1 V18.0.0 clause 4.1.5 (https://www.3gpp.org/ftp/Specs/archive/32_series/32.111-1/)

</details>

**012.** An existing alarm record changes its perceivedSeverity from MAJOR to CRITICAL. Which notification reports this?

1. notifyChangedAlarmGeneral
2. notifyNewAlarm, because the severity has increased
3. notifyMOIAttributeValueChanges
4. notifyClearedAlarm with the new severity

<details><summary>看答案</summary>

**答案**　1

**詳解**　notifyChangedAlarmGeneral is sent when perceivedSeverity changes to any value except CLEARED (and for several other attributes). Option 2 is wrong: notifyNewAlarm is sent only when a new record is added. Option 3 is wrong: the general-purpose attribute value change notification is not used for alarm records. Option 4 is wrong: notifyClearedAlarm is only for a change to CLEARED.

**出處**　3GPP TS 28.111 V18.8.0 clause 6.12 and clause 8.4.1 (https://www.3gpp.org/ftp/Specs/archive/28_series/28.111/)

</details>

**013.** No notification announces the removal of an alarm record. When acknowledgement is supported, how can a consumer deduce that a record was removed?

<details><summary>看答案</summary>

**答案**　From receiving, for the same alarm, both a notification reporting its clearance (notifyClearedAlarm) and one reporting its acknowledgement (notifyAckStateChanged with ACKNOWLEDGED), in either order.

**詳解**　TS 28.111 states that removal is notified only indirectly; with acknowledgement supported, the consecutive reception of the clearance and acknowledgement notifications for the same alarm means the record was removed, and the order is not relevant.

**出處**　3GPP TS 28.111 V18.8.0 clause 6.12 (https://www.3gpp.org/ftp/Specs/archive/28_series/28.111/)

</details>

**014.** Has the power problem behind C-301 taken NRCellDU=1 out of service?

<details><summary>看答案</summary>

**答案**　Cannot be determined: the notifications report only alarms; a read of NRCellDU=1 operationalState and cellState (and its KPIs) is needed.

**詳解**　C-301 is raised on NRSectorCarrier=1 and C-302 reports degraded performance on NRCellDU=1, but neither says whether the cell is disabled. A fault can degrade a resource without making it inoperable, so the state must be read.

**出處**　3GPP TS 28.622 V18.14.0 clause 4.4.1 (https://www.3gpp.org/ftp/Specs/archive/28_series/28.622/); 3GPP TS 32.111-1 V18.0.0 clause 4.2.0 (https://www.3gpp.org/ftp/Specs/archive/32_series/32.111-1/)

**016.** Which entries in the trail are operations by noc-op03 that wrote to alarm records?

1. Only 02:31:15, because clearing is the only write on an alarm record
2. 02:06:44, 02:07:02 and 02:31:15
3. 02:05:10, 02:06:44 and 02:20:30
4. None of them, because operator actions on alarms never change the alarm list

<details><summary>看答案</summary>

**答案**　2

**詳解**　Setting ackState, adding a comment and setting perceivedSeverity to CLEARED are all writes by the consumer on alarm records; the two getMOIAttributes calls only read, and the 02:31:16 and 02:33:40 entries are notifications sent by the system, not operator operations. Option 1 forgets acknowledgement and commenting. Option 3 includes the two reads. Option 4 is wrong: TS 28.111 explicitly lets consumers set ackState, clear ADMC alarms and add comments.

**018.** What is an ADMC alarm, and how does it reach perceivedSeverity CLEARED?

<details><summary>看答案</summary>

**答案**　An automatically detected, manually cleared alarm: the system does not clear it, so an MnS consumer must set the perceivedSeverity of the alarm record to CLEARED.

**詳解**　TS 28.111 distinguishes ADAC alarms (cleared by the system when the condition disappears) from ADMC alarms, which consumers need to clear manually by setting perceivedSeverity to cleared.

**出處**　3GPP TS 28.111 V18.8.0 clause 6.8 (https://www.3gpp.org/ftp/Specs/archive/28_series/28.111/)

</details>

**020.** Did the 02:20:30 read show NRCellDU=1 in service?

<details><summary>看答案</summary>

**答案**　Cannot be determined: the trail records that the read happened but not the returned operationalState and cellState values; the stored response (or a new read) is needed.

**詳解**　The trail notes that response values of the getMOIAttributes calls are not stored. Knowing that a check was made is not the same as knowing its result, which is why the textbook asks that queried values, time and scope be recorded.

**078.** Who sets operationalState, and can an MnS consumer write it?

<details><summary>看答案</summary>

**答案**　It is set by the object instance itself or by the MnS producer and is read-only for the consumer.

**詳解**　TS 28.622 describes operationalState (ENABLED/DISABLED) as set by the object instance or the MnS producer and hence READ-ONLY, whereas administrativeState is set by the MnS consumer.

**出處**　3GPP TS 28.622 V18.14.0 clause 4.4.1 (https://www.3gpp.org/ftp/Specs/archive/28_series/28.622/)

**080.** Why does administrativeState = UNLOCKED on NRCellDU=2 matter for the diagnosis?

<details><summary>看答案</summary>

**答案**　It shows that NRCellDU=2 itself has not been locked, so its DISABLED state is not the result of a lock on the cell; it reports a real loss of capability, caused by a fault or by a resource the cell depends on being out of service (disabled or locked).

**詳解**　When an operator locks a resource, its own administrativeState changes, not its operationalState; dependent resources, however, can become disabled. Here the cell is UNLOCKED but DISABLED, so the producer reports that it cannot provide service, and the next step is to find the faulty or out-of-service resource.
