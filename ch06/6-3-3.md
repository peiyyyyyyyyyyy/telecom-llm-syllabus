# 6.3.3 對照過去案例

所屬：[6.3 處置](6-3.md)

## 內文

#### 是什麼、什麼時候會用到

對照過去案例，是拿眼前的障礙去比對業者過去處理過、已有紀錄的案例，借用當時的假設、查證方法與處置經驗。它最常用在兩個時候：一是剛接手一個障礙、還不知道從哪裡查起，想知道「以前有沒有類似的」；二是已經想到處置方式，想確認過去用同樣方式處理的結果。前提是過去的案例有被好好記下來。Google SRE Book 第 15 章〈Postmortem Culture: Learning from Failure〉說明，事後檢討報告完成後會加入團隊或組織的過去事件資料庫，方便他人查找與學習（[Google SRE Book, Postmortem Culture](https://sre.google/sre-book/postmortem-culture/)）。以下是本教材整理的做法，不是 3GPP 規格的規定。

#### 怎麼做／怎麼判斷

1. **先把眼前障礙的特徵寫清楚**，再去搜尋案例，不要拿模糊的印象去比。常用的比對特徵：
   - 症狀：哪個量測、哪個子計數器變化、變化幅度；
   - 範圍：幾個小區、是否同站、同傳輸路徑、同設備型號或軟體版本；
   - 時間型態：突發或漸進、固定時段、是否與流量同步；
   - 同時事件：告警、變更紀錄、天候或大型活動。
2. **逐項列出相同點與相異點。** 相異點比相同點更重要：只要一個關鍵特徵不同（例如過去案例有傳輸告警、這次沒有），就不能直接套用過去的根因。
3. **把過去的根因當成「待檢驗的假設」**，放進 6.2.2 的證據表，用這次的資料去找支持證據與反證，而不是當作結論。
4. **借用查證方法，比借用結論更安全。** 過去案例「怎麼確認根因」（看了哪些資料、做了什麼測試）通常可以直接重用。
5. **注意案例紀錄的確定程度。** 紀錄裡寫「推測」的根因，參考價值低於寫「已確認」並附依據的根因。
6. **處理完要回寫案例庫**，至少包含：案例編號與日期、症狀（量測名稱與數值）、範圍、時間軸摘要、當時的告警與變更、提出過的假設及被排除的理由、根因與確定程度、確認依據、處置與驗證結果、是否復發、關聯工單。SRE Book 對事後檢討報告的描述是：記錄事件、其影響、為減緩或解決所採取的行動、根因，以及防止再發的後續行動（[Postmortem Culture](https://sre.google/sre-book/postmortem-culture/)）。

#### 實際例子

Telco-X（虛構）2026-11-24 09:00 起，兩個相鄰站下的 6 個小區 RRC 建立失敗增加。量測依 [TS 28.552](https://www.3gpp.org/ftp/Specs/archive/28_series/28.552/) V18.12.0 clause 5.1.1.15.1～5.1.1.15.3：6 小區合計 08:45–09:00 RRC.ConnEstabAtt 5,400、RRC.ConnEstabSucc 5,346（99.00%）；09:00–09:15 為 5,520 與 4,968（90.00%），失敗 552 次中 RRC.ConnEstabFailCause.NoReply 占 520 次（94.20%），NetworkReject 0 次、Other 32 次。值班人員在案例庫找到兩筆（皆虛構）：

| 特徵 | 本次 N | 案例 KB-2025-041 | 案例 KB-2026-007 |
|---|---|---|---|
| 症狀 | NoReply 為主 | NoReply 為主 | NoReply 為主 |
| 範圍 | 2 個相鄰站、6 小區 | 同一傳輸匯聚下 6 小區 | 3 個相鄰站、4 小區 |
| 開始方式 | 突發 | 突發 | 突發 |
| 同時告警 | 無 | 傳輸埠告警 | 無 |
| 同時變更 | 無 | 前一晚傳輸設定變更 | 無 |
| 紀錄的根因 | — | 傳輸設定錯誤（已確認：回復設定後恢復） | 外部上行干擾（已確認：頻譜掃描找到干擾源） |

逐步判斷：

1. 三筆的症狀都是 NoReply 為主。依原文，NoReply 是 gNB 送出 RRCSetup 後沒收到預期的 RRCSetupComplete（clause 5.1.1.15.3），很多原因都可能造成，所以「症狀相同」的區辨力很低。
2. KB-2025-041 雖然小區數、開始方式都一樣，但它有傳輸告警和前一晚的變更，本次都沒有，關鍵特徵不同，不能直接套用。
3. KB-2026-007 在「無告警、無變更、相鄰站」上更接近，因此把「外部上行干擾」列為假設，並借用它的查證方法：先看上行干擾相關量測，再決定是否安排頻譜掃描。
4. 同時保留「傳輸問題」假設，查這兩個站是否共用傳輸路徑。
5. 不能下的結論：目前只能說本次「像」KB-2026-007，在查到干擾的直接證據前，不能把它寫成根因。

#### 容易搞混的地方

- **相似不代表同因。** SRE Book 第 12 章把「抓住過去問題的原因，認為發生過一次就一定又發生」列為常見陷阱（[Google SRE Book, Effective Troubleshooting](https://sre.google/sre-book/effective-troubleshooting/)）。
- **相同點多不等於比較像。** 相同點若都是區辨力低的症狀，數量再多也沒用；一個關鍵相異點就足以排除套用。
- **案例庫只記「怎麼修好」不夠。** 沒有記下排除過的假設和確認依據，下次就無法判斷這個案例可不可信。
- **把推測寫成已確認。** 回寫時要標明根因的確定程度，否則會誤導後來的人。

#### 和其他小節的關係

從案例借來的根因要回到 6.2.2 列證據、必要時依 6.2.3 補收資料、用 6.2.4 分辨；借來的處置若會影響服務，屬 6.3.2，要工程師批准。案例內容的來源是 6.5.2 障礙報告，事實與推測的區分見 5.5.3。NIST SP 800-61 Rev. 3 也強調從事件經驗中找出改進（[NIST SP 800-61 Rev. 3](https://csrc.nist.gov/pubs/sp/800/61/r3/final)）。

**出處**　Google SRE Book, Chapter 15 "Postmortem Culture: Learning from Failure"（https://sre.google/sre-book/postmortem-culture/ ）；Google SRE Book, Chapter 12 "Effective Troubleshooting"（https://sre.google/sre-book/effective-troubleshooting/ ）；NIST SP 800-61 Rev. 3, Incident Response Recommendations and Considerations for Cybersecurity Risk Management: A CSF 2.0 Community Profile（https://csrc.nist.gov/pubs/sp/800/61/r3/final ）；3GPP TS 28.552 V18.12.0 clause 5.1.1.15.1、5.1.1.15.2、5.1.1.15.3（https://www.3gpp.org/ftp/Specs/archive/28_series/28.552/ ）

#### Writing the incident's feature profile before searching the case base

**情境 001**　A vague ticket note and the data behind it

The reporter wants to search the case base with the text "TN-0218". The on-call engineer pulls the data below first (NorthLink Mobile, fictional).

```

Reporter note: "TN-0218 is bad again, looks like the March problem. Search KB for TN-0218."

KPI excerpt, 15-min ROP, NRCellCU, sum of cells TN-0218-1/-2/-3
ROP          ConnEstabAtt  ConnEstabSucc  FailCause.NoReply  FailCause.NetworkReject  FailCause.Other
06:45-07:00  2,100         2,079          15                 0                        6
07:00-07:15  2,880         2,592          21                 260                      7
07:15-07:30  3,420         3,078          18                 318                      6
07:30-07:45  3,960         3,564          24                 366                      6
(ConnEstab* = RRC.ConnEstabAtt / RRC.ConnEstabSucc; FailCause.* = RRC.ConnEstabFailCause.*)

Neighbour site TN-0219 (2 cells): RRC setup success 99.1%-99.3% in all four ROPs
Active alarms on TN-0218 at 07:40: none
Change log TN-0218, last 7 days: none
Software version TN-0218: GNB 24.2.1 (unchanged since 2026-10-02)
```

**001.** Which feature profile should the engineer use to search the case base?

1. Setup success fell from 99% to 90% at 07:00 on TN-0218's three cells; NetworkReject dominated, with no alarms or changes.
2. The previous March incident explains all three TN-0218 cells, so link to its case and use the same symptom, scope and timing details.
3. Symptom: RRC.ConnEstabFailCause.NoReply-dominant failures on TN-0218 and TN-0219; time: step at 07:00; concurrent events: none.
4. Symptom: RRC setup success falling to 90.0%; time: gradual degradation since 06:45; concurrent events: recent software upgrade.

<details><summary>看答案</summary>

**答案**　1

**詳解**　Option 1 lists all four feature groups with values taken from the data: success 2,079/2,100 = 99.0% before and 3,564/3,960 = 90.0% after; NetworkReject is 260–366 per ROP while NoReply stays at 18–24; TN-0219 stays at 99.1–99.3%; failures grow from 288 to 396 as attempts grow from 2,880 to 3,960. Option 2 is the reporter's impression and a site label, not features. Option 3 names the wrong sub-counter and the wrong scope (TN-0219 is normal). Option 4 calls a step change "gradual" and invents a software upgrade (the version is unchanged since 2026-10-02).

**出處**　Curriculum 6.3.3 (step 1: write the features first; symptom, scope, time pattern, concurrent events); 3GPP TS 28.552 V18.12.0 clauses 5.1.1.15.1–5.1.1.15.3 (https://www.3gpp.org/ftp/Specs/archive/28_series/28.552/)

</details>

**002.** Why should the incident's features be written down before the case base is searched, instead of searching with the reporter's impression or the site name?

<details><summary>看答案</summary>

**答案**　Because a case can only be compared item by item (matches and mismatches) when the current incident is described by explicit features — symptom measurement and magnitude, scope, time pattern, concurrent events — whereas an impression or site name retrieves cases by label and cannot be checked feature by feature.

**詳解**　Curriculum 6.3.3 says not to compare from a vague impression. A search by site name returns everything that ever happened on that site, whatever the cause; a feature profile gives the criteria against which each retrieved case is later judged.

**出處**　Curriculum 6.3.3 (step 1)

</details>

**003.** In the 07:30–07:45 ROP, what share of the failed RRC connection establishments is counted under RRC.ConnEstabFailCause.NetworkReject?

1. 9.2%
2. 90.0%
3. 92.4%
4. 6.1%

<details><summary>看答案</summary>

**答案**　3

**詳解**　Failures = 3,960 − 3,564 = 396 (check: 24 + 366 + 6 = 396). NetworkReject share = 366 / 396 = 0.9242 → 92.4%. 9.2% divides by attempts (366 / 3,960); 90.0% is the success rate (3,564 / 3,960); 6.1% is the NoReply share (24 / 396).

**出處**　3GPP TS 28.552 V18.12.0 clause 5.1.1.15.3 (NetworkReject = RRCReject transmitted; NoReply = expected RRCSetupComplete not received) (https://www.3gpp.org/ftp/Specs/archive/28_series/28.552/)

</details>

**004.** In the feature groups used in this curriculum for case comparison, which items belong to "concurrent events"?

2. Alarms, change records, weather and large public events at the same time
3. The number of cells, whether they share a site, a transport path, an equipment model or a software version
4. Whether the onset is sudden or gradual, tied to a fixed hour or synchronised with traffic

<details><summary>看答案</summary>

**答案**　2

**詳解**　Curriculum 6.3.3 lists four groups: symptom (option 1), scope (option 3), time pattern (option 4) and concurrent events — alarms, changes, weather or large events (option 2).

</details>
