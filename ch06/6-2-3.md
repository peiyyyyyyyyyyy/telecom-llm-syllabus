# 6.2.3 還缺什麼資料、怎麼補收（追蹤、MDT、測試）

所屬：[6.2 推理](6-2.md)

## 內文

#### 是什麼、什麼時候會用到

6.2.2 的證據表裡常有一欄「尚缺」：現有的告警與 KPI 是以小區、以收集週期為單位的統計，回答不了「是哪支手機、在哪個位置、在哪一則信令失敗」。這時要補收資料，常用的有四種：補抓更細的 KPI、信令追蹤（trace）、MDT（Minimization of Drive-Tests）、主動測試。典型情境是企業客戶抱怨某棟大樓某樓層斷話，但小區 KPI 一切正常。TS 32.421 的引言說明了追蹤的定位：「Contrary to Performance measurements, which are a permanent source of information, trace is activated on user demand for a limited period of time for specific analysis purposes.」（[TS 32.421](https://www.3gpp.org/ftp/Specs/archive/32_series/32.421/) V18.4.0 Introduction）也就是說，追蹤要先想清楚問題、限定範圍和時間再開。

#### 怎麼做／怎麼判斷

1. **先把缺的資料寫成問題**（例：斷線前 UE 量到哪些鄰區），再選能回答的資料。
2. **從影響最小的開始**：先補抓既有量測細項，不夠再開追蹤或 MDT，最後才派人測試。
3. **限定範圍與期間**：只追需要的對象、介面與時段。追蹤與 MDT 的啟動屬於網管組態作業，要照業者內部申請流程（虛構規定）辦理。

| 資料 | 能回答的問題 | 原文要點與條號 |
|---|---|---|
| 補抓 KPI | 哪個小區、哪個環節、哪個鄰區關係在變差 | RRC 建立失敗依原因分成 RRC.ConnEstabFailCause.NetworkReject／NoReply／Other（TS 28.552 V18.12.0 clause 5.1.1.15.3）；跨 gNB 換手執行失敗分 MM.HoExeInterFail.* 子計數器，量測物件為 NRCellCU;NRCellRelation（clause 5.1.1.6.1.9） |
| 信令追蹤 | 某個 UE 或某些小區在哪一則信令、哪個程序失敗 | 見下方 |
| Immediate MDT | 連線態 UE 量到的服務／鄰區信號、功率餘量、速率、延遲、掉包 | 見下方 |
| Logged MDT | 閒置／非活動態時 UE 所在處的信號強度與品質 | 見下方 |
| 主動測試 | 問題能否在可控的終端上重現 | 實務做法（步測、路測、撥測），非本節所引規格的內容 |

**信令追蹤**（[TS 32.422](https://www.3gpp.org/ftp/Specs/archive/32_series/32.422/) V18.7.0）：
- management based activation：管理系統直接把追蹤參數設定給網元，網元不再往其他網元傳（clause 4.1.1.1.2）；在 NG-RAN 是以 cell traffic trace 對一個或一串小區啟動（clause 4.1.1.9.1）。適合「這幾個小區」的問題。
- signalling based activation：在 5GS 設定在 UDM、AMF、SMF 等 5GC 網元，再依參數傳到 RAN 與核心網的選定網元（clause 4.1.2.1.2）。適合「這個用戶」的問題。
- Trace Target 的 ID 類型包含 IMSI、IMEI、IMEISV、SUPI、NG-RAN cell、gNB 等（clause 5.12）。
- Trace Depth 分 Minimum、Medium、Maximum，以及三個 WithoutVendorSpecificExtension 版本；Medium 比 Minimum 多記錄無線量測 IE，Maximum 記錄完整信令（encoded），同一個 Trace Session 內所有網元深度相同（clause 5.3）。
- gNB-CU-CP 可追的介面為 NG-C、Xn-C、Uu、F1-C、E1、X2-C（clause 5.5）；Job Type 列舉含 TRACE_ONLY、IMMEDIATE_MDT_ONLY、LOGGED_MDT_ONLY、IMMEDIATE_MDT_AND_TRACE、RLF_REPORT_ONLY 等（clause 5.9a）。

**MDT**（[TS 37.320](https://www.3gpp.org/ftp/Specs/archive/37_series/37.320/) V18.5.0）：
- Immediate MDT 是 UE 在連線態量測、符合回報條件時回報給 RAN，加上網路側為 MDT 做的量測（clause 3.1）。NR 可支援 M1 下行信號量（服務與鄰區，含 cell／beam 層級）、M2 功率餘量、M4 PDCP SDU 資料量、M5 平均 UE 速率、M6 封包延遲、M7 封包遺失率、M8 RSSI、M9 RTT（clause 5.4.1.1）。
- Logged MDT 是 UE 在閒置或非活動態記錄、之後才回報（clause 3.1）；NR 記錄 RSRP 與 RSRQ（clause 5.1.1.2），由網路以 UE Information 程序取回（clause 5.1.1.3.2）。
- 不針對特定 UE 時用 management based；針對特定 UE 時用 signalling based（clause 4.1、5.1.3）。signalling based 須經允許，核心網才可對該用戶啟動（clause 5.1.3）。

#### 實際例子

```
資料補收申請（Telco-X 虛構範本）
工單：TT-1120-118（虛構）  客戶：A 公司（虛構）
現象：大樓 12F 通話中斷；涵蓋 12F 的 3 個小區 KPI 無明顯異常
Q1 斷線時 UE 在哪一則信令失敗？
   signalling based activation；Trace Target：SUPI（客戶同意的 3 支測試門號）
   Job Type：IMMEDIATE_MDT_AND_TRACE；Trace Depth：Medium
   List of Interfaces：NG-C、Xn-C、Uu、F1-C；期間 72 小時（虛構規定上限）
Q2 12F 室內服務小區與鄰區信號？
   Immediate MDT M1；Reporting Trigger：Periodical
   Report Interval：5120 ms；Report Amount：INFINITY
Q3 閒置時 12F 是否落在弱涵蓋？
   management based Logged MDT；Area Scope：3 個 NG-RAN CGI
   Logging Interval：5120 ms；Logging Duration：7200 sec
Q4 失敗集中在哪個鄰區關係？
   補抓 MM.HoExeInterFail.* 與 RRC.ConnEstabFailCause.*
Q5 能否重現？  3 支測試機實地步測 12F
```

逐步說明：

1. 參數值都對過原文：Report Interval 5120 ms、Report Amount INFINITY（[TS 32.422](https://www.3gpp.org/ftp/Specs/archive/32_series/32.422/) clause 5.10.5、5.10.6.8）；Logging Interval 5120 ms、Logging Duration 7200 sec（clause 5.10.8、5.10.9）；Area Scope 以 CGI 列舉，最多 32 個（clause 5.10.2）。
2. Q1 針對特定用戶，所以用 signalling based；選 Medium 是因為要看信令中的無線量測 IE，若要完整訊息才改 Maximum。
3. Q3 不指定用戶，由 RAN 在區域內選 UE，只能看到被選中、且允許參與的 UE；UE 若記錄期滿未被取回，「should」保存 48 小時（TS 37.320 clause 5.1.1.3.1），要及時取回。
4. 不能下的結論：資料回來前不判斷根因；3 支測試機的結果不代表所有用戶；MDT 的詳細位置只有在 UE 有提供時才有（clause 5.1.2.2），沒有時只能靠服務小區與 RF fingerprint 推估。

#### 容易搞混的地方

- **management based MDT 不等於不必考慮用戶同意。** 兩種方式差在啟動路徑；management based 時，核心網會依用戶同意、漫遊狀態等告知 RAN 該用戶是否允許，只有不受用戶同意限制的量測例外（[TS 37.320](https://www.3gpp.org/ftp/Specs/archive/37_series/37.320/) clause 5.1.3）。
- **Trace Depth 越深不一定越好。** Maximum 資料量大且是 encoded 格式，要另外解碼；問題只需要部分 IE 時，Minimum 或 Medium 就夠。
- **Immediate MDT 與 Logged MDT 看的是不同狀態**：前者是連線中，後者是閒置／非活動態；斷話問題主要看前者與 RLF report（clause 5.4.1.2）。
- **補抓 KPI 仍是統計值**，能縮小範圍，但無法指出哪支 UE。

#### 和其他小節的關係

本節的問題清單來自 6.2.2 證據表的「尚缺」欄；收回的資料再交給 6.2.4 分辨假設。只讀的查證動作見 6.3.1；追蹤或 MDT 的啟動屬組態作業，依第 9 章異動流程。KPI 與追蹤資料的判讀方法見第 5 章 5.1～5.5。TS 32.421 Annex A 把「用戶申訴」列為追蹤的使用情境之一（[TS 32.421](https://www.3gpp.org/ftp/Specs/archive/32_series/32.421/) Annex A.2）。

**情境 001**　RRC setup failures split by cause

NorthLink Mobile (fictional) sees the RRC setup success ratio of cell KH-0412-2 dip in the late morning. The NOC pulled the failure sub-counters for four hourly granularity periods.

| Period start | RRC.ConnEstabAtt (sum of causes) | RRC.ConnEstabSucc (sum of causes) | RRC.ConnEstabFailCause.NetworkReject | RRC.ConnEstabFailCause.NoReply | RRC.ConnEstabFailCause.Other |
|---|---|---|---|---|---|
| 09:00 | 4210 | 4168 | 2 | 35 | 5 |
| 10:00 | 4630 | 4402 | 3 | 219 | 6 |
| 11:00 | 4580 | 4321 | 4 | 247 | 8 |
| 12:00 | 4395 | 4344 | 2 | 41 | 8 |
| Object | NRCellCU KH-0412-2 | | | | |

**001.** Which statement correctly reads the 10:00 and 11:00 rise in failures?

1. The gNB is rejecting more setups: RRC.ConnEstabFailCause.NetworkReject explains most of the rise.
2. Most added failures are cases where the gNB sent RRCSetup but did not receive the expected RRCSetupComplete.
3. Most added failures are "Other" causes, so the cause is unknown and the counters are useless.
4. Most added failures are handover execution failures towards neighbouring cells.

<details><summary>看答案</summary>

**答案**　2

**詳解**　NoReply goes from 35 (09:00) to 219 and 247, while NetworkReject stays at 2–4 and Other at 5–8; NoReply counts each expected RRCSetupComplete not received after RRCSetup. Option 1 is wrong because NetworkReject (RRCReject transmitted) barely moves; option 3 is wrong because Other stays at 5–8; option 4 is wrong because these are RRC connection establishment counters on NRCellCU, not handover counters.

**出處**　3GPP TS 28.552 V18.12.0 clause 5.1.1.15.3 (https://www.3gpp.org/ftp/Specs/archive/28_series/28.552/)

</details>

**002.** According to TS 28.552, which event is added to the sub-counter RRC.ConnEstabFailCause.NetworkReject?

<details><summary>看答案</summary>

**答案**　Each RRCReject message transmitted from the gNB to the UE.

**詳解**　Clause 5.1.1.15.3 splits failed RRC establishments into NetworkReject (each RRCReject transmitted), NoReply (each expected RRCSetupComplete not received after RRCSetup) and Other (any other reason).

**出處**　3GPP TS 28.552 V18.12.0 clause 5.1.1.15.3 (https://www.3gpp.org/ftp/Specs/archive/28_series/28.552/)

**003.** For the 11:00 period, what is the RRC setup failure ratio (all failure sub-counters ÷ attempts), and what share of the failures is NoReply?

1. 5.99 % and 95.4 %
2. 5.39 % and 95.4 %
3. 5.66 % and 4.6 %
4. 5.66 % and 95.4 %

<details><summary>看答案</summary>

**詳解**　Failures = 4 + 247 + 8 = 259 (also 4580 − 4321 = 259). Failure ratio = 259 ÷ 4580 = 0.05655 → 5.66 %. NoReply share = 247 ÷ 259 = 0.9537 → 95.4 %. **004.** Which statement about these extra RRC failure counters is correct?

1. Per-cell counts locate failing setup steps, not individual UEs.
2. They are per-UE records, so the failing subscribers can be listed directly from them.
3. They are collected only when a trace session is active for the cell.

<details><summary>看答案</summary>

**情境 003**　Reviewing a request for extra counters

An engineer at Telco-X (fictional) filed a request to activate extra measurements for an enterprise drop complaint. You are the reviewer.

```
Collection request CR-0318 (fictional)        Site TP-2207 = one gNB (gNB-ID 2207)
Complaint: calls drop while walking the 12F corridor (enterprise customer B Corp, fictional)
Cells on 12F: TP-2207-1, TP-2207-2, TP-2207-3 (all on gNB 2207)
Neighbour gNB 2210: cell TP-2210-1 covers the stairwell
Proposed extra measurements (15-min granularity, 7 days):
 P1  RRC.ConnEstabFailCause.*                 TP-2207-1..3            "why calls drop mid-call"
 P2  MM.HoExeInterReq / MM.HoExeInterSucc     TP-2207-1 -> TP-2207-2  "corridor HO between 12F cells"
 P3  MM.HoExeIntraReq / MM.HoExeIntraSucc     TP-2207-1 -> TP-2207-3  "corridor HO between 12F cells"
 P4  MM.HoExeInterFail.*                      TP-2207-2 -> TP-2210-1  "HO to stairwell cell"
 P5  RRC.ConnEstabAtt.Cause                   TP-2207-1..3            "split attempts by establishment cause"
Reviewer rule (fictional operator rule): approve only items whose counter matches the stated question
```

**011.** Which proposed item uses a counter family that does not apply to the stated cell pair?

1. P3, because intra-gNB counters cannot be collected per relation.
2. P4, because the stairwell cell belongs to another gNB.
3. P5, because establishment causes are not counted per cell.
4. P2: same-gNB cells use intra-gNB, not inter-gNB, counters.

<details><summary>看答案</summary>

**答案**　4
