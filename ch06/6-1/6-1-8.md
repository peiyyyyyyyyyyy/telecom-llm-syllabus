# 6.1.8 傳輸中斷與核心網問題

所屬：[6.1 根因的類型](../6-1.md)

## 正文

In a mobile network, **transmission interruption** denotes a *communication failure* between two network entities (NEs) or between an NE and an operation support system (OSS) — the loss of a logical or physical link that prevents the exchange of signalling or user data [TS 32.111-1 §4.1.0]. When such a failure occurs in the **core network** (e.g., the Access and Mobility Management Function, AMF), the result is often a *functional fault*: the NE cannot perform its defined functions even though no hardware component is physically damaged [TS 32.111-1 §4.1.0]. Both conditions generate alarms that point to the affected physical or logical resources [TS 32.111-1 §4.1.0].

### Fault Categories Relevant to Transmission

The 3GPP fault model groups the relevant causes as follows:

| Category | Description |
|----------|-------------|
| **Hardware failures** | Malfunction of a physical resource within a NE [TS 32.111-1 §4.1.0] |
| **Software problems** | Bugs or database inconsistencies [TS 32.111-1 §4.1.0] |
| **Functional faults** | Failure of a functional resource with no identifiable hardware cause [TS 32.111-1 §4.1.0] |
| **Loss of capability due to overload** | Resources become unavailable because the NE is overloaded [TS 32.111-1 §4.1.0] |
| **Communication failures** | Loss of signalling or data paths between NEs, or between NE and OSS [TS 32.111-1 §4.1.0] |

Only **communication failures** directly correspond to *transmission interruption*, while the other categories may manifest as *core‑network problems* that indirectly cause the same symptom.

### NG Reset – Re‑initialising the NG Interface

When a failure in the core network (e.g., AMF) leads to the loss of *transaction reference information*—the identifiers that bind a UE’s context to the NG interface—a **NG Reset** procedure is triggered [TS 38.413 §8.7.4.1]. The reset uses *non‑UE‑associated signalling* and does **not** affect application‑level configuration data.

**Key steps (AMF‑initiated):**  

1. AMF sends an **NG RESET** message to the NG‑RAN node.  
2. NG‑RAN releases **all allocated NG and Uu resources** for the indicated UE associations and removes the associated UE contexts and NGAP IDs [TS 38.413 §8.7.4.2.1].  
3. NG‑RAN replies with **NG RESET ACKNOWLEDGE**, listing the UE‑associated logical NG‑connections that were reset [TS 38.413 §8.7.4.2.1].  

During this process, **any other ongoing procedure** on the same NG interface concerning the affected UE(s) is *aborted* [TS 38.413 §8.7.4.2.1]. The counterpart (NG‑RAN‑initiated reset) follows the same logic in reverse [TS 38.413 §8.7.4.2.2].

### Overload Start – Controlling Signalling Load

If the core network experiences an overload, it can issue an **OVERLOAD START** message to the NG‑RAN node [TS 38.413 §8.7.7.1]. The NG‑RAN must then *reduce signalling traffic* according to the **Overload Action** IE, which may include:

* Rejecting RRC connection establishments for non‑emergency traffic,  
* Rejecting all signalling, or  
* Permitting only emergency or high‑priority sessions [TS 38.413 §8.7.7.2].

When a *Slice Traffic Load Reduction Indication* is present, the reduction is applied selectively to the indicated NSSAI(s) [TS 38.413 §8.7.7.2]. If a subsequent OVERLOAD START arrives, the NG‑RAN **replaces** the previous parameters with the new ones [TS 38.413 §8.7.7.2].

### O‑RU C/U‑Plane Connectivity Monitoring

At the radio access level, the **O‑RU** monitors the **C/U‑plane** logical connection per processing‑element [O‑RAN MP.0 §7.10]. The monitoring uses a **timer** that is started when at least one array‑carrier on the processing‑element becomes active and is **reset** each time a C/U‑plane data flow is received. The *default* timer value is **160 ms** [O‑RAN MP.0 §7.10].

If the timer expires without receiving any C/U‑plane traffic, the O‑RU **raises an alarm** indicating a connectivity failure. The timer is **configurable** via the `cu-plane-monitoring` container in the `o-ran-supervision.yang` model; a NETCONF client can set the `configured-cu-monitoring-interval` leaf, including disabling the timer altogether [O‑RAN MP.0 §7.10].

### Worked Example – Detecting a C/U‑Plane Failure

Assume an O‑RU with a single active processing‑element. The default monitoring timer is 160 ms.

| Event | Time (ms) | Action |
|------|-----------|--------|
| First C/U‑plane packet received | 0 | Timer started (160 ms) |
| Next packet received | 120 | Timer reset to 160 ms |
| No further packets | – | Timer counts down |
| Timer expires | 280 (120 + 160) | O‑RU raises an alarm |

**Interpretation:** The alarm at 280 ms signals a *transmission interruption* on the C/U‑plane, prompting the operator to check the fronthaul link or the DU’s data‑flow generation.

### Practical Notes and Common Mistakes

* **Neglecting NG‑Reset side effects.** Engineers sometimes assume that a reset only clears UE contexts; however, *any other ongoing procedure* on the same NG link is aborted [TS 38.413 §8.7.4.2.1]. Failing to re‑initiate those procedures can cause prolonged service disruption.  
* **Mis‑configuring the C/U‑plane timer.** Using the default 160 ms without considering the DU’s start‑up latency may generate *spurious alarms* during carrier activation [O‑RAN MP.0 §7.10]. It is advisable to disable the timer temporarily until the DU begins regular traffic.  
* **Overload response mismatch.** The NG‑RAN must apply the exact *Overload Action* indicated; applying a stricter action (e.g., rejecting all traffic when only non‑emergency traffic should be rejected) unnecessarily degrades user experience [TS 38.413 §8.7.7.2].  
* **Alarm correlation.** A transmission interruption alarm alone does not identify the root cause; correlating it with NG‑Reset or Overload Start events helps distinguish whether the fault originates in the *core* (functional fault/overload) or in the *transport* (physical link loss) [TS 32.111-1 §4.1.0].  

By systematically applying the NG‑Reset and Overload procedures and by correctly configuring O‑RU monitoring, operators can rapidly isolate and recover from transmission interruptions and core‑network problems, maintaining service continuity for end‑users.

## 練習題

**1.** 在 TS 32.111‑1 中，哪一類故障是因為過載而導致的功能失效？

- A. 硬體失效
- B. 軟體問題
- C. 功能性故障
- D. 因過載而失去部分或全部規定能力

<details><summary>看答案</summary>

正解：D。過載會使網路元素失去其規定的功能或容量。

</details>

**2.** 當 AMF 主動發送 NG RESET 時，NG‑RAN 節點在回覆 NG RESET ACKNOWLEDGE 前必須先執行哪項動作？

- A. 立即回傳 ACK，不需釋放任何資源
- B. 釋放所有與 UE 相關的 NG 與 Uu 資源並移除 UE context
- C. 只釋放 NG 資源，Uu 資源保留
- D. 等待無線資源全部釋放後才回覆

<details><summary>看答案</summary>

正解：B。NG‑RAN 必須先清除與 UE 相關的所有 NG 與 Uu 資源，才能回覆 ACK。

</details>

**3.** 若 NG RESET 訊息中的 UE‑associated Logical NG‑connection Item 同時缺少 AMF UE NGAP ID 以及 RAN UE NGAP ID，AMF 應如何處理？

- A. 直接回傳錯誤訊息給 NG‑RAN
- B. 嘗試以其他資訊辨識 UE
- C. 忽略該 UE‑associated Logical NG‑connection Item
- D. 仍回傳空的 UE‑associated Logical NG‑connection Item

<details><summary>看答案</summary>

正解：C。沒有任何 ID 可用於辨識時，AMF 必須忽略該項目。

</details>

**4.** O‑RU 用於監控 C/U‑plane 連線的預設計時器值是多少？

- A. 100 ms
- B. 120 ms
- C. 150 ms
- D. 160 ms

<details><summary>看答案</summary>

正解：D。標準規定的預設值是 160 毫秒。

</details>

**5.** 在 OVERLOAD START 程序中，若 *Overload Action* IE 被設定為「reject RRC connection establishments for signalling」，NG‑RAN 應採取的主要行動是什麼？

- A. 完全拒絕所有 RRC 連線請求
- B. 減少訊號流量，若有 *AMF Traffic Load Reduction Indication* IE 則依其百分比減少
- C. 只允許緊急服務的 RRC 連線
- D. 不做任何變更，僅記錄此狀態

<details><summary>看答案</summary>

正解：B。NG‑RAN 必須根據指示的百分比減少訊號流量，或在未提供百分比時只排除被拒絕的流量。

</details>
