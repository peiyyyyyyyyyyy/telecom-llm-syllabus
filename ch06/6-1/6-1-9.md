# 6.1.9 軟體問題：版本、升級失敗

所屬：[6.1 根因的類型](../6-1.md)

## 正文

In a mobile network a *software problem* denotes any fault that originates from the executable code or the data structures that run inside a network element (NE). The 3GPP specification groups such faults under the category “software problems, e.g. software bugs, database inconsistencies” [TS 32.111-1 §4.1.0]. Software problems are distinct from hardware failures or pure functional faults because the malfunction is traced to the logical layer rather than a physical component. In practice, version mismatches or upgrade failures are typical manifestations: an NE may be running an older software release that cannot interpret newer configuration messages, or an attempted upgrade may leave the system in an inconsistent state. Both situations can degrade service, trigger alarms, and ultimately affect user experience, making early detection and proper handling essential for any operational network.

### Key definition

| Symbol | Definition |
|--------|------------|
| **SP** | Software problem, i.e. a fault whose root cause is a software bug or a database inconsistency within an NE. |
| **AL** | Alarm generated by an NE that indicates a fault affecting a logical or physical resource. |
| **V**  | Version identifier of the software running on an NE (e.g., “Release R15”). |
| **U**  | Upgrade attempt flag (true if an upgrade is in progress). |

A software problem is formally defined as any fault that satisfies the predicate:

$$
\text{SP} = \{ f \mid f \text{ is caused by a software bug or a database inconsistency} \}
$$

When a fault $f$ belongs to **SP**, the network must generate at least one alarm $a \in \text{AL}$ that references the affected logical resource [TS 32.111-1 §4.1.0].

### Alarm generation and correlation

The specification mandates that *appropriate alarms related to the physical or logical resource(s) affected by the fault(s), shall be generated by the network entities* [TS 32.111-1 §4.1.0]. For a software problem the alarm typically carries a *software‑fault* identifier and may include the offending version $V$ and the upgrade flag $U$. Correlating multiple alarms (e.g., “software‑bug‑detected” followed by “upgrade‑failed”) helps the operations team pinpoint whether the root cause is a version incompatibility or a failed upgrade procedure.

### Worked example

Consider a base station controller (BSC) that is scheduled for an upgrade from version $V_{\text{old}}=\text{R14}$ to $V_{\text{new}}=\text{R15}$. The upgrade script sets $U = \text{true}$ and begins copying the new binaries. During the process the BSC attempts to read a configuration table that has not yet been migrated, resulting in a database inconsistency.

| Step | Event | Resulting alarm (AL) |
|------|-------|----------------------|
| 1 | Upgrade started, $U = \text{true}$ | No alarm yet |
| 2 | Database inconsistency detected | Alarm 1: “software‑fault – database‑inconsistency, V = R15, U = true” |
| 3 | Upgrade aborts, $U$ reset to false | Alarm 2: “upgrade‑failed, V = R14, U = false” |

From the two alarms the operations team infers a *software problem* (database inconsistency) that caused the upgrade to fail. The alarms satisfy the requirement that *appropriate alarms* be generated for the logical resource (the configuration database) [TS 32.111-1 §4.1.0].

### Common mistakes and practical notes

| Mistake | Why it is problematic | Correct practice |
|---------|----------------------|------------------|
| Ignoring the version field in alarms | Prevents identification of version‑related mismatches, leading to prolonged outages. | Always include $V$ in software‑fault alarms. |
| Assuming a failed upgrade is a hardware fault | Mis‑classifies the root cause and may trigger unnecessary hardware replacement procedures. | Treat upgrade failures as **software problems** unless a hardware error is explicitly indicated. |
| Not correlating sequential alarms | Separate alarms may appear unrelated, obscuring the fact that they stem from the same upgrade attempt. | Use the upgrade flag $U$ to link alarms generated during the same upgrade window. |

In addition, it is important to remember that the reference text does not enumerate specific upgrade mechanisms or version numbering schemes; any detailed procedure description would be outside the scope of the cited specification. The key takeaway is that any fault arising from software bugs or database inconsistencies must be reported through alarms, and those alarms provide the primary evidence for diagnosing version‑related or upgrade‑failure issues.

## 練習題

**1.** 在 TS 32.111‑1 中，版本或升級失敗屬於哪一類故障？

- A. 硬體失效
- B. 軟體問題
- C. 功能性故障
- D. 通訊失敗

<details><summary>看答案</summary>

正解：B。版本或升級失敗是軟體層面的問題，屬於「Software problems」類別。

</details>

**2.** 若因升級失敗導致系統功能受限，根據規範應產生什麼？

- A. 只產生硬體警報
- B. 產生適當的警報
- C. 不需要產生任何警報
- D. 僅記錄在日誌檔

<details><summary>看答案</summary>

正解：B。任何故障都必須產生與受影響資源相關的適當警報。

</details>

**3.** 根據規範，軟體問題（如版本衝突）發生時，哪個實體負責產生警報？

- A. 網路使用者
- B. 網路元素 (NE)
- C. 外部監控系統
- D. 第三方供應商

<details><summary>看答案</summary>

正解：B。規範指出網路元素應產生與故障相關的警報。

</details>

**4.** 在故障分類中，升級失敗不屬於以下哪一類？

- A. 硬體失效
- B. 軟體問題
- C. 功能性故障
- D. 通訊失敗

<details><summary>看答案</summary>

正解：A。升級失敗與硬體無關，屬於軟體問題，而非硬體失效。

</details>
