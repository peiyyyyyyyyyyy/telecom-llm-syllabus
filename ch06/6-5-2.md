# 6.5.2 障礙報告

所屬：[6.5 交接與報告](6-5.md)

## 內文

#### 是什麼、什麼時候會用到

障礙報告（incident report，也常稱事後檢討報告 postmortem）是障礙處理完畢後，把「發生了什麼、影響多大、為什麼發生、怎麼處理、以後怎麼避免」整理成一份可以被別人檢查的文件。讀者包括管理層、相關部門、受影響的企業客戶，以及負責追蹤改善措施的人；若事件達到法定通報門檻，報告中的事實也是向主管機關登錄障礙事件說明的素材（6.4.2）。

不是每個障礙都要寫完整報告。Google SRE Book 第 15 章〈Postmortem Culture: Learning from Failure〉列出常見的觸發條件，例如用戶可見的中斷或劣化超過一定門檻、需要值班工程師介入（回退、改路由等）、修復時間超過門檻、監控失效，並建議事先定好標準（[Postmortem Culture](https://sre.google/sre-book/postmortem-culture/)）。

#### 怎麼做／怎麼判斷

**1. 報告的結構**

| 段落 | 內容 | 寫作要點 |
|---|---|---|
| 摘要 | 3～5 句：什麼服務、多久、多大範圍、主因一句話、目前狀態 | 讓只讀這段的人也知道重點 |
| 時間軸 | 依時間列出事件、偵測、決策、處置與恢復 | 統一時區；每筆附來源（告警、日誌、工單、交接單） |
| 影響 | 受影響的服務、區域、基地臺／小區數、用戶數或連線嘗試數、持續時間；是否達法定通報門檻 | 量化並寫明是實測還是推估、怎麼算 |
| 根因 | 觸發事件（trigger）、根因、促成因素分開寫，**每項標明確定程度與證據** | 不要把觸發當根因 |
| 處置 | 做了什麼、誰批准、效果如何 | 包含沒有效果的嘗試 |
| 改善措施 | 每項有負責人（角色）、期限、類型（預防／偵測／緩解）、追蹤單號 | 不寫「加強宣導」這種無法驗收的項目 |

SRE Book 附錄 D 的[範例報告](https://sre.google/sre-book/example-postmortem/)也有類似欄位：Summary、Impact、Root Causes、Trigger、Resolution、Detection、Action Items、Lessons Learned、Timeline。資安事件可另外參考 NIST SP 800-61 Rev. 3（Incident Response Recommendations and Considerations for Cybersecurity Risk Management）對事後改善的建議。

**2. 事實與推測分開**（承接 5.5.3）

時間軸與影響段只放有紀錄可查的事實；推論集中寫在根因段，每一項推論都要寫出依據。報告裡的數字若是推估，要寫推估方法，例如「依前一週同時段平均值推估」。

**3. 根因標明確定程度**

本教材建議用三級描述（這是寫作慣例，不是標準規定）：

- **已確認**：有直接證據（日誌、組態、重現測試），且其他可能已被排除。
- **很可能**：證據支持，但還有替代解釋沒有完全排除；要寫出還缺什麼查證。
- **推測**：只符合時序或經驗，沒有直接證據。

一份報告可以同時有「已確認」的觸發和「很可能」的促成因素；不確定的部分列為待查事項，查完後更新報告版本。

**4. 對事不對人**

SRE Book 第 15 章強調不究責（blameless）：報告聚焦在找出促成事件的原因，不指責個人或團隊。寫「升級程序沒有要求先切換流量」，而不是「某工程師疏忽」；這樣改善措施才會落在流程與系統上。

#### 實際例子

```
障礙報告（節錄，虛構）　戊電信　INC-2026-0821-0093　版本 v1.1
摘要：2026-08-21 10:02～10:49（47 分鐘），河港區（虛構）16 臺 gNB 與核心網
      連線中斷，48 個小區無法提供服務。觸發為匯聚路由器 AGG-R3 軟體升級時
      介面卡重啟；備援路徑在事件前已失效（自 08-07 起 down，確定程度：很可能，實體走線待確認）。已恢復，改善措施進行中。
時間軸（UTC+8）
 09:58 AGG-R3 開始軟體升級（變更單 CHG-0821-02）　[事實：變更紀錄]
 10:02 AGG-R3 介面卡重啟；16 臺 gNB 出現 NG 連線中斷告警　[事實：告警、設備日誌]
 10:06 NOC 開單，判 P1　[事實：工單]
 10:31 升級完成，介面卡恢復　[事實：設備日誌]
 10:49 16 臺 gNB 全數恢復連線　[事實：告警清除時間]
影響
 - 16 臺 gNB／48 小區，中斷 47 分鐘（10:02～10:49 為第一臺中斷至最後一臺恢復的區間）　[事實]
 - 該區戊電信共 40 臺，中斷 16 臺（40%），未達法定通報門檻　[事實]
 - 約 54,050 次連線嘗試受影響　[推估：上週同時段每分鐘平均 1,150 次 × 47 分鐘]
根因
 - 觸發：升級導致介面卡重啟　[已確認：設備日誌與變更時間吻合，原廠升級說明載明會重啟]
 - 根因：升級程序未要求先將流量切到備援路徑　[已確認：程序文件與變更單內容]
 - 促成因素：備援路徑在事件前已失效　[很可能：網管顯示備援介面自 08-07 起為 down；
   實體光纖走線尚待現場確認]
改善措施
 1. 升級程序加入「先切備援、確認備援可用」步驟｜傳輸維運主管｜09-15｜預防
 2. 備援介面 down 超過 24 小時即開單｜網管組｜09-30｜偵測
 3. 現場確認備援光纖走線並更新文件｜外線組｜09-05｜偵測
```

逐步說明：摘要用一段話交代時間、範圍、觸發與現況。時間軸每筆附來源，標成事實。影響段的「47 分鐘」由 10:02 到 10:49 算出；40% 由 16÷40 算出，並說明未達通報辦法第 3 條第 4 款「同一鄉（鎮、市、區）30 臺或 50%」（[第 3 條](https://law.moj.gov.tw/LawClass/LawSingle.aspx?pcode=K0060127&flno=3)）；連線嘗試數是推估，寫明算法（1,150×47＝54,050）。根因段把觸發、根因、促成因素分開：觸發與根因有直接證據，標「已確認」；備援失效只有網管狀態，還沒到現場看實體走線，所以標「很可能」，並列成第 3 項待查。

不能下結論的地方：備援為什麼在 08-07 失效，報告沒有證據，不能寫「光纖被挪用」之類的猜測；受影響用戶數沒有實際計數，只能給推估值。

#### 容易搞混的地方

- **觸發 ≠ 根因**：「升級」是觸發；真正讓升級變成障礙的是程序缺少切換步驟與備援失效。只寫觸發，改善措施就會變成「不要升級」。
- **確定程度要逐項標**：不要在整份報告末尾寫一句「以上為初步分析」，讀者分不出哪一項已確認。
- **時間軸只放事實**：「10:15 判斷應為光纖問題」若是當時的推測，要寫成「10:15 值班人員提出光纖問題的假設」，而不是把它寫成事件本身。
- **障礙報告 ≠ 法定事件說明**：通報辦法第 6 條第 4 項（[原文](https://law.moj.gov.tw/LawClass/LawSingle.aspx?pcode=K0060127&flno=6)）要求登錄的事件說明有指定內容；內部報告通常更詳細，兩者內容要一致，但不能互相取代。

#### 和其他小節的關係

時間軸寫法承接 5.5.1，事實與推測的區分承接 5.5.3；根因分類見 6.1，假設與證據見 6.2.1、6.2.2，處置見 6.3。影響段要說明等級與是否達法定門檻（6.4.1、6.4.2）；時間軸素材來自工單（6.4.3）與交接單（6.5.1）。改善措施若涉及組態或程序異動，走第 9 章異動流程。範例格式參考 [SRE Book 附錄 D](https://sre.google/sre-book/example-postmortem/)。

#### Report structure and when a full report is required

**情境 002**　Choosing a summary from a fact sheet

NorthLink Mobile (fictional) prepared a fact sheet for INC-2026-1014-0077 and three candidate summaries.

```
Fact sheet INC-2026-1014-0077 (NorthLink Mobile, fictional), times UTC+8
Service      : VoNR call setup in Pinehill District (fictional)
Start        : 2026-10-14 13:47 (first SIP 503 burst, P-CSCF log)
End          : 2026-10-14 15:05 (call setup success back to baseline)
Scope        : 64 NR cells on 21 gNBs; data sessions unaffected
Trigger      : restart of P-CSCF pool PC-2 during patch CHG-1014-05 [confirmed]
Root cause   : patch procedure did not drain PC-2 before restart    [confirmed]
Contributing : failover timer on PC-1 set to 600 s, design 60 s     [likely]
Status       : restored; 3 action items open

Candidate A: "On 14 October we had a VoNR issue. Engineers responded
             and fixed it."
Candidate B: "2026-10-14 13:47-15:05 (78 min): VoNR call setup failed for
             users of 64 NR cells (21 gNBs) in Pinehill District; data
             sessions unaffected. Trigger: a patch restarted P-CSCF pool PC-2
             without draining it first. Service restored; 3 actions open."
Candidate C: "13:47 SIP 503 burst seen. 13:52 alarm. 14:05 ticket opened.
             14:30 PC-1 checked. 14:48 failover timer suspected. 15:05 OK."
```

**006.** Which candidate meets the requirements for a summary?

1. Candidate A
2. Candidate B
3. Candidate C
4. None of them, because a summary must list every timeline event

<details><summary>看答案</summary>

**答案**　2

**詳解**　B gives the service (VoNR call setup), duration (78 min), scope (64 cells, 21 gNBs, data unaffected), the main cause in one sentence and the status. Option 1 is wrong: A has no duration, scope, cause or status. Option 3 is wrong: C is a list of events, i.e. timeline content. Option 4 is wrong: the summary is 3–5 sentences; the event list belongs in the timeline.

#### Separating trigger, root cause and contributing factors

**情境 004**　An expired gateway certificate written up as the root cause

Meridian Net (fictional) is reviewing the root-cause section of a draft report. All times are UTC+8 on 2026-09-01.

```
Meridian Net (fictional) - INC-2026-0901-0012 - root-cause section, draft v0.9
Records
 00:00:00  TLS server certificate of SMS gateway SMSGW-1 expires     [gateway log]
 00:00:04  ESME bind failures start ("certificate expired")           [gateway log]
 00:00:10  Certificate-expiry alarm raised by the EMS                 [EMS alarm log]
 00:00:10  Alarm e-mailed to noc-old@meridian.example
           (mailbox closed 2026-03, nobody reads it)                  [EMS config]
 07:12:00  Enterprise customer reports OTP SMS not delivered          [ticket]
 07:40:00  New certificate installed; ESME binds succeed              [change log]
 Certificate inventory: SMSGW-1 not listed
   (inventory created 2025-11; SMSGW-1 installed 2024-09)             [inventory]
 Renewal procedure PRC-SEC-04: a renewal is started only for
   certificates that appear in the inventory                          [procedure doc]

Author's draft classification
 Root cause   : certificate expired at 00:00
 Contributing : none identified
```

**016.** What is wrong with the author's draft classification?

1. Nothing; the certificate expiry is directly evidenced by the gateway log, so it is the root cause
2. It names the trigger as the root cause; the root cause is that renewal depends on the inventory and SMSGW-1 was missing from it, so no renewal was started
3. It should name the enterprise customer's report at 07:12 as the root cause, because that is when the incident became known
4. It should name the closed mailbox as the root cause, because the alarm was raised in time

<details><summary>看答案</summary>

**答案**　2

**詳解**　The expiry at 00:00 is the event that set the failure off (trigger). What allowed a predictable expiry to become an outage is that PRC-SEC-04 only renews inventoried certificates and SMSGW-1 was not in the inventory. Option 1 is wrong: being well evidenced does not make the trigger the root cause. Option 3 is wrong: the time of discovery is a detection fact, not a cause. Option 4 is wrong: the closed mailbox delayed detection and lengthened the outage, but the certificate would still have expired; it is a contributing factor.

**出處**　Curriculum 6.5.2 (trigger ≠ root cause); Google SRE Book Appendix D, Example Postmortem, separate "Root Causes" and "Trigger" fields (https://sre.google/sre-book/example-postmortem/)

</details>

**017.** Define trigger, root cause and contributing factor as they are kept apart in an incident report.

<details><summary>看答案</summary>

**答案**　The trigger is the event that set the failure off; the root cause is the underlying condition that made that event turn into an incident; a contributing factor did not cause the incident alone but made it more likely, larger or longer.

**詳解**　The three are written separately, each with its own evidence and confidence level, so that improvement actions can target each one. Writing only the trigger leads to actions that avoid the event instead of fixing the weakness.

**出處**　Curriculum 6.5.2 (report structure table, Root cause row; trigger ≠ root cause); Google SRE Book Appendix D (https://sre.google/sre-book/example-postmortem/)

</details>

**018.** Which item is best classified as a contributing factor?

1. The certificate of SMSGW-1 expired at 00:00:00
2. SMSGW-1 was missing from the certificate inventory used by PRC-SEC-04
3. A closed mailbox delayed detection until a customer report.
4. The enterprise customer used SMS for one-time passwords

<details><summary>看答案</summary>

**答案**　3

**詳解**　The closed mailbox did not cause the expiry, but it removed detection and made the outage last until 07:40. Option 1 is the trigger. Option 2 is the root cause. Option 4 describes the customer's use of the service, not a factor in the failure.

**019.** Can the report state why SMSGW-1 was left out of the inventory built in 2025-11?
