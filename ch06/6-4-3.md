# 6.4.3 工單

所屬：[6.4 流程](6-4.md)

## 內文

#### 是什麼、什麼時候會用到

工單（trouble ticket）是障礙從發現到結案的正式紀錄：誰在什麼時候發現什麼問題、影響多大、做了哪些查證與處置、現在進行到哪一步。客服接到客訴、監控中心收到告警、或另一個系統自動偵測到異常，都會開立工單；之後每次查證、升級、處置、交班都要更新同一張工單，結案時它也是撰寫障礙報告的主要素材。TM Forum 的 Trouble Ticket API（TMF621）定義了工單系統對外交換工單的標準介面，可以用它的欄位當作工單應有內容的參考；其原文說明，網管或故障管理系統也可以是建立工單的一方（[TMF621 OAS v5.0.1](https://raw.githubusercontent.com/tmforum-apis/TMF621_TroubleTicket/main/TMF621-Trouble_Ticket-v5.0.1.oas.yaml)）。

#### 怎麼做／怎麼判斷

**一、工單要有的內容，以及在 TMF621 對應的欄位**（[TMF621 Trouble Ticket OAS v5.0.1](https://raw.githubusercontent.com/tmforum-apis/TMF621_TroubleTicket/main/TMF621-Trouble_Ticket-v5.0.1.oas.yaml)，schema `TroubleTicket`）

| 內容 | TMF621 欄位 | 說明 |
|---|---|---|
| 障礙描述 | `name`、`description` | `name` 是簡短名稱；`description` 是問題描述 |
| 嚴重程度、優先順序 | `severity`、`priority` | 原文舉例 severity 可為 Critical、Major、Minor；priority 由工單系統依嚴重度、類型等決定 |
| 工單類型 | `ticketType` | 原文舉例 incident、complain、request |
| 影響 | 無專用欄位 | 可寫進 `description`，或用 `troubleTicketCharacteristic`（名稱／值清單）記錄；受影響的物件用 `relatedEntity`（含 `role`、`entity`） |
| 時間 | `creationDate`、`expectedResolutionDate`、`resolutionDate`、`lastUpdate`、`statusChangeDate` | 建立、預計解決、實際解決、最後更新、狀態變更時間 |
| 處置與查證紀錄 | `note`（每筆含 `author`、`date`、`text`） | 每次查證、處置、交接各寫一筆 |
| 相關人員 | `relatedParty` | 開單者、負責人等 |
| 狀態 | `status`、`statusChangeReason`、`statusChangeHistory` | 歷程由伺服器填入 |
| 工單之間的關係 | `troubleTicketRelationship`（含 `relationshipType`） | 例如多張客訴工單指向同一張網路障礙工單 |

建立工單時，`TroubleTicket_FVO` 的必填欄位是 `description`、`severity`、`ticketType`。API 提供 `GET`／`POST /troubleTicket`、`GET`／`PATCH`／`DELETE /troubleTicket/{id}`，以及 `troubleTicketStatusChangeEvent`、`troubleTicketResolvedEvent`、`troubleTicketInformationRequiredEvent` 等事件通知。

**二、狀態值**：`status` 的型別 `TroubleTicketStatusType` 有八個值：`acknowledged`、`rejected`、`pending`、`held`、`inProgress`、`cancelled`、`closed`、`resolved`。OAS 的說明把這組狀態稱為「a basic set of states ... (as an example)」，也就是示範用的基本集合；狀態之間怎麼轉移，OAS 檔裡沒有規定，由各業者自訂。

**三、甲電信（虛構）工單狀態流轉規定**

| 從 | 到 | 條件（虛構） |
|---|---|---|
| （新建） | `acknowledged` | 監控中心確認收到，15 分鐘內 |
| `acknowledged` | `rejected` | 查證後非障礙或重複開單，需寫 `statusChangeReason` |
| `acknowledged` | `inProgress` | 指派負責工程師，開始查證（6.3.1） |
| `inProgress` | `pending` | 等待外部資訊（例如客戶補充、廠商回覆） |
| `inProgress` | `held` | 等待已排定的處置時段（例如第 9 章的異動時段） |
| `pending`／`held` | `inProgress` | 等待條件解除 |
| `inProgress` | `resolved` | 服務恢復並已確認 KPI 回到正常 |
| `resolved` | `closed` | 觀察 24 小時無復發，且障礙報告（6.5.2）已提交 |
| 任一未結案狀態 | `cancelled` | 開單者撤回 |

判斷原則（一般實務）：狀態要反映**實際進度**，不是「看起來好了」；`resolved` 和 `closed` 分開，是為了留一段觀察期。

**四、內容怎麼寫才有用**（一般實務，不是 TMF621 規定）

1. `description` 寫「現象＋範圍＋開始時間」，例如哪個小區、哪個指標、從幾點開始、變化多少；開單當下還不知道根因，就不要把猜測寫成事實。
2. 每一筆 `note` 只記一件事：做了什麼查證或處置、結果是什麼、是誰做的；推測要明寫「推測」，和查到的事實分開（承接 5.5.3）。
3. 需要批准的處置，要在 `note` 裡寫明批准人和異動單號，方便事後對照第 9 章的異動紀錄。
4. 同一個網路障礙引發多張客訴工單時，不要各自查一遍，而是用 `troubleTicketRelationship` 把客訴工單關聯到主工單，主工單結案時再一起回覆。
5. 每次變更狀態都要寫 `statusChangeReason`；`statusChangeHistory` 會保留每次變更的狀態、時間與原因，事後可以拿來檢討哪一段等待最久。

#### 實際例子

延續 6.3.1、6.3.2 的事件（業者、設備、人名、數值皆虛構），工單在 05:47 的樣子（依 [TMF621 v5.0.1](https://raw.githubusercontent.com/tmforum-apis/TMF621_TroubleTicket/main/TMF621-Trouble_Ticket-v5.0.1.oas.yaml) 的欄位格式，內容精簡）：

```json
{
  "id": "TT-20261125-0093",
  "name": "TPE 北區 NRCellDU=3 下行吞吐下降",
  "description": "客訴上網慢；gNB-TPE-0417 NRCellDU=3 02:00 起下行平均吞吐由 142.6 降至 38.9 Mbps，RRC 連線建立成功率約 99%。",
  "severity": "Major",
  "priority": "High",
  "ticketType": "incident",
  "creationDate": "2026-11-25T02:20:00+08:00",
  "resolutionDate": "2026-11-25T05:47:00+08:00",
  "status": "resolved",
  "statusChangeReason": "更換射頻單元後吞吐回到 140 Mbps 以上",
  "relatedEntity": [{ "role": "affectedCell",
    "entity": { "id": "SubNetwork=TW-N,ManagedElement=gNB-TPE-0417,GNBDUFunction=1,NRCellDU=3" } }],
  "troubleTicketCharacteristic": [{ "name": "impactedArea", "value": "北區 3 個里" }],
  "note": [
    { "author": "值班 王小明", "date": "2026-11-25T02:35:00+08:00", "text": "讀 AlarmList：A-88213 EQUIPMENT_ALARM MAJOR，01:58:42 起。" },
    { "author": "主管 林大同", "date": "2026-11-25T04:10:00+08:00", "text": "批准 NRCellDU=3 設為 SHUTTING DOWN 後換件（緊急異動單 CR-1125-07）。" }
  ]
}
```

逐步說明：

1. 從告警發生（01:58:42）到開單（02:20:00）相隔 21 分 18 秒；從開單到 `resolved` 共 3 小時 27 分。這兩段時間要分開算，前者反映監控反應，後者反映處理效率。
2. `status` 是 `resolved` 而不是 `closed`：依虛構規定還要觀察 24 小時並提交障礙報告。
3. `impactedArea` 是甲電信自訂的特性名稱，不是 TMF621 規定的欄位；TMF621 只提供 `troubleTicketCharacteristic` 這個容器。

不能從這張工單下的結論：`note` 只記到換件後吞吐恢復，並沒有證明射頻單元就是唯一根因；根因確定程度要在 6.5.2 障礙報告裡另外標明。

#### 容易搞混的地方

- **工單不是告警**：告警由 NE 產生、故障清除後由系統移除（[TS 28.111 V18.8.0 clause 6.5、7.3.1](https://www.3gpp.org/ftp/Specs/archive/28_series/28.111/28111-i80.zip)）；工單由人或系統開立、要人工推進到結案。告警清除不代表工單可以結案。
- **`severity` 和 `priority` 不同**：前者是對功能影響的程度，後者是要多快處理，由系統綜合嚴重度、類型等決定（TMF621 原文說明）。
- **狀態轉移規則不是 TMF621 規定的**：OAS 只列出八個狀態值並註明是示範用；哪個狀態能轉到哪個狀態、要什麼條件，是業者自訂。
- **`resolved` 不等於 `closed`**：前者是問題已解決，後者是工單正式結束。

#### 和其他小節的關係

工單的 `severity`／`priority` 依 6.4.1 障礙等級決定，升級與通報依 6.4.2；`note` 記錄 6.3.1 查證與 6.3.2 處置（含第 9 章異動單號），交班時摘要成 6.5.1 交接單，結案前寫 6.5.2 障礙報告；時間欄位是排 5.5.1 時間軸的材料（[TMF621 GitHub](https://github.com/tmforum-apis/TMF621_TroubleTicket)）。

**出處**　TM Forum TMF621 Trouble Ticket API，OAS v5.0.1（schema `TroubleTicket`、`TroubleTicket_FVO`、`TroubleTicketStatusType`、`Note`、`RelatedEntity`、`StatusChange`；paths `/troubleTicket`、`/troubleTicket/{id}`），[GitHub 儲存庫](https://github.com/tmforum-apis/TMF621_TroubleTicket)、[OAS 檔](https://raw.githubusercontent.com/tmforum-apis/TMF621_TroubleTicket/main/TMF621-Trouble_Ticket-v5.0.1.oas.yaml)；同儲存庫 v4.0.0 swagger 狀態值相同（[swagger 檔](https://raw.githubusercontent.com/tmforum-apis/TMF621_TroubleTicket/main/TMF621-TroubleTicket-v4.0.0.swagger.json)）；3GPP TS 28.111 V18.8.0 clause 6.5、7.3.1（[FTP](https://www.3gpp.org/ftp/Specs/archive/28_series/28.111/28111-i80.zip)）；甲電信工單狀態流轉規定（虛構）

**001.** Which field of this ticket expresses how quickly the issue should be handled, and per the OAS is set by the ticket management system taking severity and ticket type into account?

1. `priority` ("High")
2. `severity` ("Major")
3. `expectedResolutionDate` ("2026-11-03T16:05:00+08:00")
4. `ticketType` ("incident")

<details><summary>看答案</summary>

**答案**　1

**詳解**　The TMF621 OAS describes `priority` as "the priority of the trouble ticket and how quickly the issue should be resolved", with a value "set by the ticket management system considering the severity, ticket type etc." Option 2 is wrong because `severity` indicates the implication of the issue on the expected functionality, not handling urgency. **004.** In a TMF621 `relatedEntity` item, what do `role` and `entity` carry, and which of them are required when the item is sent in a create request (`RelatedEntity_FVO`)?

<details><summary>看答案</summary>

**答案**　`role` is a free string naming the role the object plays for the ticket (e.g. "affectedCell") and `entity` is an entity reference whose `id` identifies the object; in `RelatedEntity_FVO` both `role` and `entity` are required.

**詳解**　`RelatedEntity` is "a reference to an entity, where the type of the entity is not known in advance", with properties `role` (string) and `entity` (EntityRef). The `RelatedEntity_FVO` variant used in create requests lists `role` and `entity` as required, and `EntityRef` itself requires `id`. In this ticket the role is "affectedCell" and the entity id is the DN of NRCellDU=2.

**出處**　TM Forum TMF621 OAS v5.0.1, schemas `RelatedEntity`, `RelatedEntity_FVO`, `EntityRef` (https://raw.githubusercontent.com/tmforum-apis/TMF621_TroubleTicket/main/TMF621-Trouble_Ticket-v5.0.1.oas.yaml)

</details>

**005.** From the ticket's date fields, how long after creation did the status change to inProgress, and how long is the planned window from creation to `expectedResolutionDate`?

<details><summary>看答案</summary>

**答案**　13 minutes to the status change, and a 6-hour planned resolution window.

**詳解**　`creationDate` is 10:05:00 and `statusChangeDate` (the change to the current status inProgress) is 10:18:00: 10:18 − 10:05 = 13 min. `expectedResolutionDate` is 16:05:00 on the same day with the same offset +08:00: 16:05 − 10:05 = 6 h 00 min. `lastUpdate` (11:20) is the time of the last change to the ticket (here the second note), not a status change.

**019.** Can you tell from the request and response whether alarm A-71006 is still active now?

<details><summary>看答案</summary>

**答案**　Cannot be determined: the note records only the raise time 03:12:31; the current AlarmList (or the alarm's alarmClearedTime) for gNB-HL-0907 is needed.

**020.** Which TMF621 operations (HTTP method and path) create a trouble ticket and partially update an existing one?

<details><summary>看答案</summary>

**答案**　`POST /troubleTicket` creates a ticket and `PATCH /troubleTicket/{id}` partially updates it.

**詳解**　The OAS defines `createTroubleTicket` as POST on `/troubleTicket` with request body `TroubleTicket_FVO`, and `patchTroubleTicket` as PATCH on `/troubleTicket/{id}` with request body `TroubleTicket_MVO` ("updates partially a TroubleTicket entity"). **105.** Why are related complaint customers answered when the master ticket is closed rather than as soon as it is resolved?

<details><summary>看答案</summary>

**答案**　Because closure, unlike resolution, comes after the observation period has shown no recurrence, so the answer given to customers will not have to be withdrawn.

**詳解**　The textbook says related complaint tickets are answered together when the master ticket is closed, and that resolved and closed are separated to leave an observation period. TT-0068 shows why: a reply sent at resolution time would already be contradicted.
