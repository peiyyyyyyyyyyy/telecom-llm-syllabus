# 6.2.3 還缺什麼資料、怎麼補收（追蹤、MDT、測試）

所屬：[6.2 推理](../6-2.md)

## 正文

When a fault is reported, the alarm often contains only a high‑level indication (e.g., “resource X failed”). If this information is insufficient to pinpoint the exact faulty component, the fault‑management (FM) process stalls: corrective actions may be applied to the wrong element, leading to prolonged outages and unnecessary traffic loss. Therefore, engineers must deliberately acquire the missing data before a definitive hypothesis can be accepted. The 3GPP test‑management function exists exactly for this purpose: it enables the operator to request additional measurements that can confirm or refute a suspected cause [TS 32.111‑1 §4.3].

### Test‑management service – definition and scope
A **test** is defined as any activity that verifies whether a physical or functional resource performs according to its specification and, if a fault is detected, supplies information that helps the operator localize the problem [TS 32.111‑1 §4.3]. The service involves three participants:

* **Operator** – initiates the test request.  
* **Operating System (OS)** – forwards the request to the managed network element (NE).  
* **Managed NE** – autonomously executes the test and returns the result [TS 32.111‑1 §4.3].

The service can be invoked in three contexts:

1. **Post‑alarm localisation** – when the alarm report is insufficient.  
2. **Proactive monitoring** – during normal operation to detect latent faults.  
3. **Post‑repair verification** – after a component has been repaired or replaced, before it is returned to service [TS 32.111‑1 §4.3].

### Trace as a complementary data‑gathering method
In addition to dedicated tests, operators may request **Subscriber/UE Trace** or **Service Level Tracing**. Traces capture protocol‑level signalling and user‑plane events, providing a richer view of the network behaviour. The use cases are split into two high‑level categories [TS 32.421 §5.8]:

* **Troubleshooting** – solving an existing problem (e.g., “malfunctioning UE”, “QoS profile checking after a subscriber complaint”).  
* **Validation testing** – analysing, fine‑tuning or optimising the network when no specific problem is known (e.g., “testing new features”, “fine‑tuning algorithms”).

These categories are orthogonal to the test‑management function; a trace can be launched before, during, or after a test campaign to corroborate the findings.

### Throttled trace sessions – resource‑aware operation
Because tracing can be resource‑intensive, the NE may **throttle** a trace recording session when internal resources are scarce. The specification mandates that the NE must be able to start a throttled session under such conditions and must indicate when a session is throttled [TS 32.421 §5.9]. Conversely, when resources become available again, the NE shall clear the throttled session [TS 32.421 §5.9].

### Simple quantitative example
Assume an alarm points to a Radio Access Network (RAN) node but does not identify the faulty carrier. The operator requests three tests:

| Test ID | Description                     | Result |
|--------|---------------------------------|--------|
| T1     | Carrier power measurement       | PASS   |
| T2     | Antenna return‑loss verification| FAIL   |
| T3     | Scheduler latency check         | PASS   |

The **test success ratio** $R$ is defined as  

$$
R = \frac{N_{\text{PASS}}}{N_{\text{TOTAL}}}
$$  

where $N_{\text{PASS}}$ is the number of passed tests and $N_{\text{TOTAL}}$ the total executed tests. Here $R = \frac{2}{3} \approx 0.67$ (67 %). Because $R < 1$, the operator concludes that the antenna is the likely culprit and may proceed to replace or re‑align it. The trace function could be used concurrently to capture UE‑level symptoms (e.g., dropped packets) that further confirm the antenna fault.

### Practical notes and common pitfalls

| Pitfall | Why it happens | Correct approach |
|---------|----------------|------------------|
| Assuming the operator must manually run every test | The reference states the NE executes tests autonomously after a request [TS 32.111‑1 §4.3]. | Issue the request from the OS; let the NE run the test. |
| Ignoring throttling warnings | A throttled trace may omit events, leading to incomplete analysis [TS 32.421 §5.9]. | Monitor the NE’s throttling indication and, if needed, postpone non‑critical traces. |
| Confusing “troubleshooting” with “validation testing” | Both use the same trace mechanisms but differ in intent [TS 32.421 §5.8]. | Classify the activity first; use troubleshooting traces for known faults, validation traces for optimisation. |
| Treating test results as binary without quantification | Simple pass/fail may hide marginal performance issues. | Compute metrics such as the success ratio $R$ to quantify confidence. |
| Attempting “local maintenance” or “inter‑NE testing” within this framework | The present document explicitly excludes those aspects [TS 32.111‑1 §4.3]. | Restrict activities to the defined test‑management and trace functions. |

When the available data are still insufficient after the initial test set, the operator may iterate: request additional targeted tests, enable a throttled trace once resources permit, or, if the situation is outside the scope of the current specifications (e.g., MDT‑specific procedures), acknowledge the limitation and refer to the appropriate external standard.

## 練習題

**1.** When an alarm report does not contain enough detail to locate a fault, which 3GPP function is specifically designed to acquire the missing information?

- A. Service Level Tracing
- B. Test‑management service
- C. Network Slice Selection Function
- D. Authentication Server

<details><summary>看答案</summary>

正解：B。The test‑management service is invoked when alarm information is insufficient to localize the faulty resource.

</details>

**2.** After the operator requests a test, which entity normally carries out the test autonomously?

- A. The operator’s handset
- B. The managing system (OS)
- C. The managed Network Element (NE)
- D. An external test‑equipment rack

<details><summary>看答案</summary>

正解：C。The specification states that the managed NE executes the tests without further operator support.

</details>

**3.** Which category of trace use case is intended for solving an already known problem in the network?

- A. Validation testing
- B. Troubleshooting
- C. Performance benchmarking
- D. Security auditing

<details><summary>看答案</summary>

正解：B。Troubleshooting use cases are defined as those where the operator is solving an existing problem.

</details>

**4.** According to the specifications, under what condition may a Network Element start a throttled trace recording session?

- A. Only when the operator explicitly disables throttling
- B. When there are insufficient resources available within the NE
- C. After a successful firmware upgrade
- D. When the trace duration exceeds 10 seconds

<details><summary>看答案</summary>

正解：B。The NE is allowed to start a throttled session specifically when resources are insufficient.

</details>

**5.** Which of the following is NOT listed as a purpose of the test‑management service in the reference text?

- A. Verify that a resource performs properly
- B. Provide information to help localize faults
- C. Replace a faulty hardware component
- D. Execute tests during normal operation

<details><summary>看答案</summary>

正解：C。The reference describes verification, localisation, and execution of tests, but does not mention hardware replacement.

</details>
