# 6.2.2 支持證據與反證

所屬：[6.2 推理](../6-2.md)

## 正文

Root Cause Analysis (RCA) is defined as a process that can determine and identify the network condition (e.g., fault, mis‑configuration) causing the alarms. The purpose of RCA is to isolate the single fault that explains a set of observed symptoms, thereby enabling targeted remediation and reducing mean time to repair. Without reliable supporting evidence, engineers may chase symptoms rather than the underlying cause, leading to prolonged outages and inefficient use of resources [TS 32.111-1 §4.1.9].

### Types of Supporting Evidence
The specification lists five principal sources that may be used to build a case for a particular root cause:

1. **Information carried in alarm(s)** – the raw parameters (alarm identifier, severity, timestamp, and descriptive text) that are generated by the network element when a condition deviates from normal operation.  
2. **Information carried in correlated alarm sets** – the relationship among multiple alarms that have been grouped because they share a temporal or logical link.  
3. **Information carried in network notifications** – unsolicited messages from the network (e.g., fault notifications, state changes) that provide additional context.  
4. **Network configuration information** – the static and dynamic settings of the affected element, such as parameter values, software version, and topology data.  
5. **Operators' network management experience** – the tacit knowledge accumulated by personnel through previous incidents and routine operations.

These sources together constitute the **supporting evidence** that an Operations Support (OS) system can analyse to pinpoint the Root Cause Alarm. The OS is encouraged, “if possible,” to perform an RCA and indicate the alarm that best represents the root cause [TS 32.111-1 §4.1.9].

### Using Counter‑Evidence to Refute a Hypothesis
While building a hypothesis, engineers must also seek **counter‑evidence** – pieces of information that contradict the assumed cause. For example, if an alarm suggests a hardware failure, but the network configuration shows the hardware is in a standby state and recent notifications indicate a software upgrade, the latter items serve as counter‑evidence. Counter‑evidence is not listed explicitly in the specification, but it follows logically from the need to evaluate all available information, including the five sources above, to avoid false attribution. By systematically checking each source for inconsistencies, the analyst can discard hypotheses that do not align with the totality of the data.

### Worked Example
Consider a simplified scenario in a radio access network:

| Alarm ID | Timestamp (s) | Severity | Text                     |
|----------|---------------|----------|--------------------------|
| A1       | 1000          | Major    | "RF power drop"          |
| A2       | 1002          | Minor    | "Temperature high"       |
| A3       | 1005          | Major    | "Cell outage"            |

The alarms A1–A3 are correlated because they occur within a 5‑second window and involve the same cell.  

1. **Gather supporting evidence**  
   - **Alarm information**: A1 reports RF power loss; A3 reports cell outage.  
   - **Correlated set**: The three alarms share the same cell identifier, indicating a common origin.  
   - **Network notifications**: A notification received at 999 s reports “Power supply fault detected.”  
   - **Configuration data**: The cell’s power supply is configured for redundancy but the backup is disabled.  
   - **Operator experience**: Past incidents show that a power‑supply fault often triggers both RF loss and cell outage.

2. **Form hypothesis**: The root cause is the primary power‑supply failure.  

3. **Seek counter‑evidence**  
   - No notification of a software crash is present, reducing the likelihood of a software‑related cause.  
   - Temperature alarm A2 is consistent with a power issue rather than a separate cooling failure.

Because all five evidence streams support the hypothesis and no counter‑evidence contradicts it, the OS can label the “Power supply fault detected” notification as the **Root Cause Alarm**. This aligns with the specification’s guidance that “one alarm may relate to the fault which is the root cause of all the correlated alarms and events” and that the OS should “perform a Root Cause Analysis to identify and indicate the Root Cause Alarm” [TS 32.111-1 §4.1.9].

### Practical Tips and Common Mistakes
- **Mistake 1 – Ignoring correlated alarm sets**: Treating each alarm in isolation discards valuable temporal relationships, making it harder to identify the root cause.  
- **Mistake 2 – Over‑relying on a single evidence source**: For instance, trusting only alarm text without checking configuration may miss a mis‑configuration that masquerades as a hardware fault.  
- **Mistake 3 – Failing to consider operator experience**: Experienced operators often recognize patterns that automated systems miss; dismissing this input can prolong diagnosis.  
- **Tip – Document counter‑evidence**: Even when a hypothesis appears strong, recording why alternative causes were rejected improves future analyses and supports audit trails.  
- **Tip – Update configuration records promptly**: Accurate configuration information is essential for both supporting and counter‑evidence; stale data can lead to incorrect root‑cause attribution.

By systematically collecting the five listed evidence types, actively searching for contradictions, and adhering to the guidance in TS 32.111‑1, engineers can perform robust RCA that isolates the true fault quickly and reliably.

## 練習題

**1.** Which of the following is NOT listed as a possible source for determining the root cause in TS 32.111‑1?

- A. Information carried in alarm(s)
- B. Network configuration information
- C. Operators' network management experience
- D. Customer billing records

<details><summary>看答案</summary>

正解：D。The specification lists five sources; billing records are not among them.

</details>

**2.** According to TS 32.111‑1, what does Root Cause Analysis aim to determine?

- A. The optimal routing path for data packets
- B. The network condition (e.g., fault, mis‑configuration) causing the alarms
- C. The total number of users affected by an outage
- D. The financial impact of a service disruption

<details><summary>看答案</summary>

正解：B。RCA is defined as a process to identify the network condition that causes the alarms.

</details>

**3.** In a set of correlated alarms, what role may a single alarm play?

- A. It always represents the most severe fault.
- B. It may relate to the fault which is the root cause of all the correlated alarms and events.
- C. It is unrelated to the other alarms.
- D. It indicates a successful recovery.

<details><summary>看答案</summary>

正解：B。The specification states that one alarm can be the root cause for the whole set.

</details>

**4.** Besides automated data, whose input is explicitly mentioned as useful for root‑cause determination?

- A. Third‑party vendors
- B. End‑user feedback
- C. Operators' network management experience
- D. Regulatory auditors

<details><summary>看答案</summary>

正解：C。Operator experience is listed as one of the evidence sources.

</details>

**5.** What should the OS do “if possible” regarding root cause analysis?

- A. Ignore correlated alarms and focus on individual alarms.
- B. Perform a Root Cause Analysis to identify and indicate the Root Cause Alarm.
- C. Shut down the affected network element immediately.
- D. Generate a detailed financial report of the outage.

<details><summary>看答案</summary>

正解：B。The specification explicitly directs the OS to perform RCA when feasible.

</details>
